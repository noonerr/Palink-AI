## 3. 施工方没说的 3 条残留（我查出来的）

**R1（必须与 §4 前端批同批做）词条编辑不刷新向量。**
`PUT /api/worldbook/{wb}/stages/{stage_id}`（`api/worldbook.py:583-635`）在 `db.commit()` 后**不调用任何向量同步**，
而 P2 的就绪检测只比"向量行数 ≥ vectorized 条目数"、不做内容哈希脏检查（`_book_vectors_ready` docstring 已言明）。
后果：用户改了一条已向量化的词条内容，向量仍是旧文本，**直到下一次书级 PUT / 导入才收敛**——
表现就是"我改了设定，它按老设定召回"。§4 词条 UI 上线时，schema 加 `vectorized` 字段与"commit 后触发同步"必须一起做，
否则第一个用 UI 的人就会撞上。

**R2 `synced` 的语义仍会骗人。**
`sync_worldbook_vectors` 里 `synced += 1` 是**单条 SQL 执行成功计数**，最后整批 `commit()` 失败时返回
`{'synced': N, 'error': ...}`。这正是上一轮"写入已实测可用"误判的来源（那次报的是 `{'synced':1,...}`，省略号里藏着 error）。
本批调用方（`_fire_vector_sync` / `_fire_lazy_vector_sync`）只在有 `error` 时打 warning，运行时无害；
但**任何拿返回值当"写入成功"判据的人都会重蹈覆辙**。建议小改：成功路径返回 `committed=True`，
或干脆返回落库行数（一次 `SELECT count(*)`）。

**R3 两个"生效延迟/失败模式"必须进 UI 文案与运维文档。**
- 首次开启后**第一轮必然降级**（向量未就绪 → 懒触发后台补齐 → 第二轮才走向量）。这是 P2 的有意设计，
  但用户看不到就会以为"开关没起作用"。
- P4 门禁是**静态对照表**（ollama 1024 / fastembed 512 / openai 1536）。换成 ollama 的其他模型
  （例如 768 维）会被**拒建表 = 永久退回关键词模式**，且只在日志里报错。换嵌入模型必须同批更新此表 +
  `MEMORY_VECTOR_DIMENSION` + 重测阈值——`SimpleHash` 384 维兜底不在表内，但被写入侧逐向量校验拦住，
  所以"服务挂了不会写进坏向量"这个预期是成立的（我已从代码路径确认）。
