# 重复造轮子审计（2026-10-23）

> 只读审计，未改动任何代码。口径：`backend/app` 79,306 行 + `frontend/src` 83,516 行（不含测试），合计约 16.3 万行。
> 假设负载：家用单机、docker compose、单个浏览器标签页、一张卡最多 7 个 iframe；不是多租户高并发。

## 这个仓库在做什么

一个自托管的 AI 角色扮演聊天应用：FastAPI 后端 + React 前端。
核心难点是「跑别人写的 SillyTavern 角色卡」——卡片脚本跑在沙箱 iframe 里，所以每一帧都塞进一整套手写的 ST 兼容运行时。

## 一句话结论

轮子不是零散重复，是**成体系地重复**：同一件事有两到八份实现，而且几份之间结果不一致。
可删/可合并的代码保守估计 **约 4,200 行**，其中 4 处会直接改变用户看到的结果。

## Must fix

### 1. "默认模型"有两个解析器，同一用户会拿到两个答案
- **这是什么**：选不出模型时用哪个，全仓有两个函数在决定。
- **问题**：`utils.py:627 get_default_ai_model()` 取「第一个 active provider 的第一个模型」，**完全不看**系统设置里的 `default_character_chat_model`；而 `silly_tavern.py:775-787 _default_model_id_for_db()` 优先读那个系统设置。管理员把默认模型设成列表里第二个（比如 deepseek-v3），原生链路（`character_ext.py:2366 / 2501 / 2609 / 5819` 的导入、合并、剧情线）仍然用第一个（比如 gpt-4o），ST 兼容面用 deepseek-v3。
- **修法**：`_default_model_id_for_db` 里删掉自己那套扫描，改调 `get_default_ai_model(db)`，只保留最后的 `"palink-default"` 兜底。约 -30 行。
- **不修的后果**：同一份导入/合并任务，账单落在管理员没选的模型上；排查时两边日志对不上。

### 2. 认证解码写了两遍，ST 面丢了滑动续期
- **这是什么**：JWT 解码 + 黑名单 + 用户状态检查。
- **问题**：`api/dependencies.py:32 get_current_user` 有滑动续期（`:88-99` 写 `request.state.token_refresh`，由中间件回写 Cookie/响应头），inactive 用户返回 400；`api/silly_tavern.py:620 _user_from_request_token` 是手抄版，**没有续期**，inactive 返回 401。只走 ST 端点的 Bearer 客户端（卡插件、外部工具）到点就被踢，而网页端会静默续期。
- **修法**：在 `core/security.py` 抽一个 `decode_token_user(token, db) -> User`，两处都调它；续期逻辑留在 `get_current_user` 里。约 -40 行。
- **不修的后果**：以后加任何一条鉴权规则（比如新增 scope 校验），一定会漏一处；漏的那处是 60+ 个 ST 端点。

### 3. 两套世界书引擎，两套 token 公式，结果对不上
- **这是什么**：决定「这一轮哪些世界书条目进提示词」。
- **问题**：权威注入在后端 `worldbook_service.py:1811 build_worldbook_context`（经 `roleplay_prompt_assembly.py:4699 _append_worldbook_context`，用 `st_tokenizer_service` 计数）。前端 `lib/worldbook/*` 是第二套完整引擎（扫描 348 + 递归 96 + 预算 209 + 计时效果 132 + 管理器 320 ≈ 1,105 行），经插件面 `getContext().getWorldInfoPrompt()`（`getContext.ts:2355-2394`）暴露给卡片。它的计数公式是 `中文字数*2 + 英文单词数`（`budget.ts:173-178`、`scanner.ts:316-326`），默认预算 16,000（`budget.ts:11`）。1000 个汉字的条目，前端算 2000 token，后端算约 700~1000。⇒ 插件问「现在激活了哪些世界书」得到的列表，和模型实际收到的不是同一份；前端还会在真实预算的一半处就开始裁。
- **修法**：`getWorldInfoPrompt` 改调后端已有的扫描端点，删掉前端这套计算（类型定义留着）。约 -1,100 行。
- **不修的后果**：卡片作者按插件返回的列表调参，永远调不准；「世界书没生效」类问题查不到根因。

### 4. 改一次角色卡，会把这个角色的所有聊天记录重写一遍
- **这是什么**：角色卡保存后同步到 ST DATA_ROOT（一个磁盘上的文件镜像）。
- **问题**：`api/character.py:599 / 756`、`character_ext.py:3095` 都调 `trigger_async_sync` → `st_sync_service.py:337-390 sync_character_to_st`，里面 `for session in sessions:` 逐条写 JSONL。改一句开场白 = 这个角色 50 个会话的 50 次文件写。同一段里头像只在 `if not avatar_path.exists()`（`:352-355`）时写，所以换头像后镜像永远是旧图。
- **修法**：角色保存只写卡片 JSON；会话 JSONL 在会话变更时写，或在 ST 读路径上按需生成。约 -60 行。
- **不修的后果**：磁盘抖动随会话数线性增长；镜像与 DB 的偏差没有任何机制能发现。

## Should fix

### 5. 两套错误模型，中间还架了一座桥
- **这是什么**：`lib/errorHandler.ts`（98 行，`ErrorInfo` + `analyzeError`）和 `lib/error-handler/index.ts`（`AppError` 类）。
- **问题**：`AppError` 里专门写了 `get title()` 去模拟另一套的字段（注释写着"向后兼容属性"）——这就是两份轮子互相打补丁的证据。`services/api.ts:1` 用第一套，`stream-engine/index.ts:7`、`hooks/useCharacterChat.ts:4` 用第二套。同一次 500，两条路径产出两种对象。
- **修法**：留 `AppError` + 一个 `toUserMessage()`，删掉另一份的文案表。约 -200 行。
- **不修的后果**：每个新错误路径随手挑一套，Toast 组件迟早漏判一种形状。

### 6. 两个 tokenizer 后端栈，模型→词表映射不一样
- **这是什么**：按型号精确计数。
- **问题**：`st_tokenizer_service.py`（845 行，tiktoken + sentencepiece + HF，自带 `app/tokenizers/` 词表，claude 用本地 `claude.json`）和 `token_counter_service.py`（237 行，tiktoken + HF 远程，文档明写 claude/gemini/grok → `None` 走启发式）。同一个 Claude 模型，提示词预算用精确值，配额扣费用启发式。
- **修法**：`token_counter_service` 内部直接委托 `st_tokenizer_service.get_token_count`，只保留配额需要的回退顺序。约 -200 行。
- **不修的后果**：两个数字长期并存，谁对谁错没有唯一答案。

### 7. `utc_now` 定义了 30 次
- **这是什么**：`return datetime.now(timezone.utc)` 这一行。
- **问题**：`models/` 下 20 个文件各抄一遍，`api/` 下 7 个 `_utc_now`，另有 3 个 `_utc_now_iso`。现在内容一致，但这是 30 个会各自漂移的入口。
- **修法**：`models/base.py` 放一个，其余全部 import。约 -60 行。
- **不修的后果**：某天有人在一个文件里写成 `datetime.now()`（无时区），SQLite 里就混进 naive 时间，排序和比较开始出错。

### 8. `_safe_json_loads` 四份、`_safe_json_dumps` 两份
- **位置**：`api/plugins.py:1558`、`api/silly_tavern.py:160`、`api/st_groups.py:26`、`services/st_sync_service.py:51`（dumps 在 `st_groups.py:37`、`st_sync_service.py:62`）。
- **问题**：签名不同（`fallback` / `default`），行为都是 try/except + 类型校验。
- **修法**：`utils.py` 收一对。约 -40 行。

### 9. `_st_read_upload` 是 `read_upload_with_limit` 的手抄件
- **位置**：`api/silly_tavern.py:3669` vs `utils.py:560`。
- **问题**：`utils.py:549` 的注释已经点名「未收口：api/silly_tavern.py::_st_read_upload」——写注释的时候就知道，只是没删。
- **修法**：删掉本地实现，import 那一份。约 -16 行。

### 10. `_public_models` 和 models API 各算一遍模型列表
- **位置**：`api/silly_tavern.py:726-760` vs `api/models.py:180-220`。
- **问题**：两边都把 provider 模型和本地模型拼起来，`context_length` 缺省都写 `4096`。改默认值必须改两处。
- **修法**：抽一个 `services/model_listing.py`，两边都调。约 -35 行。

### 11. 三份 SSE 消费，其中一份会丢事件
- **位置**：`lib/sseStream.ts:8 consumeSseStream`（权威）、`CharacterView.tsx:1549-1595`、`WorkspaceView.tsx:269-310`。
- **问题**：CharacterView 那份只认 `'data: '`（**带空格**），`sseStream` 两种都认；WorkspaceView 按 `'\n'` 切，另两份按 `'\n\n'` 切。任何以 `data:{...}` 发出的流，CharacterView 会静默跳过每一条 —— `sessionId` / `branchId` 永远拿不到，分支选择器不初始化。
- **修法**：两处都换成 `consumeSseStream`。约 -100 行。
- **不修的后果**：换一个 SSE 生产端（或中间加个会改格式的代理）就复现，而且不报错。

### 12. 同一个卡片帧里塞了三套 jQuery 替身
- **这是什么**：卡片脚本期望有 `$`。
- **问题**：`CharacterCardRenderer.tsx:584-598` 把两个 shim 直接拼在一起注入：`${legacyShim}${compatV2Shim}`。
  1. legacy 轨 `frame-shim/legacy-st-sim-parts/part-c.ts:820` 装 `window.$`；
  2. v2 轨 `runtime-body/part-04.ts:801` 的 `createParentDollarCollectionCompat`，`part-05.ts:314-360` 的 `fallbackDollarCompat`，共 **48 个方法**；
  3. 卡片自己 `<script src>` 带的真 jQuery，`part-05.ts:316 isRealJQueryCompat` 专门认它。
  代码自己承认不兼容：`part-05.ts:313` 写「排除 legacyShim 注入的简易 dollar（其集合缺少 `.blur()` 等 jQuery 方法）」。而 v2 的集合有 `attr`，**没有** `.text / .html / .append / .val / .on`。同一句 `$(sel).text()` 落到哪个对象上，结果取决于脚本拿到的引用。
- **修法**：`jquery@4` 已经在 `package.json` 里，并且已经在 `plugin-system/sandbox.ts:53`、`inline/inline-st-globals.ts:28` 两处注入过。把真 jQuery 注入卡片帧一次，保留一层薄桥；删掉 48 方法的替身。约 -1,200 行。
- **不修的后果**：每写一个新卡片脚本都在赌；报错信息是 `is not a function`，看不出是兼容层缺方法。

### 13. 本地推理栈还在（约 2,000 行），但产品方向已经出局
- **位置**：`local_model_registry.py` 463、`llama_runtime.py` 407、`inference_queue.py` 413、`inference_dispatcher.py` 里的本地分支。
- **问题**：本地只保留向量嵌入（ollama bge-m3），本地**生成**已判定不做。但 `api/admin.py:22` 仍能启用本地聊天模型，`api/models.py:17` 仍把它们列进模型列表，dispatcher 仍保留 `llama_runtime` 调用。
- **修法**：`ensure_model_available` 去掉本地分支、admin 去掉启用开关，嵌入路径不动。
- **不修的后果**：管理员能配出一个「看着能选、一聊就 503」的模型；排查要翻三层。

### 14. 后端两个 `_estimate_tokens` 公式差一倍
- **位置**：`inference_dispatcher.py:22` 与 `stream_builder.py:116` 都是 `中文*1.5 + 其他*0.25`；`st_tokenizer_service.zh_aware_guesstimate` 是实测校准过的 `0.70 / 0.38`（注释里写明拟合依据）。同一段中文，前者算出来约是后者的 2.1 倍。
- **修法**：两处改调 `smart_guesstimate`。约 -20 行。

### 15. 世界书预算的估算函数被抄成了两份
- **位置**：`lib/worldbook/budget.ts:173` 与 `lib/worldbook/scanner.ts:316`，函数体逐字相同。
- **修法**：`scanner` 调 `budget` 的那一个。约 -10 行。

## 结论

- `Verdict:` 不是坏掉了，是同一件事被做了两遍以上，且 4 处结果不一致。先修 1-4，它们会直接改变用户看到的东西（模型账单、登录续期、世界书内容、磁盘写入）。
- `Lean:` 约 **-4,200 行**，不需要新增任何依赖（反而是 `jquery` 已在依赖里却被手写替身取代）。
- `Not checked:` `st-plugins/`（710 文件）、`_reference/`、`_BACKUPS/`、前端构建产物；`roleplay_prompt_assembly.py`(6,084)、`character_ext.py`(6,927)、`silly_tavern.py`(6,521) 只抽读了工具函数簇与关键路径，没有逐行通读；没有跑测试、没有起服务、没有真机验证卡片帧内行为；除认证重复外没有做深入安全审计。
