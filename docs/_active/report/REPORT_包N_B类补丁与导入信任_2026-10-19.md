## 1. B-2：`window.context`

### 改前
真机（现网旧包，露缇雅 `c28061bb-a9b7-46a9-a255-2692d57001fc`，7 个卡帧）：

```
hasWindowContext: "undefined"   × 7
hasGetContext:    "function"    × 7   (ctxKeys = 196)
```

ST 1.18 的 `context` 是 `st-context.js` 的 `export const context = getContext()`（一次性快照），
插件大量直接读 `context.chat` / `context.name1` ⇒ 在 Palink 帧内直接 `ReferenceError`。

### 改后
1. **帧内** `runtime-body/part-08.ts`（`window.getContext = getContextCompat;` 之后）：
   ```js
   try {
     Object.defineProperty(window, 'context', { configurable: true, enumerable: true, get: () => getContextCompat() });
   } catch (e) { /* 静默 */ }
   ```
   用 getter 而不是快照：语义是 ST 快照的**超集**，且无副作用；定义失败静默（不打断卡脚本）。
2. **沙箱包装壳** `sandbox.ts buildWrappedCode`：`var context = getContext();`
3. **`script.js` 模块映射**新增 `get context()` —— 这一条是必须的：插件写
   `import { context } from '.../script.js'` 时转译产物是 `var { context } = require('script.js')`，
   模块映射缺键会拿到 `undefined` 并**覆盖**包装壳里预置的 `var context`（只补 ② 等于白补）。

### 证据
`__tests__/n-package-context-rename-media-trust.test.tsx`：
- 从**注入产物**（`RUNTIME_BODY_PART_08`，模板字符串求值后的真文本）切出该段真实源码求值，
  断言 `typeof window.context === 'object'`、`context.chat[0].mes`、`context.name1` 可读、
  getter 每次读都重新取值（`reads >= 2`）。
- 沙箱侧：源码断言 `var context = getContext();` + `script.js` 块内有 `get context()`。

    const newName = String(title == null ? '' : title).trim();

## 3. B-1：SD 出图落库（沙箱轨 `appendMediaToMessage`）

### ⚠️ 与交接单的一处**实质偏差**（必须先读）

交接单 §3.2 要求沙箱轨走 `applyStChatMessages(nextChatArray)`。**这条路走不通**，源码为证：

1. `getContext.ts:1671-1674` 的自述：`applyStChatMessages` "只写内存态，刷新/重载后丢失"，
   并会 `recordStubHitOnce('setChatMessages:persist', …)`。
2. `getContext.ts:1742` 派发 `palink:chatMessagesUpdated` → `CharacterView.tsx:1642-1646`
   监听后 **`loadMessages(sessionId)` 从服务端重载** ⇒ 刚写进内存的媒体会被服务端快照立刻冲掉
   （比"刷新后丢失"更糟：图会闪一下就消失）。

⇒ 改用**等价且真落库**的通道（与卡内轨 `setChatMessage` 完全同一条写入路径）：

| 层 | 实现 |
|---|---|
| 纯映射 | 新增 `lib/plugin-system/st-message-media.ts`：`normalizeStMediaEntry` / `resolveStMessageIndex` / `buildStMediaAppendPlan` / `appendStMessageMedia`（无 window、无网络，可单测） |
| 沙箱 | `sandbox.ts` 的 `script.js.appendMediaToMessage` 换成 async 实现：`__palinkChatMessages`（或 `buildStContext().chat`）→ 映射 → 调宿主桥 |
| 宿主 | `CharacterChat.tsx` 注册 `window.__palinkAppendMessageMedia`：`PUT /api/character-sessions/{sid}/messages/{dbId}`，body `{ content: 权威原文, extra: {…, media, media_index} }`，成功后 `setMessages` 刷新 |

为什么必须是宿主桥（而不是沙箱自己 PUT）：
- `window.__palinkChatMessages` 的 `mes` 被 `stripStyleBlocks` 洗过，直接回写会**抹掉消息内样式块**；
  而 `MessageEditRequest.content` 是必填且会覆盖正文。
- 宿主侧 `displayedMessages` 才有权威 `content` 与真实 DB `id`（ST 侧只有 `mesid` 下标）。

### 红线遵守
- **不许假成功**：`normalizeStMediaEntry` 对 jQuery 形状、消息对象、空串、只有 `id` 无 `status` 的对象
  一律 `null`；映射失败 `message_not_found` / `media_unresolved` → `false`；宿主回报非 `success:true` → `false`；
  桥缺失 → `false`。**不会**把消息 id 当 URL 写进 `extra.media`。
- **不碰 DOM**：没有往消息元素插节点（原空实现的理由仍然成立，注释已改写说明）。
- 形状按 `lib/messageMedia.ts:18` 的 `MediaItem`（`id/status/url/width/height`，缺尺寸落 1024 默认）。

### 证据
- 单测：3 种入参归一化；5 种不可映射入参返回 `null`；下标解析（`mesid`/数字/对象身份/浅拷贝）；
  落库 4 态（`success:true` → true；`success:false` / 抛错 / 无桥 → false）。
- 接线：`sandbox.ts` 不再有 `appendMediaToMessage: () => {}`，且块内不含 `applyStChatMessages(`；
  `CharacterChat.tsx` 含 `__palinkAppendMessageMedia` 与 `/messages/${dbId}`。

## 4. C-1：导入时信任提示（TOFU）

### 4.1 检测（`import-trust-prompt.tsx` 的 `detectCardScripts`）

⚠️ 交接单写的是 `result.data.extensions…`；实际导入接口返回的是 **`result.character.extensions`**
（`silly_tavern.py:3768` → `character_to_dict`，没有 `data` 包装层）。按实际形状实现。

命中任一条即弹（纯函数、可单测）：
1. `extensions.tavern_helper.scripts[]` 有非空 `content` 且 `type` 为空或 `'script'`；
2. `first_mes` / `alternate_greetings[]` / `group_only_greetings[]` 需要 iframe 跑脚本
   —— 复用渲染侧真判据 `htmlNeedsIframe`（`<script>`、`on*=` 内联处理器、`iframe|object|embed|form`、
   `window|document|localStorage` 引用、`getContext|SillyTavern` 调用），**不另起一套正则**；
3. `extensions.regex_scripts[].replaceString`（含嵌套 `extensions`/`data` 层）需要 iframe 跑脚本；
   `disabled: true` / `enabled: false` 的不算。

纯文本卡与"只有 `<style>` 的静态卡"**不弹**（无脚本可信任，弹了就是狼来了）。

### 4.2 流程
导入返回 `result` 之后、`openImportedCharacter` **之前** `await askImportedCardTrust(result.character)`：
- 弹窗（`CardScriptTrustPrompt`，`data-palink-card-trust-prompt="1"`）→ 用户点"信任此卡"
  → `writeSmartCardTrustOptIn(cid)` 写 `palink:card-trust-optin:v1:<cid>` = `{pending:true, at}`
  → 之后才打开该角色（保证**首帧渲染前**落盘）。
- 点"暂不信任"/点遮罩 → 不写任何键（卡片里的「信任」开关仍可随时授权）。
- 用 `await` 阻塞而不是"先弹后异步打开"：否则首帧已按 opaque origin 建好 iframe，点了也要等下次渲染。

### 4.3 采纳与撤销
`CharacterCardRenderer` 的信任解析改为三级（`useState` 初始化与 fingerprint 变化 effect 两处同一条）：
```
mode === 'trusted-native'
|| readSmartCardTrustGrant(cid, fingerprint)   // 现有：会话级 30 分钟 TTL
|| readSmartCardTrustOptIn(cid, fingerprint)   // 新增：TOFU
```
`readSmartCardTrustOptIn`：
- 读到 `{pending:true}` ⇒ 把**当前** `sourceFingerprint` 写进去并返回 `true`（TOFU 绑定）；
- 读到 `{fingerprint:X}` ⇒ 仅 `X === 当前指纹` 才 `true`（**卡内容一改，信任自动失效**）；
- 损坏/无键 ⇒ `false`。
撤销（`confirmTrustedNative` 的 `revoke`）里 `clearSmartCardTrustOptIn(cid)` —— 否则 localStorage 里的
`{fingerprint}` 会在下次渲染把信任自动授回来。

### 4.4 安全口径变更（必须记录）
| 项 | 改前 | 改后 |
|---|---|---|
| 存储 | `sessionStorage`，`cid:fingerprint` | 新增 `localStorage`，`cid`（独立新键，不复用 grant 键） |
| 有效期 | 30 分钟 TTL | **持久**（跨会话） |
| 绑定 | 指纹 | 指纹（TOFU：首次渲染时绑定；不匹配即失效） |
| 触发 | 用户点卡片「信任」 | 导入弹窗显式点"信任"（或卡片「信任」） |
| 撤销 | 清 grant | 清 grant **+** 清 optin |

补偿措施：① 只对用户**显式点过**的卡生效；② 指纹绑定，卡内容一改即失效；③ 可撤销且撤销会清键；
④ 未点信任的卡**行为零变化**（P1-1 不破，见 §5）。

**已知粒度限制（不是 bug，需知会）**：`sourceFingerprint` 是**逐条消息**的智能卡 HTML 算的
（`CharacterCardRenderer.tsx:270-273`），所以 TOFU 绑定的是"首次渲染那条消息"的指纹；
同一张卡的其它消息若指纹不同，仍需各自授权（与会话级 grant 的既有粒度一致）。

### 4.5 证据
- 检测 6 例（纯文本/只有 style/tavern_helper/`<script>`/`onclick`/regex 注入/禁用 regex）。
- optin 生命周期：无键 → `pending` 采纳 → 绑定 → 同指纹 true → 异指纹 false → clear 后 false。
- 独立新键断言：`getSmartCardTrustOptInKey('c1') === 'palink:card-trust-optin:v1:c1'`，
  写 optin **不碰** `sessionStorage`。
- 渲染器源码：`readSmartCardTrustOptIn` 出现 ≥2 处（初始化 + effect）；`if (!nextTrusted) clearSmartCardTrustOptIn(...)`。
- 组件行为：点"信任"只回调 `onAccept`、点"暂不信任"只回调 `onSkip`，组件**不写存储**。
