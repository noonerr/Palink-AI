## 3. ⚠️ 但有一个实质缺口：MVU 的症状大概率没修好

这是我核验中发现、交付方未意识到的问题。**形状修对了，但真机症状（`initialized_lorebooks` 键 = `'unknown'`）在单间轨下大概率依旧。**

**推理链（每步都有 file:line）**：

1. 单间轨 iframe 内 `activeWorldbookName` 初始为 `''` —— `legacy-st-sim.ts:943` `let activeWorldbookName = ''`。
2. 它只在两种情况下才有值：① 卡自己创建/替换世界书后（`:948-949`）；② 异步 warm 完成后（`:1405`）。
3. 父侧 `state.worldBook` 初始为 `null` —— `SmartCardCompatController.ts:127`；且**生成 srcdoc 时没有把世界书名内联进 iframe**（我已 grep `CharacterCardRenderer.tsx`，无任何 `worldBook.name` 注入）。
4. ⇒ **首次调用 `getCharWorldbookNames('current')` 必然返回 `{primary: null}`** → MVU 的 `.primary ?? 'unknown'` → **`'unknown'`**。
5. 而 warm 是**异步**的（`.then()` 里填值），**MVU 恰恰只在模块顶层调用一次**（真机原文就是一次赋值），所以 warm 对它无效。

**架构性根因**：这是个**同步 API + 异步数据源**的矛盾。改成同步返回之后，首次调用就注定拿不到异步数据。

**更麻烦的一点**：`getcharworldbooknames-contract.test.ts:171` 那条用例写的是
```ts
it.each(FRAME_TRACKS)('…：空绑定返回 { primary: null, additional: [] }（不是 undefined）', …
  expect(out).toEqual({ primary: null, additional: [] });
```
—— 它把「首次返回 null」**钉成了期望行为**。将来真要修这个症状，会被这条测试拦住。所有用例都预设 `activeWorldbookName` 已有值，**没有一条覆盖"首次调用、名字为空"的真实场景**。

**建议下一步**（不构成本次验收不通过，但必须登记）：
1. **真机验证一次**：加载带 MVU 的卡，看 `initialized_lorebooks` 的键是否仍是 `'unknown'`。这是唯一能定性的方法。
2. 若确认未好，解法是**在 iframe srcdoc 生成时把世界书名内联进去**（父侧 `state.worldBook.name` 若已加载）—— 这是让同步 API 首次就有值的唯一通路。
3. 修之前先改 `:171` 那条测试，否则改不动。
