## 0. 一句话结论

- **K-4 修好**：帧内报错条目现带可归因真信息（message / filename / lineno / **colno** / kind / errorReason），
  取不到的字段**明写缺失原因**，不再用空串或 `unknown error` 交差。
- **新增节点身份取证**（不弹 toast、不改行为）：卡样式被移除/替换时，`__palinkFrameErrors` 里
  带 `tagName / id / data-* / href / 文本字节长度`，并按同批 `addedNodes` 区分 `node_removed` vs `node_replaced`。
- **K-1 归因定案（本包最重要产出）**：卡自己的 `<style>` **不是被删、也不是 `head.innerHTML=` 整块重写**，
  而是**被搬到一张「随后脱离文档的临时 DIV」里丢弃**。搬运工 = 卡片自带的 **MagVarUpdate(MVU) CDN bundle**

  后者以 `div.appendChild(style)` 把每条 head 样式逐个挪走。Palink 的守护只认自己快照里那 8 条
  （3 基样式 + 5 插件 CSS）并补回 head，所以**插件 CSS 活、卡侧样式死**。
- **K-3（Failed to fetch）**：证据**不足以完全定责**，只能缩小到「MVU/懒加载外部 CDN 依赖的动态 import 失败、
  仅主实例」——理由见 §4。

## 2. K-1 归因：谁、用什么方式「删」掉卡自己的 `<style>`

### 2.1 取证链（同步栈只在 `.tmp_probe` 临时探针里挂，不进仓库；红线遵守）

- 探针 `probe_N_k1c.js` / `probe_N_k1d.js`：在每个卡帧内**同步** monkeypatch
  `Node.removeChild` / `Node.replaceChild` / `Element.remove` / `replaceWith` / `replaceChildren` /
  `head.innerHTML=` / **`appendChild`（检测 head 子节点被 relocate）** / `outerHTML=` / `Range.deleteContents`，
  命中 styled 节点就抓 `new Error().stack`。

实测结果（7 卡帧、163 次命中、全部同一调用方）：

```
caller 命中分布（163 次，单一来源）：
  163 x at o (https://testingcf.jsdelivr.net/gh/MagicalAstrogy/MagVarUpdate@beta/artifact/bundle.js:2:333586)
relocate 目标：163 x → DIV#-（无 id、无 class）
完整深栈（一条样本，逐字）：
  at Array.forEach
  at .../palink-smart-card-runtime-87b9e8e97268.js:3594:20      ← Palink 兼容层 collection.append 内部 values.forEach(node.appendChild(item))
  at Proxy.forEach
  at collection.append (...palink-smart-card-runtime-*.js:3588:12)  ← part-04 的 collection.append
  at o (…/MagVarUpdate@beta/artifact/bundle.js:2:333586)          ← MVU bundle
  at …/bundle.js:2:557689
  at HTMLDocument.<anonymous> (…/bundle.js:2:557731)              ← DOMContentLoaded 触发
```

### 2.2 关键否证与定案

- **`removeChild / remove / replaceChild / replaceWith / replaceChildren / head.innerHTML= / outerHTML= / Range`
  同步钩子命中 = 0**。这正是包E「否证 removeChild/remove 路径」的强复现——但本包把它从「猜 innerHTML/节点替换」
  推进到**实测锁定真实路径**：
- **真实方式 = relocate（搬运），不是删除**：MVU 在 `DOMContentLoaded` 用 jQuery 风格
  `$(容器).append($('head 里的 style/link'))`，而 Palink 的 jQuery 兼容层把 `.append()` 实现为
  `node.appendChild(item)`（part-04 `collection.append`），于是 head 的每条样式被 `appendChild` 移进一张 DIV。
- **那张 DIV 随后脱离文档**：探针 `probe_N_k1e.js` 实测——搬运目标 `DIV.connected=false`、`offsetParent=null`、
  内部聚了 23 条样式；t16 静息态 `headStyles==docStyles==9`（head 之外没有游离活样式），且
  `document.querySelector('style#tavern-cg-album-style')` → **null（cgParent=absent）**。
  ⇒ 卡侧样式确实从「生效文档」里消失（不是 head 计数口径假象），galgame/CG 样式随之失效 = 用户可见裸奔。
- **为什么 Palink 自家 5 条插件 CSS 反而没事**：它们在守护快照里（3 基 + 5 插件 = `guardSnapshot=8`），
  守护的 MutationObserver 看见 head 少节点后把**这 8 条**重新 `appendChild` 回 head；
  而卡侧样式（`tavern-cg-album-style`/`galgame-ui-plugin-styles`）**从没经 `__palinkStyleGuardAddNode` 登记**，
  守护不认识 → 不补 → 留在脱离的 DIV 里死掉。这与包J「只追加、不重拍快照」的定稿一致，**守护没做错，是覆盖面按设计如此**。

### 2.3 一句话归因

> 删卡样式的是**卡片自带的 MVU bundle**（外部 CDN），它走的是 **Palink 自家 `collection.append`→`appendChild` 的搬运路径**
> 把 head 样式移进一张随后脱离的 DIV；Palink 守护只救自家快照 8 条，卡侧样式不在其列 → 真丢。

## 4. K-3（Failed to fetch）定责结论：**证据不足以完全定责**

实测（`probe_N_k1b.js`，dev :5206 主实例）：

- toast 时间线：`{at:6..9 → ["Failed to fetch"]}`，at:10 起消失 ⇒ 复现包K 报的 4.5–7.5s 仅主实例（dev 时序略后移到 6–9s）。
- `billedHits=0`、`billedUrls=[]`（计费端点全程本地 fulfill 从不转发），`/api/ws/ticket` 命中 1 次（非计费，单列）。

**为何不能定责**：
1. `__palinkFrameErrors`（本包补强后的取证面）在 K-3 窗口里**没有任何对应的 resource_load_failed / unhandled_rejection 条目**
   （分组只有 `8x script_error(message_unavailable)` 与 `42x node_removed`）。
2. 包I §1.2 已写明：兼容运行时的「真·脚本错误 / 非 Event 的 rejection」走 `reportDiagnostic → st:diagnostic`（**toast**），
   **不**经 `palinkRecordFrameErrorForEvidence`（frame-error）；因此这类失败的原文/URL 只进**帧内 `cardErrorLog`**
   （闭包私有，父侧读不到），不落 `__palinkFrameErrors`。本包「只补取证字段」无权把它改道进观测面（那会动 I-2 的处置口径）。
3. 能确证的只有：与 §2 同源——**MVU bundle 从 `testingcf.jsdelivr.net` 加载并懒拉外部依赖**，动态 import 失败会以
   `TypeError: Failed to fetch` 形态出现（与包I §6.1「动态 import 型死链」同一类，被 I-2 口径排除在静默之外→仍弹 toast）；
   且**仅主实例**有这些外部依赖（包K §5.2 实测两克隆 `enabled=None`、`pluginCss=0`，没有 MVU 插件链）。
   但**具体是哪一条 URL 失败**，取证面拿不到，不猜。

⇒ 结论：**证据不足以定责到具体资源**。要把 K-3 钉死，需要下一条包允许「把帧内非资源形态 rejection 的 reason 原文/URL
也镜像进 frame-error 取证面」（不改 toast 判定，仅加观测字段）——本包按红线未做。

## 6. 给用户：「若要扩守护恢复范围（救卡侧样式），风险边界在哪」

本包**没有**改守护恢复范围（用户已裁定等取证后再单独拍板）。基于 §2 实测，把边界写清楚：

1. **病灶在卡片自带脚本，不在 Palink 装配**：卡样式的消失是 MVU bundle 主动 `append` 搬运所致。
   「把卡侧 `<style>` 也纳入恢复」= 让守护去和卡自己的运行时**抢同一批节点的所有权**——这是与卡行为对抗，不是单纯补漏。
2. **回搬会引发乒乓/风暴**：卡侧样式被 MVU 反复 relocate（实测一帧窗口内累计上百次搬运），
   守护若也把它抢回 head，两边 `MutationObserver` 互触 → 移除→补回→再移除的死循环。插件 CSS 现状能收敛，
   是因为它**只登记进快照一次**、守护幂等补回；卡侧样式数量大、无 id 多、且被外部反复改写，**必须配收敛上限 + 幂等去重**才能扩，
   否则帧内 CPU 直接打满（本仓帧是 opaque origin，父侧不可见，一旦卡死只能刷页）。
3. **重复样式导致级联错乱**：DIV 里聚了 23 条样式（含同名/同选择器副本）。盲目 re-append 回 head 会**重复注入**，
   改 CSS source order / 特异性 → 富卡自身版式可能被自家副本覆盖出视觉回归。
4. **快照语义红线**：包J 定稿「只追加、禁止整快照重拍」。把卡侧动态样式吸进基线 = 变相重拍，会把「卡运行后某个中间态」
   冻成不可覆盖的真相。扩围若要做，只能走**按稳定 id 找回**（如 `getElementById('tavern-cg-album-style')` 语义）的旁路，
   且**仅限有稳定 id 的卡侧样式**，无 id 的（`#STYLE/15483`、`#STYLE/440KB` 这类）无法可靠找回也不应强找。
5. **爆炸半径**：`runtime-body` 是所有智能卡共用运行时，改一处恢复逻辑波及全部富卡；
   扩围前务必按包L 求值后载体先建「卡侧 id 样式 relocate 后能否按 id 稳定补回、且不乒乓」的行为钉子，再动生产串。

⇒ 建议下一条包（如要修 K-1）：**只在「有稳定 id 的 head `<style>` 被移除且文档内（含影子/游离）已无该 id」时，
按 id 幂等补回一次，并设每帧恢复次数上限**；绝不做整快照重拍、绝不无脑抢无 id 卡侧样式。
