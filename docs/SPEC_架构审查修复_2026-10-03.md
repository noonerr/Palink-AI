### A. 世界书三源机制（`public/scripts/world-info.js`）

ST 的世界书来自**三个独立来源，注入时合并**：

| 来源 | ST 存储位置 | 语义 |
|---|---|---|
| **卡内嵌** | `character.data.extensions.world`（另有 `data.character_book`） | 角色卡自带的 lorebook，**随卡走，天然隔离** |
| **角色附加** | `world_info.charLore[] = { name: 角色文件名, extraBooks: [书名] }` | 手动给某角色额外挂的书，**按角色名绑定**（`:1132`、`:4376`、`:6039-6052`） |
| **全局勾选** | `world_info.globalSelect` ← `selected_world_info`（`:85`、`:998`） | 用户在设置里手动勾的全局书 |

**关键事实（直接决定本项目改法）**：
1. ST **没有**「所有书默认全局」这回事。三源都有明确的绑定维度。
2. 卡内嵌书走 `character.data.extensions.world`，**跟角色卡同生共死** —— 这正是用户说的「世界书基本上都是角色卡自带的」。
3. `charLore` 按**角色文件名**（`getCharaFilename()`）绑定，不是全局。
4. 删除书时会同步清理引用（`:2336-2343` 清理 `charLore.extraBooks`、`:4151-4156` 改名时同步）。

**⇒ 对本项目的意义**：用户说「完全没有必要做全局的『角色卡内部会自动带的』全局提示词这个概念」——
**与 ST 完全一致**。Palink 现在把 `character_id IS NULL` 的书无条件注入所有卡（`worldbook_service.py:1893`），
这个"隐式全局"在 ST 里**不存在**。改法就是照 ST 建三源。

### B. 思考预算算法（`src/prompt-converters.js:1120` `calculateClaudeBudgetTokens`）

ST 的思考预算是**按 `max_tokens` 的百分比算的**，不是取 max：

```javascript
switch (reasoningEffort) {
  case auto:   return null;              // 交给模型自适应
  case min:    budgetTokens = 1024;      break;
  case low:    budgetTokens = floor(maxTokens * 0.1);  break;
  case medium: budgetTokens = floor(maxTokens * 0.25); break;
  case high:   budgetTokens = floor(maxTokens * 0.5);  break;
  case max:    budgetTokens = floor(maxTokens * 0.95); break;
}
budgetTokens = Math.max(budgetTokens, 1024);        // 下限 1024
if (!stream) budgetTokens = Math.min(budgetTokens, 21333);  // 非流式上限 21333
```

另有自适应档（Opus 4.6+ / Gemini 3）：返回**字符串** effort（`low`/`medium`/`high`/`max`）而非数字。

Claude 分支还有个保护（`src/endpoints/backends/chat-completions.js:342-346`）：
`max_tokens <= 1024` 时自动 +1024，因为「Claude thinking requires a minimum of 1024 response tokens」。

**⇒ 对本项目的意义**：Palink 现在的 `budget = max(effective_max_tokens, 8192)` 是**把思考额度顶到和正文一样高**，
ST 是**按档位给百分比**（low 只要 10%）。照抄 ST 的档位表即可，不需要自己发明。

**ST 的 effort 档比 Palink 多**：`auto / min / low / medium / high / max`（6 档），
Palink 只有 `off / auto / low / medium / high`（5 档，缺 `min` 和 `max`）。

### T1 世界书加角色绑定

**问题**：`worldbook_service.py:1893` 把 `character_id IS NULL` 的书**无条件注入任何卡**，
来源标记 `"global"`。而 `api/worldbook.py` 建书时**根本不传 `character_id`**
（`models/worldbook.py:16` 该字段存在但建书路径不用）—— 等于用户建的每个世界书都是全局的。
用户给角色 A 建的世界书，必然进角色 B 的提示词。

**这是"提露雅的思考里出现桃溪好感度"最可能的通路。**

**修法**：
1. 建书 API 接受可选 `character_id`，写入 `WorldBook.character_id`
2. 前端世界书管理页加"绑定角色"选择器
3. 装配时区分三种来源：绑定了本卡的 → `"character"`；`character_id IS NULL` 的 → `"global"`
4. **存量处置（需你选）**：

| 方案 | 做法 | 代价 |
|---|---|---|
| A（推荐） | 存量全部视为 global，行为不变；用户可手动改绑 | 串味问题对存量用户**不自动消失**，但不会新增 |
| B | 按"该书只被一张卡引用过"自动推断绑定 | 有误判风险，且需要扫全量引用关系 |
| C | 存量全部要求用户手动确认归属 | 一次性工作量，N 张书 N 次点击 |

**我的建议：A。** 理由：项目当前**没有存量用户**（记忆里明确记着"多用户产品但没有存量用户，
向后兼容/迁移一律不做"），所以 B/C 的成本是为不存在的问题付费。A 保持行为不变 = 零回归风险。

**验收判据**：
- 建两本书，A 绑角色 X、B 绑角色 Y → 在 X 的会话装配报告里 `included` 只有 A
- 不绑任何角色的书 → 任何卡都注入（保持 global 语义）
- 查 DB：`SELECT id, name, character_id FROM world_books WHERE character_id IS NOT NULL` 能看到绑定

### T4 思考额度拆分

**问题**（已完整定位）：

`max_completion_tokens` 是**思考+正文合计**额度。而

`short=8192 / medium=16384 / long=32768`。用户选"详细"档 →

### T5 输入框卡顿

**问题**（已完整定位）：

每次按键的完整链路：
```
ChatInput.onChange
  → setInputValue (useCharacterChat.ts:227)
    → CharacterView 重渲染（持有全部 state）
      → CharacterChat 重渲染（CharacterView.tsx:1818，**未包 React.memo**）
        → 消息列表全量重渲染（displayedMessages，**无虚拟列表**）
          → Message.tsx × N，每条内部有 10+ 个 useMemo
```

**三重放大**：
1. `CharacterChat` 没 `React.memo`，props 里含 `messages` / `setMessages` 等
2. 消息列表**没有虚拟列表**（`grep virtual` 零命中），几百条消息全渲染
3. `Message.tsx`（2049 行）每条消息内部有 10+ 个 `useMemo`，其中
   `pipelineResult`（:922）、`contentSegments`（:1092）依赖复杂

**"吞字"的成因**：`wrappedHandleSendWithInput`（`CharacterChat.tsx:817`）在
`useCallback` 依赖里含 `inputValue`，每次按键都重建该回调 → 连带重建所有消费它的子组件。
加上主线程被渲染阻塞，React 的受控更新会被后续事件覆盖 → 字符丢失。

**修法**（按性价比排序）：
1. **`ChatInput` 内部改用 `useRef` + 受控转非受控**（或 `useDeferredValue`）——
   输入框自己立即显示，不等上游。**这是最直接的吞字修复**
2. `CharacterChat` 包 `React.memo`（需先收敛 props，避免 memo 失效）
3. `inputValue` 从 `CharacterView` 状态中**下移到 `ChatInput` 内部**，
   发送时才上抛 —— 一次按键不再触发任何上层重渲染。**这条收益最大**
4. 消息列表加虚拟化（`react-window` 或自实现）—— 收益大但改动也大，单独排期

**验收判据**：
- 输入 100 字，全程无掉字，输入框响应 < 16ms
- React DevTools Profiler：打字时 CharacterChat 及以上的重渲染次数 = 0
- 长会话（500+ 消息）下打字仍流畅
