## 1. 一句话结论

**最大的性能问题不在代码里，在运行环境里**：ollama 常驻着**两个**嵌入模型，其中
`qwen3-embedding:0.6b` **全仓零引用**，却白烧掉 3.6–6.4 核 CPU 和 2.6 GB 内存，还把真正
在用的 `bge-m3` 挤到只剩一半算力（嵌入慢 3.7 倍）。

把它卸掉之后：**整机 CPU 从 ~644% 降到 ~0.8%**，嵌入从 3678 ms 降到 1001 ms。
这一步不需要改任何代码。

## 3. 【已修·最大项】ollama 常驻了一个没人用的嵌入模型

### 3.1 现象

`ollama ps` 常驻两个模型，且**都跑在 CPU 上**（无 GPU）：

```
NAME                    ID              SIZE      PROCESSOR    UNTIL
qwen3-embedding:0.6b    ac6da0dfba84    2.4 GB    100% CPU     24 hours from now
bge-m3:latest           790764642607    1.2 GB    100% CPU     24 hours from now
```

容器 CPU 稳定在 **360%–640%**（配额 6.4 核，即吃满 56%–100%），内存 3.3–3.9 GiB。
`loadavg` 实测 `7.26 4.29 1.90`。

对照：10-07 那份报告记录 ollama 是「78 MB / CPU 0%」。**差的就是这一个模型。**

### 3.2 定性：它确实没人用

```bash
# 全仓（py/ts/tsx/yml/json/sh，排除 node_modules 与 dist）grep qwen3
backend/data/model_specs.json:7   "qwen3.7-max"   ← 聊天模型
backend/data/model_specs.json:8   "qwen3.7-plus"  ← 聊天模型
backend/app/services/unified_model_registry.py:153  ← 推理档位
```

**命中项全是 LLM 聊天模型，零处引用 `qwen3-embedding`。**
唯一在用的嵌入模型由 compose 固定：`OLLAMA_MODEL=bge-m3`、`MEMORY_VECTOR_DIMENSION=1024`。

模型是 **6 hours ago** 被 pull 进来的（`ollama list`），与任何已提交代码无关。

### 3.4 处置与残留

- **处置**：`docker restart palink-ollama`。模型文件**未删除**（`ollama rm` 未执行，可随时恢复）。
  重启后只有真实调用会加载模型，而真实调用只用 `bge-m3` ⇒ 另一个自然不会被加载。
- ⚠️ **残留风险**：`qwen3-embedding:0.6b` 仍在 `ollama list` 里。**任何人显式调它一次就会重新加载，

  （删除后若要恢复：`ollama pull`，639 MB）。**本轮未执行，属破坏性操作，待授权。**
- 顺带排除：`OLLAMA_KEEP_ALIVE=24h` 不是问题源 —— 单模型常驻时 CPU 实测 0%，常驻是合理策略
  （改短反而每次多付 ~3 s 加载）。

## 4. 【已修】AnyIO 线程池 8 → 16

依 SPEC（10-07）P0-2：`start-server.sh:273` 只在 `API_THREADPOOL_TOKENS` 非正整数时才走
`THREADS_PER_WORKER * 4` 公式，而 `THREADS_PER_WORKER = CPU_THREADS/WORKERS = 5/4 = 1`
⇒ `1*4=4` ⇒ 触底兜到 **8**。全仓 **467 个同步 `def` 端点**共用这 8 个令牌，`asyncio.to_thread` 也来抢。

**改动只落在 `.env` 一行**（`env_file: .env` 已能把变量注入容器，**无需改 compose、无需重建镜像**）：

```ini
API_THREADPOOL_TOKENS=16
```

生效证据（`docker compose up -d backend` 后）：

```
改前: AnyIO 线程池并发令牌设置为: 8     ×4 worker
改后: AnyIO 线程池并发令牌设置为: 16    ×4 worker
```

> ⚠️ **诚实标注**：这是**理论收益项，本次未能量到实际瓶颈**。压测 `GET /api/auth/config`
> 并发 30 → P50 9 ms / P95 12 ms / max 14 ms，毫无排队（当前系统几乎零负载，且该端点是
> `async def`，不走线程池）。真正的收益要等有真实并发同步端点负载时才显现。
> 之所以仍然改：SPEC 的论证（467 端点 vs 8 令牌）成立，且改动成本为零、回滚只需删一行。

## 5. 已定性但未施工（均需**重建 backend 镜像**）

> ⛔ **共同的卡点**：`backend/app/` 与 `start-server.sh` **都不在 bind mount 里**（实测 backend 只挂载
> `data`/`models`/`tests`/`frontend-src`）。改它们必须 `docker compose build backend`，
> 而当前工作区有 **152 项多会话在途未提交改动** ⇒ 重建会把别人的半成品一起烤进去。
> **这是本项目已登记的红线（OPEN_ISSUES [P0-2]），故本轮全部未动，待用户授权。**

### 5.1 【收益最大】P0-1：生成结束后事件循环被同步占满

核验 10-07 报告的 P0-1 **仍未修**：

```bash
grep -nE "persist_snapshot\(|compute_deduct_tokens\(|deduct_usage\(|store_memory\(" backend/app/api/chat.py
# 403 / 406 / 410 / 411 / 422 / 428  —— 全部无 await 前缀
grep -nE "to_thread|run_in_executor" backend/app/api/chat.py
# 只有 1 处 import asyncio（:1），无任何包裹
```

`chat.py` 是 `async def chat_stream`，里面直接同步调用 `persist_snapshot(force=True)`、
`compute_deduct_tokens`、`deduct_usage`、`mem_svc.store_memory` ×2。
其中 `store_memory` 要联网问 ollama 做向量化 —— 10-07 实测 **2000 字回复 = 9899 ms**，
这段时间该 worker 上**所有其他请求全部卡死**（实测 `memory/stats` 7 ms → 2342 ms）。

修法与施工红线详见 SPEC §三 P0-1（核心：`to_thread` 里**只包不含 `save_db` 的纯计算/网络调用**，
SQLAlchemy `Session` 非线程安全）。

### 5.2 【隐患】4 个 worker 各起一个 `[EMB-BACKFILL]` 线程

启动日志实测：

```
[EMB-BACKFILL] NULL 向量回填线程已启动（间隔 600s，批 32，宽限 300s）
   ×4 次   ← 4 个 worker 各一次
```

根因：`backfill.py` 的 `_WORKER_STARTED` 是**进程级 global**，只能保证单进程内幂等，
跨进程无效 ⇒ 4 worker = 4 个线程，每 600 s 各扫一次库、各嵌一批。
一旦出现 NULL 向量行就是 **4 倍重复嵌入 + 并发写入竞态**。

当前 `conversation_memories` 实测 **764 行、NULL 向量 0 行** ⇒ 线程空转、暂无实际影响，
所以定性为隐患而非故障。

> ⚠️ 顺带排除：本次 ollama 高 CPU **不是**它造成的（NULL 行为 0，无活可干）。

### 5.3 【降级】nginx 起 16 个 worker 却只有 1 核 —— 实测不构成当前瓶颈

SPEC §三 P0-4 记为 P0。本轮实测**不同意该紧迫性**：

```
worker_processes auto;  →  ps | grep -c nginx = 18
容器 cgroup cpu.max = 100000 100000  →  1 核
nproc = 16   ← nginx 看到的是宿主机核数，看不见 cgroup 限额
```

但**实测 frontend 容器 CPU 0.00–3.25%、内存 21–22 MiB**，没有任何被打满的迹象。
SPEC 的担忧（上下文切换拖慢静态资源）在**当前负载下未发生**。

⇒ **建议降级为 P2（技术债）**：真要压榨，等有真实静态资源并发压力时再改。
另注意：`worker_processes` 是 **main context** 指令，而 bind mount 的 `frontend/nginx.conf`
挂的是 `conf.d/default.conf`（http context），**改不了它** —— 要改得动 compose 或镜像。

### 5.4 【降级】`shared_buffers=128MB` 固定值

实测：

```
shared_buffers = 128MB   max_connections = 100   work_mem = 4MB
pg_stat_activity: 5 连接（1 active / 4 idle）
```

数据量：**消息 185 条、记忆 764 条** —— 极小。`max_connections=100` 而实际只用 5 个。
SPEC §三 P1-1 的担忧（水箱与货架对不上）在**低配机器**上成立，本机（db 限额 2.5 GiB、
实占 71 MiB）无压力。⇒ **不动。**
