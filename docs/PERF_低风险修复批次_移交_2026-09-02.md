### 2.2 `backend/app/services/websocket_manager.py` — WS 发送并行化 + 超时（P2-06）
- `ChatRoom.broadcast`：锁内 `asyncio.gather` 并行发送 + 单连接 `wait_for(5s)`；慢连接不再阻塞同房间其他连接。**gather 保持在锁内**以保持跨次广播的按序投递语义（流式 chunk 顺序不变）。

### 2.3 `backend/app/services/websocket_manager.py` — StreamSession 清理提速（P1-06）
- `_cleanup_completed`：done 且无订阅者 → 60s 清理；error 且无订阅者 → 下一轮 tick（≤60s）清理。原统一 300s。
- 安全性依据：清理条件含 `not ss.subscribers`；`sync_connection` 对已不存在的 session 静默返回（`return`），早清不影响断线重连恢复。

## 7. 本会话经验与注意事项（踩过的坑，接手前必读）

### 工具与环境
1. **Mimosa PreToolUse hook 会拦 Bash 读写受保护源码文件**：本次用 `sed -n` 纯*读* `retriever.py` / `useChatView/*` 都被拦（提示改用 Write/Edit 提交）。经验：受保护文件（backend/app/memory_module/、frontend/src/hooks/useChatView/、services/api.ts、ChatViewDesktop.tsx 等）**读用 Read 工具、写用 Edit/Write，Bash 只做搜索/编译/测试**。
2. **Edit 工具的前置校验只认 Read 工具**：用 Bash sed/grep 看过文件不算"已读"，Edit 会报 `File has not been read yet`（TODOS.md 踩过）。编辑前老老实实 Read 一遍目标区间。

### 后端改动
3. **Python 参数顺序坑**：给 FastAPI 端点插 `response: Response`（无默认值）时，放在带默认值参数（`limit=Query(...)`）之后 = `SyntaxError: non-default argument follows default argument`。必须放在所有带默认值参数之前（本批已修正为 `sid` 之后）。
4. **FastAPI Response 注入**：`response: Response` 形参由框架注入，不会是 None；代码保留 `if response is not None` 防御即可，只在 limit>0 时写 `X-Has-More`。
5. **WS 广播并行化的顺序红线**：`asyncio.gather` 必须保持在 `async with self._lock` **之内**——拿到锁外虽然也能并行，但两次广播对同一连接可能交错（流式 chunk 乱序）。锁内 + 单连接 `wait_for(5s)` = 并行收益 + 顺序语义 + 最坏阻塞封顶，三者兼得。
6. **StreamSession 清理的"立即"语义**：cleanup loop 每 60s tick，error"立即清理"实际 ≤60s；安全性依赖两点——清理条件含 `not ss.subscribers`，且 `sync_connection` 对已清 session **静默 return**（断线重连不会炸）。改清理策略前先复核这两点。
7. **to_thread 的边界**：`_create_character` 能进线程是因为它**无 DB I/O**（网络下载+ORM 构造）。SQLite 模式下 Session 跨线程有 `check_same_thread` 风险，永远不要把 db 会话操作包进 `asyncio.to_thread`。
8. **记忆模块矩阵化的语义陷阱**：现有代码 per-row try/except——形状不匹配的 embedding 会抛 ValueError → warning+continue。改成 `np.stack` 时若不显式做形状校验，一条脏数据会炸掉整个搜索（矩阵构造在循环外）。§4-B3/B4 的实施要点里已写明。
