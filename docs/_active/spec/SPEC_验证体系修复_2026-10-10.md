## 为什么要先稳定化（2026-10-10 实测，本节是全篇的前提）

我在同一份代码、同一条命令、相隔约 3 分钟跑了两次全量后端测试：

| 次序 | 命令 | 结果 | 退出码 |
|---|---|---|---|
| 第 1 次 | `py -3 -m pytest tests/ -q --basetemp=D:/tmp/pt_full` | `1918 passed, 48 skipped, 385 warnings, 84 errors` | **1** |
| 第 2 次 | `py -3 -m pytest tests/ -q --basetemp=D:/tmp/pt_full2` | `1999 passed, 51 skipped, 385 warnings` | **0** |

差值：81 个从 error 变成 passed，3 个变成 skipped。**同一命令两次结果不同。**

同一轮里我还单独跑过那两个出错文件：`28 passed, 3 skipped`，退出码 0。

> ⚠️ **订正我自己**：在同一次会话的口头汇报里，我据"单独跑绿"下过"84 errors 已修复"的结论。
> **该结论错误**，是全量跑才复现。这正是本项目 `AGENTS.md` 警告的
> 「离线探针的参数必须与生产调用点一致，否则『修复生效』是假阳性」的同类错误。
> 教训：**判定"修好了"必须用与生产一致的入口，不能用单点探针。**

### 这对方案意味着什么

如果现在直接上 CI：第一次可能红（84 errors），第二次可能绿。团队会在两周内学会
"CI 红了就重跑一次"，然后开始给 CI 加 `continue-on-error`。
**在不确定基线上建 CI，等于把噪音升级成红灯，最终红灯被无视** ——
这正是 `pytest_gate3.log` 带 84 errors 仍被当作 gate 的成因。

所以顺序是：**第 0 步（稳定化）→ 第 1 步（上 CI）**，不能倒过来。

## ⚠️ 订正（2026-10-10 复核）—— 上面「flaky 根因」一节**已被否证**

### 订正 1：flaky 根因不是外网/单例，是**安全删除守卫 + basetemp 落在仓库内**

直接证据来自 `backend/pytest_gate3.log:30-34`（不是推断，是日志原文）：

```
=================================== ERRORS ====================================
_ ERROR at setup of TestRecursiveCleanup.test_nested_generated_images_get_cleaned _
E   SystemExit: 1
---------------------------- Captured stderr setup ----------------------------
[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":58,"threshold":50,
  "scope":"turn","targets":["\\\\?\\D:\\项目\\Palink-AI\\backend\\.pytest_tmp"],"targetCount":1}
```

真实链路（三步，全部有据）：

1. 有人把 pytest 的 basetemp 指到了**仓库内**（`backend/.pytest_tmp`，该目录至今仍在磁盘上）；
2. 清理时一次性删 58 个文件，撞上环境安全删除守卫（按轮次计数，阈值 50）→ 抛 `SystemExit: 1`；
3. 临时目录被**删到一半**，后续全部依赖该临时目录的用例在 setup 阶段连带崩。

统计佐证：84 个 error 中 **1 个 `SystemExit` + 83 个 `AssertionError`**，
`grep -oE "^E +[A-Za-z_.]+" pytest_gate3.log` 的结果是 `83 AssertionError / 1 SystemExit`。
**83 个是连带故障，只有 1 个是真的**（守卫）。

### 订正 2：受影响文件不是那两个

上面点名的 `test_token_counter_service.py`、`test_unified_model_registry_thin.py` **都不是**。
实际受影响的是 image / media / cleanup 类测试：
`TestRecursiveCleanup`、`TestGenerateImageDispatch`、`TestSdProxyUnconfiguredReportsError`、
`TestLocalModelUploadLimit`、`test_generate_image_for_message_*`、media 快照类用例。

那两个文件被怀疑，是因为它们的 `_isolate` fixture 用了 `tmp_path` + `monkeypatch.setattr(app_settings, "DATA_DIR", ...)`，
看起来像"全局单例污染"。实测它们**离线可跑、全量也绿**。

### 订正 3：「safe-delete 只影响 3 个用例」是错的

本文 §第 1 步与 `ci.yml` 头部原本写的「只影响 3 例」已被上面 84 例推翻。
已在 `ci.yml` 头部加「旧结论作废」块替换。

### 订正 4：基线其实是确定的

2026-10-10 连续两次全量，**结果完全一致**：

| 次序 | 命令 | 结果 | 耗时 |
|---|---|---|---|
| A | `pytest tests/ -q -p no:cacheprovider` | `1999 passed, 51 skipped, 385 warnings` | 128s |
| B | `pytest tests/ -q --basetemp=D:/tmp/pt_B` | `1999 passed, 51 skipped, 385 warnings` | 128s |

两次都是 **0 errors / 0 failed**。带不带 `--basetemp` 都一样（只要不落在仓库内）。
⇒ **第 0 步的验收标准（连续三次四个数完全一致）已经实质达成**，
前提是"同一时间没有别人在改 `backend/app` 下的源码"。

补充证据：`backend/app/utils.py` 的 mtime 是 `2026-10-10 00:53:11`，
审计跑测试正在那前后；工作区当时有 200 项未提交改动。
**并发改源码是另一个真实的非确定性来源**，比外网下载更值得防。

## ⚠️ 订正 5（2026-10-10 第二方复核）—— 对上面「订正 1/2/4」的三处修正

### 5.1 修正「订正 2」：84 个 error **横跨多族**，那两个文件的类**确实在里面**

「订正 2」写「`test_token_counter_service.py`、`test_unified_model_registry_thin.py` **都不是**」——
**这个表述过头了。** 对 `pytest_gate3.log` 做文件族统计，实际分布是：

```
8 TestValidation            7 TestFindModelContract      7 TestFamilyResolution
6 test_invalid_media_id_*   6 TestGenerateImageDispatch  4 TestRecursiveCleanup
4 TestReasoningEffort       4 TestDisplayOverrideAndTokenLimits  4 TestCounting
3 TestUpgradeableMapping    3 TestMirrorVariants         3 TestBrowserDelegationFlow
```

`TestFindModelContract` / `TestFamilyResolution` / `TestCounting` / `TestReasoningEffort` /
`TestDisplayOverrideAndTokenLimits` / `TestUpgradeableMapping` —— **这六个类正是那两个文件的类，它们都在 84 个里。**

**正确的表述**：那两个文件**确实受影响**，但**根因不是它们的 `_isolate` fixture**（不是单例污染），
而是同一个守卫故障的连带结果。「订正 2」把"根因不是它"误写成了"它不是受影响者"。

**对方案的影响**：受影响面比 image/media/cleanup **更宽**，凡是用 `tmp_path` 的用例族都可能被连坐。
排查复发时不要只盯着 image/cleanup 类。

### 5.2 修正「订正 4」：`--basetemp` 落在**仓库外**也会炸 —— 「路径」不是唯一变量

「订正 4」结论是「带不带 `--basetemp` 都一样（**只要不落在仓库内**）」。
**这条与两处实测矛盾：**

| 来源 | basetemp 位置 | 结果 |
|---|---|---|
| 审计人第 1 次全量（2026-10-10） | `D:/tmp/pt_full`（**仓库外**） | `1918 passed, 48 skipped, **84 errors**`，EXIT 1 |
| 运维手册 §3 实测（2026-10-05） | `D:\tmp\pt_diag`（**仓库外**） | 照样被拦，手册原文：「因为计数是**按轮次**的，与路径无关」 |
| 「订正 4」A/B 两次 | 一次不传、一次 `D:/tmp/pt_B` | 均绿 |

**为什么会有分歧**：「订正 4」的 A/B 两次实验**都在删除预算充足的轮次里做的**，
两个变量（路径 / 预算）同时变动且都没触及阈值 —— 这组实验**无法区分**是哪一个在起作用，
所以从它推出的「仓库外就安全」不是有效结论。

而审计人第 1 次跑的 84 errors 恰好是它缺的那个对照组：**仓库外 + 预算耗尽 → 仍然炸**。

> ⚠️ **诚实标注**：审计人第 1 次跑未存完整日志（只有 `tail -25`），
> 因此「那次是同一守卫机制」是**高度一致但未经完整证实**的推断 ——
> 证据是形态一致（同为 84 errors，且 error 类目相同）。**不要把这条当铁证引用。**

**修正后的机制表述（建议采信这个）**：
- 触发条件 = **单次批量删除 ≥ 50 个文件**（`count:58` 是单次操作计数，`targetCount:1` 说明是 1 个目录被一次清掉）
- basetemp 落在仓库内会**加剧**（`backend/.pytest_tmp` 反复累积，目前 **156 个条目**，非日志里的 58）
- 但**仓库外也会触发** —— 所以「不落仓库内」是**缓解**，不是**根治**
- 根治只能靠：不在同一轮做大量删除 + `gate.sh` 的守卫自检把 84 个 error 翻译成人话

### 5.3 「并发改源码是非确定性来源」是**未验证推断**，且与「订正 4」自相矛盾

「订正 4」同时写了两个互斥结论：
- 前半：「基线其实是确定的」（连续两次完全一致）
- 后半：「**并发改源码是另一个真实的非确定性来源**」

**二者不能同时成立。** 而且「改源码 → 炸一片 setup error」这个机制**未经验证**：
改源码更可能触发 **collection error**（import 失败），与 setup error 是不同形态。
「订正 4」给的证据只有 `backend/app/utils.py` 的 mtime，那是**时间相关性**，不是因果。

**建议**：在做出对照实验（固定源码 + 故意在跑测试时改一个无关文件）之前，
把这条降级为「待验证假设」，不要写进方案的风险清单当既成事实。

### 设计要点（改之前先读）

**CI 靠什么拦截问题**：实测 pytest 在 `1 passed, 1 error` 时退出码 = **1**，
`2 failed` 时退出码 = **1**。也就是说 **pytest 命令行天然就会拦截 errors/failed**，
不需要写任何解析脚本。所以 `ci.yml` 里：

- 绝不加 `|| true`
- 绝不加 `continue-on-error: true`
- 绝不加 `--continue-on-collection-errors`

**谁加回去，谁就是把门禁重新变成安慰剂。**

**本机 vs CI 的差异**：本机 safe-delete 守卫（按轮次计数，阈值 50）会让 3 个依赖文件删除的用例误报红
（`test_admin_image_cleanup.py::TestRecursiveCleanup` 两例、
`test_c_batch_security_hygiene.py::TestLocalModelUploadLimit` 一例）。
GitHub Actions 上无此守卫。若 CI 上也见这 3 例红，那是真问题。

**已知实施风险（诚实标注）**：`requirements.txt` 含 `llama-cpp-python==0.3.34`（需 C++ 编译）
和 `faster-whisper`，首次 CI 可能卡在装依赖。两种回退方案已写在 `ci.yml` 注释里：
① 走上游预编译 wheel；② 拆出 `requirements-test.txt`。
**推荐 ②** —— 测试实际只用 sqlite 内存库（`tests/conftest.py:72`），不需要 llama。

**本文件未在任何真实 CI runner 上验证过**，首次 push 后必须观察第一次运行结果。

### 用法

```bash
bash scripts/gate.sh            # 全跑
bash scripts/gate.sh backend    # 只跑后端
bash scripts/gate.sh frontend   # 只跑前端
bash scripts/gate.sh docs       # 只校验文档目录
```
