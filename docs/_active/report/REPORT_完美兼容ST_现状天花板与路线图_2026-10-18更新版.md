### 3.1 P0-3：命令"枚举不出来"是包B 留下的真缺口

包B 做的懒代理只让 `commands['xxx']` **取值**命中，**没让 `keys()` / `size` /
`Object.keys()` 枚举出来**。实测：

```
Object.keys(cmds).length = 135     ← 看着很多
但 ST 289 里只有 87 条能取到值
```

⇒ 卡脚本/ST 插件如果用 **`for (const n in commands)`** 做命令补全、或用
**`commands.size`** 判断命令表规模，看到的数与 ST 差很远。
修法：在 `part-07.ts` 的 `slashCommandViewCompat` Proxy（`part-07.ts:584`）里
把 `ownKeys` 的已知名集合扩展为「Map 键 ∪ Palink 自有命令名 ∪ ST 289 已知名」，
并让 `getOwnPropertyDescriptor` 对 ST 289 全量返回 `enumerable: true`。**约 40 行**。

⚠️ 注意口径：这**不会**让命令真的能执行，只让"存在性/枚举"与 ST 一致 ——
但很多卡的兼容性判断就是靠枚举做的，所以值得做。

### 3.2 P2-1：内联渲染把同一份 CSS 重复注入 15 份（今天新发现，根因已定位）

`frontend/src/components/ui/custom/Message.tsx:1006-1031`：

```js
const detachStyleFromMesText = () => {
  const styles = Array.from(container.querySelectorAll('style'));
  for (const styleEl of styles) {
    if (styleEl.getAttribute('data-palink-mes-style-moved') === '1') continue;  // ← 去重靠这个标记
    ...
    document.body.appendChild(clone);   // ← 每次都新造一份
```

**根因**：去重标记打在「源 `<style>` 元素」上，但 `.mes_text` 的 innerHTML 每次被
React/正则/流式重建时，**源元素是新生成的、标记丢失**；而已经移走的 clone 在
`document.body` 里，`container.querySelectorAll` 看不到 ⇒ 无从去重。
实测猫娘卡：`document.body` 下 **15 份内容完全相同**的 `<style>`
（`uniqueContents = 1`，每份 3,156B，合计 **47,340B**），三个时间点采样恒为 15（非持续增长）。

**修法**：按 CSS 内容 hash 在 `document.body` 端去重（带引用计数，避免 cleanup 误删）：

```js
const key = cssHash(cleanCss);
let slot = document.body.querySelector(`style[data-palink-css-hash="${key}"]`);
if (!slot) { slot = document.createElement('style'); slot.dataset.palinkCssHash = key; document.body.appendChild(slot); slot.__refCount = 0; }
slot.__refCount += 1;   // cleanup 时递减，归零才 remove
```

**约 30 行 + 1 个测试**（断言：同一消息重渲染 5 次后 body 里该 hash 的 style 仍为 1 个）。

## 4. 天花板：什么是"完美兼容"里结构不可达的（补了有害）

| 不要补 | 为什么 |
|---|---|
| **恢复主页面插件轨（大堂）** | 安全倒退。S5 的核心收益就是"不可信代码一律进 iframe"，留一条绕过的路 = 白做 |
| **ST 预设体系 `getPresetManager`** | Palink 模型/预设体系与 ST 结构不同，硬补会返回"形状对、语义错"的对象，比缺失更危险 |
| **ST UI 类命令**（`bg`/`bgcol`/`panels`/`movingui`/`theme`/`gallery`/`chat-render`） | Palink 没有对应界面，补了只能是空操作或假成功 |
| **`checkpoint-*` / `closure-*` / `char-*` 数据模型命令** | ST 私有概念（检查点、闭包序列化、角色库），Palink 后端数据模型不同 |
| **让 ST 扩展 UI 在角色卡内可见** | 口径 c 已拍板（2026-10-15）；且技术上未信任卡是 opaque origin，父侧全盲 |
| **追求 289/289 命令** | 其中约 60 条是 UI 类、约 30 条依赖 ST 私有数据模型 |
| **`getRequestHeaders` 给真实认证头** | = 把 `palink_session`/`palink_csrf` 送进 opaque origin 帧，与 P1-1 沙箱红线冲突。**需用户拍板** |
| **卡内脚本改页面级执行**（对齐 ST 酒馆助手扩展） | = 把 untrusted 卡代码放进主页面。今天实测确认这是**真实差异**（猫娘首屏 `window.Mvu` 为 undefined），但改它换来的是安全倒退。**建议记录在案，不改** |

### 4.1 一个必须承认的架构取舍

| | ST 1.18.0 | Palink |
|---|---|---|
| 卡内 `<script>` | **根本不执行**（DOMPurify 剥掉），靠酒馆助手扩展在**页面级**跑 `tavern_helper.scripts` | 在 **iframe 内**执行（超集能力） |
| 消息渲染 | 裸 `innerHTML` 进 `.mes_text`，**无 iframe** | 判定为智能卡才走 iframe，否则内联 |
| CSS 作用域 | `.mes_text ` 前缀 + `custom-` 类前缀 | **已实现**（实测 `custom-nk-msg` + `.mes_text .custom-nk-msg`）✅ |
| CSP | 显式关闭，防御靠 DOMPurify 单点 | opaque origin，不把 DOMPurify 当可信边界 |

⇒ Palink 是**用隔离换执行能力**：能跑 ST 跑不了的卡内脚本，代价是"没有 iframe 就没有脚本执行"。
这是**设计取舍，不是缺陷**。要"两全"必须引入 **D 档（信任分级 `allow-same-origin`）**，
即：用户显式授信的卡走同源帧、走直渲染；未授信的维持现状。包D 的提示词已写好
（`HANDOFF_提示词_包D_信任分级最后一公里_2026-10-18.md`）。
