### 3.2 核出来的真缺口：`type` 列没有写通道

「这本是该角色的角色书」在本仓是**两列的合取**：

- `WorldBook.character_id`（归属，`models/worldbook.py:16`）
- `WorldBook.type == 'character_book'`（角色书标记，`models/worldbook.py:24`）

而 `type` 同时被两处消费，任缺一处绑定就名存实亡：

- `api/worldbook.py:287` 列表的 `type == "character_book"` 过滤
  ⇒ 前端 `SmartCardCompatController.resolveCharWorldbookExport:453` 认 primary 靠它；
- `services/mvu_entry_filter.py:42` 的同名过滤
  ⇒ MVU 的 `<initvar>` / schema 提取靠它。

核到的结论：**`type` 在全仓没有任何 API 写通道** —— 只有「角色卡导入」这条 service 内部路径
（`_create_worldbook_from_character_book`）会把它写成 `character_book`，`PUT` 改不了。
⇒ 只改 `character_id` 会造成「卡调完 `setCurrentCharLorebooks` 后重新加载仍是旧绑定」，
即任务书明令禁止的"只在内存里生效的假通道"。

**处置**：给 `PUT /api/worldbooks/{id}` 开 `type` 写通道 ——

- `schemas/worldbook.py` `WorldBookUpdate.type`：只收 `'world_book'` / `'character_book'` 两枚举，
  第三态一律 ValueError ⇒ 422（不造读不到的孤儿类型）；
- `api/worldbook.py:421` 照 `character_id` 同手法处理（`model_fields_set` 区分"没传/传 null"）；
- 安全面：PUT 前面已有 `user_id == user.id` 过滤 ⇒ 改不到别人的书（有测试）。

### 3.3 顺手修掉的既有真 bug：列表缓存失效恒不匹配

第一次跑端到端用例时，PUT 返回 200 但紧随的 GET 仍是改前的值。查下来不是我写错，是既有 bug：

```
list_worldbooks 的缓存 key（core/cache.py:93-110 按 kwargs 键名字典序拼）形如
    worldbook_list:character_id=<hash>:type=<hash>:user=<id>
而失效调用写的是
    invalidate_cache(f"worldbook_list:user={user.id}")   # core/cache.py:75 走 startswith
⇒ 前缀永不匹配，要等 TTL=15s 自然过期才刷新。
```

本项目已有正解 `invalidate_user_cache(prefix, user_id)`（后缀匹配），`api/character.py:379` 等均在用；
worldbook 侧 4 处（`worldbook.py:341/426/459/690`）+ `worldbook_blueprints.py:142` 一处写成了错的形式。
全部改成 `invalidate_user_cache("worldbook_list", user.id)`。

这条不修，任务书 A 的验收项"绑定/解绑后，重新加载会话仍是新绑定"在 15 秒窗口内**直接不成立**。

> 副作用面：`invalidate_cache` 在这两个文件里已无调用点，import 一并收紧（避免 lint F401）。

## 4. 实现

### 4.1 父侧（SmartCardCompatController.ts）

| 函数 | 作用 | 被帧内哪个键调用 |
|---|---|---|
| `resolveWorldbookByName(name)` | 书名 → id 的**唯一**解析 | 删除族 + 绑定族共用 |
| `demoteOtherCharBooks(characterId, keepId)` | 把多余的角色书降级，保 primary 唯一 | 绑定族 |
| `deleteSmartCardWorldbook(payload)` | 删书 | `deleteWorldbook` / `deleteLorebook` |
| `rebindSmartCardCharWorldbooks(context, payload)` | 卡↔书绑定 | `rebindCharWorldbooks` / `setCurrentCharLorebooks` |

三个刻意的决定：

1. **书名→id 必须唯一，同名多本一律拒绝**（`worldbook_name_ambiguous`）。
   ST 侧书名实质唯一，Palink 允许重名；删除不可逆，挑第一本等于替用户掷骰子。
2. **绑定前先把既有角色书全部降级**，再绑 primary。
   理由是 primary 的判定口径是 `books[0]`、排序 `updated_at desc` —— 留着多本 `character_book`
   会让"谁是 primary"取决于写入顺序。
3. **归属核对放在父侧**。帧内只有卡传来的名字，无从判断归属；`worldbookApi.list()` 带登录态、
   后端按 `user_id` 过滤 ⇒ 越权书根本解析不到。

删除族与绑定族的失败传播方式按 §2 的表各不相同（false vs throw）。

### 4.2 帧内（runtime-body/part-07.ts）

四个成员加在 `tavernHelperTh134Compat` 的 lorebook 族里，全部桥到父侧同一份实现，
deprecated 名与现行名**共用**父侧动作，不复制第二份逻辑。

模板串红线自查：本区域改动未引入反引号、未引入 `${`（`grep -c '\${' part-07.ts` ⇒ 0），

### 4.3 为什么没进手势闸门

`SMART_CARD_MUTATING_ACTIONS_REQUIRING_GESTURE` 上方的论证（§2）明确反对扩大集合：
用户激活不向下传播到 opaque-origin iframe，而"卡片在自己管理的世界书里增删"是 ST 插件

## 7. 语义偏差与已知遗留（照实写，不许含糊）

1. **`additional` 不等于 ST 的 additional。**
   ST 里 additional 是参与注入的**第二挂载位**；本仓只有一个 primary 注入位（读侧取 `books[0]`，
   排序 `updated_at desc`）。若把 additional 也标成 `character_book`，谁被读成 primary 就成了轮盘赌。
   ⇒ 本批给 additional 只绑归属、不标 `character_book`，换来 primary 唯一；
   代价是 **additional 目前不等于 ST 那组注入语义**。这是故意的取舍，不是漏做。

2. **按角色名绑定不支持。** `rebindCharWorldbooks` 的首参照 d.ts 只认 `'current'`，
   非 current 返回 `character_name_unsupported`，与既有 `getCharLorebooksCompat` 的口径一致
   （父侧桥只服务当前卡，不替别人绑书）。

3. **读侧 `getCharWorldbookNames().additional` 的形状未改。** 现有实现返回 `[primary]`，
   这不是本批的目标键，改它有回归风险 ⇒ 未动，仅在此登记。

4. **`renameWorldbook` 仍未实现。** d.ts:192-193 的 TODO 明确「rename 需要处理世界书绑定」，
   本批未触及（不在四个目标键内）。
