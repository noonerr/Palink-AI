## §1 施工铁律（违反即视为事故）

1. **禁 `git add -A` / `git add .`**。多 agent 共享工作区，会卷入别人的在途改动。
   一律 `git add <明确文件路径>`。
2. **每批提交独立、可回滚**。批与批之间不混合生产代码与文档。
3. **每批提交后必须跑** `bash scripts/gate.sh backend`（见 §3 修好之后才可用）。
4. **改后端必须重建容器**：`docker compose build backend && docker compose up -d backend`。
   改前端必须重建 dist 并确认容器在服务新指纹。**提交完不重建 = 用户跑旧代码。**
5. **不要为让门禁变绿而改测试或加 `|| true`**（`AGENTS.md` 已有此红线，本方案重申）。
6. **不要碰提示词装配链**（`roleplay_prompt_assembly.py` 的装配逻辑），除非用户明确授权。
   本方案 §4 只改**常量与计量口径**，不改装配行为。

### 2.6 终极验收：从 HEAD 重建，比对 md5

批次 A/B/C 提交后，做这个验证 —— **它是"生产可重建"的唯一客观判据**：

```bash
export MSYS_NO_PATHCONV=1   # 必须！否则 Git Bash 会把 /app/... 转成 Windows 路径

# 1) 在仓库外新建一个干净的 HEAD 检出
mkdir -p /tmp/palink-head && git archive HEAD backend/app | tar -x -C /tmp/palink-head

# 2) 与生产容器逐文件 md5 比对（抽查 8 个关键文件，与审计 §1 同一组）
for f in memory_module/retriever.py api/character_ext.py core/config.py \
         memory_module/service.py services/mvu_engine.py memory_module/config.py \
         api/chat.py services/character_message_builder.py; do
  a=$(md5sum "/tmp/palink-head/backend/app/$f" | awk '{print $1}')
  b=$(docker exec palink-ai-backend-1 md5sum "/app/app/$f" | awk '{print $1}')
  [ "$a" = "$b" ] && echo "SAME $f" || echo "DIFF <<< $f"
done
```

**验收标准：8 个全部 SAME。**

### 3.1 修门禁假红（审计报告 §5）

**根因（已定位，不要再猜）**：
`gate.sh` 不传 `--basetemp`，pytest 落在系统 temp 的 `pytest-of-<user>/`，
并自动 garbage-collect 旧代 basetemp。实测本次清理 **59 个文件 > 守卫阈值 50**
⇒ 抛 `SystemExit` ⇒ 退出码 1，**且 pytest 连汇总行都没打印**。

`gate.sh:113` 的注释写「实测一次全量只产生 17 个临时子目录，远低于阈值 50」——
**这个判断错在：它统计的是"本次产生"，而触发守卫的是"清理历史累积"。**

**修法（治本：让 garbage 收集无从发生）**：

```bash
# scripts/gate.sh 的 backend 段，改为每轮一个全新 temproot
if should_run backend; then
  STAMP="$(date +%Y%m%d-%H%M%S)"
  BTROOT="$LOGDIR/pytest-bt-$STAMP"     # LOGDIR 在 /tmp 下，仓库外
  mkdir -p "$BTROOT"
  run_stage "后端 pytest" backend bash -c \
    'cd "'"$ROOT"'/backend" && PYTEST_DEBUG_TEMPROOT="'"$BTROOT"'" '"$PY"' -m pytest tests/ -q --junitxml="'"$BTROOT"'/junit.xml"'
  diagnose_env_guard "$LOGDIR/backend.log"
fi
```

要点：
- **每轮 temproot 是新建的空目录** ⇒ 无历史 basetemp ⇒ 不触发 garbage 收集 ⇒ 守卫永不命中
- **不加 `|| true`、不加 `--continue-on-collection-errors`**（`AGENTS.md` 红线）
- 临时目录仍在仓库外（`/tmp/palink-gate/…`），不违反既有约定

**双保险：让 `run_stage` 能区分"真失败"与"结果不可信"**

`--junitxml` 写出来后，即使 pytest 在收尾被杀，也能从 xml 里读到真实结果。
在 `diagnose_env_guard` 里加一段：xml 存在且 `failures=0 errors=0` 时，
明确输出「⚠️ 退出码非 0，但 junitxml 显示无失败 —— 环境拦截，非代码回归」，
**并仍以非 0 退出**（保持"退出码即结论"，只是让人一眼看懂红的是什么）。

**验收**：连续跑 3 次 `bash scripts/gate.sh backend`，无 `safe-delete` 字样，退出码 0。

## §4 阶段二：解开"计量 bug 绑定"（审计报告 §2）

### 4.1 问题

`backend/app/utils.py:472-481`：`cost = len(text) // 2`
实测中文约 **0.66 token/字**，此处按 0.5 算 ⇒ **低估 1.37 倍**。
注释明写「**已知且刻意保留**」——因为
`roleplay_prompt_assembly.py:5111` 的 `_MEMORY_BUDGET_LEVEL_TOKENS = (750, 4000, 6000, 8000)`
是在这个错误口径下用 **53 题 LLM 打分**扫出来的（0.698 vs 0.509, p=0.0024）。

⇒ **核心正确性锚定在一个计量 bug 上：修计量 = 分数退步 = 不敢修。**

### 4.2 修法（推荐方案：正名，不动数值）

**不要改数值**（改了要重扫 53 题，成本高且可能引入新偏差）。**改单位名**：

1. 把常量重命名，让名字不再撒谎：
   ```python
   # roleplay_prompt_assembly.py:5111
   _MEMORY_BUDGET_LEVEL_TOKENS = (750, 4000, 6000, 8000)
   #  → 重命名为
   _MEMORY_BUDGET_LEVEL_INTERNAL_UNITS = (750, 4000, 6000, 8000)
   #  并注明：单位为「内部口径 = 字符数 // 2」，非真实 token，
   #          换算真实 token 需 ×1.37；二者绑定，改任一必须同步改另一个。
   ```
2. 在 `utils.py` 的 `cost = len(text) // 2` 处保留注释，但把「刻意保留」
   改写为明确的**契约说明**："本口径是档位表的定义基准，改它等于重定义档位"。
3. `_resolve_memory_max_tokens()` 的 docstring 同步改（现写「token 上限」，实际是内部单位）。

**收益**：零行为变更、零回归风险，但**消除了"叫 4000 实为 5490"这个长期隐患**——
以后不会再有人把 4000 当成真实 token 预算去推理。

### 4.3 备选方案（若要动真格，必须打包做）

若坚持要"真实 token 口径"：**必须同时**做这两件事，顺序不可反：

1. 档位值 ×1.37：`(750, 5480, 8220, 10960)`（取整）
2. `cost` 改为真实估算（0.66 token/字，或用 `token_counter_service`）
3. **重扫 53 题验证分数不退步**，退步则回滚整套

⚠️ 不选此方案的理由：53 题单会话单卡、判分是 LLM 未人工抽样（审计报告已标"可信边界"），
**在这个实验强度上做数值外推，是把参数再过拟合一次。**

### 4.4 验收

- `grep -rn "_MEMORY_BUDGET_LEVEL_TOKENS" backend/` 返回 0（已改名）
- 记忆注入行为**无任何变化**（用同一会话跑装配，注入条数/条序与改动前一致）
- `gate.sh backend` 绿

## §9 风险与回滚

| 风险 | 触发场景 | 回滚 |
|---|---|---|
| 提交卷入他人在途改动 | 用了 `git add -A` | `git reset --soft HEAD~1` 后按文件重加；**不要用 `--hard`** |
| 43 个删除项被误复活 | 有人 `git checkout .` | 批次 E 提交后即免疫；未提交前用 `git stash` 保护 |
| 门禁改动引入新假绿 | `--basetemp` 又指进仓库 | 见 `AGENTS.md` 红线；回滚 gate.sh 到 `git log -- scripts/gate.sh` 上一版 |
| 端点瘦身删掉在用端点 | 调用方用了动态拼接路径 | 每个端点一个 commit，`git revert <sha>` 精确回退 |
| ST 兼容层被误删 | 有人照审计报告 §3 施工 | 本文件 §0 已作废该建议；立即 `git revert`，以 `CharacterCardRenderer.tsx` 能渲染为准 |

## §10 本方案的自我约束（防"许愿式方案"）

审计报告批判的核心是「**把描述问题的工作误当成解决问题的工作**」。
为避免本方案犯同样的病，每条任务都必须满足：

1. **有可执行的命令**（不是"应该加强…"）
2. **有客观验收标准**（不是"确认无误"）
3. **有明确的不做什么**（负向清单，见 §6.3、§7）

**本方案完成后，唯一值得汇报的数字不是"做了几项"，而是 §2.6 的 8 个 SAME。**
那 8 个 SAME 之外的一切，都只是让下次审计更容易一点。
