## 2. 触发频率评估

- **书籍集合重叠度：高**。前端 `loadCharacterWorldBooks(characterId)` 与后端 `char.world_books` 指向同一批角色关联世界书，条目集合基本一致。
- **扫描输入差异**：前端只扫「最近 20 条消息」，后端扫完整装配上下文 → 命中集合有重叠但非恒等（前端漏掉更早的命中，后端更全）。
- **SSE 是否实际启用**：`useChatWebSocket.ts:68` `useWebSocket` 默认 `true`，WS 连接正常时走 WS（无双份）；**SSE 仅在三类场景**：① WS 未连接（断线/未握手完成）；② 用户显式不用 WS；③ `isSmartCardTrigger && options.awaitResult`（智能卡触发）。即触发频率为「偶发/降级路径」而非稳态。
- **有效重复注入判定**：SSE + 角色带世界书 + 同一条目被两端同时命中 → prompt 内同一段世界书文本出现两次；同时该文本被写入存储的 user 消息。**判定：成立，但仅在 SSE 降级路径。**

## 3. 影响面

1. **Prompt 双份**：重复的世界书内容占用预算、可能强化/扭曲上下文（模型把同一条目当两个来源）。
2. **user 消息持久化污染**：前端展示用原始 `displayContent`（[useCharacterChat.ts:1125](file:///d:/项目/Palink-AI/frontend/src/hooks/useCharacterChat.ts#L1125)），但后端落库用 `effectiveMessage`（含世界书文本）→ 显示/存储不一致；历史回流后，后续世界书扫描会把「含世界书文本的已存消息」当作素材，可能放大匹配（次级放大效应）。
3. **双引擎一致性风险**：前端 `stWorldBookManagerSingleton` 与后端扫描的多项参数（深度预算、概率、delay 队列、group scoring 等）各自独立实现，SSE 下两者叠加时一致性无法保证。

## 4. 最小去重方案（本期不动手，推荐后续实施）

**倾向后端为权威 → 前端 SSE 路径删除世界书拼接**（删 `useCharacterChat.ts:1229-1231` 的 `worldBookContext` prepend，`effectiveMessage` 改直接使用 `messageForApi`）：

- 后端 palink-native 装配已具备完整世界书扫描（`_append_worldbook_context`），是唯一的权威注入点；
- 删除后 WS/SSE 两路径行为一致（WS 本就无前端拼接）；
- 附带修复 user 消息持久化污染（存储不再含世界书文本）；
- 风险兜底：保留 `buildWorldBookContextForChat()` 函数定义（不调用即可，避免连带改动）；实施前用一次 SSE 实测确认后端扫描在「初始会话 / 群聊模式 / 智能卡触发」下均覆盖（已确认主装配路径 L3567 覆盖 palink-native；群聊走 L2697 世界书策略，需实施时抽样验证）。
- 若后续想保留前端预览能力：可把前端扫描结果仅用于 UI 预览（world_info_activated 事件已由 scanner 触发），不再进请求体。
