## 1. 实测现状（先纠正一个流传的错误认知）

**服务端执行回路是有的**，此前被误判为"没人执行"：

- `inference_dispatcher.py:778` `max_tool_rounds = 3 if tools else 1` → 有界循环，最多 3 轮，不会失控。
- `:865` 向流里 yield `tool_call` → `:869` 若传了 `tool_executor` 就用它（WebSocket 把调用转给前端 handler）→ `:877` 否则查角色闸 → `:882` **否则服务端自己执行**：`mcp_service.execute_tool_call(...)`，结果以 `role="tool"` 回填并继续生成（`:896-905`）。

**真正的三个缺口（本计划要补的就是这三个）**：

| # | 缺口 | 证据 |
|---|---|---|
| G1 | 角色扮演路径**根本不给模型这批工具**。通用聊天会 `get_all_tools_openai_format()` 再传 `tools=mcp_tools`（`chat.py:357,368`、`websocket.py:334,349`）；而 `character_ext.py:4881` 只传 `tools=req.tools`（前端插件注册的工具），**全文件零处引用 mcp_tools** → 模型压根不知道有出图这回事 |
| G2 | **没有"内置工具"这个位置**。`execute_tool_call` 只从 `_tool_name_registry` 解析名字，且要求 `server_id` 在 `_active_connections` 里，否则报 `MCP server not found` → 只能执行**外部 MCP server** 的工具。出图能力在后端进程内，却挂不进这张表 |
| G3 | **角色闸默认只放管理员**：`core/config.py:42 MCP_ALLOWED_ROLES = ["admin"]`。非管理员拿到的工具返回值是字符串 `"Tool execution requires admin permission"`，模型会当成"工具失败"继续瞎编 |

## 2. 技术选型：不新建 MCP 服务

出图能力已在进程内（`message_media_service` + 服务商配置 + 落盘 + 事件推送）。走 MCP 要付：一个新常驻进程 + 网络跳 + JSON-RPC + 连接与密钥管理 + 还得单独解决 G3 的角色闸。**收益为零。**

→ **选 G2 的补法：加一层"内置工具注册表"，让服务端执行回路能调到进程内函数。** 约 40 行，且天然不碰 G3（内置工具自己判定权限，不动全局 `MCP_ALLOWED_ROLES`）。

> ⚠️ **明确禁止的省事做法**：把 `MCP_ALLOWED_ROLES` 加上 `"user"` 来"让它能用"。那等于把所有已配置的外部 MCP 工具一次性开放给全体用户 —— 那是花钱、越权、且可被投毒角色卡诱导的能力面。**权限必须逐工具判，不能放全局闸。**

## 3. 分解（每步含触碰点与验收）

### S1 内置工具注册表 + 执行分支
- 新增 `backend/app/services/builtin_tools.py`：`{name → (openai_schema, handler, 权限判定)}`，命名加独立前缀（如 `palink__generate_image`）避免与 MCP 工具名撞车。
- 改 `inference_dispatcher.py` 的 elif 链：在 `tool_executor` 之后、角色闸之前插入「内置工具」分支；未授权时返回**结构化的拒绝理由**而非泛泛失败。
- **验收**：单测覆盖三条分派（executor / 内置 / MCP）互不串道；未授权用户调用得到明确拒绝且模型不崩。

### S2 出图工具本体
- handler 直接复用 P1 管线：解析目标消息 → 建 pending → 调服务商出图 → 落 `extra.media` → 推事件。
- **返回值只给一句短文本**（例："图片已生成并附在本条回复"）+ 失败时给人话原因。**严禁把 base64 或长 URL 塞进 tool 返回值** —— 单次返回可达 11MB，会把上下文直接打爆。
- 权限判定在此处：要求该用户已启用图片服务商，且按用户级开关与配额放行。
- **验收**：假上游跑通"模型调用 → 落库 → 事件 → 前端挂图"全链；DB 里 `error` 存真因、界面显示脱敏文案（沿用 P1 既有约定）。

### S3 让角色扮演路径把工具交给模型
- 在 `character_ext.py` 组装生成请求处合并 tools（沿用 `req.tools` 已有形状，做去重与上限裁剪）。
- **红线**：提示词的注入必须走 `tools` 参数，**不得改 `roleplay_prompt_assembly` / 装配链**（AGENTS.md 明令）。本步不允许出现"往 system prompt 里塞工具说明"的实现。
- **验收**：开关关闭时 `tools` 与改前**逐字节一致**（防回归）；开关打开时模型能发起调用。

### S4 护栏（这个功能的风险全在这一步）
- **默认关闭**，且是**用户级开关**，不是全局。
- 每轮**最多 1 张**；`max_tool_rounds=3` 已有上界，但要再加"出图调用次数"计数，防模型反复调。
- 服务商未配置/失败时**不重试**（避免打爆上游与额度）。
- 明确降级：工具失败 → 模型继续以纯文本回答，**不阻塞生成、不给用户报错弹窗**。
- 成本可见：每次出图计入用量（与现有 token 额度体系统一记账）。
- **验收**：故意让上游 100% 失败，用户侧只看到"回答略慢 + 没有图"，无错误弹窗、无重复请求（用请求计数证明）。

### S5 兜底路径（标记解析），给不支持工具调用的模型
- 约定 `<img_prompt>…</img_prompt>`：解析→剥除→走同一个 S2 handler→落库推事件。
- **能力探测决定走哪条**：模型/网关支持 tool calling 用 S1-S3；不支持才用本步。两条共用同一个出图入口，不分叉实现。
- 剥除必须在落库前完成，用户永远不该看见这个标记。
- **验收**：两条路径产出**完全相同**的 `extra.media` 结构（用同一份断言测）。

### S6 测试与真机
- 后端：假上游（不起真服务商）覆盖 S1/S2/S4 全链 + 角色与配额判定；容器内全量回归。
- 前端：媒体显示已有 P1 测试，本步只补"模型自主出图事件到达时骨架→原位换图"。
- 浏览器真机：**0 付费**做法沿用 P1 验收时那套（页面级拦截器挡掉付费请求）。
- **反向验证**（硬要求）：关掉用户级开关，确认模型**看不到**该工具；破坏 S4 计数，确认能变红。
