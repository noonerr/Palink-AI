## P0-1 `[MVU]` 页面级变量在"不可得"时**整份替换**，会丢掉 `variables` 里的其它键

**【单证】**（我实测了 5 个会话，`chat_metadata.variables` 里**恰好只有** `stat_data` 一个键，所以本轮**没有观察到**丢键；但代码路径确定会丢）

**位置**：`backend/app/api/character_ext.py`，`get_character_session_messages`，MS-2 新增块
（`_tip_state.available` 为假的那一支）

**现状**：
```python
if _tip_state.available:
    _merged = dict(session_variables) if isinstance(session_variables, dict) else {}
    _merged["stat_data"] = _tip_state.stat_data
    _merged["mvu_state_source"] = _tip_state.reason
    session_variables = _merged
else:
    session_variables = {"stat_data": {}, "mvu_state_source": "unavailable"}   # ← 整份替换
```
`session_variables` 的初值来自 `json.loads(chat_metadata)["variables"]`，**是任意 dict**，不保证只有 `stat_data`。

**后果**：任何往 `chat_metadata.variables` 里放了非 `stat_data` 键的卡/插件，一旦视点解析不可得，这些键**全部消失**，前端拿到的是 `{stat_data:{}, mvu_state_source:'unavailable'}`。

**修法**（一行）：
```python
else:
    session_variables = {
        **(session_variables if isinstance(session_variables, dict) else {}),
        "stat_data": {},
        "mvu_state_source": "unavailable",
    }
```

**验收**：
1. 造一个 `chat_metadata.variables = {"stat_data": {}, "自定义键": 1}`、且**没有任何楼层带 `stat_data`/`mvu_patch`** 的会话；
2. `GET /api/character-sessions/{sid}/messages` 必须返回 `自定义键 == 1`；
3. 反向证明：把修法回退，该断言必须变红。
4. ⚠️ 造数据只能进一次性容器 + 空库（生产库禁写）。

**风险**：极低。不改任何正常路径（`available` 为真时行为不变）。

## P0-2 `[R2]` `POST /api/chats/get` 是"读"接口，但会建会话并 `commit`

**【直证】**（代码 + `_ensure_session` 的 `db.add`/`db.commit` 我逐行读过；**我没有实际调用**以免违反零写入，所以"会不会真的建"是靠代码推的）

**位置**：`backend/app/api/silly_tavern.py:2915-2931` → `_ensure_session`（`:1062-1091`，`db.add(session)` / `db.add(branch)` / `db.commit()`）

**现状**：ST 客户端拿一个不存在的 `file_name` 调 `chats/get`，Palink 会**新建一条会话 + 一条分支并落库**。
上游 ST 的 `chats/get` 对不存在的 chat 返回 `{}`（`src/endpoints/chats.js:529/533`）。

**为什么是 P0**：① 违反本项目"读接口不写库"的纪律；② 一个插件循环探测 chat 名就能把库刷满；
③ 与 ST 行为不一致（ST 返 `{}`，Palink 返 `[header]` 并**悄悄建了一条会话**）。

**修法（建议，需设计决策）**：
- 方案 A（贴 ST）：`chats/get` 找不到就不建，返回 `{}`。**风险**：Palink 前端可能依赖"打开角色页自动建会话"，要查调用方。
- 方案 B（保守）：保留建会话，但**只允许显式开关**触发（如 header `X-Palink-Ensure-Session: 1`），默认不建。前端改一处。
- 方案 C（最小）：不改行为，只在**非 GET 语义**上加审计日志 + 速率限制，把"静默写"变成"可见写"。

**我倾向 B**：既贴 ST（默认不写），又不砸现有前端。但**必须先 grep 前端谁在调 `chats/get`、是否依赖自动建会话**——我没查，这是本条的空白。

**验收**：用**只读账号**打一个不存在的 `file_name`，前后 `select count(*) from character_chat_sessions` 必须不变。

## P0-3 `[SEC]` ST 端点族零限流，含烧钱端点

**【直证】**（`grep -c rate_limit silly_tavern.py` = 0；30 次 `/version` 全 200；`backend/app/middleware/` 不存在）

**位置**：`backend/app/api/silly_tavern.py:1950` `/api/backends/chat-completions/generate`（会打外部网关）

**为什么是 P0**：这是**唯一一条能直接烧钱的缺口**。任何登录用户可无限刷。虽然要登录（不是未授权 DoS），但本项目历史上"40 次失败请求 = ¥17.74"。

**修法**：
```python
from ..core.rate_limit import enforce_rate_limit   # 已在 character_ext.py:31 用过同一套
...
async def st_generate_chat_completion(payload, request, user=Depends(get_st_current_user), db=Depends(get_db)):
    enforce_rate_limit(request, user_id=user.id, scope="st_generate", limit=..., window=...)
```
参数照 `character_ext.py:4344` 那处的既有写法抄，**不要自创新限流器**。

**顺带**：把 `st_speech_generate` / `st_elevenlabs_synthesize` 两个外部副作用端点一起加上（同一批，别分两次）。

**验收**：连打 N+1 次，第 N+1 次必须 429 且 body 机器可读。**只能用不烧钱的端点验**（如 `/version` 若也接限流），或把 limit 调到 2 在隔离栈里验。

## P0-4 `[MVU]` 进程启动后第一次装配，记忆上下文必然丢失

**【直证】**（`docker logs -t` 02:20:56 有 WARNING；容器重建后该日志**恰好 1 次**；离线 8 变体只有 V1 报）

**位置**：`backend/app/services/roleplay_prompt_assembly.py:5874` `nested.commit()` → `except` 分支 `:5875-5885`

**现象**：`report` 里出现 `memory = error / This transaction is closed`，这一次请求的**记忆上下文整段不进提示词**。

**根因（我的推断，未证）**：`_append_memory_context` 里先 `req.db.begin_nested()`（`:5615` 的 `_card_probe`），
再在 `:5764` 开第二个 `nested`；两个 savepoint 的生命周期交叉，某个分支把外层事务关掉了，
导致 `nested.commit()` 抛 `This transaction is closed`。**【推断】**

**为什么是 P0**：确定性 100%（每次进程启动必现），虽然频率低（只在重启后第一次）。
但它会静默降级——`report` 里有 error，**用户侧看不出来**，只会觉得"这次回复怎么不记得之前的事"。

**修法**：
1. **先定位**：在 `:5615` 和 `:5764` 之间打 `db.in_transaction()` / `db.get_transaction()` 的日志，跑一次重启复现，看事务在哪一步被关。
2. 大概率修法：把 `_card_probe`（`:5615`）改成**不 commit、只读**，或与 `nested` 合并成同一个 savepoint。
3. 兜底：`except` 分支里加 `report.append(... "error")` 之外，**同时**写一条 `logger.error` 并带 `request_id`，让它可观测。

**验收**：重启 backend → 立刻发一次装配 → `docker logs` 里**不应**出现该 WARNING，`report` 里 `memory` 应为 `included`。

**风险**：动 savepoint 语义容易踩"脏事务"坑。**建议先只做第 3 步（可观测化）**，把问题从"静默"变成"有记录"，再动第 2 步。

## P1-1 `[WB]` ST 世界书面只暴露"未绑定"的书 ⇒ 已绑定书在 ST 侧不可见不可编辑

**【直证】**（`worldinfo/list` 返回 1 本；DB 里 admin 有 5 本；`world_names` 也只有 1 项）

**位置**：`backend/app/api/silly_tavern.py:4212` `.filter(WorldBook.user_id == user.id, WorldBook.character_id.is_(None))`；docstring（`:4188`）自述"仅全局世界书"

**这是"设计取舍"还是"缺陷"？** —— 我倾向**取舍成立、但能力损失必须补偿**：
Palink 的模型是"书绑卡"，ST 的模型是"书是全局文件、由 `charLore` 引用"。两者不等价，
所以"只列未绑定的书"在 Palink 里是**自洽**的；但 ST 插件调 `getContext().world_names` / `updateWorldInfoList`
时，会认为"这张卡没有世界书"，进而**改不了、也看不到**。

**修法（建议，需老板拍板）**：
- 方案 A（贴 ST）：`worldinfo/list` 返回**全部** `user_id` 名下的书，用 `character_id` 作为额外字段标出归属；
  前端 ST 侧按归属分组。**代价**：世界书面会出现同名重复（3 本都叫 `露缇雅1.2`），需要去重策略。
- 方案 B（补偿式）：保留现在的过滤，但**新增** `/api/worldinfo/list?scope=all` 或 `?character_id=`，
  让 ST 侧能按卡取书。**代价**：ST 原生代码不会带这个参数，插件仍然看不到 ⇒ **不解决问题**。
- 方案 C（最小可见性）：至少让 `world_names` 包含**当前角色绑定的书**（`active_character` 已知），
  这样 ST 的"世界书下拉"至少能选到本卡的书。

**我倾向 C**：改动最小、不破坏现有语义、直接解决"看不到自己卡的书"这个最痛的场景。
A 是终局但需要先定同名去重规则。

**验收**：admin 登录 → `/api/settings/get` 的 `world_names` 至少包含当前角色的书；`worldinfo/list` 能取到该书的 entries。

## P1-4 `[ASSEM]` 插件 `IN_CHAT depth=0` 被强制改成 1，与世界书 `atDepth=0` 落在末条 user 两侧

**【直证】**（`probe_depth.py` 队列打印 `(1, 100, 0, 'extension_prompt', 'audit_d0', 5)`；落点 `[28]` vs user `[29]` vs 世界书 `[30]`；新旧容器一致）

**位置**：`roleplay_prompt_assembly.py:2220-2235` `[INJ-CLOSE-TAG-GUARD]`

**修法（二选一，需拍板）**：
- 方案 A：把 guard 的适用范围**扩大到世界书 atDepth=0**（统一改成 1）。**代价**：可能让现在正常的卡变差。

  让"被改写"这件事**可观测**，并把差异写进台账。

**验收**：`report` 里能看到该条被 guard 的记录。

# 附录 C · 对"1:1 复刻 ST"这个目标本身的一句话判断

**别把"1:1"当成验收标准，它不可达也不该达。**

本项目已经有一批**有证据支撑的主动偏离**（`INJ-CLOSE-TAG-GUARD` 的 depth 0→1、
世界书尾部落点、世界书只列未绑定、`silly_tavern_mode` 列删除……），
每一条背后都有"实测某个模型会坏"的记录。把它们改回 ST 原样，等于**把踩过的坑再踩一遍**。

**可操作的替代标准**：
> 每一个与 ST 不同的行为，都必须（a）有台账条目，（b）写清"为什么不同"，（c）写清"怎么观测"，
> （d）有回归守卫。**没有台账的偏离才算 bug。**

按这个标准，本计划 P1-3 / P1-4 的"修法 C（只做可观测 + 台账）"才是正解，
而不是把它们改成 ST 的样子。
