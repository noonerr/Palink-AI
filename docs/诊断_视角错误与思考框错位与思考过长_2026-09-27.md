## 一、思考框：前端把正文第一段当成了"思考"

### 实测物证

浏览器 DOM 实取（`mcp__browser-use__evaluate_script`）：

```
thinkButtons=1
--- BOX 0 len=102 ---
深度思考
清晨的阳光从法国梧桐稀疏的叶片间漏下来，在南方联合大学教育学院楼前的砖石地面上落了一地碎金。
周一早上的校园还不算太喧闹，三三两两的学生抱着包从食堂方向走过来，空气里有豆浆的焦香和晨露潮湿的气息。
```

而数据库里这条消息真正存的思考（`character_chat_messages.extra ->> 'reasoning'`）是 **6830 字**，开头是：

```
让我思考一下这个场景。作为admin，我站在南方联合大学教育学院楼前。时间刚过早上7:50……
```

两者完全不同 → 框里显示的不是 `extra.reasoning`。

### 根因

`frontend/src/lib/utils.ts:71-81`：

```js
if (!thinkingParts.length) {
  const thinkingMatch = strippedContent.match(/^([\s\S]*?)\n\n([\s\S]*)$/);
  if (thinkingMatch && thinkingMatch[1].trim().length > 0) {
    const potentialThinking = thinkingMatch[1].trim();
    const potentialContent  = thinkingMatch[2].trim();
    if (potentialThinking.length > 20 && potentialContent.length > 0) {
      thinkingParts.push(potentialThinking);   // ← 正文第一段被判为"思考"
      cleanedContent = potentialContent;       // ← 正文从第二段开始
    }
  }
}
```

语义：**只要模型没打 `<think>` / `<model_reasoning>` 标签，就把回复的第一个自然段（>20 字）认定为思考并移出正文。**

这是"思考与正文混在一个 content 字段"时代的遗留产物。仓库后来上了分离存储
（`stream_builder.py:37` 的 `[REASONING-SEPARATE]` 注释、思考单独落 `extra.reasoning`），
但这段兜底启发式没跟着删，于是从"救旧格式"变成了"每轮偷走正文第一段"。

`git log -L` 显示它早于 2026-08-17 的对象丢失基线提交（`7d5dea1`），即原始代码，非近期引入。

### 连带后果（比原现象更严重）

1. **真思考永远看不到。** `Message.tsx:855` 是 `if (!effectiveThinking && !isUser)`，
   第一段被抢走后 `effectiveThinking` 已非空，读 `extra.reasoning` 的分支不执行。
   用户看到的"深度思考"永远是假的，6830 字真思考被完全丢弃。
2. **关掉"深度思考"开关时正文缺段。** `Message.tsx:884-892` 在 `showModelReasoning=false`
   （`CharacterView.tsx:248` 的默认值）时直接返回 `displayContent: cleanContent`，
   而 `cleanContent` 源自已剥掉第一段的 `rawMainContent`。
   → 首段在界面上凭空消失（DB 完好，重进会话仍缺）。这条影响**所有**多段回复，不限角色扮演。

## 二、视角错误：模型被提示词要求"成为"一个作品标题

### 实测：模型自己承认选了用户视角

从 `extra.reasoning` 原文摘录（逐字）：

> 让我思考一下这个场景。**作为admin，我站在南方联合大学教育学院楼前。**
> ……
> **我是admin，一个大学二年级的学生。** 桃汐是我的青梅竹马，长着奶油色的猫耳和粉樱色的短发。
> ……
> 我的回复……我不应该直接复述她的完整设定，而应该自然地展现这样一个早晨的相遇。
> **我会从我的视角出发，描写周围环境、看到她，然后是她的反应。**
> ……
> 让我来起草：
> **我站在教育学院楼前，阳光穿透树叶**……周一早晨，手里拿着咖啡。然后我看到了她——

模型把"以谁的视角写"当成一个**它需要自行决定的创作问题**，并明确选择了 admin（用户）。
它不认为自己在"扮演用户"——它认为自己在"以用户为主角写这一章"。
这个区分正是下面提示词缺口所在。

### 实测：装配出来的提示词长什么样

用仓库自身的装配函数实跑（`scripts/probe_assemble_dump.py`，只读，容器内执行后已清理）：

### 四个叠加因素

1. **卡是空的。** 实测 `characters` 行：
   `system_prompt=0, description=0, personality=0, scenario=0, mes_example=0, post_history_instructions=0, jailbreak=0`，
   只有 `first_mes=575`。角色设定全在 MVU 变量（12260 字）和世界书（3809 字）里，
   卡的人格字段一个字没有 → 提示词打出"（没有提供额外角色卡字段）"。
2. **`name` 是作品标题，不是人名。** `characters.name = 我被猫娘包围了！`。
   `default_prompts.py:21-30` 把 `{name}` 当身份句重复 6 次：
   "你是我被猫娘包围了！""永远以我被猫娘包围了！的身份回应""像我被猫娘包围了！那样回应"。
   这句话语法上是**以"我"开头的第一人称陈述**，且指向的不是任何一个人。
   身份锚点塌了，模型只能从上下文抓一个真实存在的人当"我"——就是 admin。
3. **全 prompt 没有一条禁止代写用户。** `grep` 全后端，与"不要写用户的言行/心理"相关的
   指令**只有 1 条**：`default_prompts.py:27` 的"不要扮演用户或其他角色"。
   "扮演"≠"以用户为叙事主语"，模型恰好绕过了这个措辞。
4. **用户档案占据最显著位置。** 世界书消息 `[2]` 的第一个条目就是 `<admin信息>`，
   进一步强化"这个场景的主角是 admin"。

### 另外两个独立缺陷（本次未直接致错，但同属视角/空响应风险面）

- **提示词以 system 结尾。** `[3]` 是 user，其后还跟着 `[4]` `[5]` 两条 system。
  硬编码在 `character_message_builder.py:274-295`：`final_reminder` 无条件 append 在
  `user_msg` 之后，没有任何守卫。
  而**本仓库自己已经记录过这个坑**——`roleplay_prompt_assembly.py:1772-1778`：
  > deepseek-v4-flash 等（推理）模型在「最后一条消息是 system 注入」时高概率立即停止生成
  > （5 次采样 3 次空响应：completion_tokens=1 直接 EOS，或 reasoning 写完不写正文）

  装配层给插件注入做了 depth 0→1 的规避，但 `final_reminder` 这条主链路自己踩在同一个位置上。
- **用户消息被指令淹没。** `[3]` 共 631 字，用户真实输入只有"开始"两字，其余 600+ 字是
  `roleplay_prompt_assembly.py:3796-3817` 拼进去的 MVU `<UpdateVariable>` 强制指令。
  模型思考里也确实为它单独规划了一段（"我还需要按格式要求更新变量"）。

## 三、思考过长的量化归因

| 指标 | 实测值 | 来源 |
|---|---|---|
| 思考长度 | 6830 字 | `extra ->> 'reasoning'` |
| 正文长度 | 1009 字 | `content` |
| 思考/正文比 | **6.8 : 1** | 同上 |
| 思考耗时 | 25.857 秒 | `extra ->> 'reasoning_duration'` |
| token_count | 4973 | `extra ->> 'token_count'` |
| reasoning_type | `thinking` | `extra ->> 'reasoning_type'` |

思考内容逐段对账，它把多少预算花在了什么上面：

1. **重读并复述设定**（约 1/3）：「时间刚过早上7:50，星期一，天气晴朗，28°C」「她的好感度是50（"青梅竹马 · 不可或缺的存在"），穿着一件奶油色的针织毛衣配粉色短裙，脖子上戴着星星吊坠」——这些全在 `[1]` 的 12260 字变量状态里，模型每轮自行捞一遍。
2. **自行解决"我是谁/谁的视角"**（约 1/4）：「作为admin，我站在…」「我是admin，一个大学二年级的学生」「我会从我的视角出发」——**这一整块是提示词失职造成的，本该由身份锚点直接给定。**
3. **格式合规规划**（约 1/4）：「我不需要用〈猫神〉标签，因为这不是猫神」「我还需要按格式要求更新变量。让我加入…」——`[标题]` + `【声音】` + `<UpdateVariable>` 三项额外输出义务。
4. **起草**（约 1/4）：「让我来起草：我站在教育学院楼前……」——正文的实际预写。

即：**思考膨胀不是模型"太努力"，而是提示词把身份判定、设定检索、格式约束三件事的失败成本
都推给了模型在思考里补偿。**

另：`reasoning_effort` 未被会话显式设置时，`provider_registry.py:66-72` 会给模型补 `"auto"`，
deepseek-v4-flash 在 auto 下自行决定深度 → 没有上限闸门。

## 四、与 SillyTavern 的区别

对照对象：本机 `d:\SillyTavern-release`，`package.json` 版本 **1.18.0**
（与仓库声明的对齐目标同版本）。项目内 `.codex/st-source/` 只有 5 个前端文件
（`script.js` 12570 行 / `message-formatter.js` / `regex-engine.js` / `events.js` / `st-context.js`），
不含 `openai.js`，所以本次用 `d:\SillyTavern-release` 取权威实现。

### 4.1 身份框架：第三人称指令 vs 第二人称断言

ST `public/scripts/openai.js:101`：

```js
const default_main_prompt =
  'Write {{char}}\'s next reply in a fictional chat between {{charIfNotGroup}} and {{user}}.';
```

Palink `default_prompts.py:21-30` + `105`：

```
你是{name}。这是你的唯一身份，不可改变。
以第一人称回应，就像你就是这个角色。
```

差异的实质：

- ST **不做身份断言**，只下**任务指令**——"写 `{{char}}` 的下一条回复"。
  主语是 `{{char}}`，`{{user}}` 在句法上是被谈论的对象，不是被扮演的对象。
  即使卡是空的，`{{char}}` 仍会被解析为卡名，指令结构本身不崩。
- Palink **先断言"你是X"，再要求"以第一人称"**。当 X 是"我被猫娘包围了！"这种
  非人名、且以"我"开头的字符串时，断言失效，"第一人称"就失去了归属，
  模型只能把"我"落到上下文里唯一确定的真人身上 = 用户。

> 这一条是视角错误的**结构性**差异。同一张空卡，ST 大概率仍写角色（因为它没要求模型
> "成为"任何人），Palink 会滑到用户视角。

### 4.2 提示词尾部：user 轮结尾 vs system 轮结尾

ST 的 `jailbreak` 槽确实在 chatHistory 之后，但：

```js
const default_jailbreak_prompt = '';     // openai.js:103
```

默认为空 → 不产出消息 → **默认配置下 ST 的 prompt 以 user 轮结尾**。
且 ST 有显式守卫，`openai.js:920-923`：

```js
const lastChatPrompt = messages[messages.length - 1];
const message = await Message.createAsync('user', oai_settings.send_if_empty, 'emptyUserMessageReplacement');
if (lastChatPrompt && lastChatPrompt.role === 'assistant' && oai_settings.send_if_empty && chatCompletion.canAfford(message)) {
    chatCompletion.insert(message, 'chatHistory');
}
```

即 ST 专门处理"最后一条是 assistant 时补一条 user"，保证续写位置落在用户轮之后。

Palink 反向：`character_message_builder.py:274-295` 在 user 消息**之后**无条件再追加
`[标题指令]` + `final_reminder` 两条 system，把续写位置推到一个 system 消息后面。

### 4.3 卡字段的槽位化

ST 把 `charDescription` / `charPersonality` / `scenario` / `worldInfoBefore/After` /
`exampleDialogue` 作为**独立可开关槽位**（`preparePromptsForChatCompletion` 的参数即这套），
空槽直接缺席，不影响 main 槽。
Palink 把卡字段压进一个 `【角色卡】` 段落，全空时打印
"（没有提供额外角色卡字段）"——**一行对模型毫无信息量、却明确宣告"你没有设定"的文本**，
反而提示模型"自己找一个身份"。

### 4.4 需要如实说明的一点（不要夸大差距）

"禁止代写 `{{user}}`"**不在 ST 默认 main prompt 里**——它是社区预设（Guanjiu / 中文角色扮演预设等）
普遍追加的一条。所以准确说法是：

- ST 默认：靠 4.1 的第三人称句法**隐含**排除，无显式禁令；
- ST 社区实践：显式加 `Do not write/narrate for {{user}}`；
- Palink 现状：**两层都没有**——既用了会失效的第二人称断言，也没有社区层禁令。

Palink 的缺口比"和 ST 不一样"更大一点：它同时缺了 ST 的默认结构和 ST 社区的补丁。

```bash

docker exec palink-ai-db-1 psql -U ai_user -d ai_hub -A -F'|' -c \
  "SELECT name, length(coalesce(system_prompt,'')), length(coalesce(description,'')), \
```
