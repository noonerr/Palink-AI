## 0. 结论速览（TL;DR）

| 问题 | 结论 |
| --- | --- |
| 卡内插件在卡与卡之间是否独立？ | **不独立**。`plugins` 表无 `character_id` 列，开关是全局的（仅按 `user_id` 做多租户隔离） |
| 能否做到"某卡只启用 A、B"？ | **能**。地基已有一半（后端 `_filter_runtime_config_for_character` 已实现），但主链路没接线 |
| 能否热插拔（切卡即时装卸）？ | **能，且只差两处代码**。卸载/幂等注入/沙箱清理**均已实现**（§2.7.1），卡点是「切卡不触发」+「卸载清单手写」 |
| 本次方案形态 | 导入卡时自动识别 → 弹窗让用户勾选 → 结果存为**卡级白名单** → 下发时按白名单过滤 → 切卡热插拔 |

**核心设计（一句话）**：新增 `character_plugin_state` 关联表 + `characters.plugin_scope_mode` 卡级模式位。
**老卡零行数据 = 行为完全不变**（`inherit` 模式），只有用户在导入时确认过才切到 `allowlist` 精确模式 —— 这是本方案不炸现有卡的关键。

## 2. 方案设计

### 2.1 数据模型

#### (a) 新建关联表 `character_plugin_state`

```sql
CREATE TABLE character_plugin_state (
    id            VARCHAR PRIMARY KEY,
    character_id  VARCHAR NOT NULL REFERENCES characters(id) ON DELETE CASCADE,
    plugin_id     VARCHAR NOT NULL REFERENCES plugins(id)   ON DELETE CASCADE,
    enabled       BOOLEAN NOT NULL DEFAULT true,
    source        VARCHAR NULL,          -- 'declared' | 'detected' | 'manual'
    created_at    TIMESTAMP NULL,
    updated_at    TIMESTAMP NULL
);
CREATE UNIQUE INDEX uq_char_plugin ON character_plugin_state (character_id, plugin_id);
CREATE INDEX ix_char_plugin_char   ON character_plugin_state (character_id);
```

#### (b) `characters` 表加一列 `plugin_scope_mode`

```
plugin_scope_mode VARCHAR NOT NULL DEFAULT 'inherit'
```

| 取值 | 语义 |
| --- | --- |
| `inherit` | **默认**。无卡级覆盖，行为与今天完全一致（沿用 `plugins.enabled` 全局开关 + 现有二类划分） |
| `allowlist` | 白名单模式。**只有** `character_plugin_state` 中 `enabled=true` 的插件才下发给该卡 |

> 分离出一个独立模式位，而不是靠"有没有行"来推断，是为了让「用户明确确认过一张卡什么都不装」这种**空白名单**也能被正确表达（有行推断法无法区分"空名单"和"没设过"）。

#### (c) 逃生门

插件侧 `plugins.config` 支持 `"exclude_from_scope": true` —— 标记为基础设施类插件，任何卡都下发，不受 `allowlist` 约束（对齐现有 `global_runtime=true` 逃生门思路）。

### 2.2 识别器（导入时自动判定这张卡需要什么）

识别结果按**优先级**合并：

| 优先级 | 来源 | 说明 |
| --- | --- | --- |
| 1（最高） | 卡显式声明 | `extensions.palink.required_plugins: ["<插件名或ID>", ...]` —— **本方案新立的约定字段**，向后兼容（老卡没这字段就走下一级） |
| 2 | 插件自声明特征 | `plugins.config.detect` 规则命中（见下） |
| 3 | 内置兜底规则 | 代码内固定的几条（见下） |

**插件自声明 `config.detect` 形态**（声明式，管理员可配）：

```json
{
  "detect": {
    "any_of": [
      { "json_path": "extensions.tavern_helper.scripts", "non_empty": true },
      { "text_pattern": "@bubble", "where": ["description", "personality", "mes_example", "scenario", "worldbook"] },
      { "json_path": "extensions.palink.required_plugins", "contains": "酒馆助手" }
    ]
  }
}
```

**内置兜底规则**（无需配置即可工作，覆盖当前唯一的 `酒馆助手`）：

1. `extensions.tavern_helper` 是 dict **且** `.scripts` 是非空数组 → 需要「酒馆助手」（复刻现有 `_character_card_entitles_card_extension_plugins` 判定）；
2. 卡正文字段含 `@bubble` → 需要「酒馆助手」。
   ⚠️ 勘误：`@bubble` 是 **ST 生态气泡对话的源格式标记**（不是 Palink 的渲染标记），
   靠它识别属**启发式**，存在漏判（卡未写标记但实际依赖）与误判风险，
   故只作兜底、优先级低于"卡显式声明"与"插件自声明 detect 规则"；
3. `extensions.regex_scripts` 非空 → **不进插件建议清单**（走 scoped 正则，天然隔离，见 §1.5）。

匹配范围（"卡正文"）：`data.name / description / personality / scenario / mes_example / system_prompt / post_history_instructions` + 卡内世界书 `character_book.entries[].content`。

**输出**：`[{plugin_id, plugin_name, reason, confidence}]`，`reason` 供 UI 展示给用户看（"卡里写了 tavern_helper 脚本" / "正文出现 @bubble 标记"）。

### 2.3 后端接口

| 接口 | 用途 |
| --- | --- |
| `POST /api/characters/import`（改造返回值） | 在现有 `{"status","character","auto_parsed"}` 上追加 `plugin_suggestions: [...]`。**不写库**，只给前端展示 |
| `GET /api/characters/{id}/plugin-state` | 返回该卡 `plugin_scope_mode` + 全部插件的启用态 + 建议清单（供设置页事后修改） |
| `PUT /api/characters/{id}/plugin-state` | 批量写入。body: `{"mode": "allowlist"\|"inherit", "plugins": [{"plugin_id": "...", "enabled": true}]}` |

> `POST /api/characters/import` 现状在 `backend/app/api/character.py` 的 `import_character`，返回 `{"status": "ok", "character": character, "auto_parsed": False}`。

### 2.4 前端：导入确认弹窗增加一步

现状：`CharacterView.tsx` 持有 `showImportOptions: string | null`，`CharacterList.tsx` 有**两处**同名弹窗（移动端 ≈L926、桌面端 ≈L1210），当前只问"是否 AI 解析和翻译"。

改造：在"解析并翻译 / 跳过"之前插入**第二步**——「这张卡识别到 N 个插件，要启用哪些？」

- 勾选框列表，每项显示插件名 + 识别理由；
- **默认勾选识别到的**，未识别到的以折叠区展示（默认不勾）；
- 用户点"确认"→ `PUT /api/characters/{id}/plugin-state`（`mode=allowlist` + 勾选结果）；
- 用户点"暂不设置"→ 什么都不写，该卡保持 `inherit`（行为与今天一致）。

> 两处弹窗都要改，别只改一处。

#### 2.5.1 与装配层自动门控的优先级（**设计缺口补全，2026-09-26 二轮审计提出**）

⚠️ 本方案初版漏了一条：装配层已存在**自动门控**（检测角色卡/世界书是否含气泡对话协议，
决定要不要注入气泡对话语法规则；且带 `BUBBLE_DEBUG` 环境变量逃生门）。
若不做优先级约定，会出现「用户在 UI 显式启用了某插件，装配层却又自动判定该卡不需要」的**决策打架**。

**统一优先级规则**（从高到低）：

| 优先级 | 来源 | 说明 |
| --- | --- | --- |
| 1（最高） | `BUBBLE_DEBUG` 环境变量 | 调试逃生门，保持现状不动 |
| 2 | **用户显式选择**（`plugin_scope_mode='allowlist'` 时的 `character_plugin_state` 行） | 用户勾选即权威，装配层自动门控**对该卡让位** |
| 3 | 装配层自动门控（气泡协议检测） | 仅在卡无显式选择（`inherit`）时生效 |

落地要求：

- 装配层判定入口需读取 `characters.plugin_scope_mode`；
- 命中 `allowlist` 时直接返回 `allow`（或跳过气泡条件判定），**不再跑自动检测**；
- 命中 `inherit`（含 NULL）时行为与今天完全一致；
- 前端「插件」Tab / 导入弹窗需提示用户：一旦手工确认过名单，该卡的自动门控即被接管。

**结论：热插拔不是"做不到"，是"触发不到 + 卸不完全"。**

#### 2.7.2 真正的两个卡点

**卡点 1：切卡根本不触发重载（1 行代码的事）**

```tsx
// CharacterChat.tsx —— 现状
useEffect(() => {
  const runtime = stRuntimeRef.current;
  runtime.loadRuntimeConfig().then(() => { /* ... */ runtime.injectIntoContainer(pluginHost); });
  return () => { runtime.unloadAll(); };
}, []);          // ← 空依赖：只在挂载时跑一次
```

且 `CharacterView.tsx` 渲染 `<CharacterChat ...>` **未设 key**（条件为 `viewState === 'chat' && selectedCharacter`）→
切卡时 React **复用**组件实例（仅 props 变化、不 unmount）→ 该 effect 永不重跑 → 插件永不重装。

→ 修法：依赖数组加入 `selectedCharacter?.id`，并在 effect 内把 `characterId` 传给 `loadRuntimeConfig()`。
由于 `injectIntoContainer` 自带幂等，"再调一次"即可完成一轮干净的重载，**无需刷新页面**。

**卡点 2：卸载完整性靠手写清单，不是通用机制**

`unloadAll()` 清外部 UI 用的是**硬编码的 3 个选择器**（`.gal-open-btn` / `#gal-global-overlay` / `#galgame-database-container`），
`cleanupGalgameState()` 用的是**硬编码的 9 个全局标志**。这是"给 Galgame 插件打的补丁"，换个新插件就会漏
—— `cleanupGalgameState` 的存在本身就证明残留真实发生过（该插件 overlay 切卡不关）。

残留面（脚本执行后的不可逆副作用，共 6 类）：

1. `window` 上新增的全局属性 / 函数（含 `window.SillyTavern.*` 扩展）
2. `document` / `window` 上注册的 `addEventListener`
3. `setInterval` / `setTimeout` / `requestAnimationFrame` 句柄
4. 挂到 `document.body` 等**容器之外**的 DOM 节点
5. jQuery 扩展：`$.fn.xxx`、`$._data(el, 'events')` 里的委托事件
6. 对全局函数的 patch（如 fetch guard —— 已有专门恢复函数）

#### 2.7.3 热插拔三档方案

| 档 | 内容 | 工作量 | 效果 |
| --- | --- | --- | --- |
| **L0 触发** | 依赖数组加 `selectedCharacter?.id` + 主链路传 `characterId` | **极小** | 切卡立即重装（全量，会短暂闪烁） |
| **L1 差集热插拔** | 维护 `currentPluginIds`，切卡时算 `toUnload = cur - next`、`toLoad = next - cur`，只装卸差异部分 | 中 | 公共插件状态不丢、无闪烁 |
| **L2 通用副作用回滚** | 注入前装"副作用记录器"，卸载时按记录回滚 | 中大 | 任意插件都能卸干净 |

**L1 单插件卸载**（锚点数据已具备，只缺方法）：

```ts
unloadPlugin(pluginId: string) {
  this.container
    ?.querySelectorAll(`[data-palink-st-plugin-id="${pluginId}"]`)
    .forEach((el) => el.remove());
  this.rollbackSideEffects(pluginId);
}
```

**L2 副作用记录器**：在 `injectIntoContainer` 注入脚本**之前**安装，注入完成后 `capture()`，
卸载时 `rollback()`。

| 副作用类型 | 记录手段 | 回滚手段 |
| --- | --- | --- |
| window 全局属性 | 注入前 `Object.keys(window)` 快照，注入后 diff | `delete window[key]` |
| 事件监听 | patch `EventTarget.prototype.addEventListener`，记录 `(target, type, listener, options)` | `removeEventListener` |
| 定时器 / rAF | patch `setTimeout` / `setInterval` / `requestAnimationFrame`，记录句柄 | 对应 `clear*` / `cancel*` |
| DOM 新增 | `MutationObserver` 观察 `document.body` / `document.head`，记录 addedNodes | `node.remove()`；或限定只清挂载点容器 |
| jQuery 扩展 | 注入前快照 `Object.keys($.fn)`；读 `$._data(el, 'events')` | `delete $.fn[key]`；`$(el).off()` |
| 自毁钩子（可选） | 约定 `window.__palinkPluginDestroy__[pluginId]` | **优先调用**，插件可自行收尾 |

**为何不采用 iframe 全隔离**：`tavern_helper` 脚本需要用 jQuery 在整个 `document` 上查询、并把面板渲染到主页面（如 `#bam-container`）。放进 iframe 后它拿到的 `document` 是 iframe 自己的，查不到主页面元素 → UI 整体失效；若把 `document` 代理回主页面，则 DOM 变更依旧落在主页面，删 iframe 也清不掉。**隔离收益与兼容成本不成正比**，故走"记录 + 回滚"而非"隔离 + 销毁"。

#### 2.7.4 残留自检（工程化保障）

L2 落地后仍可能有漏网。建议加**卸载后自检**：比对 `window` 属性快照、统计 `document.body` 子节点数、统计活动定时器数，将差异 `console.warn` 输出。

> ⚠️ production 构建配了 `pure_funcs: ['console.log']`，**必须用 `console.warn`**，否则留痕被剔除。

这样每接入一个新插件都能立刻看出"它往哪儿塞了东西"，把手写清单迭代补齐。

**教训 1：实际生效的导入端点在 `silly_tavern.py`，不是 `character.py`**

- `backend/app/api/character.py` → `import_character`（返回 `{status, character, auto_parsed}`，**老端点**）

**教训 2：勾选弹窗不能挂在 `CharacterList` 里**

导入成功后 `openImportedCharacter` 会立刻 `handleStartChat` 切到聊天视图，
`CharacterList` 随之卸载，挂在其内的弹窗**会跟着消失**（实测：弹窗一直不出现）。
现渲染在 **`CharacterView` 视图层**（与视图切换无关，且移动端/桌面端天然共用一份）。

**教训 3：`@router` 定义必须在 `router = APIRouter(...)` 之后**

接口代码若插在 import 区（`router` 尚未赋值），会在**模块导入期**直接
`NameError: name 'router' is not defined`，后端起不来。本次已修正位置。

### 9.6 装配层让位：实现记录（2026-09-26 补做，对应原 §9.5 第 5 条）

**改动文件**：`backend/app/services/roleplay_prompt_assembly.py`（仅此一个生产文件）

**新增两个私有函数**（`_has_bubble_render_support` 之后、`_collect_extension_prompts` 之前）：

| 函数 | 作用 | 失败时的退化 |
| --- | --- | --- |
| `_bubble_debug_forced()` | 读 `BUBBLE_DEBUG`，`1/true/on/yes` 为真 | 读不到 → `False`（等于没设） |

值为 `None`、`char` 是单测替身对象、甚至属性访问抛异常，都退化成 `inherit`，

**门控块改写**（`_collect_extension_prompts` 内 `if bubble_entries:`）为三分支：

```
1. _bubble_debug_forced()               → 保留，不跑检测（调试逃生门，最高优先级）
2. plugin_scope_mode == 'allowlist'     → 保留，不跑检测（装配层让位给用户选择）
3. 其余（inherit / NULL / 未知）        → 跑 _has_bubble_render_support，与原逻辑一致
```

分支 1/2 命中时**不再调用** `_has_bubble_render_support`，从根上避免"UI 勾了、
装配层又判不需要"的决策打架。

### 9.7 勘误：被撤回的"7 个用例本来就坏"（2026-09-27）

**原结论（错误，已作废）**：某轮把 `tests/test_st_vectors_full.py` 的 7 个用例判成
"既有失败，与本线改动无关"，并顺带得出"容器内存 2GiB，全量会被 OOM 杀，必须分批"。

**真相**：

1. **向量例子从未坏过**。所谓 7 个红，是**分批跑法制造出来的假象** ——
   那批用例依赖前面用例建立的 Fixture / 认证上下文，被切成段之后链断了才红。
2. 数字自证：分批合计 `1430 + 7 = 1437`，与标准全量的通过数**正好相等**
   → 全量跑时这 7 个是过的，不存在的"坏"。
3. 用户于 2026-09-27 在宿主机与容器各跑一遍标准全量：
   **2 分多钟跑完，内存正常**。此前那次 `exit 137` 是偶发事件，不是容量上限。
   2026-09-27 05:14 本轮复核（容器内单命令全量）：**`1437 passed / 42 skipped / 0 failed`**。

**方法论教训（比结论重要）**：

> 当时是用「同批次上下文 + 改动前原始代码」做对照，得出"与本次改动无关"——
> **对照组本身就是人为制造的错误环境**。它只能证明"两种代码在坏环境下表现一样"，
> **完全不能证明"本来就坏"**。
> 以后判定"既有失败"，必须**先确认基线跑法本身标准且健康**，否则不许下这个定论。

**唯一正确跑法**（写进 §5，此处再钉一遍）：

```
docker exec palink-ai-backend-1 sh -c "cd /app && python -m pytest tests/ -q"
```

一条命令跑全量。⛔ 不拆批次；⛔ 不把非 `test_` 开头的脚本塞进 pytest 命令行；
最终判定以容器口径为准（宿主会静默跳过 9 个 DB 用例）。
