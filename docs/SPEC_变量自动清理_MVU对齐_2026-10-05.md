- 日期：2026-10-05（01:2x 按实测数据**修订过一次**，见 §0.1）
- 状态：**待拍板，未开工**
- 上游：`docs/REPORT_MVU插件设置项与Palink对应关系_2026-10-05.md`（该项被列为 P1「该补」）
- 一句话结论：**照插件做「真清理」是对的 —— 原方案里的「压缩」实测只省 25%，已放弃。** 但要在插件方案上**多加一步"跳过重复"**（实测省 41%、零损失、零读路径改动），并保留最近 **50** 楼（我们回看窗口是 30）。

## 0. 三十秒速览

| 问题 | 答案 |
|---|---|
| 插件怎么做的？ | **抽稀 + 减重**：每 50 楼留一份完整快照，其余楼层把大字段摘掉（不是删掉整条） |
| 它为什么敢这么做？ | 它**保留了原始变量指令文本**，被清理的楼层可以**重演重建**（`Ya()` 函数） |
| 我们能照抄吗？ | **能**（见 §0.1 的修订）—— 但"删除大量消息后回看窗口落到被清楼层"这一种情形会降级，需登记可见 |
| 我们现在的量有多大？ | 变量总计 **33 KB**、最长会话 **35 楼**、单楼均值 **1159 B** —— **还很小** |
| 那该怎么办？ | ① **跳过重复快照**（免费省 41%）② **真清理**（省 99%）③ 仪表盘 + 删除场景的降级登记 |
| 建议默认值 | **默认关闭**（插件默认开，但我们不可逆，不能默认开） |

### 0.1 ⚠️ 本 SPEC 的修订记录（2026-10-05 01:2x）

**初版建议「压缩式清理」，被实测数据推翻，已改为「真清理」。**

用库里真实的变量数据（3 个最大样本，合计 6,942 B）实测：

| 方案 | 体积 | 节省 |
|---|---|---|
| 原始 JSON | 6,942 B | — |
| gzip | 3,919 B | 44% |
| **gzip + base64 编码（初版方案）** | **5,228 B** | **仅 25%** |
| **真清理（摘掉大字段）** | **90 B** | **99%** |

**结论：压缩 + 编码只省 25%，不值得。** 原因是 base64 会把体积**撑回 33%**，
而小体积 JSON（1.2–2.3 KB）本身压缩率就一般。**用户判断正确，初版方案已作废。**

复现命令见 §9 第 ⑥ 条。

## 1. 插件算法完整解码（从 bundle 源码读出，非推测）

数据源：`backend/data/smart_card_assets/0c646fb31a8cd5610d22ccd26323258a430f83a09e6a0a09596b2b1875eabac2.js`（307,179 B）。

### 1.1 参数与默认值（zod schema 原文）

```js
自动清理变量: z.object({
  启用:                   z.boolean().default(true),
  快照保留间隔:           z.number().default(50),
  要保留变量的最近楼层数: z.number().default(20),
  触发恢复变量的最近楼层数: z.number().default(10),
}).loose().prefault({})
```

**注意：默认是「开」。** 插件认为这是常规卫生功能，不是高级选项。

### 1.2 核心清理函数（原文）

```js
function Za(start, end, interval) {
  let cleaned = 0;
  SillyTavern.chat.slice(start, end + 1).forEach((msg, r) => {
    if (msg.variables === undefined) return;
    let marked = false;
    msg.variables = _.range(0, msg.swipes?.length ?? 1).map(i => {
      if (msg?.variables?.[i] === undefined) return {};
      // ① 已经是快照 → 原样保留
      if (_.get(msg.variables[i], 'snapshot') === true) return msg.variables[i];
      // ② 每到间隔楼层 → 打快照标记，保留完整
      if ((start + r) % interval === 0) {
        _.set(msg, ['variables', i, 'snapshot'], true);
        return msg.variables[i];
      }
      // ③ 其余楼层 → 摘掉大字段，只留轻量信息
      if (!marked) { marked = true; ++cleaned; }
      return _.omit(msg.variables[i],
        'initialized_lorebooks', 'stat_data', 'display_data', 'delta_data', 'schema');
    });
  });
  fn();          // 落盘
  return cleaned;
}
```

**逐行解读（这是全部精髓）**：

- 它**不是删掉整条变量**，而是**摘掉大字段**（`stat_data` / `schema` / `delta_data` / …）。
  楼层上仍然有 `variables` 对象 → **"这楼有没有变量"这个事实仍可判断**。
- **每 `interval` 楼留一份完整快照**（打 `snapshot: true` 标记）→ 保证"往前总能找到一个锚点"。
- **按 swipe 逐份处理**（`msg.variables[i]`）→ 多候选回复各自独立，不互相污染。

### 1.3 三个触发入口

| 入口 | 时机 | 清理范围 |
|---|---|---|
| **自动（增量）** | 每收到 **5 楼**（`chat.length % 5 === 0`） | `Za(max(1, n - 2 - 2*保留楼层), n)`，其中 `n = 当前楼层 - 保留楼层` |
| **首次启用** | 首次打开且有可清内容 | `Za(1, chat.length - 1 - 保留楼层, 快照间隔)` |
| **手动按钮**「清除旧楼层变量」 | 用户点击 | 弹窗问"清到倒数第几楼"（默认 10）→ `Za(1, chat.length - 1 - n, 快照间隔)` |

### 1.4 恢复函数（它敢清的根本原因）

```js
async function Ya() {
  const last = chat.length - 1;
  const { 触发恢复变量的最近楼层数: a } = settings.自动清理变量;
  const r = Math.max(1, last - a);
  const o = chat.findLastIndex(m => !_.has(m, ['variables', m.swipe_id ?? 0, 'stat_data'])
                                 || !_.has(m, ['variables', m.swipe_id ?? 0, 'schema']));
  if (r > o) return;                                     // 最近 N 楼没有被清过 → 不用恢复
  const i = Math.max(1, last - 要保留变量的最近楼层数);
  const l = gn(i);                                       // 从 i 往前找最近的快照楼层
  if (l === -1) return toastr.warning('无法恢复');
  let c = chat[l + 1].mes, u = e(chat[l].variables[...]);  // 从快照出发
  for (let t = l + 1; t <= o; t++) {
    c = chat[t].mes;
    await Tn(c, u);                                      // ★ 重演：解析该楼文本、重建变量
    if (t >= i && 该楼缺 stat_data) {
      await updateVariablesWith(...写回 u..., {type:'message', message_id: t});
      u = e(u);
    }
  }
}
```

**★ 关键在 `Tn(c, u)`**：它读的是 **`chat[t].mes`（楼层原始正文）**，
从中重新解析出变量更新指令 → 重算出该楼的变量 → 写回。

**所以插件能"删了再算回来"，前提是楼层正文里的变量指令还在。**

### 1.5 首次启用弹窗（三选一）

| 按钮 | 行为 |
|---|---|
| 只清理 | 直接 `Za(...)` |
| 不再提醒 | 在楼层上打 `ignore_cleanup: true`，以后不问 |
| **备份并清理** | **先调 `/api/chats/export` 导出该会话 jsonl 下载**，再清理 |

**"备份并清理"这个选项本身就是承认：清理是破坏性操作。**

### 1.6 值得学的五条设计思想

1. **抽稀而非删除** —— 摘字段，不摘整条。
2. **锚点 + 间隔** —— 每 N 楼一个完整快照，保证可回溯。
3. **可重建** —— 从锚点重演，按需恢复（我们的短板，见 §3）。
4. **增量而非大扫除** —— 每 5 楼小步清一次，避免一次性长阻塞。
5. **破坏性操作必须给备份出口** —— "备份并清理"是默认推荐项。

| 最长会话楼层数 | **35** |
| `extra` 总大小 | **289 kB** |
| 变量（`extra.variables`）总大小 | **33 kB** |
| 单楼变量均值 / 最大 | **1,159 B / 2,333 B** |
| 数据库总大小 | 44 MB（变量占比 < 0.1%） |

### 2.2 ★ 意外收获：41% 是重复的

实测（同一批数据）：

| 指标 | 值 |
|---|---|
| 带变量的楼层总数 | **29** |
| 其中内容**完全重复**的份数 | **12**（41%） |

也就是说：**接近一半的楼层，存的是和上一楼一模一样的变量。**

**这条价值很高，因为它是"免费的"**：

- **零损失** —— 内容完全一样，不存也不丢信息
- **零读路径改动** —— `_load_effective_stat_data`（`roleplay_prompt_assembly.py:5182`）
  **本来就是"往前找最近一个有快照的楼层"**；某楼没有快照是它已支持的正常情形
- **对前端「变量变化」面板也是安全的** —— 某楼变量与上一楼相同 ⇒ 本来就没有变化可显示；
  而下一楼做 diff 时会往前找到最近一个真快照，结果依然正确

**唯一要注意的**：`Mvu.getMvuData({type:'message', message_id: 该楼})` 会返回空 ——
但插件的清理方案有**完全相同**的副作用，属可接受。

分布（哪个会话在贡献体积）：

| 会话 | 楼层 / 带变量 / 变量体积 |
|---|---|
| `0043cacb…` | 35 楼 / 17 带变量 / **33 kB（几乎全部）** |
| `666dcbda…` | 13 楼 / 6 带变量 / 102 B |
| `525eed15…` | 6 楼 / 3 带变量 / 51 B |
| `d50689ae…` | 5 楼 / 2 带变量 / 34 B |
| `4f32b97a…` | 2 楼 / 1 带变量 / 17 B |

### 2.3 数据落在哪

| 位置 | 内容 | 是否累积 |
|---|---|---|
| `character_chat_messages.extra → variables` | **每楼一份完整 stat_data 快照** | ✅ **线性累积**（当前唯一累积点） |
| `character_chat_sessions.chat_metadata → variables` | 会话级"当前值"（单份） | ❌ 不累积 |

### 2.4 增长模型

```
变量体积 ≈ 楼层数 × 1.2 KB（实测均值）
  1,000 楼 ≈ 1.2 MB / 会话

```

### 2.5 谁在读这些老快照

| 消费方 | 回看窗口 | 位置 |
|---|---|---|
| 提示词注入（swipe / 分支回退对齐） | **最近 30 楼** | `roleplay_prompt_assembly.py:5182` `limit(30)` |
| 前端 `Mvu.getMvuData({type:'message'})` | 单楼（按需） | `SillyTavernCompatRuntime.ts:6469-6482` |
| 前端「变量变化」面板（本批新增） | 本楼 + 往前找最近一个有快照的楼 | `Message.tsx` `variableChangePair` |
| 消息接口下发 | **分页，默认 10 楼**（`limit: int = 10`） | `character_ext.py:2814` |

**关键**：**超过 30 楼的快照，后端已经没有任何消费方**（回看窗口就是 30）。
前端也是分页取，不会一次全下。

### 2.6 结论：现在不是火，是结构隐患

- **眼前无故障**：33 KB 总量、最长 35 楼 —— 没有任何性能或容量压力。
- **结构性隐患成立**：没有任何上限，纯线性增长，且**没有仪表盘**（没人知道什么时候会疼）。
- 所以**最该先做的不是清理，是度量**。

## 3. 与插件的四条差异（方案要按此调整，但**不构成"不能做"**）

### 3.1 ★ 我们不可重演 —— 影响范围比初判窄得多

插件的 `Ya()` 依赖 `chat[t].mes` 里的变量指令原文。而我们：

```
character_ext.py:4801 / 6002 / 6138、websocket.py:785
  → 先解析 <UpdateVariable> 落库变量，再 strip_update_variable_blocks() 剥掉正文
  → 落库的 content 已无变量指令
```

且 `msg_extra` 只存 `gen_id / reasoning / model / token_count / ext_prompts / variables`，
**没有保留剥离前的原文**（实测 `websocket.py:742-778`）。

**初版据此判定"不能照抄"，但重新推演后范围要收窄** ——
插件的 `Ya()` **只用于一种情形**：**删楼之后，被清过的楼层滑进了"需要变量"的窗口**。

```js
// Ya() 的触发条件（原文）
const r = Math.max(1, last - 触发恢复变量的最近楼层数);      // 默认 last-10
const o = chat.findLastIndex(m => 该楼缺 stat_data 或 schema); // 最近一个被清过的楼
if (r > o) return;   // 最近 10 楼里没有被清过的 → 什么都不做
```

**它在做的是"把滑进窗口的被清楼层补回来"，不是"按需还原任意老楼层"。**

对我们逐条推演：

| 情形 | 我们保留 50 楼时会怎样 | 严重度 |
|---|---|---|
| 正常聊天（不删楼） | 回看窗口 30 楼永远落在保留区内 → **完全无影响** | 无 |
| 前端读老楼 `Mvu.getMvuData({type:'message', 老楼})` | 返回空 —— **插件清理后行为完全相同** | 与插件一致 |
| 前端「变量变化」面板看老楼 | 不显示 —— 但老楼本来也没变化可显示 | 无 |
| **删掉 ≥20 楼**（使回看窗口滑进被清区） | 找不到快照 → **回落到会话级**（`_load_session_stat_data`），模型看到的状态比可见聊天"更靠前" | ⚠️ **真实降级**，但**不崩** |

**结论：可以照抄，代价是最后一行那个窄场景。** 处置见 §4 阶段 2 的「降级登记」。

> 补充：这个降级**今天就已存在** —— 任何没有消息级快照的会话（如该机制上线前的历史数据）
> 走的都是同一条回落路径。清理只是把这个窗口**略微扩大**，不是引入新故障类。

### 3.2 回看窗口 30 楼 → 保留楼层必须 ≥ 30

插件的默认「要保留变量的最近楼层数 = 20」。
我们的 `_load_effective_stat_data` 回看 **30** 楼找快照。
若保留 20 楼，则第 21–30 楼的快照被清掉 → swipe/重生成回退到"找不到快照"
→ **静默回落到会话级** → 分支状态不一致（这正是 `5154-5170` 注释里修过的老问题复发）。

**所以我们的该参数默认值应 ≥ 30，建议 50。**

### 3.3 我们在服务端 → 可以"写入时顺手清"，不需要前端定时器

插件跑在浏览器，只能靠 `MESSAGE_RECEIVED` 每 5 楼触发。
我们在生成落库的同一条路径上就能顺手做（`apply_mvu_reply_to_session` 的调用方），
**一次事务内完成**，无定时器、无并发竞争。

### 3.4 前端分页（默认 10 楼）→ 前端压力天然有界

插件把整个 `chat` 数组放内存里操作；我们前端是分页取。
所以**前端不是清理的动机**，动机只在 **DB 存储与热表行宽**。

## 4. 建议方案（Palink 版 · 三阶段）

> 总原则：**先量后清、先免后减、默认关闭、降级可见。**
> **不做压缩**（实测只省 25%，见 §0.1）。

### 阶段 1 · 跳过重复快照（免费，建议立刻做）

**落库时先比一下：若本楼变量与"上一个有快照的楼"完全一致，就不重复存。**

- **收益**：实测当前数据 **省 41%**（29 份里 12 份重复）
- **风险**：**零**。内容一样，不存不丢信息
- **读路径改动**：**零**。`_load_effective_stat_data` 本来就是"往前找最近一个有快照的楼"
- **前端面板**：安全。变量没变 ⇒ 本来就没变化可显示；下一楼做 diff 时会往前找到真快照
- 落点：`apply_mvu_reply_to_session` 的调用方（写入前比对，一致则跳过写 `msg_extra["variables"]`）

### 阶段 2 · 装仪表盘（零风险，与阶段 1 同批）

**不改任何数据**，只加度量：

1. 后端每次生成落库后，记录该会话的：
   - 楼层数、带变量楼层数、变量总体积、**被跳过的重复数**
2. 落点二选一（建议 b）：
   - a) 新增 `chat_variable_metrics` 表（session_id, floor_count, var_bytes, measured_at）
   - b) 只在 `chat_metadata` 里存一个轻量计数（零新表）
3. 前端「变量变化」面板旁展示一行小字：`变量 33 KB / 29 楼`（可选）

**为什么先做这个**：没有仪表盘，"该不该清、清多少"全是拍脑袋。
有了它，阈值可以按真实曲线定，而不是抄插件的 50/20/10。

### 阶段 3 · 真清理（照插件，摘掉大字段）

**对「超出保留窗口且非快照锚点」的楼层，摘掉大字段**（同插件 `Za()`）：

```jsonc
// 清理前
"variables": { "stat_data": {…1.9 KB…}, "initialized_lorebooks": {…} }

// 清理后（同一行，仍可判断"这楼有没有变量"）
"variables": { "pruned": true, "pruned_at": "2026-10-05T01:20:00Z", "orig_bytes": 1900 }
```

- **收益**：实测 **省 99%**（6,942 B → 90 B）
- **不动锚点**：每 **50** 楼留一份**完整**快照（同插件）
- **不动最近 50 楼**：N ≥ 30（我们回看窗口），建议 50
- **触发**：每次生成落库后顺手做（§3.3），范围限定
  `[max(1, 当前楼 - 保留楼层 - 200), 当前楼 - 保留楼层]`，**不做全表扫描**
- **默认关闭**

**§3.1 那个窄场景的处置（降级必须可见）**：

清理后若某次读取落到了被清楼层（`_load_effective_stat_data` 找不到快照而回落会话级），
**必须登记一条记录**（同 `recordStubHit` 的口径：可见、不静默），
而不是像现在这样只留一句 `logger.warning`。

> 备选增强（**不在本批，属可选**）：若要彻底消除该降级，可在清理时**额外保留该楼的变量补丁**
> （`extract_update_variable_blocks` 的产物），这样"从锚点 + 逐楼应用补丁"可精确重建。
> 补丁比全量状态小，但**需要改读路径**（读时重放），复杂度明显上升 ——
> 建议先不做，等仪表盘数据证明这个降级真的会发生再说。

### 阶段 4 · 通知（可选，与 §2.6 的「通知缺失」同源）

- 清理了多少楼、省了多少字节（复用阶段 2 的度量）
- 发生了降级回落时，明确告知

## 5. 参数建议（与插件的差异对照）

## 12. 测试加固（2026-10-05 01:4x · 用户"继续做测试"后）

### 12.1 ★ 测出一个存量真 bug（与本功能无关，但被本批测试照出来）

**`_load_effective_stat_data` 的消息级快照分支从未生效过。**

```python
# roleplay_prompt_assembly.py（改前）
for row in rows:
    extra = getattr(row, "extra", None)
    if not isinstance(extra, dict):     # ← extra 列是 Text（JSON 字符串），恒为 False
        continue
```

**探针实测**（临时用例，已删）：

```
[探针] row.extra 的 Python 类型 = str
[探针] isinstance(extra, dict) = False
[探针] _load_effective_stat_data 返回 = {'来源': '会话级'}   ← 消息级应为 {'来源':'消息级'}
```

**后果**：该函数文档里声称修好的 `[ST-ALIGN P0-2]`（swipe / 重生成 / 切分支时
变量跟着回退）**实际是空转** —— 一直静默回落会话级。模型看到的状态与用户眼前的分支状态不一致，
正是它自己文档里描述的那个问题。

**已修**：加 `isinstance(extra, str) → json.loads` 解析分支。**既有测试零覆盖**（全仓 grep 无命中），
生产调用点只有 1 处（`roleplay_prompt_assembly.py:5292`），故修复面可控。
**新增回归守卫**：`TestMessageLevelSnapshotActuallyRead`（2 例），并额外钉住
"extra 列确实是字符串"这一前提（若将来改成 JSON 类型列，该测试会红并提示同步改）。
