## 0. 一句话目标

**让"卡自带状态面板"这类卡在 Palink 上第一次真正能出数**——办法不是补一个特例，而是把我们**唯一真源**（后端 `mvu_engine`）算出来的 `stat_data`，按卡生态的惯例位置供给出去，并把现在**五条路径各写各的、三处归一化各丢各的**这套结构收敛掉。

一句话根因：**后端算出来了，但没送到卡手上；而且送不到是结构性的，不是这张卡的偶发。**

## 1. 背景与现状

### 1.1 现场事实（全部为库内实测，非推理）

用户反馈：导入卡「家裡的神明大人」，**一句话都没说**，消息流里就出现红字
`无法加载状态数据 (messages empty)`。

| 取证项 | 结果 | 口径 |
|---|---|---|
| 卡行 | `characters.id=2687f81d…`，user 49，2026-10-06 10:37 导入 | DB |
| 会话行 | `3d631311…`，**全库唯一一条消息** | DB |
| 该消息 | id=2740，role=assistant，正文 1175 字，**5 个滑动候选** | DB |
| 开场白 | 主开场白 1215 字 + **4 个备选开场白** = 5 | DB |
| ⇒ 结论 | **那条"回复"就是开场白本身**，用户"没对话"为真 | 推断，证据闭合 |
| 该消息 extra | 只有 `swipe_info` 一项；**无 `variables`、无 `mvu_patch`、无 `model`、无 `token_count`、无 `ext_prompts`、无 `reasoning`** | DB |
| 会话 `chat_metadata` | `{}`（2 字节）——**初始状态从未落地** | DB |
| 对照卡「露缇雅1.2」 | 同一天两个会话的 `chat_metadata` 分别为 787 / 725 字节，**含 variables + stat_data**；其 06:49 的消息 extra 有 10 项，含 `mvu_patch` + `variables` | DB |
| 全库 | 带 `stat_data` 的消息 49 条；**该卡所在会话 0 条** | DB |

### 1.2 卡的判据（老板 2026-10-06 授权阅读该段脚本，仅取判据，未读正文）

```js
const messages = await getChatMessages(getCurrentMessageId());
if (!messages || messages.length === 0 || !messages[0].data) { 显示 "(messages empty)"; return; }
const gameData = messages[0].data;
const characterData = gameData.display_data || gameData.stat_data;
if (!characterData) { 显示 "(characterData missing)"; return; }
```

三点要紧的：

1. 卡**只读不写**：全卡 extensions 文本里 `insertOrAssignVariables` / `replaceVariables` /
   `updateVariablesWith` / `setChatMessage` / `updateMessageBlock` / `localStorage` **命中数全为 0**。
   它把"谁去算状态"完全交给宿主。
2. 卡要的位置是 **消息对象上的 `data`**（ST 生态 MVU 的存放位：`chat[楼].data`）。
   Palink 把同一份数据存在 **`message.extra.variables.stat_data`**。
3. 报错文案是卡自己写的，**"messages empty" 实际含义是"消息上没有 data"**——
   这句话在本次排查中直接把第一轮引到了错误方向。

## 2. 为什么这么做

### 2.1 根因分三层，责任不同

**层一｜卡自身设计（不全是我们的锅）。**
该卡在 `first_mes`、`alternate_greetings`、导入快照、世界书 `raw_content` 四处**均无 `<initvar>`**，
也没有 schema 默认值。也就是说它**不带初始状态**，面板按设计要等第一轮 AI 回复产出 `<UpdateVariable>` 之后才有东西。
对照：露缇雅 1.2 的导入快照含 `<initvar>`，所以我们 `character_ext.py:4478` 的初始化路径能给它建出 787 字的状态。

**层二｜读侧供给缺失（决定性，且是结构性的）。**
前端把消息整理后交给卡的地方共 **5 处**，**没有一处输出 `data` 键**：

| # | 位置 | 输出 `data`？ |
|---|---|---|
| 1 | `smart-card-runtime/frame-shim/legacy-st-sim.ts:843-873` | 否 |
| 2 | `smart-card-runtime/SillyTavernCompatRuntime.ts:2765-2786` | 否 |
| 3 | `views/character/CharacterChat.tsx:146-176`（`buildSmartCardChatEntry`） | 否 |
| 4 | `CharacterChat.tsx:1547-1559`（`__palinkChatMessages`，插件沙箱轨） | 否 |
| 5 | `CharacterChat.tsx:1746-1754`（`stContext.chat`，主文档插件轨；`stContext` 起于 `:1718`） | 否 |

`extra` 在三处归一化里**是透传的**（compat 仅剥 `swipe_info`），后端 `character_ext.py:400` +
`_extra_without_swipe_info:273-276` 也保留 `extra.variables` —— 所以**数据到得了卡附近，只差最后那个键名**。

⇒ **后果：即使用户聊下去、模型每轮都交表、后端每轮都解析成功，这类卡的面板也永远出不来。**
层一只解释"此刻为什么空"，层二解释"为什么永远修不好"。

**层三｜两个次要缺口。**

- **写入口不对称**：5 条会新增 AI 回复的路径里，4 条跑 MVU 解析
  （`websocket.py:760`、`character_ext.py:4861/6083/6231/6586`），
  1 条**完全不跑**——卡/插件经 `CharacterChat.tsx:1127` 追加消息 → `character_ext.py:3065 POST /messages`，
  该路径只经 `_st_message_kwargs:470` / `_compose_message_extra_with_swipe_info:313` 写 `swipe_info`，
  **永不产出 `variables` / `mvu_patch`**。（本次 2740/2741 的 extra 形状与此完全吻合。）
- **解析容错偏窄**：`mvu_engine.py:83` 的裸数组识别白名单
  `_JSONPATCH_OPS = {replace, delta, insert, remove, move}` **不含 `add`**；
  而该卡世界书里的规范**只教了 `add`**（`replace/delta/insert/remove/initvar` 命中均为 f，`add` 为 t）。
  注：包在 `<UpdateVariable>` 里的 `add` **能正常应用**（`apply_patches:495`），
  所以这条只在"模型不包壳、直接吐裸数组"时致命——是概率性丢数据，不是必然。

### 2.2 一条已被否证的结论（写下来防止重走）

2026-10-06 第一轮曾给出结论：「帧内 `legacy-st-sim` 先注入并占用 `window.getChatMessages`，
带 id 回退的 compatV2 那份是死代码」，并据此改 + 上线。

**该结论错。** 对照组实测：用生产拼接（`buildShim` + `buildSillyTavernCompatRuntimeV2Shim`）在真 jsdom realm
里跑，**撤掉补丁与不撤结果完全一致**（都返回 1 条）。真实生效的那份本来就带 id 回退。

错的机理值得记：**把函数从源码里切出来喂 mock，仍是"实测"的假象**——mock 的接线（谁先注入、谁覆盖谁、
载荷里 `messageId` 与条目 `id` 恰好相等）全是我脑补的，它只回答"我的假设自洽吗"。
**判据：任何"我修了 X 所以 Y 会好"的结论，必须先跑"把 X 撤掉"的对照组；两次一样就说明找的不是原因。**

## 4. 方案设计

### 4.1 问题 → 根因 → 修复 映射

| 现象 | 根因 | 修复 |
|---|---|---|
| 刚导入就红字 | 卡无初始状态 + 我们不给空壳 | F-E1（待拍板）或 F-D1（至少说清） |
| 红字写"messages empty" | 卡判据把"没有 data"写成"没有消息" | 改不了卡 ⇒ F-D1 在我们这层翻译 |
| 聊了也没面板 | 5 处归一化都不输出 `data` | **F-A1** |
| 偶发某轮数值不动 | 裸数组 + `add` 被白名单判掉 | **F-B1** |
| 卡追加/开场白楼层永无数据 | 该写库路径不跑解析 | **F-A2** |
| 事后无法定性"模型有没有交表" | 0 块不告警、日志丢弃、原文剥离不留底 | **F-C1** |

### 4.2 F-A1｜读侧供给 `data`（P0，本件主线）

**做法**：在 5 处消息对象出口统一补一个派生键，语义与 ST 的 `chat[i].data` 对齐：

```
data = (extra.variables 是非空对象) ? extra.variables : undefined
```

要点与边界：

1. **只在 `extra.variables` 存在时挂**，不要挂 `{}`。
   理由：卡有两条不同的原因码，挂空壳会让"(messages empty)"变成"(characterData missing)"，
   看似进步实则把"我们没供给"伪装成"模型没产出"。空壳策略统一交给 F-E1 决定。
2. **不要新写第三份 stat_data 归一化**。复用 `SillyTavernCompatRuntime.ts:6116` 起的 `window.Mvu.*`
   那套（注释已写明"作为唯一真源、无条件覆盖"），或把它提到共享模块。
   **另写一份即违反 10-04 专题"0 个单一真源"的整改方向。**
   旁证：主文档插件轨在 `CharacterChat.tsx:1735` 已经挂了 `stContext.stat_data`
   —— **数据就在手边，只差没挂到每条消息上**。
3. 第 4/5 处（插件沙箱轨、主文档插件轨）的条目形状本身就不全（第 5 处缺 `mesid`/`is_system`），
   本件**只加 `data`，不顺手补形状**——补形状影响面是插件，另立议题。
4. 与 10-04 P0-1（读优先级倒挂）的关系：那条修的是"真源被镜像行遮蔽"，
   本条修的是"真源到了但键名不对"。**两条都要修，顺序 P0-1 → F-A1**，否则 F-A1 可能把旧值供出去。

**验收判据（必须做正反对照，不接受"读代码认为对"）**：

- 反例基线：取库里真实带数据的消息 2739（`extra.variables.stat_data` 存在），
  按生产链路喂进 5 处出口，断言改前 `data === undefined`、改后 `data.stat_data` 存在。
- 正例不误伤：取 2740（`extra` 无 `variables`），断言改后 `data` **仍为 undefined**（不许挂空壳）。
- 三 realm 对照测试：沿用 2026-10-06 已加的
  `smart-card-runtime/__tests__/frame-getchatmessages-id-lookup.test.ts` 的写法
  （把各份实现用真实函数体跑同一载荷比对），扩到 `data` 键。**这类"同一 API 多份实现"的分叉，只有对照测试能拦。**

### 4.3 F-D1｜卡内报错说人话（P0，用户可感知）

现状：卡把红字写进它自己的容器，我们原样渲染，用户读到"消息丢了"这种误导信息。

**做法**：卡面板文本命中已知卡侧原因码时，在我们这层替换为准确表述。
最小实现：识别 `(messages empty)` / `(characterData missing)` 两类文本，
映射为「这张卡的状态要聊过一轮、模型交出状态更新之后才会出现」。

**判据**：导入该卡、不开口 → 看到的是那句人话，不是英文原因码。
**注意**：这是**兜底翻译**，不是修复；F-A1/F-E1 才是。别用翻译掩盖真缺陷。

### 4.4 F-A2｜写入口收敛（P1）

把"解析→剥离→落库"抽成单一函数，`POST /messages`（`character_ext.py:3065`）、
`PATCH .../swipe`（`:6699`）、导入（`:5457`/`:5512`）三条现在不解析的路径全部改走它。

**判据**：经卡追加/导入产生的 assistant 楼层，若其正文含 `<UpdateVariable>`，落库后 `extra.variables` 必须出现；
不含则不出现（不许造出来）。

### 4.5 F-B1｜解析容错（P2）

- `mvu_engine.py:83` 白名单补 `add`。
- `_safe_json_loads_list:191-192` 对"全量 JSON 对象"直接判 None 的分支，**先只加日志、不改行为**：
  全量对象是否要支持，取决于有多少卡这么写，本件不擅自扩协议。

### 4.6 F-C1｜可观测三件套（P1，防下一次靠猜）

1. `mvu_engine.py:1280-1281` 现在"提取到 0 个块"是**静默返回** ⇒ 加一条 `no_update_variable_block` 标记进 `extra`。
2. `mvu_logs` 在 5 个调用点都被接走但**从不落库** ⇒ 落进 `extra.mvu_logs`（截断上限，防膨胀）。
3. 正文落库前被 `strip_update_variable_blocks` 剥离且**无原始副本** ⇒ 在 `extra` 留一份未剥离原文
   （或独立的 `raw_blocks` 键，只留状态块，别整份复制正文）。

**判据**：任取一条新消息，一条 SQL 就能回答"模型这轮有没有交状态块"。
这条是本件的**防复发主线**——这次排查绕的弯路，根子上是因为这三个数拿不到。

## 5. 后果与风险

| 风险 | 缓解 |
|---|---|
| F-A1 让某些卡**第一次真的显示出面板**，暴露出数值不对/格式错位等下游问题 | 这是收益不是风险；但要预告给老板：会有"以前不报现在报"的新反馈 |
| 挂 `data` 与 10-04 P0-1 的读优先级倒挂叠加 → 可能把**旧值**供出去 | 强制顺序：先修 P0-1，再上 F-A1；否则本件不合并 |
| `add` 进白名单后，正文里"长得像 patch 的普通 JSON"被误解析 | 该白名单只约束**裸数组**，且仍要求 `path` 以 `/` 开头、首段非空、不以 `_` 开头、不含 `<`/`>`；补一条误判回归用例 |
| 重建 dist 带入他人未提交改动 | §3.3 闸门；备份在用 dist + 台账登记（2026-10-06 已确立该流程） |
| F-C1 往 `extra` 塞原文导致行膨胀 | 只存状态块、设字节上限、不进向量记忆（防自我污染，沿用副任务轨迹的裁定口径） |

## 6. 详细执行步骤
