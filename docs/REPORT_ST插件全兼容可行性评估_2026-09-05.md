# REPORT ST 插件「全兼容」可行性评估与实现路线（2026-09-05）

> 问题：我们的 ST 兼容能力能做到**全部插件**都兼容吗？如何实现？
> 证据底账：`st-plugins/ADAPTATION.md`（11 个真实插件的逐个适配审计，§3 已于 2026-09-05 按实弹探测修正）、`st_plugin_frontend_bridge_protocol.md`、代码实况（事件表/斜杠命令注册表/三轨 runtime）。术语提示：st-compat/st-native **装配双轨已于 2026-09-03 删除**；今天讨论的「ST 兼容能力」指 **palink-native 插件体系**（沙箱轨/经典轨/智能卡轨 + 兼容端点面），无需也不应恢复旧模式。

---

## 一、结论先行（三句话）

1. **「100% 全部插件」是伪命题**——ST 自己的扩展生态就是松散契约，ST 大版本升级都会弄坏旧扩展；有三类插件在架构上不可能兼容（见 §四），任何声称全兼容的实现都是虚假承诺。
2. **「绝大多数常用插件开箱可用 + 剩余缺口有界」是可达的，且已完成约八成**——11 个审计插件里，面板/渲染/脚本/正则/事件/拦截器层已全部就绪，剩余缺口是一张**有限清单**（约 7 个薄代理端点 + 2-3 个 getContext 垫片），每个都是"同构成量级"的活，没有原理性障碍。
3. **正确的实现策略是「按需适配、以实装插件为准」，不是投机性全量 API 复刻**——这是 ST 官方生态自己的运行方式（官方 discover 也只保证索引可达），也符合本项目"厌恶过度设计"的一贯拍板口径。

## 四、做不到的三类（明确出界，不做承诺）

1. **ST 服务器插件**（server plugins）——跑在 ST Node 服务端的进程内扩展。Palink 没有 ST 服务器本体（st-native 按你拍板已删），这类东西在 Palink 语境里等同于"给 Palink 后端写原生功能"，不是兼容问题。
2. **外部服务重依赖类在未配置服务时**——SD/BLIP/翻译 API 这类，插件只是客户端；Palink 补上转发代理后插件能"跑"，但功能产出取决于用户是否自备服务。这是使用条件，不是兼容缺陷。
3. **深度绑定 ST 内部实现的**——直接读写 ST 聊天 JSONL 文件结构、依赖 ST 未文档化内部 API 的插件。Palink 用 DB 模型 + 兼容端点替代了主流路径（chats/characters/worldinfo 全套），但逐字节文件级兼容既无意义也无保证。
4. （软性）**DOM 深度耦合**——假设 ST 特定页面结构的插件在 Palink 自建容器里可能出现样式偏差；面板能出，视觉不保真。

## 五、实现路线图（按需适配，工作量实标）

**P1 · 垫片批（总计约 2-3 天，全部小改，建议下一批立项）**
1. `getContext` 加 `power_user` 别名（指向 powerUserSettings）——半小时。
2. `/api/sprites/get|delete`：映射到 Palink 资源服务（smart-card-assets 已有同构存储）——半天。
3. 向量嵌入端点：把 `/api/backends/kobold/embed` 语义映射到 Palink 既有 Ollama 嵌入——半天。
4. `/api/translate/{provider}` 路由：内部转派单一 translate 端点/外部服务——半天。
5. `/api/extra/caption|classify`：薄代理骨架（用户在设置里配外部服务 URL 即生效）——各半天。
6. tts 音源确认：浏览器实测一次，Web Speech 则零改动——1 小时。

**P2 · 视需求立项**
7. `/api/sd/*` 薄代理（仅当真要跑 SD 插件；转派用户自建 SD，只做 WebUI+ComfyUI 两 provider）——1 天。
8. extension-market 去留拍板：**建议默认删**（死代码、无 UI 入口、后端零端点）；若真想要"市场"，可行路径是代理 ST 社区的扩展索引 JSON（ST 官方 discover 同款数据源）+ 补 UI，量级 2-3 天——但要先想清楚需求强度。

**P3 · 流程化（防再欠账）**
9. 建立插件引入 checklist：每装一个新插件，浏览器跑一遍「面板出现/设置可存/动作可执行/无 console 401 404」四项，发现的缺口按 §五 分类处理——把兼容从一次性工程变成可重复流程。

## 六、回答你的原话

> "我们 st 兼容模式能做到全部插件都兼容吗"

**做不到"全部"，但能做到"你实际会用的插件都兼容"**——这两者的差距就是 §四 那三类（架构上不可能）和 §三 里 🟡 的几个小垫片（一周内可清完）。目前的状态是：装一个典型前端类 ST 插件，大概率已经能跑；装到调外部服务的插件（SD/caption/翻译），需要等 P1 补代理并且你配好外部服务；装 server plugin 则直接出界。建议下一步：拍板是否立项 P1 垫片批 + extension-market 删除，P1 清完这个生态的常用插件面就基本齐了。
