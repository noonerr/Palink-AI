## 0.5 位置判定（最高优先级，覆盖本件与 `PROMPT_报错提示系统重写` 的任何相反表述）

> 2026-10-03 之前的两份文件在这里**互相矛盾**：09-30 权威件推荐「顶部常驻」，本件 K1 却写「内联在消息流里，不许改成浮层」。已裁定：

### **报错卡放顶部常驻，不放消息流内联。**

`position: fixed; top: calc(env(safe-area-inset-top) + 12px); left/right: 12px; z-index: 100`
—— 即 `报错提示系统UI设计原型_2026-10-03.html` 已采用的那套（它是对的）。

**决定性的理由是数据通道，不是视觉：**

1. **内联就必须写进 `messages` 数组，而那是全项目最脆的一条链**：装配层对 assistant 正文**没有 role 白名单**（`character_message_builder.py:238` 直接 `append({"role": m.role, ...})`）、TTS 从该数组取词（`Message.tsx:1120-1129`）、它还被暴露给插件（`window.__palinkChatMessages`、`stContext.chat`），插件调 `setChatMessages` 会经 `POST /api/chats/save` **整表回写落库**（`silly_tavern.py:2957-2993`）。现状那条 ⚠️ 之所以没出事，只是因为**用了本地临时 id 恰好没落库** —— 那是运气，不是防线。
   → 让提示系统依赖一个 `extra.ignore` 标记才不污染上下文，等于把最简单的一件事接到最复杂的链上。
2. **顶部 fixed 挂在 body 层，不参与 `MobilePager` 槽位的层叠上下文** → 天然躲开 dock / 键盘 / 输入框三个对手。它唯一的敌人是灵动岛，而一行 `calc(env(...)+12px)` 已经解决。
3. 内联的隐性成本此前被低估：会随滚动离开视野、多次失败会累积成多张卡、需要在历史里做去重与过期。

### 但保住内联唯一真的好性质：**可追溯是哪一条失败了**

用一个**不进 `messages` 数组**的占位行实现：由组件本地状态（如 `failedTurnId`）在消息流里渲染一行，内容只有「生成失败 · 重试」，**不含错误详情文案**。

### 由此得出一条硬规则，以后不许再破

> **报错内容永远不写进 `messages` 数组。** 显示层允许有两处 —— 顶部「可操作、带完整文案」+ 流内「不可操作、只标位置」—— 但**两处文案不得重复**，所以它不构成"一次失败叠三层"。

### 双轨的生命周期与去重（**不加这节，双轨会退化成现状的"一次失败叠三层"**）

双轨的唯一风险是两处各画一份完整文案、各活各的。所以职责与生命周期必须写死：

| | 顶部常驻卡 | 流内占位行 |
|---|---|---|
| **只回答** | 「为什么失败 + 怎么办」 | 「**哪一条**失败了」 |
| 文案 | 标题 + 描述 + 建议 + 重试 + 关闭 | **仅**「生成失败 · 重试」一句，**禁止**含描述/建议 |
| 数据 | 组件/提示层状态 | 组件本地状态（如 `failedTurnId`），**不进 `messages`** |
| 消失条件 | 用户点关闭、点重试、或**新失败把它替换掉** | 该条重新生成成功、该条被删除、或用户离开该会话 |
| 同时数量 | **全局最多 1 张**（后来者替换前者，不堆叠） | 每条未解决的失败各 1 个；同一会话内连续失败**合并**，不累积 |

**三条禁令：**
1. 两处**不许**出现同一句话。判据：把顶部卡整块遮掉，流内那行仍应只让人知道"这条没成"，而不知道该错是什么 —— 反之亦然。
2. 顶部卡**不许堆叠**成列表。新错误替换旧错误；若旧错误还没被处理就发生了新错误，说明用户已经不看它了。
3. 流内占位**不许**变成第二条可操作入口。重试按钮在流内可以留（因为它贴着那条消息，位置有意义），但**不许**再带"建议切换模型"之类的处置文案。

**验收要加一条**：连续制造两次失败，检查顶部是否仍只有 1 张卡、流内是否只有 2 个一行高的占位；关掉顶部后流内占位是否仍在（它必须仍在 —— 那就是它存在的全部理由）。

## 2. 原型里必须改掉的部分（"AI 味"的量化来源）

### 2.1 色温错了 —— 这是最大的一条

| 用途 | 原型（错） | 实测色相 | Palink 真值（改成这个） |
|---|---|---|---|
| 页面底 | `#f6f4f1` | **36°** 偏橙 | `#F8FAFC`（移动端画布，`App.tsx:429`）= **210°** 偏蓝；桌面 `--background` = 纯白 |
| 聊天区底 | `#fffafa` | 偏粉白 | `bg-slate-50` / 暗色 `bg-slate-950`（`CharacterChat.tsx:1859`） |
| 描边 | `#ddd4c5` | **38°** 卡其 | `--border` = hsl(240 5.9% 90%) ≈ `#e4e4e7`，冷灰 |
| 阴影 | `rgba(120,106,79,.12)` | **棕色阴影** | `rgb(0 0 0 / .05~.1)`，中性无彩色（`index.css:100-104`） |
| 主色 | `#557bd7`（饱和 0.60） | 灰蓝 | `--primary` = hsl(217 91% 60%) ≈ **`#2f7de1`**（饱和 0.79） |
| 暗色画布 | `#171a2b` / `#1b2032` | 偏紫蓝 | 移动端 `#020617`（`App.tsx:429`）、`--background` hsl(240 10% 3.9%) |

**规则**：所有中性色（底、边、阴影、分割线）色相必须落在 **200°–250°** 区间或完全无饱和。**禁止出现任何带橙/黄/棕色相的中性色与阴影。**

### 2.2 语义色当文字用时四个全不达标

原型亮色模式实测：danger `#bd6a64` = **3.75**、warn `#a48163` = **3.44**、ok `#6b927d` = **3.37**、blue `#557bd7` = **3.90** —— AA 正文要求 **4.5**，**全部不过**。它没解决 Palink 的可读性问题，而是把问题从一种颜色摊到了四种。

**规则**：
- 语义色**只用于底色、描边、图标**；正文文字一律用 `--foreground` / `--muted-foreground`。
- 确实需要彩色文字时，亮暗两侧各自实测 ≥ 4.5:1，并把算出的比值写进交付说明。
- 暗色直接采用 K5 那三个值；亮色需另选（Palink 现 `--destructive` `#ef4444` 在白底只有 3.76，也不够）。

### 2.3 字体丢了

原型用 `-apple-system, PingFang SC`。**Palink 的身份字体是 `Manrope`（正文）+ `Sora`（标题）**，定义在 `index.css:45-46`，经 `--font-sans`（`:179`）/ `--font-display`（`:208`）生效。

**规则**：原型与落地代码都必须走这两个变量，**禁止**写 `Inter`、`system-ui`、`-apple-system` 作为首选。

### 2.4 字号整体偏小

Palink 聊天正文是 `text-[15px] leading-relaxed`（`Message.tsx:1458`）。原型：正文 13px、报错卡标题 12px、描述 **10px**。10px 中文在手机上读不动。

**规则**：正文 15px / 辅助文字 ≥ 12px / 禁止 10–11px 的中文正文。图标圆里的字符同理。

### 2.5 毛玻璃用过头

原型有 **6 处** `backdrop-filter`（16/18/18/20/22/8px）。而 Palink 那个 `.glass` 类**其实是实底卡片 + 半透明边框，根本没有 blur**（`index.css:311-314`）—— 名字骗人。真 blur 只给了少数组件：dock 药丸与模型选择器 30px（`Sidebar.tsx:522`、`ModelSelector.tsx:233`）、两个下拉 20px。

**规则**：报错卡与 toast **不用** `backdrop-filter`，用实底 `--card` + `--border`。blur 只允许出现在既有那几处。

### 2.6 圆角要按 Palink 的节奏，不要一律放大

Palink 基线 `--radius: .75rem`（12px，`index.css:86`），实际分布是 **`rounded-full` 158 次（第一名）> lg 136 > md 93 > xl 84 > 2xl 64**，另有手写 `rounded-[35px]`（dock、模型选择器）、`[28px]`、`[26px]`。
规律是：**紧凑交互件用全圆胶囊，卡片用 12–16px**。原型的 28px 输入框 / 27px dock 方向对，但报错卡 13px、对话框 18px 属"随手值"。

**规则**：卡片类取 `rounded-lg`(12) 或 `rounded-xl`(16)，按钮与标签用 `rounded-full`，不要出现 13/17/18 这类非 token 值。

### 2.7 图标

原型用 `!` `✓` `×` 这类字符。Palink 全站是 **lucide-react**。

**规则**：一律 lucide 线性图标，`stroke-width` 与既有组件保持一致。

## 4. 阶段二：落进代码

映射到 `PROMPT_报错提示系统重写` 的条目，按它的批次与红线执行：

- **顶部常驻错误卡**（见 §0.5 判定）= 该文件的 **1.3 + 1.5**：`fixed` 挂 body 层、`top: calc(env(safe-area-inset-top)+12px)`、`duration: Infinity`、带 `closeButton` 与 `action`（重试）。**报错内容不写进 `messages` 数组** —— 这样 1.5 从"写进去再标 `extra.ignore`"降级成更简单的"根本不写"，也就不依赖那个 flag。
- **流内占位行**（可追溯性）= 由本地状态渲染，不进数据数组；只有「生成失败 · 重试」，与顶部卡文案不重复。
- **细条 toast**（K2）= **1.1 + 1.2 + 2.1**：必须避开灵动岛（`env(safe-area-inset-top)`）、开 `closeButton`，并收进 `lib/notify.ts` 唯一入口。
- **加载中** = **1.4**：超时提醒并进错误卡，别再留一个无关闭按钮的浮层。
- **删除确认 / 页面异常** = **2.1 的模态类** 与 **3.1**（两套 ErrorBoundary 合一）。
- 内联卡落在消息流里，因此**天然不受 dock 与键盘遮挡** —— 这正是选它的理由。**但 `ErrorToast` 若仍保留为浮层，就必须按 1.3 做 Portal + 键盘变量两件事，只做一件无效。**
- ⚠ 复述一条已被实测纠正、很容易被再犯的错：**"按钮被 dock 压住"是错的**（实测只咬 7.7px、按钮行差 4.3px 未被盖）。真凶是键盘。别照 dock 去调 z-index。
