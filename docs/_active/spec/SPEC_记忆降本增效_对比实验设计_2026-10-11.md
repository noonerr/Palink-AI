## 〇、一句话结论

> **你测到的 "B 省 46%、掉 42.9pp" 里，约一半的"省"不是砍历史省出来的，
> 而是记忆路半失效的副产品。在修好召回之前，这个 A/B 不能用来判定"砍到 4~6 条不划算"。**

> **① 先零 token 修召回**（查询侧短扩展 + 多路 RRF + 候选池去饥饿），把命中拉回 85% 量级；

## 一、先订正：B 臂的"省 46%"里有一半是坏掉的记忆路

### 1.1 用你自己的数字反推记忆侧注入量

已知实测（P67/P70，0.66 tok/字口径，与上游 API `usage` 对拍过）：

| 项 | 实测 tok | 出处 |
|---|---|---|
| 历史 24 条 | **13,310** | `REPORT_记忆分项基线实测_2026-10-11.md` §1.1 |
| 记忆（4000 档 + 邻居 30%） | **6,427** | 同上（9,739 字 = 4,869 内部单位） |
| 边际（每增 1 条历史） | 530~600，各位置高度均匀 | 同上 §五（P70） |

由你的 A 臂反推该会话的「其他」（系统/世界书/实体卡/剧情线）：

```
A = 13,310（历史24） + 其他 = 15,153  ⇒  其他 = 1,843
```

由你的 B 臂反推记忆实际注入量：

```
B = 历史6条 + 记忆 + 1,843 = 8,159
历史6条 ≈ 13,310 × 6/24 = 3,328
⇒ 记忆 = 8,159 − 3,328 − 1,843 = 2,988 tok
```

**2,988 / 6,427 = 46.5%** —— 记忆只注了应有量的**不到一半**。
这与你自己观察到的"渲染仅 ~1000 tok、预算 4000 远没用满"方向完全一致。

### 1.2 结论：A/B 被一个混杂变量污染了

```
B 相对 A 省 6,994 tok
其中 6,427 − 2,988 = 3,439 tok（49%）来自"记忆没注满"
只有 ~3,554 tok 才是"砍历史"的真实收益
```

⇒ **修好召回后，B 应该涨到 ≈ 11,598 tok（省 23.5%，不是 46%），而命中率会显著高于 57.1%。**

⚠️ 这不代表"砍到 4~6 条就划算"（那是另一回事，且 p61 实测 6 条档要掉 0.125），
只代表：**57.1% 这个数字测的是"坏掉的记忆路 + 短历史"，不能拿来论证任何关于历史的结论。**

### 1.3 你观察到的"预算没用满"是**症状**，不是**病因**

三条候选机制，当前代码都可能存在，**必须先用 P80 探针区分**（见 §四）：

| 机制 | 代码位置 | 现象 |
|---|---|---|
| **① 阈值杀**：`MIN_SIMILARITY=0.5` 是 SQL 级硬过滤 | `storage.py:1036` `AND 1-(embedding<=>qv) >= :min_sim` | 目标块相似度 0.45 ⇒ **连候选池都进不去**，与预算无关 |
| **② top-K 杀**：`limit=50` 硬截断 | `storage.py:1038` / `config.py:228 BLOCK_CANDIDATE_LIMIT` | 227 条记忆取 top-50 = 22%，目标排 60 名 ⇒ 被切 |
| **③ 单簇塌缩**：bge-m3 对短查询返回同一条消息的多个块 | 你实测"只返回 2 个唯一 message_id、最大簇占比 80%" | 候选池被同源块占满，多样性为零 |

⇒ **这三种的修法完全不同**（降阈值 / 扩池 / 加查询多样性），
在没区分之前调任何参数都是猜。**这就是 P80 探针存在的唯一理由。**

## 三、五个方向逐项论证（方案 → 预期收益 → 验证方法 → 风险）

### 方向 1：中间路线（历史压到 12~16 条 + 向量记忆兜底）

**方案**：`CHARACTER_CHAT_HISTORY_LIMIT` 24 → 16 或 12，其余不动。

| 项 | 内容 |
|---|---|
| **预期收益** | 省 tok 是确定的：24→16 省 8×554 = **4,432**（占现状 21,580 的 **20.5%**）；24→12 省 6,656（**30.8%**）。<br>命中率：**不确定，且大概率达不到 ≤3pp** —— 现有只有 6/24/91 三个点（0.500 / 0.625 / 0.625，p61 n=20），线性插值 16 条≈0.59（−3.5pp）、12 条≈0.56（−6.5pp） |
| **验证方法** | **现有题集无效，必须先建近期题集**：`qa2.json` 的 57 题证据距末轮 min 34 / 中位 62 / max 91 条，**0/57 落在最近 24 条内**（`REPORT_记忆分项基线实测` §四）。用它测历史压缩**必然测不出差异**，而"测不出差异"会被误读成"压缩安全"。<br>⇒ 新建 ≥30 题证据在最近 8 条内的题集，再跑 C1/C2 臂 |
| **风险** | ① 插值不是实测，**8/12/16/20 四个中间点从未测过**（前序报告已列为阶段 3 硬前置）；② 砍条数丢的是**近期语境**，p61 实测 6→24 有 **+0.125** 分；③ n=90 时 95%CI 宽 ±10pp，−3pp 完全落在噪声里 ⇒ 测不出来 ≠ 安全 |

**判定：不推荐作为首选。** 同样的省幅可以用**分层压缩**拿到，且不丢信息 —— 见方向 5。

### 方向 3：混合检索权重（RRF 是否让语义侧过度主导）

**先说结论：你描述的失败题（"小玩具" vs "盒子里掉出粉红…"）不是权重问题，是词汇鸿沟问题 —— 关键词路同样救不了。**

理由：关键词路用的是**字符 bigram 覆盖率**（`storage.py:1305`），专名与数字有效，但"小玩具"与"粉红…盒子"字面重合为 0 ⇒ w_kw 调到 1.0 也没用。

**该做的不是调权重，是先诊断。** 现有权重 w_kw=0.7 是 2026-10-09 p47 用**双题集**（原题 + 同义改写）扫出来的，原题集上 0.2 之后就进入平台期（41.7%），改写题上 0.7 最优（33.3%）。

| 项 | 内容 |
|---|---|
| **方案** | ① P80 探针先量：失败题在关键词路的**覆盖率**是多少（若普遍 <0.12，说明卡在 `HYBRID_KW_MIN_COVERAGE`）；② 若确认是覆盖率问题 ⇒ 把 2a 抽出的**话题词并入关键词查询的 bigram 集**（零成本）；③ 权重扫描**只在修完 2a/2b 后**重做一次 |
| **预期收益** | 覆盖长尾专名/数字/改口类查询；对词汇鸿沟类无效 |
| **验证方法** | 双题集（原题 + 改写题）扫描 w_kw ∈ {0.5, 0.7, 1.0}，取"两套题里较差的那一侧"最大化（前序口径） |
| **风险** | ⚠️ **单看原题集会得出"纯关键词最好"的错误结论**（原题集从原文句子生成，天然字面重合度高：纯关键词 58%，改写后掉到 31%）。**必须双题集** |

### 方向 4：预算分配（检索 4000 / 渲染 5200）

**结论：预算分配本身合理，不要动；但渲染的"消费顺序"有一个真实缺陷。**

| 项 | 内容 |
|---|---|
| **4000 是否合理** | ✅ **合理，且已被端到端扫描钉死**：p55（n=53，带判分）750→0.500 / 1500→0.509 / 2500→0.575 / **4000→0.698** / 6000→0.679。**4000 是拐点**，6000 花 +2,492 tok 买到一个统计上为零的收益（McNemar p=1.0000） |
| **"远没用满"该不该调小预算** | ❌ **不该**。没用满是候选饥饿的**症状**（见 §1.3）。调小预算只会让已经饥饿的注入更饥饿。**先修召回，再看填充率** |
| **5200 = 4000×1.3** | ✅ 合理，是邻居扩展的独立额度（`NEIGHBOR_EXTRA_RATIO=0.3`），防止邻居在渲染时被整条砍掉 |
| **⚠️ 真实缺陷：渲染按时间序消费** | `utils.py:467` 按时间正序遍历，超预算 `continue` ⇒ **被牺牲的是最新的 = STM**（STM 是设计上"无条件注入"的近期上下文）。而 `retriever.py:280` 的 `relevance_order = ltm + stm` 恰好把 **STM 排在最后** ⇒ 顺序是反的 |
| **方案（零成本）** | 消费顺序改为 **STM 优先 → LTM 按相关度降序**，装满后**再按时间排序输出**给 LLM 读 |
| **验证方法** | 造一个"预算触顶"用例（注入量 > 5200），断言 STM 全部保留；加回归测试 |
| **风险** | 低。但注意：当前生产很少触顶（P67 实测 31.4 条 / 4,869 单位，仅超 22%）⇒ **收益面窄，属于正确性修复而非降本项** |

## 四、实验设计

### 4.0 Gate 0 —— 自检（**不过不许采信任何结果**）

| 臂 | 定义 | 判据 |
|---|---|---|
| **O（ORACLE）** | 把**证据所在消息的原文**直接拼进上下文，不走检索 | **命中率必须 = 100%**。低于 100% ⇒ 题集无效（答案不可由原文推出 / 标注错 / 判分器错）⇒ **整轮作废** |
| **N（NEG / 地板）** | 不给记忆、不给相关历史 | 命中率应 **≤ 40%**。若也接近 100% ⇒ 题集无区分度，作废 |
| **序关系** | O > A0（现状）> N | 不成立 ⇒ 链路有问题，先修链路 |

> 这一条是硬门槛。前序报告已吃过亏：题集存在但从未证明"喂全上下文能 100%"。

### 4.1 题集要求（**现有 `qa2.json` 不足以支撑本实验**）

| 层 | 证据距末轮 | 题数 | 用途 |
|---|---|---|---|
| **近期** | ≤ 8 条 | **≥ 30** | 历史压缩 A/B 的**唯一有效题集**（现有缺口） |
| 中程 | 9~24 条 | ≥ 30 | 中间路线（12~16 条）的判定依据 |
| 长程 | > 24 条 | ≥ 30 | 可复用 `qa2.json` 的 57 题（注意它只覆盖会话前 2/3） |
| **改写集** | 同题、同义改写提问（模拟"小玩具"式措辞） | ≥ 30 | **防过拟合**：前序实测纯关键词在原题集 58%、改写后 31% |

字段（沿用 `qa2.json`）：`qid / src_msg_id / q / a / evidence / grounded`，**必须新增 `distance`**。

**判分**：**只用字符串匹配，不使用任何 LLM 判分。**

理由（两条硬约束叠加后的必然结果）：
1. 本地 LLM 不可用 ⇒ 判分不能本地跑；
2. 付费 API 判分违反零付费约束；
3. 且前序实测 LLM 判分跨跑噪声 **±0.09**，大于部分档间差（`REPORT_记忆最优解复核` §六）。

⇒ **因此本实验只能做「检索层评测」**，主判据 = **证据是否进入注入窗口**（跨臂可比、确定性、可离线复现）。

🚫 **端到端臂（需要真实生成回答）在本约束下无法执行**：
生成回答必须调用云端生成模型（付费）或本地 LLM（已禁用）。
⇒ 所有"Δ命中"结论的口径都是**检索层命中**，**不得声称端到端得分提升**。
⇒ O/N/A0 各臂的判据统一改为"证据是否出现在注入文本中"（O 臂 = 直接拼接 ⇒ 恒 100%，自检语义不变）。
样本：**≥ 3 个会话 × 100 题**（单会话 57 题分辨不出 +1.8pp 与 −31pp）。

### 4.3 指标

| 指标 | 定义 | 备注 |
|---|---|---|
| **主：命中率** | **证据是否进入注入窗口**（检索层口径，唯一可执行口径） | 跨臂可比、确定性、可离线复现。<br>🚫 不做端到端（需生成，见 §4.1 判分） |
| **必报：注入 tok** | 0.66 tok/字口径（**禁用 cl100k**，实测高估 95%） | 不报 = "多注就赢"是作弊 |
| **性价比** | **Δ命中 / Δ(1k tok)** | 真正的决策指标 |
| 候选池画像 | #过阈值行数、target 排名与 sim、唯一 message_id 数、最大簇占比、渲染填充率 | 区分 §1.3 三种机制 |
| 延迟 | 检索 ms/题 | A4（2a+2b 叠加）必报；多路/双嵌入都要报 |
| 显著性 | **McNemar 配对检验** | n<60 一律标"不显著"，不得宣称提升 |

### 4.4 判定阈值（**事前钉死，事后不得修改**）

**有效性门槛**（任一不过 ⇒ 整轮作废）：
- O（ORACLE）命中率 **= 100%**
- N（NEG）命中率 **≤ 40%**
- A0（现状）命中率 ≥ 70%（低于此说明基线异常）

**采纳门槛**：

| 类型 | 阈值 |
|---|---|
| **降本臂**（C1/C2/H1/H2/B1） | Δ命中 **≥ −3.0pp** 且 省 **≥ 20%** 且 McNemar **p ≥ 0.05** |
| **提效臂**（A1~A4） | Δ命中 **≥ +5pp** 且 **p < 0.05** 且 注入 tok 增幅 **≤ 5%** |
| **显著性声明** | n=90 时 95%CI 宽约 **±10pp** ⇒ −3pp 落在噪声内。要宣称"不劣于"，需 CI 下界 > −10pp；否则一律写"不显著" |

⚠️ **禁止**：`|| true` / `continue-on-error` / `--continue-on-collection-errors`（`AGENTS.md` 验证纪律）。
⚠️ **禁止用 skip 掩盖失败**。

## 五、推荐首选方案

```
① 零 token 修召回（先做，且是下面所有降本项的前置）
   ├ P80 探针：区分「阈值杀 / top-K 杀 / 单簇塌缩」      ← 半天，不做这个后面全是猜
   ├ 2a 短扩展（本轮消息 + 最近 2 轮**规则抽取**的话题词，≤60 字）← 零成本、零 LLM
   ├ 2b 多路查询 RRF（治单簇塌缩，变体由模板生成）        ← +2 次嵌入 ≈40ms
   ├ 5d 双嵌入 RRF（bge-m3 + qwen3-embedding:0.6b）        ← 两个都是向量引擎
   └ 方向 4 的消费顺序修复（STM 优先）                    ← 零成本，正确性
   ⇒ 验收：命中率回到 85% 量级（A0 78.9% → 目标 ≥84%），注入 tok 增幅 ≤5%
   ⇒ 🚫 全程零 LLM：只用 bge-m3 嵌入 + 关键词路 + RRF + 纯规则

② 再动历史（① 通过后才做）
   └ 5a 分层压缩：近 8 条全文 + 第 9~24 条**抽取式压缩**（纯规则，零 LLM）
     ⇒ 预期总 prompt −25.6%（P70 实测长度），信息不丢（24 轮全在，只压表达）
   ⇒ 验收：近期题集（≥30 题）上 Δ命中 ≥ −3pp 且 McNemar p ≥ 0.05

不推荐的首选：
   ✗ 砍到 12~16 条（丢近期语境、p61 实测 6→24 有 +0.125、现有题集测不出差异）
   ✗ 加记忆预算到 6000（P72 实测不涨分，花 +2,492 tok）
   ✗ 真 cross-encoder rerank（本机无 reranker，CPU 延迟 2.5s/轮不可接受）
   ✗ **任何需 LLM 参与的方案**（HyDE / 生成式摘要 / LLM 查询改写 / LLM 上下文锚定）
     —— 违反硬约束，且本地 LLM 后续要全删，现在引入等于制造新的待删债务
```

**为什么顺序不能反**：前序 SPEC 已立此原则 —— "必须先让记忆变强，才能砍历史"。
p61 实测在记忆没变强时把历史砍到 6 条，得分掉 0.125。
你这次的 B 臂（57.1%）正是同一个坑的第二次踩。**修好召回前，任何历史压缩的 A/B 都不可采信。**
