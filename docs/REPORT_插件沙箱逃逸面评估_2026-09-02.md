**三轨信任模型（本报告的坐标系）**

| 轨 | 运行位置 | 权限 | 隔离是否到位 |
|---|---|---|---|
| ① untrusted 智能卡（默认） | `sandbox="allow-scripts"` iframe，**opaque origin** | 脚本可跑，但 `parent`/`localStorage`/Cookie 全部不可达（存储由 shim 的 memoryStorage 覆盖 + postMessage 持久化） | ✅ iframe 隔离到位 |

## 2. 轴一：postMessage origin 校验 — 通过

### 2.1 校验链（父侧 `CharacterCardRenderer.tsx`）

```
L751  if (!data || data.source !== 'palink-smart-card' || data.frameId !== frameIdRef.current) return;
                                    ↓
L761  if (iframeRef.current?.contentWindow && event.source !== iframeRef.current.contentWindow) return;
                                    ↓
      业务分派（resize / request / sendMessage / storage / extensionPrompts …）
```

三条独立校验：标记位、帧 ID、**来源窗口实例比对**。第三条是硬约束——外部页面拿不到
iframe 的 `contentWindow` 引用，因此无法伪造来源。**无 `event.origin` 校验不构成缺口**（实例比对强于字符串比对）。

### 2.2 两条加固建议（非漏洞，属"别让未来重构踩坑"）

**HARDEN-1｜`event.source` 校验写成"条件跳过"而非"失败关闭"**

```ts
// L761 现状
if (iframeRef.current?.contentWindow && event.source !== iframeRef.current.contentWindow) return;
//   ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 若 ref 为空，整个 && 短路为假 → 不 return → 跳过最强的那条校验
```
- **当前不可利用**：JS 单线程，React 提交是同步的，消息事件只在调用栈清空后才派发，
  因此"iframe 重建导致 ref 为 null 的窗口"对攻击者不可观测；且组件两条渲染分支（L1127 沉浸式 / L1273 内联）
  **都渲染 iframe**，不存在"监听器在而 iframe 不在"的稳定态。
- **风险在未来**：若哪天加了条件渲染（如折叠态不渲染 iframe），这条守卫会静默失效。
- 建议改为失败关闭：`if (!iframeRef.current?.contentWindow || event.source !== iframeRef.current.contentWindow) return;`

**HARDEN-2｜`frameId` 用 `Math.random()` 生成（非 CSPRNG）**

```ts
// L106
const frameIdRef = useRef(`palink-smart-card-${Math.random().toString(36).slice(2)}-${Date.now()}`);
```
- `Math.random()` 约 51 bit 熵，**远程不可暴力**；但 V8 的 `Math.random()`（xorshift128+）**状态可恢复**——
  采样若干连续输出即可反推后续输出。
- frameId 会进入 `window.__palinkFrameMsgs`（调试数组，记录后 6 位）与 `window.__palinkFrameErrors`，
  页内任何脚本都读得到 → ③ 经典轨插件可低成本采样。
- 建议改 `crypto.randomUUID()`（同文件 `SillyTavernCompatRuntime.ts:5253` 已经有现成用法）。

## 4. 轴三：fetch 代理 — 控制存在但可自败

### 4.1 卡内（智能卡 iframe）：无代理，用原生 fetch

`smart-card-runtime` 内没有为卡片实现 fetch 代理（仅 `SillyTavernCompatRuntime.ts:4965` 提供同名兼容函数）。
untrusted 卡是 opaque origin，**原生 fetch 不携带 Cookie**，因此卡片无法直接发已认证的同源请求 —— 这点是对的。
但它**可以向外发任意请求**（外泄自己能看到的聊天上下文与世界书内容）。

### 4.2 插件轨：白名单是"防外泄"控制，不是"授权"控制

`lib/plugin-system/sandbox.ts`

```ts
// L1371-1381
export function isUrlAllowedByPluginWhitelist(url: string): boolean {
  const parsedUrl = new URL(url, window.location.href);
  if (parsedUrl.origin === window.location.origin) return true;   // ← 同源恒放行
  return readPluginFetchWhitelist().includes(parsedUrl.hostname);  // ← 跨源才查白名单
}
```

三个必须讲清楚的点是：

1. **同源恒放行** → 插件的 `fetch('/api/...')` 一律放行。而插件（轨③）跑在**页面全局作用域**，
   该 fetch 就是页面真身 fetch，**自动携带会话 Cookie** → 恶意插件可发**已认证同源 API 调用**。
   这与渗透报告"恶意插件 = 完整账号接管"的结论一致。白名单**从不试图**阻止这件事。
2. **白名单条目存在 `localStorage['palink_plugin_fetch_whitelist']`**（`readPluginFetchWhitelist` L1348-1363）。
   localStorage 对**页内任何脚本**可读写 → 恶意插件先往里塞自己的域名，随后的外泄 fetch 就通过了检查。
   **防外泄控制可被页内攻击者自写配置绕过。**
3. 默认 CDN 白名单含 `cdn.jsdelivr.net / unpkg.com / cdnjs.cloudflare.com / raw.githubusercontent.com / github.com`
   （L1319-1325）—— 这些站都能托管任意 JS。对轨③（页面全局作用域）而言，从 CDN 拉代码再执行 = 绕过"插件从哪来"的管控。

> 定性：白名单的价值是**提高外泄的门槛、留下 `console.warn` 审计日志**（L1419 每次请求都记），
> 不是安全边界。别把它当边界使用。

### 4.3 CSP 不提供兜底

`frontend/nginx.conf:82` / `security-headers.conf:5`：

```
script-src  'self' 'unsafe-inline' 'unsafe-eval' blob: <5 个 CDN>
connect-src 'self' https: wss: ws: http:
```

- `unsafe-inline` + `unsafe-eval` → **对脚本执行基本不设防**；
- `connect-src` 放通任意 `https/wss/ws/http` → **不阻止向外传输数据**；
- 插件注入的 `<script nonce="palink-smart-card">`（常量 `SMART_CARD_CSP_NONCE`）因 CSP 未启用 nonce 机制
  而**不产生额外风险**（那个 nonce 属性是惰性的；CSP 也没有被它削弱）。
- CSP 真正挡住的是 `frame-src`/`base-uri`/`form-action` 与跨源 `default-src`，有纵深价值，但**救不了逃逸**。

## 5. 🔴 主要发现 F-1：untrusted 卡片的写能力越权（无需用户手势）

### 5.1 现象

智能卡通过 `postMessage` 的 `request` 通道向父页面请求动作，父侧在
`SmartCardCompatController.ts:646 handleSmartCardCompatRequest` 分派，**共 35 个动作**。
其中**只有 8 个**受"用户手势"闸门保护：

```ts
// L57-66  需手势的动作集合
sendMessage, sendMessageAsUser, sendUserMessage, triggerGeneration,
Generate, generate, generateRaw, generateQuietPrompt
```

**闸门实现（L68-70）：**

```ts
function smartCardPayloadHasUserGesture(payload) {
  return payload.__palinkUserGesture === true;   // ← 消息体里自声明的一个布尔
}
```

这不是浏览器 user-activation 校验，是**消息发送方自己填的字段**。
卡片脚本完全可以直接 `parent.postMessage({..., __palinkUserGesture: true})` 绕过——
shim 里那个 `hasRecentUserGesture()`（真实事件时间戳）只约束"走 shim 的诚实卡片"，**管不住恶意卡片**。

### 5.3 影响面（诚实界定）

**能做**：
- 静默删改当前会话的全部消息、伪造消息入库；
- 静默新建/替换/清空用户的世界书；
- 读取卡片可见的聊天上下文与世界书内容，并向外传输（见 §4）；
- 付费动作（`generate` 等）虽在手势集合里，但闸门可自填绕过 → 可**静默消耗用户 token 额度**（项目已实现配额，见 TODOS 用户 token 额度管理条）。

**不能做**（沙箱隔离确实生效，这部分要肯定）：
- 读不到 `palink_session` / `palink_csrf` Cookie（opaque origin）；
- 拿不到 token、无法跨用户、无法提权到 admin；
- 无法触碰页面 DOM 或其他角色的会话。

### 5.4 定级与定性

**定级：中高**（本地单用户部署下实际为**中**，多用户共享实例下趋近**高**）。

触发前提 = 用户导入并打开一张恶意角色卡（PNG 内嵌 HTML/JS，属社交工程，非远程无交互利用）。
影响限于**该用户自身**的会话与世界书数据完整性，**不涉及认证绕过、不涉及跨租户**。

**这与 ST 的模型是一致的**——SillyTavern 的角色卡/扩展同样是全权代码。所以按用户"适配优先"口径，
本报告**不建议立刻收紧**，只把它从"没想过"变成"知道且登记在案"。

### 8.3 为什么其余 26 个动作**不能**收口（兼容性论证，请勿凭直觉扩大集合）

核心是一条规范事实 + 一条工程事实：

1. **规范事实（HTML 6.4.2 第 4 步）**：用户激活向下传播到后代 browsing context 时，
   **仅包含同源后代**（`filtered to include only those navigables whose active document's origin is
   same origin`）。untrusted 卡是 `sandbox="allow-scripts"` 的 **opaque origin**
   → **用户在父页面点「发送」，卡内 iframe 感知不到**，shim 的 `lastUserGestureAt` 不会更新，令牌不会附上。
   （同一条规范第 3 步反过来是有利的：iframe 内的点击**向上传播到所有祖先且不限同源**，
   这正是"卡内点击 → 父侧能感知"的依据，也是闸门对正常卡片可用的原因。）
2. **工程事实**：**"生成结束后改写/追加消息、写世界书条目"是卡片最主流的正当用法**——
   本项目自己的 MVU 变量更新、状态栏、格式化卡都属此类，必然发生在**无手势**上下文
