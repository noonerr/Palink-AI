# SPEC — 重新生成（swipe）与分支记忆隔离修复

- 立档：2026-10-05
- 触发：用户提问「重新生成后选哪一版往下走？记忆会不会混淆？树状多分支的上下文注入是否都正确？」
- 性质：**排查已完成，缺陷已实测复现**。本 SPEC 是施工图纸，不是调研报告。
- 关联既有不变式：`backend/tests/test_memory_message_link.py` 文件头已写明
  「记忆永远是消息当前内容的镜像」——本次修的就是这条不变式被打破的地方。

---

## 0. 三十秒速览

| # | 结论 | 严重度 |
|---|---|---|
| 事实纠正 | 重新生成**不产生第二条消息**，是在同一条消息内追加候选版本（swipe）。故事线永远跟着「当前选中的那一版」走，**不存在读到旧版的错乱** | — |
| RC-1 | 切换候选 / 编辑消息时，「删旧记忆」立即生效、「写新记忆」延迟数秒在后台线程执行 → 期间任何二次操作的删除都是空删，**旧版本文本永久残留并会被召回** | **P0（已实测复现）** |
| RC-2 | 记忆召回**没有分叉点截断**，而消息历史有 → 新分支会召回到父分支「分叉点之后」的记忆，即用户已经放弃的那条剧情线 | **P1** |
| RC-3 | 祖先分支算出来为空时，召回**静默退化成整会话全分支**（等于关掉隔离） | **P1** |
| RC-4 | `memory_mode=disabled` 只在动作流路径跳过删除，编辑/切换路径无此守卫 → 三条写入路径行为不一致 | P2 |
| 产品决策 | **不做**「重新生成时询问是否开新故事线」。理由见 §6.1 | — |

**当前生产库实锤**：消息 `2599` 有 7 条记忆行，其中 **4 条来自用户已放弃的第 1 版**，
3 条来自当前选中的第 2 版，7 条全部带同一个 `branch_id` → **全部在召回范围内**。
即：界面上走第 2 版剧情，提示词里同时塞着第 1 版的描写。这就是用户担心的「记忆混淆」，已发生。

## 1. 事实基线（先对齐认知，避免修错方向）

### 1.1 重新生成的真实数据形态

`POST /api/character-sessions/{session_id}/regenerate`（`backend/app/api/character_ext.py:6077`）
**不新增消息行**，而是改写既有 assistant 行：

```
character_ext.py:6172-6180
  current_swipes = _message_swipes(msg)          # 旧候选列表
  if not current_swipes: current_swipes = [msg.content or ""]
  current_swipes.append(final)                   # 新生成追加到末尾
  msg.content  = final                           # 正文换成新版
  msg.swipe_id = len(current_swipes) - 1         # 当前指向新版
  msg.swipes   = _json_dump_or_none(current_swipes)
```

数据层实证（`character_chat_messages` 有 `swipes` / `swipe_id` 两列，已确认存在）。
前端 `1/2`、`2/2` 箭头条即候选切换（`frontend/src/components/ui/custom/Message.tsx:1758-1780`）。

### 1.2 上下文取哪一版

提示词装配读的是 `m.content`（`backend/app/services/character_message_builder.py:254`），
即**当前选中的那一版**。切换候选时后端会把 `content` 同步成所选版本
（`character_ext.py:6651-6652`）。

> **结论：用户担心的「往下走时读到第一次生成」不会发生。这一半是好的。**
> 真正的缺陷在记忆层——记忆没有跟上 `content` 的语义。

### 1.3 记忆的设计意图 vs 实际

设计意图（`storage.py:143-149` 注释、`test_memory_message_link.py` 文件头）：
`conversation_memories` 是消息当前内容的**镜像**，按 `message_id` 先删后写。

实际：**镜像会脏**。原因见 RC-1。

## 2. 缺陷清单与根因

### RC-1（P0）删写不原子：旧版本文本永久残留

**三条写入路径的时序不一致**，这是根因所在：

| 路径 | 删除时机 | 插入时机 | 是否原子 |
|---|---|---|---|
| 动作流（regenerate/swipe/continue）`character_ext.py:5877-5892` | 同事务 | 同事务 | ✅ 原子 |
| 普通轮 `character_ext.py:5093-5115` | 同事务 | 同事务 | ✅ 原子 |
| **切换候选** `character_ext.py:6663-6704` | 请求内立即 commit | **后台线程，数秒后** | ❌ **有窗口** |
| **编辑消息** `character_ext.py:3316-3356` | 请求内立即 commit | **后台线程，数秒后** | ❌ **有窗口** |
| **编辑消息（sessions 侧）** `backend/app/api/sessions.py:311-331` | 同上 | 同上 | ❌ **有窗口** |

窗口为什么有数秒：后台任务调 `store_memory` → `store_chunks`，而 `store_chunks`
是**先嵌入再插入**：

```
storage.py:494   embeddings = embed_text(chunks)   # ← 同步 HTTP 调 Ollama，秒级
storage.py:529   INSERT INTO conversation_memories ...
storage.py:563   self.db.commit()
```

`embed_text` 走 httpx 打 Ollama（`backend/app/memory_module/embedder.py:230-264`，
带 `OLLAMA_TIMEOUT`），本机实测该批次耗时约 4.4 秒。

**对照组**：单条路径 `store()` 是**先插入（embedding 写 NULL）再后台回填向量**
（`storage.py:406`、`storage.py:629-679`）——顺序正确，删除能命中。
**两条存储路径的顺序不对称，正是 bug 的结构性来源。**

#### 实测复现（生产库，2026-10-04 18:36）

消息 `2599`，`swipes` 长度 2，当前 `swipe_id = 1`：

| 记忆行 id | created_at | 文本归属 | 长度 |
|---|---|---|---|
| 1071-1074 | 18:36:17.995 | **swipe0（已放弃）** | 432/450/438/31 |
| 1075-1077 | 18:36:22.400 | swipe1（当前选中） | 426/438/302 |

- 7 行全部 `branch_id = bfe1928f-63b7-4409-9682-13ab619a072f`，与消息 2599 同分支
  → 落在召回 SQL 的 `branch_id IN :branch_ids` 内（`storage.py:743`），**会被召回**。
- 该分支祖先链长度 = 1，召回条件完全覆盖。
- 消息 2599 **不是**分支末条 assistant（末条是 2601）→ 用户随时还能再切它，
  每切一次都可能再叠一批残留。
- 消息 `2548` 同样有 2 个候选，3 条记忆行**全部来自当前版** → 未中招。
  说明这是**时序竞态**（概率性），不是必然发生。

#### 触发条件（前端已确认无防护）

`frontend/src/components/views/character/CharacterChat.tsx:1403-1412`：
箭头点击是 `void (async () => { await api.patch(...) })()` —— **无锁、无防抖、无 in-flight 去重**。
`frontend/src/lib/sillytavern/getContext.ts:2666` 插件面同样直发。
用户连点两下箭头（或切完立刻编辑/重新生成）即触发。

#### 竞态时序（与实测时间戳完全吻合）

```
T0 18:36:13  切到 swipe0 → DELETE(命中原始行 1064-1070) → commit → 起后台任务 A
T1 18:36:17.9 切回 swipe1 → DELETE(此刻 A 尚未 INSERT，空删) → commit → 起后台任务 B
T2 18:36:17.995 任务 A 完成嵌入 → INSERT 4 行【swipe0 旧文本】→ commit   ← 残留诞生
T3 18:36:22.400 任务 B 完成嵌入 → INSERT 3 行【swipe1 新文本】→ commit
终态：7 行并存，4 行是用户已放弃的剧情
```

> 原始行 id 1064-1070 在当前库中已不存在（被 T0 删除），与该时序一致。

### RC-2（P1）记忆召回缺分叉点截断

消息历史**有**截断，记忆**没有**——两者不对齐：

```
消息侧  character_ext.py:663-698
  chain 回溯时记录 up_to = cur.parent_message_id
  fork_clauses: "(m.branch_id != :bid OR m.id <= :mid)"     ← 分叉点之后的父分支消息被排除

记忆侧  character_ext.py:598-614  _get_ancestor_branch_ids
  WITH RECURSIVE 一路回溯到根，SELECT id —— 只有 branch_id，没有任何 message_id 截断
        storage.py:736-748
  WHERE ... AND (branch_id IN :branch_ids OR branch_id IS NULL)   ← 整条祖先链全量可见
```

**后果**：在第 50 楼拉新分支往下走，会召回到父分支第 51 楼之后写入的记忆——
那些正是用户决定不要的剧情。放弃的线以「记忆」形式渗进新分支。

分叉点数据**已经在库里**：`CharacterChatSessionBranch.parent_message_id`
（`backend/app/models/character.py:90`），且记忆行有 `message_id` 列可直接比较。
**不需要新增 schema。**

### RC-3（P1）祖先为空时静默退化成全分支召回

```
roleplay_prompt_assembly.py:5446
  ancestor_branch_ids = deps.get_ancestor_branch_ids(...) if req.branch_id else []
roleplay_prompt_assembly.py:5481
  branch_ids = ancestor_branch_ids if ancestor_branch_ids else None    ← 空则传 None
        storage.py:749-759
  elif session_id:  WHERE user_id AND session_id AND embedding IS NOT NULL   ← 无 branch 过滤
```

两种情况会走到这条降级：
1. `req.branch_id` 为空（主聊天）→ `[]` → `None` → **整会话所有分支的记忆全召回**；
2. 分支行查不到（数据异常）→ `[]` → `None` → 同上，且**无任何告警**。

隔离被静默关闭，不可观测。

---

### RC-4（P2）三条写入路径的 `memory_mode` 守卫不一致

`character_ext.py:5877` 的 `memory_mode != "disabled"` 只护住动作流；
编辑（`3316`）与切换（`6663`）路径**没有该判断**。
关闭记忆期间重新生成 → 不删不写；但同期编辑/切换 → 照删照写。
重新开启记忆后，脏行会重新浮现。

---

### RC-5（P2）删除成功但写入失败 → 该轮记忆直接消失

`service.py:131-133` 吞掉异常返回 `None`，而 DELETE 已在同事务内。
结果是「无记忆」而非「错记忆」——方向安全，但**静默且无计数**，
线上出现「明明聊过却召回不到」时无从排查。需补可观测性。

### 附：本轮排查中我自己的一次误判（写进 SPEC 以防后人重犯）

初版判据用 `position(记忆文本 IN 消息原始 content)` 比对，得出「120 条里 118 条不一致、
49 条无法溯源」。**这个数字不可信**：记忆存的是 `clean_memory_content()` 清洗后的文本
（`backend/app/utils.py:220-264`，剥 `<now_plot>`/`<UpdateVariable>`/思考块等），
而 `content` 是带标记的原文，清洗会删掉块中间的标记 → 子串匹配必然失败。

**正确判据**：对每个候选版本先跑同一套 `clean_memory_content()` + `semantic_split()`，
再比对（见 §5.1 清理脚本要求）。
本次唯一可确证的残留是消息 2599 的 4 行——那里用的是「块首 20 字符 LIKE 命中
`swipes[0]` 且不命中 `swipes[1]`」，块首通常不含标记，结论可靠。

> 教训：**判据本身要先自检**。本次已用 `SELECT position('ell' IN 'hello')` 验证函数语义后再下结论。

## 3. 修复方案

### 阶段 1（P0）· 关掉删写窗口 —— 对应 RC-1

**1.1 抽公共helper，消灭三份重复闭包**

现状：`character_ext.py:3327-3354`（编辑）、`6675-6702`（切换）、
`sessions.py:311-331`（编辑）是三份几乎相同的后台重嵌闭包。
抽到 `backend/app/memory_module/mirror.py`：

```python
def reembed_message_memory(
    *, session_id: str, message_id: int, user_id: int,
    role: str, expected_text: str, branch_id: str | None,
    character_id: str | None, memory_mode: str,
) -> None:
    """记忆镜像同步：删旧 + 写新，同一事务；写前校验版本新鲜度。"""
```

三处调用点改为只捕获标量后 `asyncio.to_thread(reembed_message_memory, ...)`。

**1.2 删除挪进后台事务（消除窗口）**

`DELETE` 不再在请求线程提前 commit，改为在 `reembed_message_memory` 内、
`store_memory` **之前**、**同一 session 同一事务**执行，然后一次 commit。
请求线程只负责改 `content` / `swipe_id` 并 commit 消息本身。

> 这样「删」与「写」之间不再隔着秒级嵌入调用；单次操作内部原子。

**1.3 写前新鲜度校验（消除并发交错）—— 关键**

仅靠 1.2 还不够：两个后台任务仍可能交错（A 的插入落在 B 的删除之后）。
插入前重读消息当前正文，比对不一致就**放弃本次写入**（更新的操作会负责写）：

```python
row = db.execute(
    text("SELECT content FROM character_chat_messages WHERE id=:m AND session_id=:s"),
    {"m": message_id, "s": session_id},
).first()
if row is None:
    return                                   # 消息已删，不写
current = clean_memory_content(row[0] or "") if role == "assistant" else (row[0] or "")
if current.strip() != expected_text.strip():
    logger.info("[MEM-MIRROR] 跳过过期重嵌 message=%s（正文已被更新的操作改写）", message_id)
    return                                   # ← 竞态在此被掐断
delete_by_message_id(db, session_id, message_id)
svc.store_memory(...)
db.commit()
```

`expected_text` 由调用方在**请求线程内**捕获（即当时的 `msg.content` 清洗结果），
确保比对的是「我这次操作对应的那一版」。

**1.4 前端补 in-flight 去重（降低无谓竞态）**

`CharacterChat.tsx:1403` 的箭头处理加 per-message 锁：同一条消息有未完成的
swipe PATCH 时，后续点击排队或忽略。`getContext.ts:2666` 插件面同样处理。
**这是纵深防御，不替代 1.3**（服务端必须自洽）。

**1.5 统一 `memory_mode` 守卫（RC-4）**

`reembed_message_memory` 内首行判 `memory_mode == "disabled"` → 直接 return，
使五条路径行为一致。`memory_mode` 由调用方从会话/角色配置解析后传入。

### 阶段 2（P1）· 记忆召回加分叉点截断 —— 对应 RC-2 / RC-3

**2.1 新增作用域helper（复用消息侧已有的 chain 逻辑）**

`character_ext.py` 增：

```python
def _get_ancestor_branch_scopes(db, session_id, branch_id) -> list[tuple[str, int | None]]:
    """返回 [(branch_id, up_to_message_id)]，root→self。
    up_to_message_id 为该分支的分叉点（子分支的 parent_message_id），根分支为 None。
    与 _get_full_branch_history_paged 的 fork_limits 同源同语义。"""
```

`_get_full_branch_history_paged`（`617-698`）改为调用它，**消除两份 chain 回溯逻辑漂移**。

**2.2 召回 SQL 加截断**

`storage.py:semantic_search` 的 `branch_ids` 参数升级为 `branch_scopes`，
branch-aware 分支（`736-748`）的 WHERE 改为镜像消息侧的 `fork_where`：

```sql
AND ( branch_id IS NULL
      OR ( (branch_id != :b0 OR message_id <= :f0)
       AND (branch_id != :b1 OR message_id <= :f1) ... ) )
```

**`message_id IS NULL` 的行如何处置**（必须显式决定，不能靠 SQL 三值逻辑默认）：
- `branch_id IS NULL`（主聊天trunk，现存 313 行）→ **保留可见**，维持既有行为；
- `branch_id` 属于被截断的祖先分支且 `message_id IS NULL` → **排除**
  （无法定位楼层，宁缺勿错；符合本项目既有 `[DIM-CONTRACT]` 的「宁缺勿错」惯例）。

**2.3 掐掉静默降级（RC-3）**

`roleplay_prompt_assembly.py:5481` 改为：

- `req.branch_id` 非空但祖先算出为空 → 传 `[req.branch_id]`（只认自己），**并 `logger.warning`**；
- `req.branch_id` 为空（主聊天）→ 传显式「仅 trunk」作用域，**不再传 None**；
- 彻底移除 `... else None` 这个把隔离关掉的写法。

`storage.py:749-759` 的「无 branch 过滤」分支保留给
`api/memory.py` / `api/silly_tavern.py` 等**不带分支概念**的公开端点，
但需在这些端点补 `logger.warning` 标明召回未按分支收敛（可观测，不改行为）。

**2.4 顺带修正 `exclude_message_ids` 的口径不一致（P3，可同批）**

`roleplay_prompt_assembly.py:5452-5458` 取「最近 5 条」只按当前分支过滤，
而召回按祖先链 → 祖先链尾部的消息可能既在历史窗口里、又被记忆重复注入。
改为按 2.1 的作用域取最近 5 条。

## 5. 存量数据清理

### 5.1 判据（必须用清洗后文本，见 §2 附注的误判教训）

对每条 `message_id` 非空的记忆行：
1. 取消息的 `swipes` 数组（无则 `[content]`）与当前 `swipe_id`；
2. 对**每个候选**跑 `clean_memory_content()` + `semantic_split()`（与写入侧同一函数，
   不得另写一套）；
3. 记忆行文本 ∈ 当前候选的块集合 → 干净；∈ 其它候选的块集合 → **残留**；都不属于 → **待人工判定**（可能是历史编辑造成）。

### 5.2 流程（严格遵守 AGENTS.md「备份与清理规范」§5：禁止直删）

```
① 出清单   _audit_memory_mirror.py --dry-run > 待删清单（含 id/message_id/归属候选/长度）
② 隔离     导出待删行全量到 _BACKUPS/2026-10-XX_记忆镜像残留清理/stale_rows.json
           + 同目录 BACKUP_INFO.md（日期/来源/原因/后续待办四要素）
           + 更新 _BACKUPS/_INDEX.md 台账
```

### 7.2 数据层判据（可复跑，作为回归门禁）

```sql
-- 判据A：任何多候选消息的记忆行，都不得来自「非当前选中」的候选
--        （实现见 _audit_memory_mirror.py，SQL 只做粗筛）
-- 期望：0 行
WITH multi AS (
  SELECT id, session_id, swipe_id AS cur, swipes::jsonb AS arr
  FROM character_chat_messages
  WHERE swipes IS NOT NULL AND swipes NOT IN ('', '[]')
    AND jsonb_array_length(swipes::jsonb) > 1
)
SELECT m.message_id, COUNT(*) AS stale_blocks
FROM conversation_memories m JOIN multi USING (session_id)
WHERE m.message_id = multi.id
  AND (multi.arr ->> multi.cur) NOT LIKE ('%' || left(m.content, 20) || '%')
GROUP BY m.message_id;
```

> 判据A 是**粗筛**（块首 20 字符 LIKE），权威判据以 §5.1 的清洗后比对为准。
> 本轮实测该粗筛对 2599 命中 4 行、对 2548 命中 0 行，与精确判据一致。

```sql
-- 判据B：记忆行的 branch_id 必须能在祖先链内被解释（无孤儿分支）
-- 期望：0 行
SELECT COUNT(*) FROM conversation_memories m
WHERE m.branch_id IS NOT NULL
  AND NOT EXISTS (SELECT 1 FROM character_chat_session_branches b WHERE b.id = m.branch_id);
```
