## 三、判定口径（为什么这么分类）

| 列 | 含义 | 证据来源 |
|---|---|---|
| 帧内存在 | 帧启动后 `window.event_types[KEY]` 是否定义（= 消费者写 `event_types.KEY` 拿到的是字符串还是 `undefined`） | 运行期取值 |
| 订阅可用 | 消费者按 ST 惯例 `eventSource.on(event_types.KEY, cb)` 后，用该键 emit 能否命中。键不存在 ⇒ 订阅落在字符串 `'undefined'` 上 ⇒ 记 **N** | 运行期往返 |
| emit 可达 | `观测`＝本轮驱动生产路径时真看到该值被 emit；`静态`＝载体里有 emit 调用点但本轮无离线可触发路径；`宿主静态`＝帧内零发射点、宿主 `runtime.ts`/`getContext.ts` 有 `eventSource.emit(` 调用点（**静态，未求值**）；`无`＝两级都零发射点 | 运行期 + 静态清点 |
| 与 ST 1.18 对齐 | 键名与事件值是否同时在 `d:/SillyTavern-release/public/scripts/events.js`（104 条；仓内 `_reference/sillytavern-1.18.0` 同源）出现 | 差集 |
| 备注（判定） | 真发 / 帧内未发·宿主静态 / 名存实亡 / 未实现 | 上述合并 |

判定优先级：`观测` ⇒ 真发；否则宿主有静态点 ⇒ 帧内未发·宿主静态；否则帧内无键 ⇒ 未实现；否则 ⇒ 名存实亡。

**为什么「机制往返 117/117 全通」不等于齐活**：帧内 `eventSource` 是 `Map<string, Set<fn>>` 通用总线（`part-07.ts`），任何字符串都能 on/emit 成功 —— 这一列只证明总线没坏，**不证明生产会发**，故不作为验收线，真正的判据是 emit 侧。

## 八、与规格/既有文档的偏差（实测纠正）

1. 规格写「事件名单来源：帧内运行时 `part-07.ts` 的 `event_types`」——**实测该表不在 part-07**，在 `runtime-body/part-06.ts:440`（`ensureObject('event_types', {...})`，104 条）；part-07 只有 `eventSource` 本体与读写点。探针以**运行期** `window.event_types` 为准，不依赖文件位置。
2. 规格写「117 个 `ST_EVENT_TYPES`」——117 这个数取自 `frontend/src/lib/sillytavern/getContext.ts:855`（宿主侧枚举）；帧内实际只有 104。两者不是同一份表，本报告已分开对待。
3. `emitCompatEvent` 全载体 49 处（39 处 `event_types?.KEY || '值'` + 4 处 MVU 键 + 6 处字面量），探针正则覆盖 49/49，无遗漏；另有 1 处**动态** emit `eventSource.emit('global_' + key + '_initialized')`（TavernHelper `initializeGlobal`），不属于 117。

## 九、未定性与边界（不猜）
