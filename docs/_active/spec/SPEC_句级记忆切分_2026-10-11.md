## 二、目标与非目标

### 目标
1. assistant 长回复改为**按句入库**（每句一条向量），使检索能精确定位到"那句话"。
2. 检索侧参数按新粒度适配（邻居范围 / 候选池 / 短期记忆条数），避免"切细了但补不回上下文"。
3. 保留**一键回退**到块级（`MEMORY_CHUNK_STRATEGY=structural`）。
4. 单轮写入条数有硬上限，防止超长回复把库和嵌入耗时放大失控。

### 非目标（明确不做，避免范围蔓延）
- ❌ **不改历史条数**（24 条保持）—— 第 4 步已被实测否证。
- ❌ **不重切存量 764 条块级记忆** —— 重嵌成本高、收益未验证；新旧混存可接受（见 §六）。
- ❌ **不改嵌入为异步** —— 经实测论证无必要（见 §五）。
- ❌ **不动装配链**（`roleplay_prompt_assembly.py`）—— 检索侧参数改动集中在 `retriever.py` / `storage.py`，不碰装配。

## 三、改动点清单

### 3.1 切分策略（`memory_module/semantic_chunker.py`）

**新增 `sentence_split(text)`**：复用既有 `split_sentences()`，不写新算法。

复用理由（`split_sentences` 已具备本次所需的全部性质）：
- 保留句终止符与换行，`''.join(chunks)` 可还原原文（记忆=消息镜像的不变式）；
- 碎句（< `CHUNK_MIN_SENTENCE_CHARS`=20 字）自动并入下一句 —— 天然过滤"嗯。""好的。"这类无信息量短句；
- 单句超 `CHUNK_MAX_CHARS`（450 字）在句边界强制再分；
- 纯正则实现，**零嵌入调用**，可离线单测。

```
def sentence_split(text) -> List[str]:
    text = (text or "").strip()
    if not text: return []
    sentences = split_sentences(text)
    if not sentences: return [text]
    # 条数上限：超限整体退回结构切分（保证单轮写入条数可控）
    if len(sentences) > memory_config.SENTENCE_MAX_CHUNKS:
        logger.info("[CHUNK-SENTENCE] 句数 %d 超上限 %d，退回结构切分", ...)
        return structural_split(text) or [text]
    return sentences
```

**`semantic_split()` 增加分派分支**：`CHUNK_STRATEGY == "sentence"` → `sentence_split(text)`。
分派位置与 `structural` 相同（放在"句子太少不切"短路之后，三条策略共用同一套短路条件）。

### 3.2 配置（`memory_module/config.py`）

| 常量 | 默认 | 说明 |
|---|---|---|
| `CHUNK_STRATEGY` | `structural` → **`sentence`** | **行为变更**：默认策略改句级 |
| `SENTENCE_MAX_CHUNKS`（新） | 40 | 单轮最多切几句；超限退回结构切分 |
| `SENTENCE_NEIGHBOR_RADIUS`（新） | 2 | 句级下邻居扩展范围（±2 句） |
| `BLOCK_NEIGHBOR_RADIUS`（新） | 1 | 块级下邻居扩展范围（保持旧行为） |
| `SENTENCE_STM_LIMIT`（新） | 12 | 句级下短期记忆条数 |
| `BLOCK_STM_LIMIT`（新） | 5 | 块级下短期记忆条数（保持旧行为） |
| `SENTENCE_CANDIDATE_LIMIT`（新） | 120 | 句级下语义候选池 |
| `BLOCK_CANDIDATE_LIMIT`（新） | 50 | 块级下语义候选池（保持旧行为） |

配套在 `MemoryConfig` 上加 3 个只读属性，让调用点不必自己判断策略：

```
@property
def EFFECTIVE_NEIGHBOR_RADIUS(self) -> int:
    return self.SENTENCE_NEIGHBOR_RADIUS if self.CHUNK_STRATEGY == "sentence" else self.BLOCK_NEIGHBOR_RADIUS
# 同理 EFFECTIVE_STM_LIMIT / EFFECTIVE_CANDIDATE_LIMIT
```

**为什么这些参数要跟策略走**：回退开关的语义必须是"回到改动前的行为"。
若把邻居范围写死 2，回退到块级后块级也会补 ±2 块，回退就不是等价开关（仓库既有教训：
`test_structural_and_semantic_produce_comparable_sizes` 就是为"回退必须是等价开关"立的）。

### 3.3 邻居扩展（`memory_module/storage.py`）

`get_adjacent_chunks(mem)` → `get_adjacent_chunks(mem, radius: int = 1)`。
默认 1 = 旧行为不变；`_expand_chunk_neighbors` 调用时传 `memory_config.EFFECTIVE_NEIGHBOR_RADIUS`。

**为什么句级需要更大范围**：块级一条 = 一个完整语义单元，补 ±1 块即可；
句级一条 = 一句话，命中后只补 ±1 句仍是"三句话的碎片"，读不通。±2 句才接近一个语义单元。

### 3.4 检索参数（`memory_module/retriever.py`）

| 位置 | 现状 | 改为 |
|---|---|---|
| `recent_limit = 5`（第 50 行） | 硬编码 5 | `memory_config.EFFECTIVE_STM_LIMIT` |
| `semantic_search(limit=50)`（第 123 行） | 硬编码 50 | `memory_config.EFFECTIVE_CANDIDATE_LIMIT` |

**为什么短期记忆要加**：句级下"最近 5 条记忆"很可能全部来自**同一条回复的 5 句话**，
覆盖不了最近几轮对话 —— 与 STM 的设计意图（近期上下文）相悖。提到 12 才能覆盖 2~3 轮。

**为什么候选池要加**：句级后单条信息量约为原来的 1/8~1/10，
50 条候选的信息量 ≈ 原来的 6 个块。提到 120 才与原信息量可比。

### 3.5 不改动的部分（明确边界）

- `service.store_memory()`：切分入口与 `len(chunks) > 1` 分支**无需改动**（策略分派在 `semantic_split` 内部）。
- `storage._chunk_topics()` / `_parse_chunk_meta()` / `delete_by_message_id()`：元数据编码与删除口径**完全复用**（`#chunk/#turn/#idx/#total` 对句级同样成立）。
- `mirror.py`：CAS 重嵌路径**无需改动**（`delete_by_message_id` 一次 DELETE 删该消息全部行，不逐条删）。
- `utils.build_memory_context()`：预算与"整条跳过"语义**不变**。
- `roleplay_prompt_assembly.py`：**零改动**。

## 四、参数取值依据

| 参数 | 取值 | 依据 |
|---|---|---|
| `SENTENCE_MAX_CHUNKS = 40` | 40 | 生产最长回复量级 + 嵌入耗时实测：35 条 × 34 字 ≈ 2.3s（可接受）。3000 字回复约 100 句 → 超限退回结构切分（约 12 块） |
| `SENTENCE_NEIGHBOR_RADIUS = 2` | 2 | 命中句 + 左右各 2 句 ≈ 5 句 ≈ 一个语义单元；被 `NEIGHBOR_MAX_ADDS=4` 封顶，不会失控 |
| `SENTENCE_STM_LIMIT = 12` | 12 | 12 句 × 约 30 字 ≈ 360 字，覆盖 2~3 轮；占预算（4000 内部单位）不到 10% |
| `SENTENCE_CANDIDATE_LIMIT = 120` | 120 | 与块级 50 条的信息量对齐（50 × 295 字 ≈ 120 × 30 字 量级） |

**未改的参数**：`NEIGHBOR_MAX_ADDS=4`（保持封顶）、`NEIGHBOR_EXTRA_RATIO=0.3`、
`MIN_SIMILARITY=0.5`、`HYBRID_WEIGHT=0.7`、记忆预算档位 `(750,4000,6000,8000)`。

> `NEIGHBOR_MAX_ADDS` 在句级下可能成为瓶颈（±2 句 × 命中 10 条 = 想补 40 条，实际只补 4 条）。
> 本次**不动**它（放大邻居 = 放大 token，需实测），登记为后续项（见 §八）。

## 五、性能评估（实测，2026-10-11，生产容器 + 真实库）

### 5.1 检索侧：不变慢，反而更快

| 场景 | 行数 | 实测耗时 |
|---|---|---|
| 现状（单会话） | 227 | **2.2 ms** |
| 句级化后（同会话，×10） | 2,270 | **14.0 ms** |

方法：把 `conversation_memories` 复制 10 份到临时表后 `EXPLAIN ANALYZE`（只读，未写业务数据）。

⇒ 向量扫描 +12ms；而查询嵌入经第 1 步修复后为 424ms（原 1652ms）。
⇒ **整条检索 1654ms → 438ms，快 3.8 倍。**

### 5.2 写入侧：+25~40%，绝对值 < 1s

| 配置 | 条数 | 总字数 | 耗时（清 `_embed_dedup_cache` 后 2 轮） |
|---|---|---|---|
| 块级 | 4 × 272 字 | 1088 | **1846 / 1857 ms** |
| 句级 | 35 × 34 字 | 1190 | **2267 / 2641 ms** |

⇒ 同等字数下贵 +25%~40%（与 10-09 报告"写库嵌入 +30%"吻合），绝对值增加约 0.5s。
⇒ 该开销发生在**回复生成完成后的落库阶段**，不占用用户等待首字的时间。
⇒ ⚠️ 测嵌入耗时**必须 `reset_embed_dedup_cache()`**，否则命中内容去重缓存得到 0ms 假数据。

### 5.3 为什么不改异步嵌入

- `store()` 单条路径本就是异步（`loop.create_task`）；
- `store_chunks()` 同步，但 +0.5s 且不在关键路径；
- **编辑/切候选的重嵌路径**（`mirror.sync_message_memory`）运行在**后台线程 + 独立 Session**，
  本身就不阻塞用户；其删除走 `delete_by_message_id`（一条 DELETE 删全部行），无逐条删除放大。
⇒ 改异步的收益 < 引入的风险（事务边界、会话生命周期），**本次不做**。

## 六、存量数据策略

- **不重切**：764 条块级记忆保持原样，与新的句级记忆**混存**。
- 混存可接受的理由：两者都带 `#chunk/#turn/#idx/#total` 元数据，检索、邻居扩展、去重、
  按 `message_id` 级联删除全部走同一套口径，不存在兼容分支。
- 效果预期：句级条目更聚焦，在候选池里排序更靠前，新数据会逐步主导召回结果。
- 可选工具（**本次不自动执行**）：`scripts/_rechunk_memories_semantic.py` 已存在，
  但其筛选条件是"`len(content) > CHUNK_MAX_CHARS` 且不含 `#chunk`"——
  **会跳过已切块的存量行**。若要重切存量，需先扩展该脚本（登记为后续项）。
