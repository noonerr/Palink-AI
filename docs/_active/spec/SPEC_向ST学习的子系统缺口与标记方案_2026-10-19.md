## 0. 两分法（本文件唯一的分类依据）

- **甲类｜ST 有、我们也有对应数据，只差"照 ST 语义把口子开出来"** → 学 ST，收益直接，工作量小。
- **乙类｜ST 有、我们没有那个子系统** → 先标记，不假装；等包W 的诊断排行证明"真被卡用到"再决定搬不搬。

⛔ 任何一档都**不许**用"返回个像样的空壳"糊过去（本仓反复踩过：形状对语义错 = 卡以为有、一用就废，且无声）。

## 1. 标记机制（三件事，缺一件就是"标了就忘"）

1. **代码内可 grep 的稳定 id**：每处缺口在其实现处留一行注释 token —— `// [ST-GAP:<id>] <为什么不做/等什么>`。
   id 用本文件 §2 表里的，全局唯一，**中文说明随意写，token 不许改**。
2. **运行时归属字段**：包W 的记录器里，`host_capability` 类记录必须带
   `missingStSubsystem: <id>`（取不到 id 的填 `unknown`），使诊断导出能按 id 聚合成"哪口井真被踩到"。
3. **守门测试（防漂移）**：一条后端/前端测试读取本文件 §2 表的 id 清单，断言
   ① 每个 id 在源码里至少出现一次（防"台账有、代码没标"）；
   ② 源码里出现的每个 `ST-GAP:<id>` 都在台账里（防"代码标了、台账没记"）。
   ⚠️ 这是**双向**的；单向检查会让台账先烂掉。

## 3. 命令侧（202 条"在场未实现"）怎么归因到同一套 id

包F 的 §4.2 把 202 条按 10 族给了理由。要求：每条命令注册点在**未实现分支**上留
`// [ST-GAP:<id>]`，id 复用 §2（多数落 `preset_prompt` / `wb_delete` / `persona_crud` / `audio_player` / `ext_install`），
使"命令缺失"和"键缺失"在诊断里聚成同一张表，不要分两套统计。

## 4. 施工顺序（我的建议，等用户点头再派包）

1. **包W 先落地**（已在跑）→ 拿到 `missingStSubsystem` 聚合排行；**排行出来之前不投入乙类**。
2. **甲类一批小包**（每个都很小，且都"只差桥/只差槽位"）：`wb_delete` → `chat_binding` → `stop_by_id` → `persona_crud` → `macro_register`。
   共同验收：对应键/D 类计数从 58 往上走，且**真机实调形状正确**（不许用枚举数充数，见包H §1 的教训）。
3. **`jailbreak_slot` 单独一包**：它在装配链里，牵动提示词顺序与深度锚点（见记忆"depth anchor 无地板"），改完必须复跑装配探针。
4. **乙类按排行决定**：排行里没人踩的，就让它继续标记着、不做。

## 5. 红线

- ⛔ 禁止"补个返回空对象/空串"当作实现（本仓两次被这类事坑：包G 的 stubApi 噪音、包H 的 14 键实现期改判 D）。
- 标记本身**不得改变用户可见行为**；运行时记录归包W 的记录器，不许自己 `console.warn` 刷屏。
- `raw_import` / `charlib_write` 涉及"卡能写什么"，属权限面，**动手前要用户拍口径**。
- `opaque_dom` 一行都不许朝"放宽沙箱"方向修（P1-1）。
- 台账改动走"只进不出"：划旧文加订正，不删行。
