## 1. 解决的问题是什么

### 1.1 症状
- 第二轮对话 **100%** 思维链进入死循环（推理模型无限自我审查）。
- 思维链中疑似"提示词泄露"（模型复述提示词内容）。
- 偶发空响应（HTTP 200 但无 content/reasoning 增量），触发重试后仍失败报错。

### 1.2 根因（完整因果链）
```
assistant 回复 full_content（正文 + <UpdateVariable><Analysis>…<JSONPatch>…</UpdateVariable> 大 XML 功能块）
  ↓ ① 入库不清洗：websocket.py 直接 store_memory(content=result.full_content)
  ↓ ② 功能块整块进入向量记忆库 conversation_memories
  ↓ ③ 注入不设防：build_memory_context 用 content[:200] 硬截断
  ↓ ④ 正文较短时第 200 字符正好切在 <UpdateVariable>/<Analysis>/<JSONPatch> 中间
  ↓ ⑤ 残缺半截 XML 标签被注入下一轮 prompt
  ↓ ⑥ 推理模型思维链反复自我审查："系统禁止 XML 但 MVU 豁免又说允许 → 记忆里出现残缺标签 → 它是什么？要不要补全？"
  ↓ ⑦ 无限自我辩论 → reasoning 流不停 → reasoning-only 触发空响应重试 → 报错
```

**为什么第一轮正常、第二轮必死循环**：第一轮记忆库为空（无注入），第二轮检索必然命中第一轮的 user+assistant 记忆（同主题相似度最高，且 retriever 的 context_proximity 权重还加分）→ 脏数据必然注入。

### 1.3 为什么之前没发现
- 此前修复聚焦"Error 文本不入库 + 空响应重试"，只打破"Error 入库→循环污染"的表层，未触及"功能块/思维链块入库"这一真正污染源。
- 记忆库是共用数据，websocket.py（palink-native 主链路）和 character_ext.py（SSE 链路）两处都写，只修一处不彻底。

## 3. 与另一个项目共用 Ollama 向量模型（关键细节）

### 3.1 背景
- 另一个项目（奈酱/hemers 助手）已用 **Ollama + bge-m3（1024 维）**，本地 Docker 容器 11434，核显（Intel UHD 32EU）Vulkan 加速已验证 +57%。
- 用户要求：**让另一个项目使用 Palink 的引擎**，且**兼顾性能与效果**。
- 最终决策（用户拍板）：**Palink 与奈酱同机部署在 NAS**（i3-1315U / 16GB 单通道 DDR5），**统一到 Ollama + bge-m3**——核显加速已验证、效果最强、两项目共享同一常驻模型（内存最优）。

### 3.2 为什么选 Ollama + bge-m3（而非 fastembed 生态）
- **bge-m3 vs bge-small-zh/jina-base-zh**：bge-m3 是当前开源中文语义检索第一梯队（1024 维、dense+sparse、多语言、长文本 8K）；jina-base-zh 中文也不差但综合弱于 bge-m3。
- **GPU 加速**：fastembed（ONNX Runtime）默认纯 CPU，且 fastembed 0.8.0 不暴露 execution provider，**无法吃核显**；Ollama（llama.cpp/Vulkan）已验证 +57%。
- **内存**：16GB 单通道紧张，Ollama 让两项目共享一份常驻模型；进程内再加载一份 bge-m3 反而双份占内存。
- **不用 Ollama 的替代方案（llama-cpp-python + GGUF + Vulkan）**：技术上可行但需升级依赖验证、效率上只省 1-5ms HTTP 开销、内存反而更差——不值得。

### 3.3 连接方式
- Palink backend 容器通过 `host.docker.internal:11434` 访问宿主机（NAS）上的 Ollama。
- `docker-compose.yml` 已加 `extra_hosts: host.docker.internal:host-gateway`。
- 若 NAS 上 Ollama 不在宿主机而在另一容器，需改为同一 docker network 直连（届时改 `OLLAMA_HOST` 环境变量即可，代码无需动）。

### 3.4 降级兜底（重要）
- `OllamaEmbedder.embed()` 内部 try/except：Ollama 不可达/HTTP 错误/返回空 embeddings → 自动回退 `FastEmbedEmbedder`（bge-small-zh 512 维）。
- **注意**：降级时维度从 1024 变 512，与存量 1024 维向量**不兼容**（检索时 numpy 点积会报维度错误）。这是"Ollama 故障"的临时状态，可接受（功能不崩），但**故障恢复后必须重算受影响记忆**。
- 工厂层 `_create_embedder()` 的 ollama 分支也有 try/except（创建失败降级），但 OllamaEmbedder 构造是惰性的（httpx.Client 不立即连接），**真正的降级靠 embed() 内的运行时降级**，工厂层降级只是兜底。

## 7. 注意事项（给后续维护者）

1. **改记忆相关代码前先读 `TODOS.md`**，同步状态。
2. **入库清洗是硬约束**：任何新增的 assistant 入库路径都必须过 `clean_memory_content()`，否则脏数据闭环会复发。
3. **Ollama 降级是临时态**：降级期间维度 512 与存量 1024 不兼容，检索可能报维度错误——这是可接受的故障态，恢复后重算即可。
4. **换模型/换维度必须全量重算**：embedding 维度与模型强绑定，混用会导致检索崩溃。
5. **容器重建是生效前提**：改后端代码后必须 `docker compose up -d --build backend`，探针/源码验证 ≠ 容器生效。
6. **模型可能把思维链写进 content**（reasoning 字段为空）：入库前必须剥离 ` thinking... response` 块（`[THINK-IN-CONTENT-FIX]`），且剥离要在拼 reasoning 前缀**之前**，避免误伤 ST 兼容的 reasoning 前缀。
7. **不要用 SentenceTransformer 替代 Ollama**：此前其他 agent 误加 `sentence-transformers==6.0.0 / torch==2.13.0 / transformers==5.15.0`（版本不存在、Python 3.10 装不上）导致构建失败。向量引擎统一走 Ollama（NAS 部署），开发机降级 fastembed 即可。
