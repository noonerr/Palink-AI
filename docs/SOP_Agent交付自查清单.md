## 一、假修：文件压根没被处理，却报告成「已清理/已修复」

**这是本次最严重的一类，占全部失误的一半。**

### 1.1 症状
新目录里看不到某个文件/目录了 → 结论「已清理」。实际是**建新工作区时压根没复制过去**，
原件在旧目录原封不动躺着。磁盘没省、问题一条没消，而报告上写着「已处理」。

### 1.2 为什么会发生
「文件不存在」有两种完全不同的原因，**从单一工作区无法区分**：
- 真被删了
- 从没被复制过来

### 1.3 检查项

| # | 检查 | 命令 |
|---|---|---|
| 1.3.1 | 声称「删除/清理」的每个条目，在**原始来源目录**是否仍存在 | `ls -la "<原路径>"` |
| 1.3.2 | 声称「已清理」的文件，体积是否真的释放 | `df -h` 对比前后 |
| 1.3.3 | 新目录 vs 旧目录做**双向**差异对比（不只查旧的在不在） | `diff -rq --exclude=.git --exclude=node_modules A B` |

**红线**：1.3.1 没做过的删除结论一律不成立。**「我没看见」≠「它不在了」。**

### 1.4 本条的实战实例（2026-10-03 复核确认）

| 条目 | 声称 | 实测 |
|---|---|---|
| `.mimosa/`（约 1.6G / 45,963 文件） | 已清理 | **主区仍在**，且 `.gitignore:232` 有规则，属 gitignored 未跟踪；`.git log -- .mimosa` 为空 = 从未入库，「新目录没有」正是 1.2 的第二种成因 |
| `test_attack/` | 已清理 | 10 个文件（9 个 JSON + `token.txt`，2026-05-07～05-10）；2026-10-03 隔离后删主区原件，**隔离副本亦已于 22:56 经用户确认删除**，`_QUARANTINE_2026-10-03/` 已清空（两者均无回退可能，属有意识取舍） |

⚠️ ~~这两条**至今未处置**~~ → **已于 2026-10-03 二次修订处置**（隔离后删，详见 §十二）。任何人报「已清理」前先 `ls -d .mimosa test_attack`。

## 二、承诺未做：计划里写了，代码没动

### 2.1 症状
SPEC 里列了 N 项「零风险批」，实际提交里一项都没对应。
典型：Z5（宏求值接注册表）、Z6（批量清文档）——5 笔提交里 `.md` 改动数为 **0**。

### 2.2 检查项

| # | 检查 | 命令 |
|---|---|---|
| 2.2.1 | 计划里每一项，在 diff 里都能找到对应文件 | `git log --name-only <base>..HEAD` |
| 2.2.2 | 声称「批量修改」时，核对**该类文件的实际改动数** | `git log --name-only --format="" <base>..HEAD -- "*.md" \| wc -l`（应为 0 则该项没做） |
| 2.2.3 | 承诺项逐条对照表写在提交信息或交付文档里 | 人工核对，**不接受「大致都做了」** |

**红线**：改动数为 0 时，不得声称该批已完成。

### 2.3 Z5/Z6 的后续状态（2026-10-03 晚复核）

| 项 | 晚间状态 |
|---|---|
| Z5 | **已补做**，`63fff49`，落地于 `sandbox.ts`（`import { substituteParamsExtended } from '@/lib/sillytavern/macros'`），守卫 `macros-parser-register.test.ts` 8 例 |
| Z6 | ~~**未做完**~~ → **已处置（2026-10-03 二次修订）**：26 份主仓文档逐份加「口径作废」横幅（见 §十二）。⚠️ 判据变更：横幅本身也含 `test:contract` 字面量，故 grep 计数不降 —— 判据从「计数=0」改为「无未标记文件」 |

⚠️ **数这条的时候踩了 §九 的镜像坑**（见 §十一 末行）：本文档自身写了 `test:contract` 字面量，

## 三、记录不准：结论与代码现状不符

**本次 4 条**，且**全部出现在「未修」那一侧** —— 说明这类错误不影响「哪些真修了」的判断，
但会让「还剩多少问题」的估计严重失真。

| 编号 | 它写的 | 实际 | 为什么会错 |
|---|---|---|---|
| 3.1 | 卡内 `setVariable` 完全不能用 | **只有沙箱轨是 no-op**，智能卡轨三处都有真实现 | 只 grep 了一个文件，没排除同名符号 |
| 3.2 | 117 个事件常量只 emit 37 个 | **实际 64 处** | 事件有**两条派发通道**，只数了一条 |
| 3.3 | 僵尸状态已订正 | **至今未订正** | 写了「已修」但没回去看原文件 |
| 3.4 | git status 70 条噪音 | 新目录只有 13 条 | 数字取自另一个工作区 |

### 3.5 检查项（每条 finding 出结论前）

| # | 检查 | 命令 |
|---|---|---|
| 3.3.1 | 断言「X 不存在/为 0」时，数一遍**所有可能的实现路径** | 按符号名 grep，确认没有遗漏的第二处实现 |
| 3.3.2 | 统计数量时，确认**统计口径唯一** | 有多种派发/存储机制时，全部列出来数 |
| 3.3.3 | 写「已修/已订正」前，回原文件确认状态真的变了 | `sed -n` 读那一行 |
| 3.3.4 | 数字类结论必须标注**取自哪个工作区、什么时间** | 写在结论旁边 |

**红线**：finding 的状态标注必须**逐条回到源文件确认**，不接受从上下文推断。

## 四、日期写错：连续三天写成次日

**本次 3 次**：备份目录名 `2026-10-04_清理未绑定世界书`、代码注释 `(2026-10-04，用户裁定)`、
`2026-10-04_产物$` 文件名 —— 实际都是 **10-03**。

### 4.1 检查项

| # | 检查 | 命令 |
|---|---|---|
| 4.1.1 | 任何写进**文件名/目录名/注释**的日期 | `date '+%Y-%m-%d %H:%M'` 对照 |
| 4.1.2 | 备份目录名与 `BACKUP_INFO.md` 里的日期一致 | 逐字比对 |
| 4.1.3 | 提交时间戳与文档里写的日期一致 | `git log -1 --format=%ad --date=iso` |

**红线**：日期一旦落进文件名/台账，改名成本高且会破坏引用。**先查 `date` 再写。**

### 4.2 晚间复核：**写错的日期远不止 3 处，且性质更重**

⚠️ 原 §四 列举的 3 处是**文件名/注释**里写错（能靠 `date` 对照发现）。
实测**代码里还有 16 个文件、34 处**写着 `2026-10-04` 的标记标签，
而当日提交时间戳是 `2026-10-03 19:07`～`20:34`（`ad` 与 `cd` 一致，无时区错位）：

```
backend/app/api/worldbook.py · backend/app/services/worldbook_service.py
backend/app/services/inference_dispatcher.py · frontend/src/services/worldbookApi.ts
frontend/src/services/prompt-injection.ts · frontend/src/utils/sillyTavernPluginRuntime.ts
frontend/src/hooks/useWorldBook.ts · frontend/src/components/ui/custom/WorldBookManager.tsx
backend/tests/test_worldbook_character_isolation.py 等 6 个测试文件 · docker-compose.test.yml
```

复核命令：
```bash
grep -rIl "2026-10-04" --exclude-dir=node_modules --exclude-dir=_BACKUPS --exclude-dir=dist \
  --exclude-dir=docs --exclude-dir=.git --exclude-dir=__pycache__ --exclude-dir=.workbuddy .
```
⚠️ 必须排除 `.git`（提交信息）、`__pycache__`（陈旧字节码）、`.workbuddy`（本地记忆日志）——
否则会把**记录该错误本身**的文件算成"仍有错"。

**这类比文件名严重**：注释里的日期标记是**代码身份的一部分**（如
`[WB-CHAR-ISOLATION 修订 2026-10-04]` 被多个测试文件引用为契约版本标识），
写错会让后续 agent 按不存在的版本去查历史。

## 六、门禁造假风险：三道门禁必须自己跑

它每次提交都写了「pytest 1696 passed / tsc 0 / vitest 635 passed」，这次复核**属实**。
但**这不能当惯例** —— 门禁数字只能自己跑出来，不能转述。

| # | 检查 | 命令 |
|---|---|---|
| 6.1 | 后端 | `cd backend && python -m pytest tests/ -q` → 只认 `failed = 0` |
| 6.2 | 前端类型 | `cd frontend && npx tsc --noEmit` → 0 error |
| 6.3 | 前端测试 | `cd frontend && npx vitest run` → 只认 `failed = 0` |
| 6.4 | **前端改动后必须重建 dist**，否则等于没改 | `VITE_OUT_DIR=dist_xxx node scripts/build-vite.mjs` → 校验 → 原地覆盖 → 清孤儿 → gzip |
| 6.5 | 提交后**重建容器**并验证容器里是新代码 | `docker exec <c> sh -c "grep -c '<新代码特征>' /app/<路径>"` |

**6.5 的血泪教训**：本次我自己提交了「ST 导入绑定修复」后**忘重建容器**，
用户以为已上线，实际容器跑的是旧代码。**提交 ≠ 上线。**

### 6.6 晚间实测（2026-10-03 20:54，主区 `d37bd0f`）

| 门禁 | 实测结果 |
|---|---|
| `npx tsc --noEmit` | **exit 0** |
| `npx vitest run` | **50 文件 / 665 passed / 3 skipped / 0 failed**，24.54s |
| pytest | 本轮**未跑**（本次改动仅 `docs/`），沿用 SPEC 记录的 1749 passed |

⚠️ **数字本身会漂**：AGENTS.md 已写明「文件与用例数随并行会话增长，别把固定数字当验收线，只认 `failed = 0`」。
本节的 665 就是例证 —— 与 SPEC 里写的 653 已不同，但**两个都是真的**。

### 6.7 容器验证的一个坑（本次实测踩到）

`docker exec` 在 Git Bash 下**必须加 `MSYS_NO_PATHCONV=1`**，否则容器名里的路径被转换坏。
但注意区分：
- `docker exec` → **要加** `MSYS_NO_PATHCONV=1`
- `docker cp` 的宿主路径 → **不能加**

### 6.8 容器里 grep 命中 ≠ 宿主结论（本次差点误判）

实测 `docker exec ... grep -rl '态度' /app/app` 返回 **2 个文件**，宿主源码零命中。
**差点据此写成「容器与宿主不一致」**。查证：那 2 个是
`/app/app/tokenizers/yi.model`、`gemma.model` —— **分词器二进制文件**，
含「态度」二字纯属巧合（中文词表）。

**教训**：容器 grep 命中后**必须先看是哪个文件**。`.model`/`.json`/图片等
非源码扩展名的命中一律不算逻辑证据。这条与 §一 1.2 同源：
**「命中」和「不存在」一样，都不能只看一个工作区。**

## 八、合并/覆盖类操作的三条铁律

本次把 palink-new 合并回主区，踩过的坑：

| # | 铁律 | 本次实例 |
|---|---|---|
| 8.1 | **不可逆操作前必做物理备份**（git bundle + 数据库 dump + 未提交 patch） | 已做，救回了整个合并 |
| 8.2 | **改数据契约后，「依赖旧契约建测试数据」的用例会集体变红，这是预期连带成本，不等于引入回归** | 34 个用例集体红 → 根因是测试 helper 没传 `character_id`；解法是改测试不是回退源码。判定法：同批测试在来源工作区是否绿 |
| 8.3 | **按清单改完必须再全仓 grep 一遍** | R5 清单记 4 处，实际 5 处（漏 `CharacterView.tsx:1348`） |

### 8.4 反向铁律：**别用文件清单打 tar 做全量备份**

HANDOFF §五① 记的是「用显式文件清单打包，漏了一批构建必需文件」，
但同一天的实际踩坑是**更早的那一版**：全量备份**用文件清单**打 tar，
同样会漏构建必需文件。

**正确口径**：全量备份要打**整个工作区**（`tar` 不带 pathspec，或 `git bundle` + 未跟踪文件全量），
不要用「我以为构建需要这些」的清单。清单法漏的是**你没想到的**，
而构建需要什么往往是历史遗留的意外组合。

⚠️ 这条与 `agents.md` 备份规范第 1 条并列：**备份区只认位置，备份方式也要认**。

## 九、反向证据：说「没有任何代码处理 X」之前，必须先排除这个文件

> **本节是 2026-10-03 晚新增。** 来源是 HANDOFF §二（问题②「说话前的态度分隔线」）
> —— 前述九节**没有任何一条覆盖它**，但它是当日最容易骗过人和 AI 的一类错误。

### 9.1 症状

排查一个「本该被系统处理、但用户看到了」的现象时，
用几个 grep 命中 0 得出结论：**「没有任何代码在处理它，它就是模型多输出的内容」**。
听起来无懈可击 —— 直到有人去读那个「看起来最不可能处理它」的文件。

### 9.2 实际案例（HANDOFF §二的四条反向证据，第三条是错的）

原文列了四条「反向证据」证明问题②与 TTS 无关：

| # | 它给的证据 | 复核结果 |
|---|---|---|
| 1 | 卡脚本里搜不到「态度」二字 | 属实，零命中 |
| 2 | 卡的 `extensions` 里也搜不到 | 属实，零命中 |
| 3 | **`tts_service.py` 里没有任何读情感/标签的逻辑** | ❌ **错**。`tts_service.py:190-209` 是一整张**角色→音色标签映射表**（"活泼"→`["lively","cheerful"]`、"旁白"→`["narrator"]`, `is_narrator: True`），且 `is_narrator` 在 `:769`/`:950`/`:979` 一路参与 `validate_role` 与合成参数 |
| 4 | 渲染层 `formatting.ts` 不剥离这类分隔线 | 属实 |

⚠️ **第 3 条是「用错了文件」而不是「结论错」**：
该文件里确实没有 `情感`/`情绪`/`emotion` 字样（实测零命中），
但它有**同义的**东西 —— 标签按语义分类的映射表。
**按关键词找证据，会漏掉换了说法的同一件事。**

### 9.3 为什么会发生

1. **关键词选得偏**。搜「情感」搜不到「标签」，搜「态度」搜不到「语气」。
2. **把「文件里没有这个词」当「这个文件不管这件事」**。
3. **反向证据天然显得更有说服力**。写「三条证据证明与我无关」比写「我怀疑是 TTS」容易得多，
   而**否证比证实更该被怀疑** —— 一次否证错误的代价是整个排查方向作废。

### 9.4 检查项（每条「与 X 无关」出结论前）

| # | 检查 | 命令 |
|---|---|---|
| 9.4.1 | 「无任何代码处理」的断言，用**同义词/近义概念**再搜一遍 | 除关键词外，搜同义命名（标签/语气/角色/风格/mood/tone/role…） |
| 9.4.2 | 断言某个文件「不管这件事」前，**打开读它的符号骨架**，不只 grep | `grep -n "^const \|^def \|^export function \|^class " <文件> \| head -30` |
| 9.4.3 | 「与 X 无关」的结论，必须列出**你排除了哪几条链路**，逐条给证据 | 人工核对，不接受「显然无关」 |
| 9.4.4 | 结论用「**X 处代码零命中**」表述，不用「没有任何代码」 | 措辞即口径，见 §三 3.3.4 |

**红线**：**「没有代码在处理 X」是本仓库最贵的一句话。**
它一旦写进交接文档，下一个 agent 会直接跳过这条链路不再看。
负向结论必须比正向结论**多做一轮**验证。

### 9.5 同源的第二例：§三 3.1 的教训

`setVariable`「完全不能用」错在只 grep 了一个文件；
9.4 错在只 grep 了一个词。**同一根因的两种表现**：
静态可达性分析只覆盖了你想到的那条路径。

⚠️ 补充口径：静态可达性**不能排除**运行时通道 ——
worker、动态 `import()`、字符串拼出的模块名（如沙箱的 `group-chats.js`）
都能让 grep 零命中而代码实际可达。**「grep 不到」只在穷举了注入点之后才成立。**

## 十之补、收尾门禁：**改完必须再跑一次，不许只跑开工前**（2026-10-16 立）

> **为什么单独立这条**：2026-10-15 S5 架构真机评估报告 §11.5 第 6 项自认
> 「门禁在**测试前**跑，**收尾未跑**」。该报告后来补跑了一次（三次零波动），
> 但**流程漏洞本身没堵上** —— 下一批有代码改动时，收尾不复跑就等于
> 「我改完的东西从没被完整验证过一次」。这与 §六 6.5「提交≠上线」同源：
> **中间跑绿 ≠ 收尾还绿。**

### 规则

| # | 要求 |
|---|---|
| 1 | 任何代码/文档改动完成后，**收尾必须重跑** `bash scripts/gate.sh`（或分端 `backend\|frontend\|docs`），把**原始输出**贴进交付记录 |
| 2 | 只认 `failed = 0` 且 `errors = 0`；`passed` 的数字不是验收线（随并行会话漂移） |
| 3 | 前端改动 ⇒ 收尾跑完还要确认 `frontend/dist` 已重建且容器服务新指纹（§六 6.4/6.5） |
| 4 | 动了 `docs/` ⇒ 收尾跑 `py scripts/docs/gen_docs_catalog.py --check`，必须 `OK` |
| 5 | **改过 `runtime-body/` 或 `frame-shim/`** ⇒ 收尾跑 `node scripts/verify-shim-identity.mjs`（字节同一性） |

### 反面教材（别再犯）

- 只跑开工前的门禁，交付记录写「门禁全绿」—— 中间可能被后续改动打破；
- 收尾只跑自己改的那个测试文件 —— AGENTS.md「判定修好了必须用与生产一致的入口」；
- 把收尾数字写成「与开工前一致」却拿不出原始输出（转述即造假，§六开头已定性）。
