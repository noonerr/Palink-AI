## 4. 系统性检查新发现（此前报告未提及）

### 🔴 P0（建议立即单独 hotfix）

#### N-1【P0·XSS】智能卡经 callGenericPopup 在主 origin 注入任意 HTML——完整沙箱逃逸链
- **链路**：恶意角色卡在 opaque-origin iframe 内执行（这是沙箱设计允许的）→ 调用 shim 的 `callGenericPopup({type:'display', message:'<img src=x onerror=…>'})` → SmartCardCompatController.ts:846-886 仅做 String() 转换即透传 → Popup.tsx:102-106 DISPLAY 分支：

```tsx
<div className="whitespace-pre-wrap"
  dangerouslySetInnerHTML={{ __html: text }} />   // text 未过 DOMPurify
```

→ onerror 在**主应用 origin** 执行任意 JS → 读取 localStorage.palink_token、以受害者身份调用全部 API。iframe 的 sandbox='allow-scripts' 隔离（CharacterCardRenderer P1-1 修复目标）被此通道完全绕过；st-plugin 兼容层 getContext.ts:1180/1787/1830 同类入口同受影响。
- **影响范围**：所有使用智能卡 iframe 渲染的角色卡（默认渲染路径）+ JWT 全量失窃风险（叠加 localStorage 存 token，见 N-8）。
- **建议**：Popup.tsx DISPLAY 分支与 SmartCardCompatController 入口统一套 DOMPurify.sanitize（项目已有 sanitizeHtml 参照实现，改动极小）；TEXT/CONFIRM 分支走 React 文本节点本已安全。

### 🟠 P1

#### N-2【P1·功能缺陷】WS 普通聊天路径 NameError——每次执行必失败
- websocket.py:164-176 `run_chat_generation` 签名无 `reasoning_effort/provider_id` 两形参，函数体内也无赋值；但 :326-327 直接引用：

```python
stream = stream_text_completion(..., reasoning_effort=reasoning_effort, provider_id=provider_id, ...)
```

→ 每次 `/api/ws/chat` 的 chat_request 到达此处抛 NameError，被外层 except 吞掉后客户端收 "Error: Internal error"。HTTP `/api/chat` 正常故不易察觉；对照 run_character_chat_generation(:528) 是有这两形参的。
- **影响范围**：WebSocket 普通聊天生成路径整体不可用（角色扮演主路径不受影响）。
- **建议**：补两形参并在 `_gen` 调用处从 raw 取值（参照 ：1458-1459 的解析）。

#### N-3【P1·性能】流式期间 smartCardChatMessages 每 chunk 新引用击穿全列表 memo
- CharacterChat.tsx:1292 useMemo 依赖 displayedMessages → 每个 SSE chunk 新数组引用 → :1815 作为 prop 下发 → Message.tsx:1601 memo 比较器引用比较失效 → 每条历史消息的 pipelineResult（三层正则全量执行，:837）与 parseContentSegments 重算；且 sanitizeStCompatHtml 位于 render 体而非 useMemo（Message.tsx:1288），每次重渲染裸跑 DOMPurify。
- **影响范围**：长会话（百条级）+ 多正则脚本的卡片，流式打字机阶段明显卡顿；编辑单条消息/切换会话同样触发全列表重解析。
- **建议**：①历史消息传"冻结快照 ref+版本号"，仅正则脚本集变化时更新；②sanitize 结果并入 pipelineResult 同一 useMemo；③smartCardChatMessages 拆稳定切片（仅最后 N 条参与实时更新）。

#### N-4【P1·凭据暴露】trusted-native iframe 保留 allow-same-origin
- CharacterCardRenderer.tsx:1075-1079：显式信任的卡获得 `allow-scripts allow-same-origin` → 卡内脚本可直读 parent.localStorage(JWT)，静默无告警。信任绑定 characterId+sourceFingerprint，但指纹稳定性与内容变更后的重新授权缺乏保证。
- **建议**：信任授予增加有效期与内容变更重确认；用 memoryStorage postMessage 代理（通道已存在）替代 allow-same-origin。
