## 2. 【P0】系统的正确性，锚定在一个"刻意保留的 bug"上

这是我见过最能说明"许愿式编程"的单一证据。位置：`backend/app/utils.py:472-481`。

### 原文照抄（项目自己的注释）

```python
# ⚠️ [TOKEN-口径 2026-10-09] `len // 2` 是**内部口径**，不是真实 token。
# 实测（p59，用上游 API 的 usage 对拍）：中文约 **0.66 token/字**，
# 而这里按 0.5 token/字算 ⇒ **低估约 1.37 倍**，即「设定 4000 实际注入
# 约 5490 真实 token」。**这是已知且刻意保留的**：
# 档位表 `_MEMORY_BUDGET_LEVEL_TOKENS` 的最优值（4000）就是在这个口径下
# 扫出来的（p55）。若把这里"修正"成真实口径而不动档位值，实际注入量会
# 从 5490 掉回 4000，等于把预算偷偷缩小 27% ⇒ **分数会退步**。
# 要改口径必须**同时**把档位值按 1.37 等比放大，二者是绑定的。
cost = len(text) // 2
```

### 这段话在说什么

- token 计数器是**错的**（低估 1.37 倍），项目**知道**
- 但它**不能修**，因为常量 `4000` 是在这个错误计数器下调出来的
- 一旦修正计量，效果会**退步**
- 所以：**保留 bug，让系统继续错着**

### 链条再往上一层的刻薄

那个 `4000` 是怎么来的？`roleplay_prompt_assembly.py:5111`：

```python
_MEMORY_BUDGET_LEVEL_TOKENS = (750, 4000, 6000, 8000)
```

其来源（见 `TODOS.md`）：**53 道题、LLM 自评打分、单会话单卡、未人工抽样**，  
得出 `0.698 vs 0.509，p=0.0024` ⇒ 选了 4000。

于是完整链条是：

> **53 题 LLM 打分 → 选定一个数字 → 该数字绑定在一个明知错误的计量口径上 →  
> 为了让这个数字继续"最优"，全系统必须永久保留这个计量 bug。**

### 判词

这不是工程决策，这是**把参数过拟合进了实验条件的噪声里，然后给噪声上锁**。

同一注释区还有两处自认错误：

- 「2026-10-09 订正：此处原写实测 2455~2709 tok，**该数字是错的**」（`MemoryService` 60 秒缓存污染）
- 「2026-10-10 订正：原写 1500」

以及 `TODOS.md` 里的「**否证**第 4 步」「**否证** 10-07 报告 §3」。

⇒ **结论的产出速度，长期快于结论的验证速度。**  
先落地，后打补丁，补丁以注释形式永久附着在代码上。

## 6.5 【P0】测试里的恒真断言：`assert X or True`（本次实测确认，至今未修）

上一轮审计（`2026-10-10.md` 记忆）列出 3 处，本轮**逐条开文件复核，全部属实**：

```python
# backend/tests/test_memory_entity_card_gate.py:412
assert "\n" not in card.split(...)[1].split("：",1)[1].split("\n")[0] or True
#                                                                    ^^^^^^^

# backend/tests/test_memory_semantic_store.py:246
assert "…" not in out.split("- Assistant: ")[1][:50] or True

# backend/tests/test_st_plugin_import.py:97
assert any(s["script_type"] == "regex" for s in detail.get("scripts", [])) or True
```

### 这意味着什么

`assert X or True` **恒为真**，无论 `X` 是真还是假。

- 第 1 处：本想断言「状态行不含换行」，实际**什么都不测**
- 第 2 处：本想断言「截断按句边界」，实际**什么都不测**
- 第 3 处：本想断言「插件含 regex 脚本」，实际**什么都不测**

**这三条断言在 pytest 输出里表现为三个绿色的 `.`。**  
它们和真正通过的 2006 条用例，**在门禁报告里完全无法区分**。

### 判词

> 这是「许愿式编程」最纯粹的形态：  
> **写下了验证的样子，跳过了验证的行为。**
>
> 一条恒真断言比没有断言更坏 ——  
> 没有断言，读者知道这里没验证；  
> 恒真断言，读者以为这里验证过了。
>
> 它让 `2006 passed` 这个数字里，混入了**无法分辨的水分**。  
> 而且这类断言的存在说明：**测试是被"写够数量"驱动产出的，不是被"验证行为"驱动产出的。**

⚠️ 这三处**至今仍在代码里未修**（上一轮已记录为待处置项）。

**代码里几乎不写 TODO，但文档里堆了 1901 行待办** —— 再次印证 §4。

## 8. 必须说清楚的反面（否则这份审计不诚实）

刻薄要刻薄在点上。以下四条，我实测后**必须为项目辩护**：

1. **代码质量本身不差。** 后端 2006 passed / 23 skipped / **0 failed / 0 errors**；  
   前端 tsc `--noEmit` 过 + vitest **810 passed / 3 skipped / 65 文件**。这是真实的绿。
2. **注释质量高于平均。** 能写出"这是已知且刻意保留的，改口径必须同时放大档位值"的人，  
   是真的推演过因果链的。§2 批判的是**结论**，不是**思考质量**。
3. **有真实可用的自纠机制。** `gate.sh` 会自己提示"大概率不是代码回归"；  
   `OPEN_ISSUES.md` 有 P0–P4 分级且区分「P2 优先级问题」与「P3 决定不做」；  
   文档里有大量"订正"。**有病但能自诊，比没病但麻木强。**
4. **容器编排是健康的。** 6 个容器全部 `Up (healthy)`，  
   后端/前端/DB/Ollama/隧道/new-api 都在跑，说明运维层是认真的。

## 9. 结论：关于"是不是许愿式编程"

| 指控 | 判定 | 依据 |
|---|---|---|
| 用文档代替实现 | **成立** | 文档 65,411 行 ≈ 后端代码 74,489 行；声称删除的 ST 仍存活 17,237 行 |
| 用状态声称代替验证 | **成立** | P0 标"已上线+待真机验收"；未提交+未验证+已进生产三者并存 |
| 用调参代替建模 | **成立** | 核心常量锚定在明知错误的计量口径上，且刻意不修 |
| 用纪律代替执行 | **成立** | 8 条验证纪律 vs 208 个未提交改动；门禁铁律在本机不可达 |
| 测试只是"看起来在测" | **成立** | 3 处 `assert X or True` 恒真断言（§6.5，实测确认，未修） |
| 代码本身是许愿式 | **不成立** | 2006+810 测试真实通过，注释推理链扎实，容器健康 |

### 最终判词

> **这个项目不是"许愿"，它是"记账"。**
>
> 它极其认真地记录了每一次决策、每一次订正、每一条纪律、每一个 P0 的来龙去脉 ——
> 认真到文档体量逼近代码体量。
>
> 但**记账不等于还债**。
> 208 个未提交改动、一个被刻意保留的计量 bug、
> 一个标着"已上线"却"待真机验收"的 P0、
> 一个在本机第一次跑就红的门禁 ——
> 这四件事，每一件都在文档里被写得清清楚楚，然后**每一件都还保持着原样**。
>
> 许愿式编程的特征不是"代码写不出来"，
> 而是**"把描述问题的工作，误当成了解决问题的工作"**。
> 本项目精确地命中了这个特征。
