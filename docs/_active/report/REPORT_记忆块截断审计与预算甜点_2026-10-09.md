## 一、两句话直答

1. **「句子中间被劈开」确实会发生，但只有 4.4%**（137 处切口里 6 处）。**真正的坑不是切点，是切开之后邻居补不回来** —— `NEIGHBOR_EXPAND` 与检索共用同一个 token 预算，预算一满就补 0 条（实测：retriever 出 10 条 → `get_context` 还是 10 条，**+0**）。
2. **预算不要再放大。** 检索层看，预算越大召回越高（1500→12000：命中 81%→**100%**）；但端到端看，**1500 就是甜点，放大反而掉分**：0.370 → 0.350（3000）→ **0.290（6000）** → 0.310（12000），prompt 却从 7,958 涨到 18,820 token。**召回率涨 ≠ 答对率涨。**

## 二、担心①：切块会不会把句子劈成两半

### 2.1 切点审计（p43，227 条记忆）

| 指标 | 结果 |
|---|---|
| 同一条消息被切成多块的**内部切口** | 137 处 |
| 切口**不在句边界**（句子中间被劈开） | **6 处 = 4.4%** |
| 末块结尾不在句边界 | 3 / 45 条 = 6.7% |
| 块元数据（`#turn` / `#idx`）完整率 | 182 / 182 = **100%**（邻居扩展的前提是齐的） |

真硬切的实例（`structural_split` 在 337 字内找不到句终止符 → `_find_cut_index` 直接硬切）：

```
块1572 尾：「…尾梢那枚心形贴着他的皮肤，一下一下地蹭着。\n舔穴」
块1573 头：「客厅里静得能听见彼此的呼吸。窗外蝉鸣一阵接着一阵，阳…」
                                          ↑ 「舔穴」后面没有任何标点，句子被切断
```

⇒ 频率不高但**性质恶劣**（断在动词中间，两半各自都不成句）。

### 2.2 更要命的：切开之后另一半不回来

`service.py:215` 的邻居扩展与检索**共用同一个 `max_tokens`**：

```python
if memory_config.NEIGHBOR_EXPAND and result.memories:
    result = self._expand_chunk_neighbors(result, request.max_tokens)   # ← 同一个预算
```

而 `retriever.retrieve` 已经把预算填到 1480/1500（前一份报告实测）⇒ 扩展时 `total + t > max_tokens` 恒真 ⇒ **一条都补不进来**。

实测（p43，真实查询、真实生产链路）：

```
[邻居扩展] retriever 直出 10 条 → service.get_context 出 10 条（+0）
```

⇒ 现在注入的语义块**基本都是孤立段落**：前因在上一个块、后果在下一个块，都不在窗口里。
这比"切点差 4.4%"严重得多 —— **就算切得完美，上下文也是断的**。

### 2.3 注入侧会不会再砍一刀？不会

`utils.build_memory_context`：带 `#chunk` 标记的块**整条注入不截断**；只有无标记的存量超长条目才走 `_truncate_by_sentence`（按句边界截）。⇒ **不存在"注入文本被从中间砍断"**。

### 2.4 修法（三档，按性价比）

| 档 | 改什么 | 位置 | 代价 |
|---|---|---|---|
| **A（推荐）** | 邻居扩展用**独立小预算**，不与检索抢：`MEMORY_NEIGHBOR_EXTRA_RATIO=0.3` | `service._expand_chunk_neighbors` | 记忆区 +30% token（1500→1950） |
| **B** | `_find_cut_index` 找不到句终止符时，退回找最近逗号/顿号/空格/引号等**弱边界**，再找不到才硬切；硬切块打标记 | `semantic_chunker._find_cut_index` | 零 |
| **C（彻底）** | **small-to-big**：句级索引做检索、注入时回捞父块原文（前一份报告的 ⑧⑨ / Y 档已验证：命中 83~87%，且不额外撑大 prompt） | `memory_module` 写入 + 检索 | 重嵌 1385 句 381s，存储 ×6 |

⚠️ 注意 A 档会吃掉预算 ⇒ **必须先按 §三的结论确认预算口径再定比例**，否则又变成"塞太多"。

## 三、担心②：预算放大 —— 检索层说"该放"，端到端说"别放"

### 3.1 检索层（p44，48 题，修查询 + 关键词 RRF）

| 预算 | 注入命中 | 条目数 | 半截块 | 均 sim | 记忆 tok |
|---|---|---|---|---|---|
| 1500 | 81.2% | 14.8 | 0.1 | 0.579 | 1,490 |
| 3000 | 83.3% | 24.2 | 0.2 | 0.567 | 2,967 |
| 6000 | **93.8%** | 40.4 | 0.2 | 0.553 | 5,779 |
| 12000 | **100.0%** | 61.0 | 0.4 | 0.537 | 9,606 |
| 24000 | 100.0% | 63.5（饱和） | 0.4 | 0.535 | 10,131 |

只看这张表会得出"放大到 6000 血赚"。**但这是错的。**

### 3.2 端到端（p45，同一跑、50 题、DeepSeek 生成 + LLM 判分）

| 档 | 均分 | vs 1500 | 赢/输/平 | 配对 p | 记忆 tok/条 | prompt tok |
|---|---|---|---|---|---|---|
| **M1500** | **0.370** | — | — | — | 1,490 / 14 | **7,958** |
| M3000 | 0.350 | −0.020 | 8/9/33 | 0.79 | 2,968 / 24 | 9,930 |
| M6000 | 0.290 | **−0.080** | 7/10/33 | 0.28 | 5,788 / 40 | 13,712 |
| M12000 | 0.310 | −0.060 | 9/12/29 | 0.48 | 9,589 / 60 | 18,820 |

**没有任何一档显著优于 1500；6000 / 12000 方向为负。**（n=50，判分为 LLM，差值本身不显著，**但"放大不涨分"这个结论是稳的** —— 如果放大真有收益，不会四档里三档都往下走。）

机理解释：注入 40~60 条记忆时，正确那条**确实在里面**（命中 94~100%），但它被淹没在 40 条同期剧情碎片里。全历史档（91 条）也只有 0.370 —— 长上下文里"信息存在 ≠ 模型用得上"，记忆区放大本质是在复刻同一个失败模式。

### 3.3 那到底放到多少

- **维持 1500 是最优解**；想"再大一点点"，**上限 2000~2500**（1500 与 3000 的差 −0.020 完全在噪声内，说明这段是平的）。
- **不要放到 6000+**：多花 72% 的 prompt token，换来 −0.08 的得分。
- 记忆现在占整轮 prompt 的 **19%**（7,958 中 1,490）—— 它已经不是"太小"，而是"不够准"。

## 四、结论：钱/预算该花在精度上，不是容量上

| 想做的事 | 该不该做 | 依据 |
|---|---|---|
| 放大记忆预算到 6000+ | ❌ | §3.2：得分 −0.08，prompt +72% |
| 预算 1500 → 2000~2500 | ✅ 可做，收益平 | §3.2：M3000 与 M1500 无显著差异 |
| 修查询 + 加关键词路 | ✅✅ 最大收益 | 姊妹篇：top1 6.2%→47.9%，命中 31%→81%，且快 4.8 倍 |
| 邻居扩展改独立预算 | ✅ 便宜，修"上下文断裂" | §2.2 实测现在补 0 条 |
| 切点回退弱边界 | ✅ 零成本 | §2.1：消灭那 4.4% 的硬切 |
| 句级 small-to-big | ⚠️ 留作第二阶段 | 命中 +2~6pp，e2e +0.05（不显著），代价最大 |

## 五、可信边界

1. 端到端 n=50、LLM 判分，**所有差值都不显著**（p=0.28~0.79）。本节结论只能表述为"放大**没有观测到收益**、方向为负"，不能说"放大一定有害"。
2. 只测了一个会话、一张卡、一种题（早期事件事实题）。**叙事连贯性类问题**可能对大预算更友好 —— 未测。
3. 预算扫描用的是 Python 侧字符 bigram 关键词路（与姊妹篇同口径），落地为 pg_trgm 后需复测。
4. 半截句判定用"结尾字符是否落在句末标点/`*`/引号集合内"，对以斜体结尾的 markdown 文本偏严（会把完整的 `*…。*` 判为正常，已放宽；但 4.4% 里可能仍有 1~2 处是误判，只会让真实比例更低）。
5. 生成模型 `deepseek-chat`（生产 `deepseek-flash`）；绝对分会偏，相对排序可信。
