## 批次 A：显示层语义保真（体感第一优先）

> 目标：ST 卡"一装就漏宏 / 显示错乱"两类问题根治。改动面小、无行为争议。

### A1【P1-1】正则 ESCAPED 改逐值转义（前端对齐后端）

- **问题**：`substituteRegex=2`（ESCAPED）时前端主链路先替换宏、再对**整个 findRegex** sanitize，模式本体 `()`+`\w` 全被转义 → 显示层必然失配；后端与智能卡是正确的逐值转义 → 前后端行为分裂。
- **ST 真值**：regex-engine.js:403-404 + script.js:2756-2758——只对**每个宏替换值**转义，模式本体不动。
- **方案**：
  1. `frontend/src/lib/regex-pipeline/pipeline.ts`（L294-296 附近）与 `frontend/src/lib/sillytavern/regex/engine.ts`（L255-257 附近）：改为在宏替换时对替换值逐个做 `escapeRegexReplacement` 式转义，删除对 findRegex 整串的 sanitize；
  2. 逐值转义工具函数直接照抄后端 `character_ext.py:1157-1163` 的语义（JS 侧已有 `{{match}}`→`$0` 的 escape 先例可复用）。
- **测试**：新增 `frontend/src/lib/__tests__/regex-escaped-contract.test.ts`（TDD 先红后绿）：substituteRegex=2 + 含分组/量词的 findRegex + `{{user}}` 替身 → 断言模式本体不被转义、替换值被转义；同时锁定智能卡 CompatRuntime 行为一致。
- **验收**：契约测试绿 + tsc 干净 + build；浏览器冒烟：构造 substituteRegex=2 的状态栏正则卡验证显示正常。

### A2【P1-2】宏命名兼容四件套 + 条件宏

- **问题**：`{{hasvar}}/{{hasglobalvar}}/{{deletevar}}/{{deleteglobalvar}}` Palink 用了 ST 不存在的名字（`{{exists}}/{{delvar}}`）→ ST 卡宏原样泄漏；`{{if}}/{{else}}` 条件块整体缺失；`{{group}}` 等群聊名单宏缺失。
- **ST 真值**：core-macros.js:134/:217（if/else）；variables 宏族命名以 ST macros definitions 为准。
- **方案**（`backend/app/services/macro_service.py`）：
  1. **命名别名（低成本，先做）**：注册 `{{hasvar}}/{{hasglobalvar}}`（存在性→"true"/"false"）、`{{deletevar}}/{{deleteglobalvar}}`（与现有 delvar 同实现）；
  2. **条件块（中成本）**：实现 `{{if <expr>}}...{{else}}...{{/if}}` 块级求值——在现有迭代求值前做块扫描（raw_content 捕获阶段已有块处理先例 `{{//注释}}` 可参照）；条件表达式支持 `getvar::x` 与字面量比较（对齐 ST 基础语义即可，不等价实现全部 JS 表达式）；
  3. **可选顺带**：`{{group}}/{{groupNotMuted}}`（群聊成员名单，装配上下文已有群成员数据）、`{{charDepthPrompt}}`（depth 队列已有数据源）——工作量小，建议同批。
- **测试**：`backend/tests/test_macro_st_aliases.py`：四别名 + if/else 真/假两分支 + 嵌套宏条件 + 未知宏不误伤；if 块在真实装配链路（build_character_chat_messages）生效的集成断言。
- **验收**：定向新测试 + 全量 pytest 0 failed；浏览器冒烟：导入含 `{{if}}` 的 ST 卡验证不泄漏。
- **注意**：`{{exists}}/{{delvar}}` 旧名保留（向后兼容存量卡），不删除。

## 批次 B：无分框模式消息交互补齐（体感第二优先）

> 目标：补齐 ST 最高频交互。**重要修正**：分框模式（NativeRoleplayChat.tsx L902/912）已有 swipe 箭头与删除，缺口仅在无分框模式（Message.tsx）。

### B1【P1-4a】消息编辑入口

- **现状**：后端 PUT /messages/{mid} 完整（含记忆镜像同步）；CharacterChat.tsx 已有 handleEditAt（L1347-1351）并传给 Message `onEdit`（L1908）；但 Message.tsx L685/686 将 `onEdit`/`canEdit` 解构为弃置 prop → 无触发点。
- **方案**（`Message.tsx`，局部 Edit 禁整写）：
  1. 消费 `onEdit`/`canEdit`：assistant/user 消息 hover 操作区新增"编辑"按钮（对齐 ST pen icon 位置）；
  2. 编辑态：正文区切换为 textarea + 保存/取消（对齐 ST Edit/Save/Cancel 三按钮语义）；保存调 `onEdit(newContent, messageId)`（链路已通）；
  3. memo 比较器 L1671 已含 onEdit，无需改；新增比较项（editing 状态）按现有模式补。
- **测试**：前端契约测试（编辑态出现/保存回调参数/取消不落库）。
- **风险**：Message.tsx 1700+ 行、memo 敏感——编辑态必须局部 state，不得破坏现有 memo 稳定性（参照 N-3 稳定切片经验）。

### B2【P1-4b】无分框模式 swipe 箭头

- **现状**：分框模式已有 handleSwipe(msg.id, 'prev'|'next')（L620）+ 左右箭头（L902/912，多候选时显示）；无分框模式 Message.tsx 无 swipe UI（实测 chevrons=0）。后端 PATCH /messages/{mid}/swipe 完整。
- **方案**：Message.tsx 对 `swipes.length > 1` 的消息（含开场白 greeting_swipes）在气泡下方渲染 `‹ 1/N ›` 计数条（样式对齐 NativeRoleplayChat 已有实现），点击回调由 CharacterChat.tsx 新增 handleSwipeAt 调 PATCH 端点并本地更新 swipes/swipe_id。
- **取舍说明（登记，不阻塞）**：ST 中 swipes=1 时箭头也可 roll 新候选（swipe right=生成）；Palink 该职责由「重新生成」按钮承担（regenerate=追加 swipe，语义见 E-3 拍板项）。本期只在多候选时显示箭头，与分框模式行为一致。
- **测试**：契约测试（多候选渲染计数/回调参数）+ 浏览器冒烟（Seraphina + 自造 alternate_greetings 卡）。

### B3【P2-9 前端半】隐藏/取消隐藏菜单项

- **方案**：消息操作区（或长按菜单）加 隐藏/取消隐藏 → PATCH is_hidden；隐藏消息半透明样式 + "显示隐藏消息"过滤开关（对齐 ST isHidden 视觉）。后端与装配过滤已就绪，纯前端。
