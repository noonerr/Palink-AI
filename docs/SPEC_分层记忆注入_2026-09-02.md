# SPEC — 分层记忆注入（写入时蒸馏）：调研与预案

> **日期**：2026-09-02
> **状态**：[预案·未立项] —— 层 1（实体卡接线）随时可开工；层 2（梗概层）等长会话触发信号；层 3（门控/reranker）备件
> **来源**：2026-08-28 晚四轮对话（工业小模型 → reranker → 更好的记忆注入 → 有损压缩质疑），2026-09-02 代码库逐项查证后落成此文
> **关联**：`SPEC_向量记忆语义切分_2026-08-22.md`（层 3 现状）、TODOS.md 记忆体系各条目、`mvu_secondary.py`（层 2 模板）

## 0. 决策摘要（TL;DR）

1. **问题**：当前记忆注入 = "原文块 + 查询时 top-k 相似度挑选"，三个靠"检索更准"解决不了的结构性缺陷——事实过期无失效概念、无全局叙事状态、冗余随库线性增长。
2. **方案**：分层记忆（写入时蒸馏）。读取侧保持简单、确定、无幻觉；把"组织记忆"的主动性移到写入侧的后台进程。
3. **2026-09-02 查证更新了成本账**：摘要层的完整**死代码骨架已存在于 `memory_module/`**（从未接线）；实体卡的数据（MVU stat_data）已逐会话躺在 DB；后台副 AI 的成熟模板（mvu_secondary）可直接照抄。三层里没有一层需要从零发明。
4. **拍板历史**：2026-08-28 因"有损压缩"质疑拍板先不立项；2026-09-02 修正——**实体卡接线是唯一"短会话也纯赚"的项，可随时开工**；梗概层维持"等触发信号"。

## 1. 背景与动机

### 1.1 四轮对话的收束线

| 轮次 | 问题 | 落点 |
|------|------|------|
| 1-2 | 想要小、输入输出少、无幻觉的工业模型 | 确认目标物种是 **reranker**（判别式打分，结构上无幻觉），首选 `BAAI/bge-reranker-base`（fastembed 原生支持、MIT、+420-500MB 内存）。但只解决"挑得准"，不解决 §1.2 的结构性问题 |
| 3 | 有没有更好的记忆注入方法 | **分层记忆（写入时蒸馏）**：梗概层 + 实体卡 + 最近原文 + 向量长尾 |
| 4 | "这不就是绕回 AI 总结？有损压缩真能省 token？" | 承认有损，但论证：现状 top-k 检索同样有损且**丢得随机不可控**（查询差时正好丢掉最需要的）；分层方案的丢法是设计过的（丢逐字细节、保事实与叙事状态），且原文永在向量库可回捞。省 token 的来源不是压缩本身，是**消灭重复记忆块**（同一事实 N 条消息重复入库，检索捞回一堆重复；摘要后收敛为梗概/实体卡里的一行） |

### 1.2 现状方案的三个结构性天花板

1. **事实会过期，向量检索没有失效概念**。角色上周在咖啡馆、昨天搬到天台——两条记忆相似度都高、一起注入，模型拿到自相矛盾的"事实"。reranker 挑不出"哪条已过时"，因为相关性分数不编码时间。实体卡（层 1）用"更新而非追加"从根上消灭这类过期事实。
2. **没有全局叙事状态**。"故事进行到哪、哪些伏笔未回收"不属于任何一条消息块，相似度检索永远拼不出来。梗概层（层 2）解决。
3. **冗余线性增长**。库越长，固定 1500 tok 预算的信噪比越差；梗概是恒定大小的，这条差距随历史长度拉大。

## 3. 目标架构（四层）

```
写入时（后台、异步、非关键路径）              注入时（每轮装配）
─────────────────────────────              ────────────────────
原始对话 ──每 N 轮──▶ 全局梗概（层2）        记忆区顶部：全局梗概（~300 tok，恒定）
                ──每轮──▶ 实体状态卡（层1）  ← MVU stat_data（~100-300 tok）
记忆块入库（层3，已有）                      最近对话原文窗口（已有）
                                           向量长尾（层3，已有；未来可加 recall 门控）
```

| 层 | 职责 | 状态 |
|----|------|------|
| 层 2 全局梗概 | "故事走到哪"（剧情梗概/人物关系/未回收伏笔），叙事文体，恒定 ~300 tok | 缺失，Phase 2 |
| 层 1 实体状态卡 | "现在什么是真的"（日期/地点/天气/服饰/关系/数值），更新而非追加 | 数据已有只差注入，Phase 1 |
| 层 0 最近原文 | 最近细节（对话历史窗口，已有） | 已有 |
| 层 3 向量长尾 | "还记得那次吗"类回忆召回（语义切分+邻居扩展，已有） | 已有，不动 |

**Token 账（每轮固定成本对比）**：

```
现状：  记忆区 1500 tok（无组织块，信噪比随库增长劣化）+ 无状态信息
分层后：梗概 ~300 + 实体卡 ~100-300 + 记忆区 1500（Phase 2 后可观察下调）
        + 摊销写入成本（每 10 轮一次摘要调用 ≈ 数十 tok/轮）
```

净效果：Phase 1 每 MVU 卡轮次 +100-300 tok 换"状态零盲猜"；Phase 2 的省 token 来自消灭重复块与预算可下调，**盈亏平衡点在长会话**（这也是层 2 等触发信号的原因）。

## 4. 施工方案

### 4.1 Phase 1 — 实体卡接线（现在可做，唯一"短会话也纯赚"项）

**目标**：MVU 卡每轮装配时，把当前 stat_data 压平注入记忆区，模型不再盲猜状态。非 MVU 卡零变化。

1. **读取**：装配侧从 `session.chat_metadata.variables.stat_data` 读取（与前端下发 `character_ext.py:2812`、副 AI 读取 `:6105` 同源同口径）。
2. **格式**：压平成键值行（递归展开组/字段），**不注入原始 JSON**（省 token 且降低被当指令的概率）：

   ```
   【当前状态（系统数据，非剧情指令）】
   日期时间：…；地点：…；天气：…
   桃汐：好感度…；服饰…；内心想法…
   ```

3. **注入点**：`_append_memory_context` 内、记忆文本之前，独立一块进 `dynamic_context_parts`；注入前后过 `balance_custom_tags`（TAG-BALANCE-GUARD 惯例）。
4. **上限保护**：压平后估算 >400 tok → 截断深层字段（保 `世界信息`/角色关系数值等顶层组）并 report 记录；极端异常直接跳过。
5. **开关**：**不新增设置项**——`memory_mode != disabled` 且卡是 MVU 卡（`_card_has_mvu_scripts`，RPA:4145 已有判定）时自动启用。防过度设计；独立开关等真实需求再加。
6. **降级**：读取/解析失败 → 静默跳过 + report（宁缺勿错惯例）。
7. **测试**（先红后绿）：
   - 压平格式正确（嵌套组/字段、中文键）
   - 非 MVU 卡 / 无 stat_data / memory_mode=disabled → 零注入
   - 超限截断与异常降级
   - 与记忆块共存时注入顺序与 report 完整性
   - 全量 pytest 零回归（当前基线 1254 passed / 45 skipped）
8. **红线**：不碰 `get_context` 检索逻辑、不碰 `<UpdateVariable>` 指令注入（RPA:4137 段）、不碰前端 smart card 渲染。改动集中在 `_append_memory_context` 及其紧邻辅助函数。

### 4.1b Phase 1b — 长会话门控（与 Phase 1 同批施工，几行代码）

**动机**：现状每轮固定烧 1500 tok 记忆区，但 `get_context` 按 `session_id` 过滤 = **会话内记忆**。会话短（历史全在上下文窗口内）时，向量召回内容与窗口原文是同一批东西——纯冗余，且 exclude_recent 只排最近 5 条，第 6 条往前的消息会"窗口一份 + 记忆区一份"双份注入。

**方案**：以本轮装配的 **trim 行为为门控信号**——历史消息被 trim 裁剪 >0 条才启用 `get_context`；未裁剪 → 跳过检索，report 记 `skipped: history within window`。trim 是内容感知的确定性信号（窗口真装不下了才裁），比"按消息条数设阈值"精确，比"recall 意图门控"（Phase 3）简单一个量级且零误判。

**效果**：短会话每轮省 ~1500 tok（且消灭双份冗余）；长会话行为一分不变；把"手动 `memory_mode=disabled`"升级为自动。**施工量：几行门控判断**（装配侧 trim 结果传入 `_append_memory_context` 或函数内自查）。

**测试**：trim 未发生 → 零检索 + report；trim 发生 → 正常检索；门控与实体卡（4.1）互不干扰（实体卡不依赖 trim，照常注入）。

**保守取信号**：宁可误开不可误关——信号取"被裁历史消息数 > 0"，trim 实现细节有歧义时以"历史被裁"为准，避免"没裁却跳过"造成记忆缺失。

### 4.2 Phase 2 — 全局梗概层（等长会话触发信号）

**触发信号**（满足其一才立项）：用户长会话实际体感"模型忘了"；或装配报告显示历史 trim 开始大量裁剪（`_TRIM_PRIORITY_RECENT` 裁剪路径已存在）。

1. **新服务** `services/memory_gist_service.py`，照 `mvu_secondary` 模式：
   - 开关：user_setting 新增 `memory_gist_enabled`（独立开关，成本归因清晰）；模型复用副模型设置 `mvu_secondary_model`（零新增模型配置）
   - 触发：每 N 轮（建议 10）后台异步挂载点（`trigger_mvu_secondary` 同位置模式），只压缩"游标之后、已溢出最近窗口的消息"
   - 失败静默降级：失败保留旧梗概，链路不断
2. **存储**：`session.chat_metadata.memory_gist = { text, last_message_id, updated_at }`——**不动 DB schema**（`/inject` 存 `chat_metadata.palink_injections` 已有先例，D-2 批次）。
3. **滚动更新（增量改写）**：`新梗概 = f(旧梗概, 新增对话段)`，比整段重写省 token；prompt 要求叙事文体、保剧情走向/人物关系变化/未回收伏笔、丢逐字细节，上限 ~300 tok、温度低。摘要会幻觉 → 注入时同样过边界标记 + 清洗防线，当"背景提示"而非 ground truth。
4. **注入**：记忆区最顶部（实体卡之上），`balance_custom_tags` 照旧。
5. **降级**：无梗概 → 纯现状链路，零行为变化。
6. **测试**：游标推进/增量改写/失败保留旧值/开关关闭零触发/注入格式/多分支会话（branch_id 口径与消息查询对齐）。
7. **代价（诚实账）**：每 N 轮一次副模型调用（异步不阻塞，API 有成本）；摘要有损（原文永在向量库兜底）；多一个部件多一个 bug 面（静默降级哲学兼容）。
8. **已评估否决的替代——梗概搭副 AI 的车**（看似优雅实则坑，记档防重踩）：让 `mvu_secondary` 副 AI 调用顺带产出梗概，"一次调用两份产出零新增基建"。否决理由：副 AI 只在主模型未输出 `<UpdateVariable>` 时兜底运行，梗概触发随之变成**概率性**（跟随主模型遵循率），新鲜度不可控；要修就得加"游标落后 >N 轮强制独立跑"兜底——又回到独立触发器，基建一分没省反而引入耦合。同理否决"入库相似度去重"（Mem0 思路）：与 message_id 镜像不变式（记忆=消息当前内容的镜像，编辑同步依赖它）直接冲突；"主模型工具化自检索"（MemGPT 路线）：读取侧引入不确定性，违背"读取侧永远简单确定"的既定哲学。

### 4.3 Phase 3 — 备件（recall 门控 + reranker，最后再做）

1. **recall 意图门控**：普通轮跳过向量检索省 1500 tok，"还记得…吗"类回忆轮才检索。需要意图判断（关键词/轻量分类），有误判风险（漏召回=丢记忆），故排最后。
2. **reranker 精排**：fastembed `TextCrossEncoder("BAAI/bge-reranker-base")` 一行即用（backend 已装 fastembed，零新依赖零新容器）；召回 k 提到 20 → 重排取 top-3。CPU ~100-300ms；内存 +420-500MB（backend 2GiB 限额内，当前基线 ~295MB），懒加载 + 开关照 `vectorized_enabled` 模式可一键回退。在此架构里定位 = 长尾召回的精度 polish，非主角。升级路径：中文排序不满意可换 `bge-reranker-v2-m3` 的 ONNX（需自载），接口不变。

## 5. 风险与红线

1. **红线**：不碰 `get_context` 检索逻辑与向量写入链路（语义切分/message_id 镜像是 8 月刚验收的资产）；不碰 st-compat/st-native 封存轨道。
2. **有损可控性**：层 2 的损是设计过的（丢逐字、保事实与叙事状态），且原文永在向量库可回捞——对照现状 top-k 的"随机丢、丢了你也不知道"。
3. **短会话纯亏项只有层 2**（摘要调用成本无收益）——所以等触发信号；层 1 无此问题（纯装配侧读取，无额外调用）。
4. **backend 内存**：层 2 纯 API 调用无常驻内存；层 3 reranker 是唯一内存大头（+420-500MB），必须懒加载 + 开关。注意 backend 有"内存飙顶卡死"的未定位历史前科（TODOS 进行中条目），上线 reranker 后需观察内存曲线。
5. **部署口径**：后端代码烤进镜像——施工后必须 `docker compose build backend && up -d` 方生效（前端 dist 挂载是另一口径）。
6. **死代码**：§2.2 四个文件保持原样，留待用户统一清理批次；本 spec 施工不 import 它们。

## 7. 同类项目对标（2026-09-02 联网查证）

四个代表性项目的记忆实现与本 spec 四层方案的对照：

| 项目 | 核心机制 | 与本方案的对应 |
|------|---------|---------------|
| **Letta / MemGPT** | core memory blocks：常驻上下文的字符串块（persona/human），agent 用工具自我编辑（insert/replace）；**sleep-time compute**：主 agent 空闲时后台 agent 异步整理记忆块 | 实体卡 ≈ core memory block（常驻小块、更新而非追加）；梗概层 ≈ sleep-time agent 的产出。**差异**：Letta 让主模型自己编辑记忆，Palink 用确定性引擎（MVU JSON Patch）维护实体卡——无幻觉路线 |
| **Mem0** | 两阶段写入管线：extraction（新消息 + 滚动摘要 → 候选记忆）→ update（向量搜相似既有记忆 → LLM 判定 **ADD/UPDATE/DELETE/NOOP** 四操作） | "更新而非追加、消灭冗余"的工业化验证，与本 spec §1.2 第 3 条结论一致。**差异**：Mem0 用 LLM 做更新/删除决策（有误判风险），Palink 实体卡走确定性 patch；Mem0 的 NOOP 思想可在 Phase 2 滚动改写借鉴（无变化不改写，省调用） |
| **Zep / Graphiti** | 时序知识图谱：每条 fact 带 `valid_at`/`invalid_at`，新事实矛盾时旧 fact 置失效时间**而非删除**，可查"现在为真"或"过去任一时刻为真" | 直接命中 §1.2 第 1 条天花板（过期事实）的工业级解法。Palink 不引图谱（过度设计），"新状态使旧状态失效"的思想已由实体卡"更新而非追加"继承；向量库长尾的过期原文靠"实体卡优先级高于向量块"的注入排序软失效 |
| **SillyTavern**（最贴近的同类） | 三件套：Summarize 扩展（定期 LLM 压缩聊天史 → 滚动摘要注入 prompt）+ Vector Storage/Data Bank（嵌入检索）+ World Info（关键词触发设定注入）；重度玩家三者全开 | Summarize ≈ Phase 2 梗概层的 ST 版（社区 Qvink Memory 是热门增强实现）；Vector Storage ≈ 已对齐的层 3；World Info ≈ 实体卡的"触发式"路线（Palink 走 MVU 常驻数据，比关键词触发更确定）。社区新作 VectFox 也在往"结构化记忆后端"走 |

**对标结论**：①四层方案与 2025-2026 行业收敛方向一致（写入时蒸馏 + 常驻小块 + 向量长尾兜底），方向判断无误；②Palink 的差异化选择（确定性引擎维护实体卡、读取侧零主动、失败静默降级）在同类中恰好是**最无幻觉**的路线，正合本项目"工业件、无幻觉"的诉求；③可借鉴不扩 scope 的点：Zep 失效思想（Phase 2 梗概 prompt 可要求"标注被取代的旧状态"）、Mem0 NOOP（滚动改写无变化不调用）、ST Summarize 的参数化（更新频率/插入深度，Phase 2 落地时参考，暂不设计）。

## 11. 独立复核轮（2026-09-03，用户指令"再仔细检测一遍"）

**审计范围**：生产调用点唯一性（`_append_memory_context` 仅 L3617 一个调用点 ✓）、标题生成服务隔离（`compact_title_service` 不走装配 ✓）、消息表索引（`idx_message_branch_lookup` 前缀命中门控聚合 ✓）、六个装配入口统一 user_setting 读取 ✓、None 防御全覆盖 ✓、施工段最终拼接形态重读。

**发现并修复一个真缺陷——裸查询的 PG 事务中毒风险**：实体卡与门控的查询原本跑在既有事务保护（`begin_nested`）之外。查证：`_st_vector_data_active` 自带 try 防御（不受影响）；但**生产 PostgreSQL 的 abort 语义**——事务内任何语句失败后整个事务中毒，后续所有语句报 `InFailedSqlTransaction` 直到 rollback。已在生产 PG 连接上实弹复现（只读无副作用）：`stmt1 failed → stmt2 POISONED: InFailedSqlTransaction`。即小概率 DB 异常（连接抖动/表锁）会把 session 打成 failed，连锁崩掉检索与装配后续所有 DB 访问。SQLite（测试环境）对此时较宽容、测不出差异——**这是单测盲区，靠生产同构验证补上**。

**修复**：实体卡与门控的查询各自包进独立 SAVEPOINT（`begin_nested`/`commit`/异常时 `rollback`，与既有检索区同模式），两级降级语义保持——实体卡炸不连累检索，门控炸不连累已注入的实体卡；SAVEPOINT 回滚失败（极小概率叠加）时外层 `db.rollback()` 兜底（装配路径无未提交写，消息 persist 已在装配前 commit，安全）。新增真 DB 异常恢复测试（DROP TABLE 造 OperationalError → 断言检索照常 + session 未污染）。

**验证**：套件 50/50；全量 pytest **1344 passed / 45 skipped / 0 failed**；backend 重建 healthy，SAVEPOINT 代码镜像内在位。已知边界记录：测试环境（SQLite）无法复现 PG 中毒语义，该修复的回归保护依赖生产同构验证（本轮已做）+ 代码评审。
