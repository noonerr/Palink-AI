# SPEC — 插件设置「按用户 × 角色卡」隔离适配方案

> **立档**：2026-10-04 · 触发：用户明确两条底线 + 一个目标
>
> - **底线一**：后端归属权必须属于我们自己，**不可能把 100% 后端权限交给插件**。
> - **底线二**：**按卡片和人物区分，按用户区分** —— 设置的作用域不是全局单例。
> - **目标**：插件很重要，运行要**尽可能趋近 SillyTavern**，适配度尽可能高，同时**规避基础风险**。
>
> **上位文档**：`docs/REPORT_插件设置冲突与100%适配可行性_2026-10-04.md`（冲突清单与可行性判定）
> **本 SPEC 回答**：既然红线是「控制权」，而作用域是解法 —— 那具体怎么落。

---

## 0. 一句话方案

> **给插件一个长得跟 ST 一模一样的设置对象（趋近 ST 的目标），但它的作用域是「这个用户的这张卡」，且写入的值经过一道钳制才生效（归属权与风险的底线）。**
>
> 形象说法：**给插件方向盘，但方向盘接在限速器上。**

---

## 1. 为什么「按卡隔离」恰好化解了那条红线

先复述红线（上位报告 §4.1）：插件「优化」面板会直接改写 `oai_settings.openai_max_context = 2000000`、`setLorebookSettings({...})`、`power_user.*`。

**为什么在 ST 里没问题、在 Palink 里是红线？**

| | SillyTavern | Palink |
|---|---|---|
| 形态 | **单用户**桌面/本地软件 | **多用户**服务端 |
| `oai_settings` 是谁的 | 就是这一个用户的 | 理论上会影响所有用户 |
| 改全局单例 | 改自己的东西，无害 | 改别人的东西 → 越权 |

→ **冲突的本质不是「插件想改参数」，而是「改动的作用域是全站」。**

**一旦把作用域改成「用户 × 角色卡」，性质就变了**：

| 项 | 全局单例（原） | 按卡作用域（新） |
|---|---|---|
| 污染半径 | 全站所有用户 | 这个人的这一张卡 |
| 性质 | 权限下放（不可接受） | **个性化配置**（完全可接受） |
| 与底线一冲突？ | ✅ 冲突 | ❌ 不冲突 |

> ⚠️ **但隔离本身不够**。即使只影响一张卡，`max_context = 2e6` 仍能打爆**这一个用户的这一次请求**；`recursive:true` + `max_recursion_steps:0` 仍可能让世界书递归卡死生成。所以隔离之外还要**三道闸**（§3）。

## 2. 四层模型：按风险分级，而不是一刀切

**核心原则：不按「能不能做」分，按「做错了代价多大」分。**

| 层 | 内容 | 风险 | 处置 | 说明 |
|---|---|---|---|---|
| **L1** | 纯数据设置：`extension_settings` / `chat_metadata` / 角色卡 `extensions` | 🟢 低 | **全开** | 只是数据，改坏了最多少数功能不生效 |
| **L2** | 生成参数：`chatCompletionSettings`（`oai_settings`）/ `powerUserSettings` | 🟡 中 | **影子副本 + 钳制** | 影响成本与稳定性，但不能完全不给（否则「趋近 ST」打折扣） |
| **L3** | 世界书参数：`getLorebookSettings` / `setLorebookSettings` | 🟡 中 | **scope 覆盖层 + 引擎硬底** | 递归/扫描深度要有不可逾越的上限 |
| **L4** | 结构性操作：角色/预设/人设/世界书条目 CRUD、`importRaw*`、`installExtension` | 🔴 高 | **不开放** | 与适配度无关，纯风险 |

## 3. 三道闸（缺一不可）

### 闸 1 · 作用域隔离

**复用现成的 `CharacterPluginStorage`**（2026-10-02 P2 已建，不是新建轮子）：

```
CharacterPluginStorage(character_id, ns, key, value) + user_id 冗余
```

它已经具备我们全部需要的安全性质（`backend/app/api/character.py:816/842`，`models/character_plugin_storage.py:15-48`）：

| 已有安全性质 | 位置 |
|---|---|
| 非本人角色返回 **404 而非 403**（防 id 探测） | `character.py:826-831` |
| **merge 语义**（不是整命名空间覆盖，防多端互抹） | `character.py:847-853` |
| `ns` / `key` / `value` / 每请求条数**四道限额** | `character.py:800-803`（16 / 512 / 256KB / 500） |
| 失败**静默降级**为纯本地，不让卡脚本崩 | `card-script-storage-sync.ts` |

**新增要求**：`user_id` **一律从 token 取**，绝不接受前端传参。

### 闸 2 · 写入钳制（clamp）

L2/L3 的写入**不直接生效**，先过一道钳制表（§5）。

**关键行为**：超出上限时**钳到上限并登记**，而不是
- ❌ 静默接受（等于放行）
- ❌ 静默丢弃（等于欺骗 —— 插件以为设成功了）

### 闸 3 · 引擎侧硬底

**无论插件设什么，Palink 引擎保留不可覆盖的下限/上限**（在 `worldbook_service` / 生成管线侧实现，不是前端能绕过的）。

例：世界书递归深度硬上限 N 层 —— 插件设 `max_recursion_steps: 0`（无限）时，实际按 N 执行。

## 4. L1 层怎么做（低风险，一次做完）

### 4.1 作用域键定义

```
scope = (user_id, character_id)          # 主作用域
ns    = 'local' | 'session' | <插件名>    # 命名空间，复用现有 ns 字段
```

回退顺序（读的时候）：`scope 值 → 用户级默认 → 系统默认`。插件只写 scope 层，**永远看不到全局层**。

### 4.2 挂载 facade（补上位报告 §5 的 #1/#2）

在经典轨把同一对象引用挂上去（**必须是引用不是拷贝**，否则 `_.set` 写不回去）：

```js
window.SillyTavern.extensionSettings = runtime.extensionSettings;
window.SillyTavern.saveSettingsDebounced = window.saveSettingsDebounced;
window.SillyTavern.chatMetadata = /* scope 化的 chat_metadata */;
window.SillyTavern.saveMetadata = /* ... */;
```

### 4.3 修那个 404（上位报告 §6）

`POST /api/plugins/runtime/settings` **后端不存在** → 设置写入是死路径。
新增时**内部走 `/api/settings/save` 已有的 namespace 级合并语义**（`silly_tavern.py:2246-2256`），避免整体覆盖破坏 ST iframe 轨。

### 4.4 顺手补的只读项

`getLorebookEntries` / `getCharLorebooks` / `getPresetNames` / `builtin`（缺口报告 A1/A3/A5/A6）—— 纯读/常量，零风险。

## 5. L2 层：生成参数「影子副本 + 钳制表」

### 5.1 机制

给插件一份**这张卡下的参数副本**（形状与 ST 的 `oai_settings` / `power_user` 一致）：

- **读**：插件看到的是 `scope 值 ?? Palink 默认值`
- **写**：值先进钳制表 → 再落 scope → 生成时按 scope 值执行
- **越界**：钳到边界 + `recordStubHit` 登记（**可见**，不静默）

### 5.2 钳制表（**数值待用户拍板**，此处给建议初值）

| 参数 | 插件可能设的值 | 建议钳制 | 理由 |
|---|---|---|---|
| `openai_max_context` / `max_context` | 2,000,000 | 上限 = min(用户套餐上限, 模型真实窗口) | 防单次请求打爆成本与超时 |
| `max_context_unlocked` | true | 接受，但**受上一行钳制** | 解锁不等于无上限 |
| `temperature` / `top_p` / `top_k` … | 任意 | 按类型钳到合法区间 | 防非法值导致 API 报错 |
| `custom_include_body` | 任意 JSON | **大小上限 + 键名白名单** | MVU 用这个做「额外模型解析」；防止注入任意请求体打到上游 |
| `chat_truncation` | 任意 | 上限 = 该会话消息总数 | 防负值/超大值把渲染搞崩 |
| `power_user.*` 布尔项 | 任意布尔 | 接受（作用域内） | 只影响这张卡的显示/渲染，代价可控 |

> ⚠️ `custom_include_body` 是**最需要盯的一项**：它的语义是「往发给模型的请求里塞任意字段」。即使作用域隔离，也应限制键名白名单 + 体积，否则等于给卡脚本开了「任意修改上游请求」的口子。

### 5.3 为什么这不算「交出控制权」

| 判据 | 全局方案（拒绝） | 本方案（接受） |
|---|---|---|
| 谁能被影响 | 全站用户 | 只有写这个设置的这张卡 |
| 上限谁定 | 插件定 | **我们定**（钳制表 + 引擎硬底） |
| 能不能绕过 | 不能（没有别的路径） | 不能（钳制在后端，前端无法绕过） |
| 出问题时 | 全站故障 | 单卡降级，可一键清该 scope |

## 6. L3 层：世界书参数

### 6.1 现状冲突（上位报告 §4.2）

ST 是**全局单例** `world_info_settings`；Palink 是**按条目**（`WorldBookStage.scan_depth` / `case_sensitive` / `match_whole_words`），且 `context_percentage` / `insertion_strategy` / `overflow_alert` **后端零命中**。

### 6.2 做法

新增一张 **scope 级世界书设置**（或复用 `CharacterPluginStorage` 的 `ns='lorebook_settings'`）：

- 存：按 `(user_id, character_id)` 存 ST 形状的那 13 个字段
- 读：`getLorebookSettings()` 直接返回它
- 生效：Palink 世界书引擎**按条目参数之外，叠一层 scope 覆盖**；**引擎侧保留递归/扫描硬上限**（闸 3）

### 6.3 上限建议

| 字段 | 硬上限建议 | 理由 |
|---|---|---|
| `max_recursion_steps` | 不可为「无限」，给固定 N | 防递归卡死生成 |
| `scan_depth` | 固定 N | 同上 |
| `budget_cap` | 受该用户 token 预算约束 | 成本控制 |
| `recursive` | 接受，但**受 `max_recursion_steps` 钳制** | 布尔无害，但组合起来有害 |

## 7. L4 层：明确不开放（写进文档防误补）

| 族 | 不开放理由 |
|---|---|
| 角色/预设/人设/世界书条目 **CRUD** | 数据源双写 + 不可逆无确认 |
| `importRaw*` | 任意数据写入 |
| `installExtension` / `uninstallExtension` … | **任意代码执行**，且本插件来源卡已不在库（上位报告 §9.12.3） |
| 跨 scope 读（A 卡读 B 卡设置） | 越权 |
| 全局层读写 | 与底线一直接冲突 |

**处置方式**：显式拒绝 + `recordStubHit` 登记（**可见地失败**），并在文档写明理由 —— 防止后续 agent 误以为遗漏而"顺手补上"。

## 8. 实施批次

### 批次 0 · 先装「仪表盘」（**建议最先做**）

> 理由：上位报告 §5.3② 指出经典轨**没有 Proxy 兜底**，未实现的 API 是裸 `undefined`，**不进 `__palinkCompatStats`**，谁也不知道插件到底缺什么。
> **没仪表盘，后面所有"补什么"都是拍脑袋。**

1. 经典轨加 Proxy 兜底（复用 iframe 轨的 `installTavernHelperCompatProxy` + `makeMissingApiFunction` + `recordStubHit`）
2. 验收：装完后 `window.__palinkCompatStats` 自动列出**这条插件真正缺什么、各缺几次**

### 批次 1 · L1 全开 + 修 404（低风险，一轮可完）

3. 挂 `SillyTavern.extensionSettings` / `saveSettingsDebounced` / `chatMetadata`（§4.2）
4. 新增 `POST /api/plugins/runtime/settings`（§4.3）
5. 设置按 `(user_id, character_id)` 落库（复用 `CharacterPluginStorage` 或新建 settings 表）
6. 补只读项 `getLorebookEntries` / `getCharLorebooks` / `getPresetNames` / `builtin`

### 批次 2 · L2 影子副本 + 钳制（需先拍板 §5.2 数值）

7. 实现 `chatCompletionSettings` / `powerUserSettings` 的 scope 副本
8. 钳制表落地（**后端实现，前端不可绕过**）
9. `custom_include_body` 键名白名单 + 体积上限

### 批次 3 · L3 世界书 scope

10. scope 级世界书设置存储
11. 引擎侧读 scope 值 + 硬上限（闸 3）

### 批次 4 · 收口

12. L4 拒绝清单落成代码 + 文档
13. 守卫测试（**行为断言，不是字符串断言** —— 见 `SOP_Agent交付自查清单.md` §七）
14. 建立「每装一个新插件跑一遍」的 checklist（面板出现 / 设置可存 / 动作可执行 / 无 console 404）

## 9. 验收口径

| # | 验收项 | 判据 |
|---|---|---|
| 1 | L1 设置可持久化 | 插件改设置 → 刷新 → **值还在** |
| 2 | 跨卡隔离 | A 卡设的值，切到 B 卡**看不到** |
| 3 | 跨用户隔离 | 换账号**看不到**他人设置；非本人角色返回 **404** |
| 4 | 钳制生效 | 插件设 `max_context=2e6` → 实际按上限执行，且 `__palinkCompatStats` **有登记** |
| 5 | 引擎硬底不可绕 | 前端怎么改都突破不了引擎上限 |
| 6 | 缺口可见 | `__palinkCompatStats` 能列出缺失项与次数 |
| 7 | 门禁 | `npx tsc --noEmit` exit 0；`npx vitest run` **failed = 0**；`py -3 -m pytest tests/ -q` **failed = 0** |
| 8 | 上线 | 改后端必 `docker compose build backend && up -d backend`；改前端必重建 dist 并**容器内 grep 校验新指纹**（`SOP_Agent交付自查清单.md` §6.4/6.5） |
