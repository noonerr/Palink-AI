## 一、鲁棒性评估：**C**

### 决定评级的两条（都在"外部环境不正常"这个命题上）

#### P0-1 三处 async 端点内**同步**调用 `embed_text`，阻塞整个事件循环

**证据（实测，已复核）**：
```python
# backend/app/api/memory.py:194  （async def vector_retrieve）
embedding = embed_text(body.query)          # 同步阻塞，未走 to_thread

# backend/app/api/silly_tavern.py:5275 / :5402  同样写法
```
**对照 —— 项目自己知道正确写法**：
```
backend/app/memory_module/storage.py:867
    embedding = await asyncio.to_thread(embed_text, content)
```

嵌入器本身是**同步**实现（`fastembed` 默认 CPU ONNX；Ollama 版是同步 httpx，超时 30s）。
**后果**：嵌入期间**独占事件循环**。若嵌入服务慢或挂，事件循环冻结最长 30s，期间**所有并发用户**的流式输出、心跳、WebSocket ping 全部停摆。默认 provider 也是同步 CPU 嵌入，**不是边缘场景**。

#### P0-2 `OllamaEmbedder` 的维度字段无锁并发写

**证据（实测代码 / 后果推断）**：`memory_module/embedder.py:280/277-279/252/286-288`
单例被 `asyncio.to_thread` 多线程并发调用；去重缓存**有**锁（`:374`），但 `self._dimension` / `self._degraded_dim` 自身状态**没有**。
**后果（推断）**：降级线程与恢复线程交错时 `dimension` 可能读到不一致值，极端情况写入维度错配向量。

### P1（高）

| # | 问题 | 证据 |
|---|---|---|
| P1-1 | 流式 LLM 固定 `timeout=30.0` 且**主生成路径无重试**。推理模型首 token 前思考 >30s 即中断整轮 | `character_ext.py:5054/5908`、`chat.py:365`、`websocket.py:353/1016`；`inference_dispatcher.py:19` 默认值 → `llm_client.py:19-33` 直达 `AsyncOpenAI(timeout=30.0)` |
| P1-2 | 后台 fire-and-forget 任务不持引用、无 `done_callback`，异常丢失 | `character_ext.py:3422/6797`、`sessions.py:335`、`smart_card_assets.py:394`、`storage.py:678`。**项目内已有正确范式**（`worldbook.py:75-77` 用集合持有） |
| P1-3 | `smart_card_assets._cache_locks` 按 URL 无界增长，从不清除 | `smart_card_assets.py:77` + `:639-643`（同文件 `_prefetch_source_fingerprints` 反而有 512 上限） |

### 查了、确认**没问题**的项（这部分相当扎实）

- **超时**：抽查所有 `httpx.Client/AsyncClient` **均带 timeout**（web_search 15s / mcp 15s / tts 30-90s / image 10-120s / oauth 30s）。无裸请求。
- **降级链**：Ollama 失败 → fastembed → SimpleHash，并暴露 `_degraded_dim` 拒绝写坏向量；web_search 失败返回 `[]`；MCP 失败返回结构化错误。
- **并发原语**：`WebSocketManager` 全套 `asyncio.Lock` + 心跳清理；`provider_registry` 有 `threading.Lock`；`TTLCache` 有锁 + generation 防脏重填；`llm_client` 缓存有锁。**未发现未保护的可变全局状态被多线程写**（P0-2 的嵌入器维度字段除外）。
- **重试退避**：`inference_queue` 指数退避、`storage._async_update_embedding` 线性退避上限 3、`search_rotator` 多引擎重试。**未发现无退避忙重试或无限重试**。
- **资源释放**：LLM 流 `finally: await stream.close()`；MCP `exit_stack.aclose()`；llm_client LRU 淘汰并关闭。
- **事务**：`chat.py persist_snapshot` 每快照 commit + 异常 rollback；记忆镜像走独立事务 + CAS。
- **边界**：除零点均有守卫；上传大小限制遍布 6 处。
- **SSRF**：`web_search._is_safe_search_url` 含私网/回环/DNS 校验。

**为什么是 C 而不是 D**：外部依赖失败大多有明确兜底，不存在"一崩全崩"。**为什么不是 B**：P0-1/P0-2 恰好落在本评估的命题上——嵌入服务抖动时一个请求冻结全站。

## 四、本次评估的**新发现**（前一轮审计未捕获）

### 4.1 测试全绿时退出码也可能是 1（本机假红）

```
tests = 2029 | passed = 2006 | failed = 0 | errors = 0 | skipped = 23
EXIT = 1
```
**原因**：安全删除守卫在 pytest **收尾清理临时目录**时命中并抛 `SystemExit`：
```
[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":59,"threshold":50,"scope":"turn",
 "targets":["\\\\?\\C:\\Users\\Pall\\AppData\\Local\\Temp\\pytest-of-Pall\\garbage-..."]}
```

**这一条同时证伪并证实了两件事**：
- **证实** `SPEC` 订正 5.2 的结论：「`--basetemp` 落在**仓库外**就安全」**不成立** ——
  本次 target 是**系统 Temp（仓库外）**，照样被拦。守卫是「单次批量删除 ≥50 文件」，**与路径无关**。
- **证伪** 我先前"守卫命中 ⇒ 84 errors"的笼统表述：**守卫在哪命中决定后果** ——
  在**测试执行期间**命中 → 污染后续用例（gate3 的 84 errors）；
  在**收尾清理阶段**命中 → 结果完好，**只是退出码变 1**。

**直接后果（需处理）**：本机 `bash scripts/gate.sh backend` 会**假红**（退出码非 0 但测试全过）。
GitHub Actions 上无此守卫，**CI 不受影响**。→ 见 §六.4。
