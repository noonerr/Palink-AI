## 0. 背景与威胁模型

| 编号 | 一句话 | 泄漏/越权半径 |
|------|--------|--------------|
| N-6 | openai_compat 的 service_key 分支允许经未签名 `X-Palink-User-Id` 头冒充任意用户（缺省回退 admin） | SERVICE_KEY 泄漏 = 全站任意身份接管 |

## 1. N-6【P2·认证边界】service_key 用户头改 HMAC 签名

### 现状（openai_compat.py:92-129 实证）

```python
if service_key and token == service_key:
    header_user_id = request.headers.get("X-Palink-User-Id") ...
    if uid: return 按 uid 查到的用户      # ← 未签名，可任意声明
    ...回退 admin
```

### 方案：HMAC-SHA256 签名头（推荐，兼容现有 sidecar 渐进升级）

**规则**：
1. 当请求带 `X-Palink-User-Id` 头时，**必须**同时携带
   `X-Palink-User-Sig: hex(hmac_sha256(key=SERVICE_KEY, msg=f"palink-user:{uid}"))`
   ——签名不匹配 → 该头视为伪造，**忽略并记 warning**，落入无头回退路径（admin），不返回 403（避免给攻击者探测信号）
2. 不带头 → 维持现状回退 admin（向后兼容直连调用）
3. `SERVICE_KEY` 未配置 → 整个 service_key 分支天然不可达（现状即如此），无需额外处理

**改动点**：
- 后端 `openai_compat.py` get_openai_compat_user：uid 解析成功后校验 Sig 头（`hmac.compare_digest` 防时序）
- sidecar 注入侧：ST 容器转发处同步计算并携带 Sig 头（定位 `PALINK_ST_NATIVE_USER_HEADER_ENABLED` 相关注入代码，仓库内 grep `X-Palink-User-Id` 全链路）
- 新增常量/工具函数放 `app/core/security.py`：`sign_service_user_id(uid) -> str` 与 `verify_service_user_id(uid, sig) -> bool`

### 测试要求

- 正确签名 → 身份解析成功
- 错误签名 / 缺签名带头 → 忽略头、回退 admin、日志有 warning
- 无头 → 回退 admin（回归）
- 时序安全：使用 compare_digest（代码审查项）

## 2. N-7【P2·凭据暴露】附件 URL 去主 JWT 化

### 现状

- `frontend/src/lib/uploadUrls.ts`：`appendUploadToken` 把**主 JWT**拼进附件 URL query（12 个调用点：ImageViewer/ImageLightbox/MarkdownRenderer/ImageGenerationManagementTab 等）
- `MarkdownRenderer.tsx:158`：把带 token 的 URL 写入 `<a href>`——用户复制/导出消息即把长效凭据泄漏到聊天记录之外
- 服务端 `_verify_upload_access`（main.py:307）：接受该 query token（N-14 黑名单检查已补）

### 方案：专用短时效上传令牌替换主 JWT（两阶段）

**阶段一（本批次实施）**：
1. 新端点 `POST /api/uploads/token`（get_current_user 认证）→ 返回
   `{ token, expires_in }`：专用 JWT，claims `{"sub": username, "scope": "upload", "exp": now+300}`（5 分钟），**不带长 exp**
2. `_verify_upload_access` 校验逻辑增加：`payload.get("scope") == "upload"` 强制检查（主 JWT 无此 claim，直接拒绝——主 JWT 从此不该出现在附件 URL）
3. 前端 `appendUploadToken` 改为异步获取短令牌：图片 URL 构造改为
   `getUploadUrl(path)` 异步函数——先取短令牌再拼 URL；调用点逐个适配（12 处，多为 `<img src>` 场景可接受一次性获取）
4. **MarkdownRenderer.tsx `<a href>` 特殊处理**：链接展示用**去 token 的裸路径**
   （点击行为改为复制原始路径或走 ImageViewer 打开），绝不在 href 中携带任何 token
5. 兼容窗口：服务端同时接受旧主 JWT（无 scope 检查回退）一个版本周期？——**不接受**。
   存量聊天里的历史图片 URL 会失效（5 分钟后全部过期），但 `<img>` 由前端重新构造
   URL 渲染（MarkdownRenderer/ImageViewer 都在前端动态拼 URL），因此实际影响 =
   仅"外部直接粘贴出去的旧链接失效"，这正是本修复目的。前端渲染链路不受影响。

**阶段二（可选优化，另行排期）**：`<img>` 改走 Cookie 认证彻底去 query。

### 测试要求

- `/api/uploads/token`：认证后返回 upload-scope 短令牌；解码断言 scope/exp
- `_verify_upload_access`：upload 令牌通过；主 JWT（无 scope）401；黑名单 401（N-14 回归）
- MarkdownRenderer：生成的 `<a href>` 不含 `token=` 子串（正则断言）
- 前端 tsc + build 通过；12 个调用点逐一列明适配方式

## 3. N-8【架构级·设计先行】JWT localStorage → HttpOnly Cookie

### 结论

**本批次不实施**。这是跨全前端的认证体系迁移（19 处读取、登录/登出/刷新/CSRF 全链路），必须单独立项。此处固化设计决策供后续细化：

1. **双轨过渡**：新增 `/api/auth/token-cookie` 设置 HttpOnly+Secure+SameSite=Lax 刷新 Cookie；
   前端 api.ts 保留 Authorization 头作为过渡期兼容，Cookie 就绪后逐步移除 localStorage 直读
2. **CSRF 配套**：Cookie 启用后所有 mutating 端点要求 `X-CSRF-Token`（登录时下发，
   sessionStorage 存放——CSRF token 可被读不构成威胁，因为它必须配同源 Cookie 使用）
3. **短期止血（可并入任意近期批次）**：ACCESS_TOKEN_EXPIRE 默认值缩短 +
   登录轮换 jti（auth.py 已有黑名单基建，登出已拉黑）
4. **验收锚点**：`localStorage.getItem('palink_token')` 全仓 grep 归零；
   XSS 演习脚本无法读到任何长效凭据
