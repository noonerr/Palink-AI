# SPEC — 图像生成与语音播放接线（媒体模型对齐 ST + 占位收敛）

> 版本：2026-09-23　作者：Qoder（本 agent）

## 0. 这份 SPEC 的边界

本 SPEC 只解决一件事：**把已经存在但断开的线接上**，让图像生成与语音播放在第一方界面真正可用。

不包含：新的出图算法、新的服务商接入、提示词工程、图片编辑/局部重绘、声音克隆的产品化。

**为什么强调"接线"而不是"新建"**：调查结论是后端异步推送链路、事件消费、extra 媒体白名单、ST 兼容 getContext 实现**全部已存在且能跑**，缺的集中在前端渲染层和一处数据模型选择。把它当新功能从零设计会造成第三套重复实现。

---

## 1. 目标与非目标

### 目标

- G1　用户能在消息上点一下就让这条消息配图，**生成期间有占位、完成后原位替换**，正文不被污染。
- G2　媒体落到 `extra.media`，对齐 ST 数据模型，支持一条消息多图与左右切换。
- G3　同一套渲染组件让 **ST 官方出图插件（`st-plugins/stable-diffusion/`）可用**，把它的自动出图/换图/画廊交互白捡进来。
- G4　语音按用户方案实现：**点击才请求**，默认不生成；带加载态、单例互斥、本地缓存。
- G5　模型自主出图有明确路径，且**复用生成拦截器**而不是新造工具协议。
- G6　把本次调查用的「假上游」手法固化成正式契约测试，补掉 TTS/图像这两块零覆盖区。

### 非目标（明确排除）

- 不做真·流式渐进出图。上游给不了：SD WebUI 的 `txt2img` 是同步一把梭（实测 `image_generation_service.py:516` 直接 POST 等回包）；`partial_images` 是 OpenAI gpt-image 系独有能力。见 §5.1。
- 不做图片历史迁移。老消息正文里的 markdown 图片保持原样渲染，不回填。见 §5.2。
- 不做声音克隆的产品化入口（后端 `/api/tts/clone-samples` 已可用，本 SPEC 不动）。
- 不在本 SPEC 内修前端 vitest 基建（另立议题，见 §5.3）。

## 3. 核心设计决策

### D1　媒体从正文迁到 `extra.media`，正文只留一个可选锚点

采用 ST 的模型：图片是消息的**侧挂数组**，不是正文文本。理由不是"像 ST"，而是 B2 那个做法有四个必然故障：编辑消息会把图片标记弄丢或弄脏、重复生成会往正文堆多份、无法一条消息多图、删除图片要改文本。

迁移动作：`extra.media[]` 承载，正文**不再被改写**。`A2` 现有消费逻辑改为写 `extra.media` 而不是 `content`。

### D2　一个渲染组件，两个消费方

`MessageMedia` 负责 pending 骨架 / ready 图 / failed 重试 / 多图切换 / 点击放大。

两个消费方：① 第一方消息组件在正文下方渲染它；② `sandbox.ts:4675` 的空函数改成「写该消息的 `extra.media` 并触发重渲染」。

**第 ② 点是整个方案里性价比最高的一招**：它让 221 KB 的 ST 官方出图插件从"静默失败"变成可用，其自动出图、swipe 换图、画廊模式全部白捡，不需要我们自己设计这些交互。

### D3　占位用「乐观插入 + 事件收敛」，不引入任务表

点击 → 本地立刻往该消息 `extra.media` 插一个 `status:"pending"` 项（零网络等待就有占位）→ 后端完成后走**已存在**的 `message_image_generated` 推送 → 前端按 `message_id` 把 pending 收敛成 ready。失败同理收敛成 failed。

**为什么不加任务表**：现有 SSE 已按 `message_id` 定位，粒度天然匹配；引入 `task_id` 是把 A1+A2 已经解决的问题重新复杂化。

**唯一需要补的状态收敛**：页面刷新/断线会让 pending 悬挂。规则——`pending` 且 `created_at` 超过 `timeout_seconds`（默认 120）视为 `failed`，前端渲染时判定，不写库。

### D4　模型自主出图走生成拦截器，不新造工具协议

项目已有 `generate_interceptor` 且前后端桥接完整（A10），而 ST 的 SD 插件正是靠它实现"回复里带触发词 → 生成 → 替换"。

所以第一方的"模型自己决定出图"**复用同一条通道**：约定标记（建议 `<img_prompt>...</img_prompt>`），后端在持久化前解析 → 异步生成 → 写 `extra.media` → 推事件。

好处是模型侧只学一个标记，且与插件走同一条路，一次实现两处受益。**不要**去实现 OpenAI Responses 那种内建 `image_generation` 工具——我们走网关/远端模型，没有那个平台能力，自己造只会得到第四套协议。

### D5　语音只做一个入口，且必须点击触发

按用户既定方案：点击才请求。这不只是偏好——后端本来就是按需合成（A8），而且浏览器禁止非用户手势的自动播放，移动端自动播会直接哑掉。

四个必备件：
- **单例播放器**：同一时刻只播一条，点第二条自动停第一条。
- **按 `message_id` 缓存 blob**：二次点击不再请求。理由实测过——900 字要 48 秒、11 MB；且 `/api/tts/audio` 挂了频率限制（`tts.py:401 enforce_rate_limit`），连点会吃 429。
- **三态 UI**：空闲 / 加载中转圈 / 播放中。加载态必须有，因为延迟量级已实测。
- **收敛成一份客户端**：B6 有三份重复（306 + 36 + 410 行），保留一份、删其余。

### D6　B8 顺手改成明确报错

未配置时返回 4xx 带原因，而不是 200 + 空数组。否则插件侧和用户都只能看到"点了没反应"。

## 6. `extra.media` 数据契约

```jsonc
// message.extra（Text 列，JSON）
{
  "media": [
    {
      "id": "m_0f3a…",              // 本地生成，pending 期即存在，用于事件收敛定位
      "status": "pending",           // pending | ready | failed
      "url": null,                   // ready 后为 /api/uploads/generated-images/<uuid>.png
      "width": 1024, "height": 1024, // 占位期即写，保证骨架不跳版
      "prompt": "…",                 // 上游实际收到的提示词，便于排障与重抽
      "seed": -1,
      "provider_id": "sd_webui",
      "error": null,                 // failed 原因
      "created_at": "2026-09-23T…"   // 超时收敛依据
    }
  ],
  "media_index": 0,                  // 当前展示项
  "media_display": "inline"          // inline | gallery（对齐 ST）
}
```

三条硬约束：
1. `url` **只存本地路径**，绝不存上游 URL。依据：实测国内服务商链接 24 小时过期。
2. `id` 由我方生成，不用上游 id，保证 pending 期就能定位。
3. 字段名与 ST 对齐（`media` / `media_index` / `media_display`），因为 `character_ext.py:224-226` 白名单和 `getContext.ts:2586` 已经是这套名字——对齐能让插件和第一方共用一条写入路径。

## 8. 风险矩阵与回滚

| 风险 | 影响 | 概率 | 缓解 |
|---|---|---|---|
| 改 `message_image_generated` 载荷破坏旧前端 | 出图后不更新 | 中 | 新增 `media` 字段而非替换 `content`；前端优先读新、降级读旧，保留一个版本周期 |

| pending 永不收敛 | 界面永久骨架 | 高 | §D3 超时判定 + P1 验收第 4 条强制覆盖 |
| P2 发现插件还差多个接口 | 工期膨胀 | 中 | P2.1 先实测再决定；最差情况下 P1 已独立交付价值，不被 P2 拖累 |

**回滚**：P0/P1/P2/P3 分别独立可回滚。P1 的关键开关是「新消息是否写 `extra.media`」——建议加一个配置项 `media_in_extra_enabled`，关闭即退回 markdown 追加路径，前端 `MessageMedia` 因无数据自然不渲染，无需回滚代码。
