## 3. 实弹攻击记录

### 3.1 🔴 凭据暴露实锤（对应静态报告 P1-1，现已从"理论"升级为"已利用"）

```
POST /api/token  username=st_audit_2026 password=[旧值已轮换·脱敏]   → 200（会话+双 Cookie 下发）
POST /api/token  username=fv_browser   password=[旧值已轮换·脱敏]     → 200
```
- 两个凭据分别来自**仓库脚本**（`scripts/st_audit/audit_api.py:11`、`compare_worldbook.py:8`）与 **TODOS.md 正文**，且分支已推 GitHub。JWT 解码可见 `role":"user"`——都是普通用户，未直接拿到管理员，但足以开展后续所有普通用户面攻击（本轮越权验证即用它完成）。
- Cookie 属性顺带核实：`palink_session` = HttpOnly + SameSite=lax + Max-Age 12h（合规），**无 Secure 标志**（本地 HTTP 部署下无解，上 HTTPS 时应加）；`palink_csrf` 非 HttpOnly（双提交设计使然）。

### 3.2 认证与角色防线（全绿）

- 未认证 GET `/api/users/me`、`/api/admin/users`、`/api/roleplay/context-templates` → 全 401。
- 普通用户（st_audit_2026）打 `GET /api/admin/users` → 403；`PUT /api/image/config`（get_admin）→ 403。
- 结论：`get_current_user` / `get_admin` 分层与 jti 黑名单在运行时真实生效。

### 3.3 🔴 水平越权实锤：context_templates（对应静态报告 P1-2，已利用证实）

以 fv_browser 创建测试模板（id=5）→ 以 st_audit_2026（另一账号）操作：

```
PUT    /api/roleplay/context-templates/5   → 200（display_name 被改为"被跨账号修改"）
DELETE /api/roleplay/context-templates/5   → 200 {"ok":true}（跨账号删除成功，测试产物已清）
DELETE /api/roleplay/context-templates/3（内置）→ 400 "Built-in context templates cannot be deleted" ✓
```
- 影响面：任意登录用户可改删**全部**非内置 context 模板（该表无属主字段，全局共享），PUT 同样无收口。多用户部署下 = 任一普通用户可篡改他人的装配模板（进而影响所有使用该模板的对话的提示词装配）。
- 对照组：`instruct_templates` 删除有完整属主校验（user_id 比对 + 系统预设保护）、`image_generation` 配置读有密钥掩码 + 写走 get_admin——**同族端点只有 context_templates 漏了**，属单点遗漏而非系统性缺失。

### 3.4 🟠 CSRF 纵深缺口（C3）：外站 Origin + 有效令牌 → 放行

中间件代码核实（`backend/app/main.py` csrf_protection_middleware）：强制区通过条件为 **OR 语义**——(a) 双提交配对 **或** (b) 同源 Origin。Origin 只在令牌缺失时作为兜底，**从不独立拒绝**：

```
C1 会话Cookie+无令牌+无Origin          → 403 ✓
C2 会话Cookie+无令牌+外站Origin        → 403 ✓
C3 会话Cookie+有效令牌+外站Origin      → 200 ← 缺口（令牌配对分支放行，Origin 未审）
C4 同源Origin+有效令牌                 → 200 ✓（正常路径）
C6 缺csrf cookie的会话                 → 响应自动补发 palink_csrf ✓（N8-d 自愈在位）
```
- 可利用性评估：**低-中**。现代浏览器 SameSite=lax 使跨站 POST 不携带会话 cookie，C3 需要攻击者同时窃得会话+令牌配对值（如子域 XSS、恶意 WebView 不执行 SameSite 的场景）才有意义。定性：纵深削弱，不是可直接利用的 CSRF。
- **修复属"不碰 ST 面"的安全动作**（见 §5.2），但注意保持端点级 csrf_guard 与全局中间件口径一致。

### 3.5 上传服务：任意文件读取与跨用户读取——全部未遂

以真实 upload-scope 令牌 + `--path-as-is` 六种变体实弹：

| 变体 | 结果 | 拦截层 |
|---|---|---|
| `..%2f..%2f..%2f..%2fdocker-compose.yml` | 400 | **nginx 前置拒绝** |
| `..%5c..%5c..%5c...`（反斜杠） | 403 | nginx / 后端 realpath |
| `sub%2f..%2f..%2f...main.py`（混合） | 404（路由未匹配） | 后端 |
| `%2e%2e%2f...` 绝对化编码 | 404（路由未匹配） | 后端 |
| 跨用户 `/api/uploads/999/x.png`、`/api/uploads/1/anything.png` | 404 | 后端用户目录隔离 |
| 自目录不存在文件（sanity） | 404 "File not found" | 认证通过后正常业务 404 |
| 主 JWT 当附件令牌 | 401 "Invalid upload token scope" | N-7 scope 强制 ✓ |

- 两个 layer 的"巧合"值得表扬：nginx 对 `../` 样式路径直接 400，漏过去的畸形被后端 `_safe_serve_upload` 的 realpath+前缀包容拦住。**未读取到任何文件**。
- 注：曾出现一次 200 假阳性，实为 nginx 把畸形路径回落到 SPA index.html（响应 5,178 字节页面壳），非文件泄露。

### 3.6 ST 适配面（[ST-COMPAT] 全部仅记录，不动手）

- 无凭据访问 `POST /api/backgrounds/all`、`/api/backgrounds/folders`、`/api/avatars/get`、`GET /api/sprites/get` → 401；带会话 cookie 无 CSRF → 403（端点级 csrf_guard 有效）。
- **发现①（卫生问题，仅记录）**：携带会话 cookie + CSRF 配对时反而 401——因为 st_resources 的 `_get_user` 只认 Bearer / `?token=` / `?palinkToken=`，**不含 cookie 兜底**（与 silly_tavern.py 主路由的 `_token_from_request` 口径不同）。攻击者视角不可利用（反而更严），但意味着前端调用这些端点时**主 JWT 会进 URL**——URL 中的令牌可能落入 nginx access log / Referer / 浏览器历史。N-7 在上传面消除的"JWT in URL"在 ST 资源面仍存在，属 ST 适配语义的既有取舍，**不修**；如未来要收口，方向是给这些端点补 N-7 式短令牌而非改回 Bearer。
- **发现②（符合 ST 语义，仅记录）**：`?token=` 换任意用户的 JWT 均能列出同一个全局背景图库——资源本身是全局共享（ST 语义），无用户隔离属预期行为，非越权。
- `_safe_join`（st_resources 路径构造）：abspath + 前缀包容校验实现正确（`sprites/get?name=../` 类穿越被 400 拦截）。

### 3.7 插件沙箱逃逸面（静态审计结论）

- **智能卡 iframe（不可信卡）**：`sandbox="allow-scripts"`（opaque origin，无法读父页/同源资源）✅——代码注释明确记录了此前 `allow-scripts allow-same-origin` 组合被浏览器警告 "can escape its sandboxing" 后做的 P1-1 隔离。父页 `handleMessage` 三重校验：`data.source` 标记 + `data.frameId` 按帧比对 + `event.source === iframe.contentWindow` 实例比对——伪造消息链路闭合 ✅。父→iframe 方向 targetOrigin 已按 N-22 收紧（trusted 用 location.origin，opaque 用 '*' 无放大）✅。
- **trusted-native 卡（用户显式信任）**：保留 `allow-scripts allow-same-origin` = 完全同源能力（可读 CSRF cookie、可发已认证请求）。这是**显式信任升级**（UI 有确认/撤销流程：`toggleTrustedNative`），与 ST"扩展即全权代码"模型一致，属接受的设计取舍 [用户已表态适配优先]。
- **经典轨插件（sillyTavernPluginRuntime）**：`createElement('script')` + `textContent` 注入页面全局作用域执行 = **全页面权限**。与 ST 扩展模型一致（ST 插件同样全权）。攻击面结论：**恶意插件 = 完整账号接管**，防线只在"插件从哪来"——建议未来在插件安装入口做来源提示/签名校验（非本轮动手项）。
- 插件沙箱 sandbox.ts 的 7 处"命令注入"+2 处"代码注入"（静态扫描 high）：实为 ESM→CJS 转换器与沙箱内代码执行设施，属能力描述非漏洞（维持上份报告结论）。
