## 1. 问题（S0 实测基线，非推导）

| 指标 | 实测 |
|---|---|
| 堆随 iframe 数增长 | 7 个 → 113MB；48 个 → 560MB（GC 后 ~300MB），边际 **+9~11MB/个，只增不减** |
| 91 条会话可滚动高度 | 12,399px → 55,753px（4.5×）；nodes 4.8k → 14.0k |
| 滚动每千像素主线程耗时 | 28.1ms → 42.3ms（**1.51×**） |

并轨后所有卡都走 iframe ⇒ 不解决则长会话**线性劣化**。

## 2. ⚠️ 地面不是空的（本次复核的重大发现）

交接文档把 T2 描述成"从零设计生命周期"。实测：

**`Message.tsx:655-746` 已有 `SmartCardDormancyGate`**，无条件包裹智能卡分支（`:1653`）：
- IntersectionObserver + 上下各一屏 `rootMargin` 缓冲（`:664`）
- 休眠前测高 + 等高占位，防滚动条跳动（`:698-703`）
- 同态重复上报守卫，防观察器抖动（`:692`）
- **卸载分支已写好**，但被 `:653 const PALINK_CARD_DORMANCY_UNMOUNT = false` 关闭

关闭原因写在 `:645-652`：卸载后重新入视口 = iframe 重建 = 一次真实导航；Safari 会话历史是**联合**的
（顶层 + 所有子框架），每次 iframe 导航插一条**幽灵条目**（顶层 URL 不变）⇒ 滑动返回要闪过 N 个
一模一样的快照。**iOS 没有 API 删除已存在的历史条目**，只能从源头不创建。

⇒ **三选一被重新定义**：

| 选项 | 现状 |
|---|---|
| ① 出视野即卸载 | = 把 `:653` 改成 `true`（一行），但**重放已付过学费的 iOS 回归** |
| ② 冻结保留（隐藏） | **就是当前实现，且已被证伪** —— S0 那 560MB 正是带着这个门跑出来的，证明"隐藏 ≠ 省内存"；`content-visibility:hidden` 也已因唤醒空白被移除两次 |
| ③ LRU 封顶 | 未实现 ← 本次要做的 |

## 3. 两个问题要分开（交接文档把它们合并在一个标题下）

| 问题 | 谁能解 |
|---|---|
| **堆**随消息数线性增长 | 只有 ①/③（必须真的移除 iframe） |
| **滚动成本** 1.51× | ② 可解（省渲染工作） |

⇒ 本方案以 ③ 为主（掐断线性增长这一**真实故障模式**），② 继续保留（它对滚动成本仍有效）。

## 4. 方案：懒挂载 + LRU 封顶，叠在现有门之上

1. **保留现有门不动**（它对普通会话是正确且已付过学费的）。
2. **懒挂载**：从未进入缓冲区的消息不创建 iframe。
3. **LRU 配额**：存活 iframe 数超过 `cap` 时，按"最后可见时间"逐出最久未见且当前不可见的那个，
   用**已有的 `dormantHeight` 等高占位**替换 ⇒ 零跳动。
4. `cap` 显著大于可见集（可见约 2~3 个 + 一屏缓冲）⇒ **普通会话根本不触发逐出，行为零变化**。

### 4.1 iOS 处理（**待拍板**，本次做成策略参数而非硬编码）

不做"iOS 永不卸载"这种二元开关，而是**分档配额**：

| 平台 | 建议 cap | 理由 |
|---|---|---|
| 非 iOS | 12~16 | 内存优先；幽灵条目不存在 |
| iOS | 40（保守档） | 内存**仍有上限**（≈400MB），不是"永不回收"；幽灵条目只在"真的来回翻 >40 张卡"时才产生 |

**为什么不是"iOS 豁免"**：豁免 = 内存无上限 = 长会话在 iOS 上会一直涨到 560MB+，
正是本次要修的毛病。分档至少把上界钉住。

**为什么上限取 40 而不是 16**：iOS 上的代价（幽灵条目）与"逐出-重建"次数成正比；
把配额放大 ⇒ 只有极端长会话才会付这个代价。

⚠️ **最高性价比的未知项**：那条 iOS 回归**从未在真机（iOS 设备）上复验过**，本仓也没有 iOS 设备。
**若它在当前 Safari 上已不复现，整条约束消失，iOS 可直接用与非 iOS 相同的配额。**
→ 建议后续拿到 iOS 设备实测一次（判定方法：连续滚过 ≥10 张卡再滑动返回，看是否闪过重复快照）。
本次实现为**策略参数**，届时改一个值即可，不需要改结构。

## 5. 状态丢失与恢复（交接文档特别要求说明）

卸载会重置帧内状态，必须说清：

- **能恢复的**：卡变量走 MVU 落库/存储；重建后从 `ctx.variables` 与存储读回（S2 之后走双兼容键）。
- **不能恢复的**：帧内 JS 模块作用域状态（计数器、一次性标记）⇒ 会重置。
- **架构上已有重建通路**（不是外来概念）：`srcDoc` 重建（`sourceFingerprint` / `assetModeVersion`
  变化）→ `onLoad` 强制重推插件脚本包（`CharacterCardRenderer.tsx:592`、`:886` `force=true`）
  → `postContextToFrame` context-update。即"重建"是现有设计里已跑通的路径。
- **增量风险**：每次逐出-重建 = 1 次导航 = 1 条 iOS 幽灵条目 ⇒ 靠 **cap 与分档把它限界**，
  而不是消除。这一点写入注释与本文档，避免后来者把它当零成本。

**红线**：不得为省内存去改卡脚本语义或变量持久化逻辑。

## 6. 守卫契约（交接文档硬性要求至少一条）

`frontend/src/components/ui/custom/smart-card-runtime/iframe-lru.ts` 为**纯逻辑模块**，
配套 `iframe-lru.test.ts`。核心断言：

- 已加载消息数增长时，**存活 iframe 数 ≤ cap**（这就是"不随消息数线性增长"的可执行形式）
- 逐出顺序 = LRU 序；只逐出**当前不可见**的
- 可见项永不被逐出
- 平台分档：iOS 档 cap 更大
- 幂等：重复 register / 重复 touch 不产生重复项

纯逻辑单测 + jsdom 集成（伪造 IntersectionObserver 驱动可见性）组合。
