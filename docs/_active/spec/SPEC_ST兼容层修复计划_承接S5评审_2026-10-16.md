### 3.2 T2 · 卡内 `triggerSlash` 缺口

**验了什么 / 怎么复核的**：本机 grep `triggerSlash` 全仓，确认三轨分治：

| 轨 | `triggerSlash` | 证据（HEAD 行号） |
|---|---|---|
| 沙箱轨（自有插件） | ✅ 有 | `lib/plugin-system/sandbox.ts:3605`（前置 `runPalinkSlashCommands`） |
| getContext 轨（主页面） | ✅ 有，且前置 9 命令 | `lib/sillytavern/getContext.ts:2517-2521` |
| **iframe 单间轨（卡内）** | ❌ 无 | `runtime-body/part-08.ts:89-309` 的 `getContextCompat` 无此字段；全 `runtime-body/` grep `triggerSlash` **0 命中** |

**⚠️ 但有个反转事实必须写进计划**：`legacy-st-sim-parts/part-a.ts:75` 的
`ST_GLOBAL_KEYS` 白名单里**有 `triggerSlash: 1`**（父窗口别名代理的透传键）。
即 `parent.triggerSlash` 在卡内能透传到 iframe 自己的 `window.triggerSlash`——
而那个值本身是 undefined。⇒ 这不是「键不存在」，是「键存在、值是 undefined」，
插件做 `typeof triggerSlash === 'function'` 特性检测时**会走优雅降级分支**
（这是好事，与 part-08:437 注释「缺口一律返回 undefined，不替卡改变结论」的设计一致）。

**修法（两条路，推荐 ①）**：

- **① 补桥（推荐）**：在 iframe 侧实现一个**真桥**版本的 `triggerSlash`：
  - iframe 侧（`part-08.ts` 的 `getContextCompat` 内）新增
    `triggerSlash: (cmd) => requestParent('runPalinkSlash', { command: String(cmd ?? '') })`；
  - 宿主侧（`CharacterCardRenderer.tsx` 的 `handleMessage` 的 `request` 分支）新增
    action `runPalinkSlash` → 调 `lib/sillytavern/slash-commands-compat.ts` 的
    `runPalinkSlashCommands`（**复用现成共享实现，不重写命令逻辑**）；
  - 未命中（返回 `null`）时，宿主侧回落 `getContext.ts:2520` 的
    `executeSlashCommandCompat`（与沙箱轨/getContext 轨**完全同源**）。
  - **红线**：只补「执行」，**不补**命令的副作用可见性承诺。
    9 条命令里 ①②③（branch-create / checkpoint-create / checkpoint-go / chat-fork）
    会改分支结构，卡内调用与沙箱轨调用**走同一条 API 路径**，行为一致。
- **② 明确不支持（备选）**：在 `st-plugins/ADAPTATION.md` 写明「卡内不支持 slash 命令」，
    并保持现状。**成本最低但用户收益为零**，仅在①有回归风险时采用。

**为什么值得做**：评审报告 §3.1 明确指出，报告 B 组「9 条命令通过」的绿色
**只在沙箱轨成立**，总表容易读成「卡内也能用」。补桥后这句话才名副其实。

**验收判据**：
- 新增用例（iframe 侧 vm 测试，参考 `console-noise-and-card-crash-guard.test.ts:93`
  的 `runProxyWithStubs` 抽段注入法）：`getContext().triggerSlash('/getchatname')`
  → 经 requestParent 拿到宿主返回值，形状为 `palink-session-<sid>.jsonl`；
- 新增用例：未知命令（`/__palink_probe_unknown__`）→ 走引擎兜底，不返回 Palink 形状；
- **真机复验（Docker 起后）**：卡帧内 `typeof getContext().triggerSlash === 'function'` = true，
  且 `/profile-list` 触发一次降级登记。

**边界**：不动 `slash-commands-compat.ts` 的语义（那是 S5 已验收的机械下沉产物，
`REPORT_slash-sink` §3 有逐字节 diff 证据），只新增一个调用方。

### 3.3 T3 · MVU 世界书读取失败（66 次/会话）

**验了什么 / 怎么复核的**（这是本批**根因最实**的一项，评审报告只给了「第一嫌疑」）：

1. 从真机卡 bundle `backend/data/smart_card_assets/0c646fb31a….js`（MVU beta）里
   **直接挖出抛错点原文**（307KB 文件，索引 207456 附近）：
   ```js
   async function $a(t){
     const n = await SillyTavern.loadWorldInfo(t);
     if(!_.isPlainObject(n)||!_.isPlainObject(_.get(n,'entries')))
       throw new Error(at('runtime.characterOverride.worldbookReadFailed',{worldbook:t}));
     return e(n)
   }
   ```
   ⇒ **报错文案 `无法读取角色世界书"{name}"` 的判据是：`loadWorldInfo` 返回值不是
   plain object，或没有 `entries` 键。**
2. 对照 Palink iframe 侧实现：`runtime-body/part-08.ts:259`
   `loadWorldInfo: async () => ({})` —— **恒返回空对象，没有 `entries` 键**
   ⇒ **必然命中抛错分支**。**根因锁定，不是"内容下发"问题，是这个 API 本身就是空桩。**
3. 同一份 bundle 里 `getLorebookEntries` / `getCharWorldbookNames` 链路**已经有值**
   （S1-G10/G11 修过，`part-07.ts:14-172` + `SmartCardCompatController.ts:801-806`
   有 9 条契约测试守着），所以 MVU **拿得到书名、拿不到内容**——
   与 `REPORT_s3-acceptance-gap` §5.1 的定性逐字吻合，现在补上了最后一环。

**修法**：把 `part-08.ts:259` 的空桩改成真桥，**数据源与 S1-G11 完全同源**：

```js
loadWorldInfo: async (name) => {
  // 与 getLorebookEntries 同源：优先卡自建，缺失回退角色 character_book
  const detail = await requestParent('getCharWorldbook', { args: [] });
  const entries = detail && Array.isArray(detail.entries) ? detail.entries : [];
  return { name: String(name || detail?.name || ''), entries };
},
```

**⚠️ 关键约束（必须满足，否则修了也白修）**：MVU 的判据是
`_.isPlainObject(_.get(n,'entries'))` —— **`entries` 必须是对象/数组且非 null**。
`getLorebookEntries` 返回的是**数组**，而 `_.isPlainObject([])` 在 lodash 里是 **false**
（数组不是 plain object）！⇒ 直接透传数组仍会抛错。

**⇒ 正确形状**：必须包一层 `{ entries: [...] }`（ST 的 `loadWorldInfo` 真实契约就是
返回 world_info 对象，内含 `entries` **对象**（uid→entry），不是数组）。
两种选法：
- **A（对齐 ST 真契约）**：`entries` 转成 `{ [uid]: entry }` 的对象形状
  （MVU 随后会 `_(e.entries).values().sortBy('displayIndex')`，对象/数组都能 `.values()`）。
- **B（最小改动）**：先试 `{ entries: array }`，若 MVU 版本换判据再调。

**落地前必须做一次真机判定**：用现有 5 个测试插件 + MVU 卡开一轮，
读 `__palinkFrameErrors` 里 `worldbookReadFailed` 的命中数是否归零。
**判据：66 次/会话 → 0 次**，不接受"降到 30 次"这种中间态。

**验收判据**：
- 单测（vm 抽段）：`loadWorldInfo('露缇雅1.2')` 在 mock requestParent 返回
  `{ success:true, name:'露缇雅1.2', entries:[{comment:'[InitVar]…',content:'stat_data: {}'}] }` 时，
  返回值的 `entries` 通过 lodash `isPlainObject` 判定（**引入 lodash 进测试断言，
  别自己写判据**——评审报告 §3.1 的教训就是判据与真实消费方不一致）；
- 真机：MVU 变量初始化成功（不再弹「[MVU]变量初始化失败」）+ console 无
  `无法读取角色世界书`。

**边界**：只改 `loadWorldInfo` 一个桩。**不动** `getLorebookEntries` 的既有实现
（9 条契约测试守着，动它等于动 S1-G10/G11 的验收成果）。

### 3.5 T5 · `setChatMessage` / `deleteMessage` 手势闸门（⚠️ 需授权）

**验了什么 / 怎么复核的**：`SmartCardCompatController.ts:58-81` 的
`SMART_CARD_MUTATING_ACTIONS_REQUIRING_GESTURE` 集合当前只含
`sendMessage / sendMessageAsUser / sendUserMessage / triggerGeneration / Generate /
generate / generateRaw / generateQuietPrompt / clearChat` 共 9 项。
`setChatMessage` 与 `deleteMessage` **确实不在集合内**（评审报告 §4.2 唯一扣分点，复核属实）。

**⚠️ 但这里有一条评审报告没引全的反向论证（必须让用户知道再拍板）**：
`SmartCardCompatController.ts:67-79` 的注释明确写了**为什么只加 `clearChat`**：

> 1. 用户激活**不会向下传播到 opaque-origin iframe**（HTML 规范 6.4.2 第 4 步）⇒
>    untrusted 卡内部**感知不到**用户在父页面点「发送」，shim 的 lastUserGestureAt 不会更新；
> 2. 而「生成结束后改写/追加消息、写世界书条目」是卡片最常见也最正当的一类用法
>    （MVU 变量更新、状态栏、格式化卡都属此类），天然发生在无手势上下文里
>    ⇒ 纳入闸门会直接打断正常流程，**属于实打实的 ST 兼容回归**；
> 3. `clearChat` 是唯一「不可逆 + 会落库 + 不存在无手势正当用法」的动作。

⇒ `setChatMessage`/`deleteMessage` 正好落在第 2 类（MVU 每轮都调），
**加闸门 = 打断 MVU 变量更新主链路**。评审报告把它列为「唯一残留的安全口子」，
但注释给的兼容性论证更硬。**这是一个安全 vs 兼容的真实权衡，不是漏修。**

**⇒ 本 Task 必须提交用户三选一**（见 §5 提问）：

| 选项 | 安全 | 兼容 | 说明 |
|---|---|---|---|
| A 不加闸门，改为「登记留痕」 | 中 | ✅ 不回归 | `setChatMessage`/`deleteMessage` 每次调用走 `recordStubHit`，插件管理页可见「卡在无人点击时改了消息」 |
| B 加闸门 | 高 | ❌ MVU 变量更新断 | 按评审报告原建议 |
| C 折中：仅 `deleteMessage` 加闸门 | 中高 | ⚠️ 部分风险 | delete 不可逆性接近 clearChat，但仍可能打断正常清理流程 |

**推荐 A**（留痕不加闸）：既不让口子静默，又不打断 MVU。
注意落点仍在**主页面侧**（`card-script-runner.ts` 那 6 处 `recordStubHit` 是既有通道），
不要在 iframe 侧新建 stats。
