## 任务 1：A-4 addOneMessage 事件面偏差

**现状**：`frontend/src/lib/sillytavern/getContext.ts:1506-1508` 的 addOneMessage 在添加一条消息时**同时** emit `message_received` + `message_sent`。

**ST 语义**（script.js 对照）：`message_received` 仅在 **AI 角色回复**产生新消息时触发；`message_sent` 仅**用户发送消息**时触发。两者在 ST 中互斥，订阅方据此区分收发方向。

**目标**：
1. addOneMessage 需按消息角色区分事件：role=user/系统消息 → emit `message_sent`；role=assistant → emit `message_received`；无法判定时（无 role 字段）维持现状双发以保证兼容。
2. 经典轨事件发射面补齐：确认 `app_ready`、`generation_started` 在经典 listeners 上是否有发射点，缺失则补（对齐沙箱轨）。
3. **不动**：其余约 15 个小众 ST 事件未定义属 P3，本批不扩展。

**验收**：新增/更新 getContext parity 测试断言事件分发按角色区分；既有 `event-contract.test.ts` 不回归。

## 任务 2：A-5 半兼容字段集（getContext）

**现状**（`getContext.ts` 各字段）：
- `tokenizers`（:1711-1723）是 `{getTokenCount,...}` 方法集；ST 是数字枚举对象（`ctx.tokenizers.OPENAI===2`）
- `getRequestHeaders` 安全化改写不含 Authorization（终态后无需 Bearer，此字段可保留现状——见备注）
- `symbols.ignore`/`constants.unset` 键名与 ST 不匹配（Palink 用 IGNORE_SYMBOL/SWIPE_COUNT_DEFAULT，ST 用 ignore/unset）
- `executeSlashCommandsWithOptions` 返回形状：getContext 轨与沙箱轨不一致（沙箱有 `.pipe`，getContext 直接返回引擎结果）
- `messageFormatter` 缺失
- `registerFunctionTool` 注册表真实但不消费；getContext 轨是 stub

**目标**（与 ST 对齐，仅 getContext 轨）：
1. `tokenizers` 增加数字枚举对齐（保留既有方法集作为附加能力，枚举常量不可破坏：OPENAI=0/OpenAI/Claude=1/.../Custom=8，以 ST constants.js 为准）
2. `symbols.ignore`/`constants.unset` 增加 ST 同款键（保留原键向后兼容）
3. `executeSlashCommandsWithOptions` getContext 轨返回形状对齐沙箱轨（补 `.pipe`）
4. `messageFormatter` 提供 ST 签名（可先空实现或委托既有 formatter，报告说明）
5. `getRequestHeaders`：终态后无 Authorization 属**正确行为**，保留现状，仅更新过时注释
6. `registerFunctionTool`：getContext 轨由 stub 改为"注册表真实入表，管道暂不消费"——与沙箱轨一致，报告说明

**验收**：getContext parity 测试覆盖新增字段/枚举；既有测试不回归。

**目标**：在经典轨（getContext 运行时）提供全局 `window.setExtensionPrompt` 真实现，语义对齐 `prompt-injection.ts` 的沙箱轨实现：入参校验 + 注册到扩展 prompt 存储（后续装配消费）。实现方式参考沙箱轨等价物即可，报告说明数据结构。

**验收**：新增测试证明调用 `window.setExtensionPrompt(...)` 不再 ReferenceError 且正确注册；chat 装配链路可见（静态断言或 mock 装配验证）。

## 任务 4：A-7 多租户插件隔离（已知遗留，按需适配）

**现状**：`backend/app/api/plugins.py:1099` runtime 配置查询仅 `Plugin.enabled==True`，无 user 过滤。

**ST/预期语义**：插件配置按用户作用域隔离（多用户部署时用户 A 的插件不应用到用户 B）。

**目标**：
1. `plugins.py:1099`（及同文件若存在同类查询）增加当前用户过滤——查询带 user_id 条件（注意兼容"全局插件"：可先按 enabled + (user_id == 当前用户 OR user_id IS NULL) 处理，报告说明取舍）。
2. **单用户部署不受影响**（当前用户即全部）。

**验收**：新增测试验证用户 A 的插件 runtime 配置不含用户 B 的插件项；既有插件测试不回归。

## 任务 5：C-4（后半）trimStrings/filterString 宏替换

**现状**：前端 `engine.ts:120-129`（及 regex-engine 同逻辑）对 trimStrings/filterString 不做宏替换——含 `{{user}}` 的 trim 串在前端失效。后端已对齐 ST（character_ext.py:1125-1139）。
> 注：C-4 前半（minDepth/maxDepth -1/0 边界豁免）已由 P1 批顺带修复，本批只做后半。

**ST 语义**：regex 脚本的 trimStrings/filterString 数组内容应先经 `substituteParams` 宏替换（`{{user}}`→实际用户名等）再参与 trim 判定。

**目标**：前端 engine.ts（及 regex-pipeline 对应路径）对 trim/filter 串执行宏替换（复用既有宏替换函数），对齐后端。

**验收**：新增测试——trim 串含 `{{user}}` 时按实际用户名 trim；既有 regex 契约测试不回归。
