## 3. 🔴 头号问题：产品底线与已实施桥接的 CORS 矛盾（须先拍板）

**SPEC 的口径**（标题+§0.5）：最低要求 = 用户装了 ComfyUI、登录网站就能出图，"不要求他敲命令行"、"禁止让用户改 ComfyUI 启动参数才能用本单功能"。

**代码与项目实测的事实链**：
1. `comfyui-client.ts:11-12` 注释明写：**"CORS：ComfyUI 必须带 `--enable-cors-header '<站点origin>'` 启动"**，两段式探针就是为区分"没启动"和"没放行 CORS"；
2. 设置页连接向导已把该参数作为正式步骤：`ImageGenerationTab.tsx:180`（`python main.py --enable-cors-header '<origin>'` 一键复制）、`:498-501`（便携包/启动器用户也要追加参数重启）；
3. 项目自己的实测记录 `TODOS.md:273`：无 CORS 头的本地服务 → `BLOCKED: Failed to fetch`；加 CORS + 应答 OPTIONS 预检后浏览器直 POST 成功；
4. 外部佐证：ComfyUI 至今（2025）默认不发 CORS 头，跨源浏览器访问仍以 `--enable-cors-header` 为文档化方案。

**推论**：浏览器桥接路径上，"装了 ComfyUI 什么都不配就能出图"在当前架构下**做不到**——至少要用户把一条启动参数塞进启动命令/便携包 .bat 重启一次。这不是本单引入的，是上一批（ce64607，待实机验收）就带进来的；但本 SPEC 把它写成了产品底线，等于给了一个当前实现达不到的验收标准，施工 agent 按底线自查会无所适从。

**技术上无绕开方案**：§9 已排除本地小助手、隧道；CORS 是浏览器安全模型强制的，前端侧无解；唯一变量在 ComfyUI 侧（启动参数或上游改默认，后者不可依赖）。

**处理选项（需拍板）**：
- **A（推荐）**：底线改写为「装了 ComfyUI + 连接向导**一键复制一条启动参数**重启 = 登录即可用」。一次性动作、无需懂命令行（复制粘贴），向导已做到这一步；本单的预检正好把 `cors_blocked` 也纳入三条失败分支的人话文案，体验闭环。
- **B**：追加调研 ComfyUI Desktop 官方安装包能否在 GUI 里持久化启动参数（覆盖面未知，不保证有，只值得半天调研）。
- **C**：维持原底线不动，接受"不肯加参数的用户"达不到，靠 T-A 预检把失败讲清楚——即底线降级为愿景。

不拍板这条就开工的后果：T-A 的文案、向导、验收口径都会在"要不要引导用户加参数"上来回打架。

## 5. T-A 能力预检：可行，4 个实现空隙

整体判定：**设计成立**。节点清单放模板旁、一次采集缓存 5 分钟、缺啥说人话、不加 /object_info 开销、不自动改配置——都对，且"模板依赖清单与模板体一致"的防漂移测试可以直接解析模板 dict 的 `class_type` 集合做比对，便宜可靠。

按模板列依赖清单的实际内容（供施工参考）：
- **SDXL**：`CheckpointLoaderSimple / CLIPTextEncode / KSampler / EmptyLatentImage / VAEDecode / SaveImage`——全是元老级核心节点，基本不会缺；
- **Flux**：`UNETLoader / DualCLIPLoader / VAELoader / ModelSamplingFlux / FluxGuidance / BasicGuider / KSamplerSelect / BasicScheduler / RandomNoise / EmptySD3LatentImage / SamplerCustomAdvanced / VAEDecode / SaveImage`——**对老版本 ComfyUI 最不友好的一套**（Flux 支持约 2024-08 后才有），正是"预检绿≠能出图"的主要命中人群；
- **Qwen**：`UNETLoader / CLIPLoader(type=qwen_image) / VAELoader / ModelSamplingAuraFlow / CLIPTextEncode / KSampler / EmptySD3LatentImage / VAEDecode / SaveImage`——qwen_image 支持约 2025-08 后才有，同样偏新。

空隙（SPEC 未写、施工时会遇到）：
1. **浏览器模式下预检发生在哪**：后端够不到用户机器，预检只能在浏览器执行（executor 提交 /prompt 前做，缺节点→走现有 `/fail` 上报通道并给结构化原因）。现有 `ComfyUIFailureCode` 枚举要扩（如 `missing_nodes` / `missing_model`），SPEC 未提；服务端模式则在后端派发前做。
2. **缓存位置**：`(user_id, device_id)` 缓存只对服务端模式成立（后端缓存）；浏览器模式的缓存只能在前端（内存/sessionStorage），SPEC 一笔带过没分模式。另外服务端模式是全局共享一个 ComfyUI，缓存键实际退化为 provider 级，无碍。
3. **采集方式**：全量 `/object_info` 在新版本上约几 MB；备选是按依赖清单里的类逐个拉 `/object_info/<Class>`（十几个小请求，每个同样带该槽的可选清单）。两条路都可行，建议施工时二选一并在注释里写明，别两套都留。
4. **现有 `/comfyui/models` 是 admin-only**：预检不能复用它的权限语义（出图的是普通用户）——但服务端模式的预检本来就该在后端派发路径里做而非走这个端点，所以不构成阻塞，只是"复用那两条现成路径"指的是传输姿势（前端直连 / 后端出站+SSRF 守卫），不是复用权限。

## 6. T-B 参考图档：可行，5 个实现空隙（flux 是工作量主体）

整体判定：**路线正确**。`/upload/image` → `LoadImage` → `VAEEncode` → 采样器部分去噪，只用自带节点，三套逐套验证的要求务实。逐套改法：

- **SDXL**（最易）：`EmptyLatentImage` → `LoadImage+VAEEncode`，`KSampler.denoise` → 重绘幅度。潜变量空间与 VAE 不换族，无结构风险。
- **Qwen**（易）：同上替换 `EmptySD3LatentImage`，`KSampler.denoise` 接幅度。注意语义：这是"重绘"不是"编辑"——官方的参考图编辑走 `TextEncodeQwenImageEdit`（也是自带节点），本单定位重绘档没错，但文案别说成"改图/编辑"。
- **Flux**（最重）：要把 `EmptySD3LatentImage` 换成 `LoadImage+VAEEncode`，且去噪幅度落在 `BasicScheduler.denoise`（不是 KSampler）；`ModelSamplingFlux` 的 width/height 要换成参考图实际尺寸（后端在装配时不知道图尺寸，得由上传后的一方补）；`RandomNoise + SamplerCustomAdvanced` 组合下部分去噪的行为**必须在真机或忠实假上游上验证**——这是三套里唯一可能"假上游过了真机不过"的。

空隙（SPEC 未写）：
1. **LoadImage 的文件名拼法**：`/upload/image` 返回 `name`+`subfolder`，工作流里要填 `subfolder/name`（subfolder 非空时）——拼错假上游测不出来（假上游不校验文件名格式），只有真机暴露。建议直接写进 SPEC 或施工提示词。
2. **谁来把文件名填进工作流**：浏览器模式只能是前端（executor 上传后 patch 工作流再 POST /prompt），意味着**任务 payload 要带"参考图填到哪个节点/哪个输入"的标记**（现有 `LocalImageTask` 只有整份 workflow）；服务端模式由后端上传后 patch。SPEC §4.2 暗示了这个分工但没点破 schema 要扩。
3. **聊天已有图当参考图的取图路径**：候选 A"从聊天已有图里挑"时，图在服务端（URL 或 base64），浏览器模式要先 fetch 回来再转发上传到本机 ComfyUI——可行，多一步中转，SPEC 未提。
4. **SD WebUI 的对称性**：SD WebUI 侧已有 img2img 但 denoising_strength 是函数硬编码 0.75，不可配；本单给 ComfyUI 加的可配重绘幅度要不要顺带给 SD WebUI 对齐（不做也行，但设置页会出现"一边能调一边不能调"，建议至少在注释里说明）。
5. **参考图入口候选 B 与模型自主出图的冲突**：`maybe_generate_image_for_message` 的自动出图链路里，"消息里的图"很可能是用户随手发的表情包/截图，被自动当参考图会产生惊吓效应——若拍板候选 B，自动出图链路必须排除在外（只限用户手点出图）。

## 10. 追加实锤（同日第二轮）：零配置与"本机模型"物理不可兼得

用户随后提出"想要最无脑的解法，不需要用户做任何配置"。为此实测了用户本机 ComfyUI **0.37.0**（`D:\千问Image2.1\ComfyUI`）的 `server.py`，并核对官方 API 文档，结论收敛：

**默认启动的 ComfyUI 会主动拒绝一切跨站网页请求，盲通道不存在。**
- 不带 `--enable-cors-header` 时，中间件链挂的是 `create_origin_only_middleware()`（server.py:241）：`Sec-Fetch-Site: cross-site` → 直接 403；Host(127.0.0.1) 与 Origin(我们的域名) 不匹配（回环 host）→ 再 403。WS 握手同样带 Origin/Host，同被拦。
- 也就是说，此前评估的"无 CORS 盲通道"（`text/plain` 免预检 POST `/prompt` + 客户端自带 `prompt_id` + 内置节点 `SaveImageWebsocket` 经 WS 推全图字节）**技术路线本身成立**（官方文档逐条背书），但在默认配置下被 403 全灭。这是上游**故意**的防"恶意网页偷偷排队出图"设计（代码注释原文写明），上游不会放松。
- 因此跨源读写只剩一条正门：`--enable-cors-header`（指定后 cors 中间件**替换** origin_only，二者互斥）。加参数不是"锦上添花"，是浏览器路径的唯一活路。

**推论**：
1. 「登录就能出图 + 用他自己的本机 ComfyUI + 用户零操作」三个条件**不可能同时满足**，与是否努力无关，是浏览器安全模型 × ComfyUI 反滥用设计的叠加。
2. 真正的"最无脑"只有一个方向：**出图不发生在用户机器上**——云端出图默认档。落地几乎零新代码：
   - 姿势一：new-api 网关接图像供应商（网关 P0 已打通、用户额度系统已上线，`openai_compatible` image provider 代码现成）——配一个供应商即"登录就出图"；
   - 姿势二：租一台 GPU 盒子跑 ComfyUI，现有 **server 模式**代码原样用（后端直连，无浏览器无 CORS），模型我们装、家族我们选。
3. 本机 ComfyUI 降级为"进阶免费档"（自带显卡、自己的模型、不按张付费），代价 = 一次性复制一行启动参数 + 浏览器授权弹窗点一次（Chrome 142+/Firefox 149+ 的本地网络权限，项目已实测记录）。
4. 本 SPEC（T-A/T-B）**不作废**：它服务进阶档；且 T-A 的服务端模式半边正好复用到云端档（后端自己就能拉 object_info）。§3 的拍板项在云档立项后自然消解（底线由云档兑现，本机档按 A 口径改写）。
5. 原 §3 选项 B（ComfyUI Desktop GUI 持久化参数）仍可作半天调研的加分项，但不再是关键路径。
