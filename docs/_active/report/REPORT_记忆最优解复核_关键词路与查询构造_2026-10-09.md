**三条读数：**

1. **④ vs ①**：只加关键词路几乎不动（31.2%→33.3%）。因为 600 字窗口查询的 bigram 集合太大，关键词路被稀释得跟向量路一样瞎。
2. **⑥ vs ③ / ⑥ vs ④**：**修查询 + 加关键词 = 47.9% top1**，而单独任一项只有 6~23%。两条路互相解锁。中位排名 17 → **2**。
3. **⑩ vs ⑥ 完全相同**：把记忆库里的【声音】等残留再纯化一遍、重新嵌入 227 条，**指标一行没动** —— 见 §4。

检索层提升的显著性：注入命中 31.2%→81.2%（n=48，净增 24 题命中，不一致对 ≥24），McNemar 保守估计 **p < 1e-6**。这一层的结论是硬的。

## 四、关于「把记忆去掉 HTML / `<UpdateVariable>` / 【声音】让它更纯」

**结论：这个方向对，但活已经干了 90%，剩下 10% 实测收益为零。别把它当主因。**

- 入库侧 `app/utils.py:clean_memory_content` **已经在剥** `<UpdateVariable>`（含内嵌块）、`<thinking>`、孤立功能标签、排版 HTML、markdown 表格空壳；注入侧 `build_memory_context` 又剥一遍。实测本会话 227 条记忆里：**功能标签 0 条、残余 HTML 0 条**。
- 剩下的只有 `【声音：…】`：**41/227 条含它，但只占 2% 字符**（293 字 → 288 字）。
- ⑩ 档把库纯化后**重新嵌入全部 227 条再测**：top1 47.9% / 命中 81.2%，与未纯化的 ⑥ **完全相同**。
- 真正"脏"的是**查询侧**：窗口查询 600 字里问题只占 3.4%，中位夹着 **3 处** `【声音】`/标签（p42）。清洗查询（②）把中位排名从 17 拉到 13 —— 有点用，但远不如换查询构造。

⇒ 该做的只有一件：**把 `clean_memory_content` 也套在检索查询上**（目前查询是消息原文，与已清洗的记忆库不同源）。顺带能省注入 token、少点噪声，但**不要指望它提召回**。

## 六、可信边界

1. **端到端三档的差值不显著**（p=0.18~0.51），且跨跑噪声 ±0.09 > 部分档间差。端到端只作方向性证据。
2. 检索层的 ① 和 ③ 复现了原报告的数字 → 两套探针互为交叉验证，这一层可信。
3. 关键词路用的是**字符 bigram 覆盖率**在 Python 侧模拟（与 10-08 的 p4/p7 同口径），不是 pg_trgm SQL；落地时需在库内实现并复测（排序能力应相当或更好）。
4. 只测了一个会话、一张卡；生成模型 `deepseek-chat`（生产是 `deepseek-flash`）；判分仍为 LLM，未人工抽样。
5. **没测角色连贯性**（语气/人设）—— 砍历史这一步在没测连贯性前不该激进执行。
6. 句级档的注入是"回捞父块原文"，与原报告的"直接注入句文本"不同口径，两者 e2e 不可直接比。
