## 1. 背景与问题（已验证的代码事实）

### 1.1 现状病灶

| # | 病灶 | 代码位置 | 后果 |
|---|---|---|---|
| P1 | assistant **整条回复存为一条记忆、一个向量**（无任何切分） | `websocket.py` L457-459 / L1114-1122、`character_ext.py` L4826-4839、`chat.py` L393-394 → `MemoryService.store_memory` → `storage.store`（整段 `embed_text(content)`） | 一段回复讲 N 件事，向量语义被平均化稀释，检索精度差 |
| P2 | 注入时**每条记忆砍头到 200 字符** | `utils.py` L202 `build_memory_context` → `_truncate_by_sentence(..., 200)` | 检索命中的是整段语义，注入的却是开头 200 字 → **记忆与当前话题错配**（用户核心抱怨） |

### 1.2 已验证的基础设施事实（本 spec 的可行性依据）

1. **批量嵌入原生可用**：`OllamaEmbedder.embed(List[str])` → Ollama `/api/embed` 一次 HTTP 返回全部向量（`embedder.py` L247-262）。25 句 = 1 次调用。
2. **写入调用点全覆盖**：所有 assistant 入库都经过 `MemoryService.store_memory`（4 处调用点），在 service 层内部切分即可全链路生效，**零调用点改动**。
3. **无 schema 迁移方案可行**：`conversation_memories.topics` 为 JSON 列（`storage.store` 以 `json.dumps` 字符串写入），块元数据可编码进 topics，**不需要 alembic 迁移**。
4. **压缩服务兼容**：`compression_service.compress_memory` 按条打分保留/删除（L139-217），对"更多、更小"的行天然兼容，无需改动。
5. **检索预算机制现成**：`retriever.retrieve` 已按 `max_tokens`（装配路径传 1500）给 LTM 做预算填充；`tokens_count = len(content)//2` 估算口径现成。
6. **降级链现成**：Ollama 不可达时 embedder 自动降级 fastembed → SimpleHash，切分逻辑不感知后端差异。
7. **无存量测试冲突**：`backend/tests/` 下无 memory 模块测试文件，新测试不会破坏现有断言。
8. **一次性脚本先例**：`backend/scripts/_clean_memory_pollution.py`（2026-08-18 容器内执行重嵌入），存量迁移可照搬模式。

### 1.3 用户目标（验收锚点）

> AI 输出长对话 → 向量引擎**自动按语义**（话题转换处，非机械句号）拆成小段入库 → 之后再次提到相近意思时，取出的是**意思相近的那一小段**，注入完整内容而非砍头碎片。

## 2. 目标与非目标

### 目标
- G1 assistant 长回复按语义断点切成小块入库（话题转换处切割）
- G2 检索命中哪个块就注入哪个块的**完整内容**，废除 200 字砍头
- G3 预算允许时自动携带命中块的**前后相邻块**（上下文完整）
- G4 短回复（< 触发阈值）零额外成本，行为与现在完全一致
- G5 全程后台线程，对话主链路延迟零增加
- G6 可配置、可一键关闭（回滚开关）

### 非目标
- 不做 LLM 事实抽取（方案 C，另行立项）
- 不做 late chunking（Ollama 不暴露 token 级向量，且需引入 torch 重依赖——已否决）
- 不改 user 消息的入库方式（用户消息通常短，保持整条）
- 不改检索打分公式（similarity 0.6 / proximity 0.2 / importance 0.2 维持现状）
- 不改压缩服务

## 3. 算法设计：语义切分器

### 3.1 新文件 `backend/app/memory_module/semantic_chunker.py`

```
输入: text (已清洗的 assistant 回复), embed_fn (默认 embed_text), config
输出: list[str] 语义块

流程:
S1 短路: len(text) < CHUNK_TRIGGER_CHARS (默认250) → 返回 [text]
S2 句子切分: 按 [。！？!?…；;\n] 切分（保留分隔符附着在句尾）；
   长度 < 20 字的句子并入下一句（避免"嗯。""……"这类碎句成为独立比较单元）
S3 句子仍超 MAX_CHUNK_CHARS 的，按句边界递归强制再分（复用句边界回退逻辑）
S4 批量嵌入: embed_fn(所有句子) —— 单次调用
   向量 L2 归一化（numpy，防后端未归一化）
S5 缓冲窗口: 句 i 的比较向量 = normalize(emb[i-1] + emb[i] + emb[i+1])
   （窗口边界句只拼存在的邻居；BUFFER 可配，默认 1）
S6 相邻距离: dist[i] = 1 - cosine(combined[i], combined[i+1])，i = 0..n-2
S7 自适应断点: threshold = percentile(dist, BREAKPOINT_PERCENTILE 默认95)
   dist[i] > threshold 的位置 i+1 处断开
   兜底: 若 n < 4 句（统计不可靠）或所有 dist 相等 → 不切，整段一块
S8 尺寸整形:
   - 相邻块合并后 ≤ MAX_CHUNK_CHARS (默认450) 且合并块不是跨断点的 → 允许
     （即：仅当某块 < MIN_CHUNK_CHARS (默认120) 时才向邻居合并）
   - 合并方向: 向信息量更小（字符更少）的邻居合并
S9 返回块列表（保序）
```

### 3.2 参数表（全部进 `memory_config`，env 可覆盖）

| 参数 | env | 默认 | 说明 |
|---|---|---|---|
| MEMORY_SEMANTIC_CHUNKING | — | `true` | **总开关**，false 时 store 路径回到现状 |
| CHUNK_TRIGGER_CHARS | MEMORY_CHUNK_TRIGGER_CHARS | 250 | 低于此长度不切分 |
| CHUNK_MIN_CHARS | MEMORY_CHUNK_MIN_CHARS | 120 | 块下限，不足则并邻居 |
| CHUNK_MAX_CHARS | MEMORY_CHUNK_MAX_CHARS | 450 | 块上限（bge-m3 8192 上下文的保守值，保证向量聚焦） |
| CHUNK_BREAKPOINT_PERCENTILE | MEMORY_CHUNK_PERCENTILE | 95 | 断点百分位（越高切得越少） |
| CHUNK_BUFFER_WINDOW | MEMORY_CHUNK_BUFFER | 1 | 相似度比较的缓冲窗口 |
| CHUNK_MIN_SENTENCE_CHARS | — | 20（常量即可） | 碎句并入阈值 |
| MEMORY_INJECT_BUDGET_DEFAULT | — | None | build_memory_context 预算缺省（None=不二次限制） |

### 3.3 块元数据（topics 编码，无迁移）

每块入库时 `topics` 写入：
```json
["#chunk", "#turn:<turn_hash>", "#idx:<i>", "#total:<n>"]
```
- `turn_hash` = `blake2b(content前64字节 + 存储时间戳).hexdigest()[:12]`——同轮唯一标识
- 邻居查询：`WHERE topics::text LIKE '%"​#turn:<hash>"%'`（PG 加 `::text`；SQLite topics 本就是 TEXT）→ 按 `#idx` 排序取 `i±1`
- user 消息与旧数据无 `#chunk` 标记 → 邻居扩展自然跳过

## 4. 改动清单（文件级）

### 4.1 新增 `backend/app/memory_module/semantic_chunker.py`
- `semantic_split(text, embed_fn=None) -> list[str]`：§3.1 全流程
- `_split_sentences(text) -> list[str]`
- `_percentile_breakpoints(distances, percentile) -> list[int]`
- 纯函数设计，embed_fn 注入 → 单测无需真实 Ollama

### 4.2 修改 `backend/app/memory_module/service.py`
- `store_memory()` 内部（role=assistant 且总开关开且 len≥trigger 时）：
  - `chunks = semantic_split(content)`
  - 单块 → 走现有 `storage.store()`（行为不变）
  - 多块 → 调新方法 `storage.store_chunks(...)`
- 新增 `get_adjacent_chunks(mem: MemoryEntry) -> list[MemoryEntry]`：按 turn_hash 取 idx±1（供 get_context 邻居扩展用）

### 4.3 修改 `backend/app/memory_module/storage.py`
- 新增 `store_chunks(user_id, session_id, role, chunks: list[str], branch_id, turn_hash, importance_score) -> list[int]`：
  1. **一次** `embed_text(chunks)` 批量出全部向量（embedder 已支持 List 输入）
  2. 单事务批量 INSERT，embedding 直接写入（不走逐条后台 embed）
  3. 嵌入失败降级：逐条走现有 `store()`（NULL embedding + 后台重试路径），保证不丢数据
  4. topics 按 §3.3 编码；tokens_count = len//2（口径与现状一致）

### 4.4 修改 `backend/app/memory_module/service.py::get_context`
- retriever 返回后、返回调用方前，做**邻居扩展**（仅 LTM 命中且带 `#chunk` 标记的）：
  - 对每条命中块取 idx±1 邻居，若 `total_tokens + 邻居tokens ≤ max_tokens` 则插入结果
  - 去重（邻居可能已在 STM/结果中）
  - `strategy_used` 追加 `+neighbors`（可观测）
- 邻居扩展受 `MEMORY_NEIGHBOR_EXPAND`（默认 true）控制

### 4.5 修改 `backend/app/utils.py::build_memory_context`
- 签名：`build_memory_context(memory_ctx, max_tokens: int | None = None)`
- 逻辑变更：
  - **废除每条 200 字砍头**
  - 按传入顺序累加 `len//2` 估算 token，超 `max_tokens` 的记忆**整条跳过**（不截断文本）
  - 兜底：无标记的**超长遗留条目**（>CHUNK_MAX_CHARS 且非 chunk）仍用 `_truncate_by_sentence(·, CHUNK_MAX_CHARS)` 防单条巨物（存量保护，随迁移脚本退役）
  - `max_tokens=None` 时不设上限（向后兼容现有 3 个调用点中未传参者）
- 三个调用点同步传入与 `get_context` 相同的预算值：
  - `roleplay_prompt_assembly.py` L4785 传 1500
  - `websocket.py` L1275、`chat.py` L128 传各自 `get_context` 用的 max_tokens（实施时核对，缺省 2000）

### 4.6 新增 `backend/scripts/_rechunk_memories_semantic.py`
- 存量迁移：扫描 `role='assistant'` 且 `len(content) > CHUNK_MAX_CHARS` 且无 `#chunk` 标记的行
- 逐条：语义切分 → 删旧行 → 按新块插入（**保留原 created_at / branch_id / importance_score / session_id**）
- `--dry-run` 模式默认开启，打印将改动的条数与样例；`--apply` 才落库
- 容器内执行（照 `_clean_memory_pollution.py` 模式）：`docker exec palink-ai-backend-1 python scripts/_rechunk_memories_semantic.py --apply`

### 4.7 修改 `backend/app/memory_module/config.py`
- §3.2 参数表全部注册（os.getenv 模式与现有一致）

## 5. 数据流（改后全貌）

```
AI 回复 (800字, 3个话题)
  │ clean_memory_content（现状保留）
  ▼
MemoryService.store_memory(role='assistant')
  │ len≥250 → semantic_split
  │   ├─ 句子切分 ~25 句
  │   ├─ embed(25句) ←── 1 次 HTTP（Ollama bge-m3）
  │   ├─ 缓冲窗口余弦 → 第95百分位断点 → 3 个语义块
  │   └─ 尺寸整形（120~450字）
  ▼
storage.store_chunks()  ← 1 个事务，3 行，embedding 直写
  id=101 "#turn:ab12 #idx:0/3"  吃饭对话块
  id=102 "#turn:ab12 #idx:1/3"  打架对话块
  id=103 "#turn:ab12 #idx:2/3"  回忆往事块

—— 数日后 ——
用户:"上次那场打斗是怎么回事?"
  ▼
get_context(query)
  ├─ STM 最近5条
  ├─ LTM 向量检索 → id=102 高分命中
  ├─ 邻居扩展: 预算够 → 带上 id=101, id=103
  ▼
build_memory_context(mem_ctx, max_tokens=1500)
  → 注入 3 个块的完整原文（无砍头）
```

## 6. 性能预算（长回复最坏路径）

| 步骤 | 耗时估算 | 依据 |
|---|---|---|
| 句子切分+整形 | <1ms | 纯字符串/numpy |
| 批量嵌入 25 句 | 50~200ms | 单次 HTTP，Ollama 核显加速（bge-m3 已实测 /api/embed 200） |
| 断点计算 | <1ms | 1024维×25 的余弦矩阵 |
| 批量 INSERT | <10ms | 单事务 3~5 行 |
| **合计** | **<300ms，全部在后台线程** | 对话主链路零延迟增加 |
| 短回复(<250字) | **0 额外开销** | 短路返回，走现有单条路径 |

## 8. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| 百分位阈值在真实对话上切得过碎/过粗 | 中 | 参数 env 可调；`_rechunk` 脚本带 `--dry-run` 样例输出，先看真实切分效果再 apply；上线后可随时调参重跑 |
| Ollama 宕机时批量嵌入失败 | 低 | embedder 自带 fastembed 降级；store_chunks 再兜底 NULL+后台重试，行不丢 |
| PG/SQLite topics LIKE 方言差异 | 低 | `is_postgres` 分支已存在，PG 用 `topics::text LIKE`，实现时以容器内实测为准 |
| 压缩服务删掉块组中间块导致邻居断裂 | 低 | 邻居查询按现存 id 取，缺失侧静默跳过（可接受：压缩本就是有损） |
| 新旧行为混合期（旧整段+新块共存） | 低 | 注入端兜底截断仅作用于旧巨物；迁移脚本一次性拉齐 |
| 混合维度向量（Ollama 降级 fastembed 时 512 vs 1024） | 低 | 与现状完全相同（现单条路径同样存在），非本次引入 |

## 9. 回滚方案

- **运行时回滚**：`MEMORY_SEMANTIC_CHUNKING=false` 重启 → 新写入立即回到整条模式；已切分的块照常检索注入（块本身是合法记忆）
- **代码回滚**：改动集中在 4 个文件的新增方法 + 1 个函数内逻辑，git revert 单点干净
- 注入端改动向后兼容（不传 max_tokens 行为=只去掉砍头+遗留兜底），可独立保留
