## 1. 现象（用户侧）

1. 在角色卡 A（露缇雅1.2）对话中解锁了 CG 立绘。
2. 用户**把库里所有卡片删干净**，重新导入一张**全新**的同款卡 B。
3. 卡 B 的 CG 图鉴**仍然是已解锁状态**。

用户预期（原话）：「这玩意不应该是跟着卡的 ID 走吗？然后卡的 ID 又跟着用户。」
→ 即：解锁态应以 `character_id` 为键，且 `character_id` 归属 `user_id`，因此换卡不污染、换账号不串、换设备能带走。

**现状三头都没做到**：解锁态既不按角色、也不按用户、也不落库。

## 2. 已取证事实

> 证据分级：**[一手]** = 本次会话我亲自读到的原文/运行结果；**[二手]** = 子 Agent 报告，未经我逐行复核，施工前必须自行确认。

### 2.1 [一手] 解锁态确实存在浏览器 localStorage，且键内无任何角色标识

在 `http://localhost:13000` 页面执行 `localStorage` 遍历，实测返回：

```
key   = "tavern_cg_album_unlocked"   len=15   value = ["露出魔纹1","哭哭1"]
key   = "tavern_cg_album_pos_v2"     len=48   value = {"left":13.04,"top":542.57}
（该 origin 下 localStorage 共 12 个键）
```

值就是用户截图里那两条 CG 名。**键名里没有 character_id、没有角色名、没有 user_id。**

### 2.2 [一手] 这个键是「卡自带的脚本」写的，不是 Palink 写的

Postgres `characters.extensions.tavern_helper` 原文（卡 `a36680d6-d714-4be9-98b8-f145173c3ae9`，偏移 4150–4900）：

```js
try { topWin.__TAVERN_CG_ALBUM_CLEANUP__(); } catch (e) { console.warn(e); }

// 2. 本地存储键名
const STORAGE_KEY_UNLOCKED = 'tavern_cg_album_unlocked';
const STORAGE_KEY_POS      = 'tavern_cg_album_pos_v2';

// 3. CG 完整数据字典 (140 项)
const CG_DICT = { '亲吻1': 'https://i.postimg.cc/...', ... }
```

两个结论：
- 键名硬编码在**卡**里 → 我们改不了卡，只能在 Palink 侧拦。
- `topWin` 字样说明脚本**主动往顶层窗口爬**，绕开任何 iframe 级隔离。

### 2.3 [一手] Palink 执行这类卡脚本的方式 = 往真实页面塞 `<script>`，不劫持 localStorage

`frontend/src/lib/sillytavern/card-script-runner.ts:212-224`：

```ts
const asModule = isTopLevelEsm(content);
const el = document.createElement('script');
el.setAttribute(CARD_SCRIPT_ATTR, id);
...
el.type = 'text/javascript';
el.setAttribute('nonce', 'palink-smart-card');
el.textContent = patchCardContentLoaded(content);
```

`card-script-runner.ts:241` `container.appendChild(el)` → 在**活文档**里执行。
调用点：`frontend/src/components/views/character/CharacterChat.tsx:1574`「[CARD-SCRIPT] 执行卡自带 tavern_helper 脚本（CG 图库悬浮按钮、图鉴、状态栏特效等）」。

→ 脚本里的 `localStorage` 就是真的 `window.localStorage`，全局一份。

### 2.4 [一手] Palink **已经有**按角色隔离的存储桶，但只服务 iframe 那条路径

`frontend/src/components/ui/custom/smart-card-runtime/storage.ts:54-71`：

```ts
export const SMART_CARD_STORAGE_PREFIX = 'palink:smart-card-storage:v1:';

export function getSmartCardStorageNamespace(context, sourceFingerprint) {
  const characterId = normalizeSmartCardStorageId(context.characterId, 'global-character');
  const sessionId   = normalizeSmartCardStorageId(context.sessionId, 'global-session');
  const sourceId    = normalizeSmartCardStorageId(sourceFingerprint, 'source');
  return `${characterId}:${sessionId}:${sourceId}`;
}
```

**这是本 SPEC 最重要的现成资产**：隔离方案不用从零设计，把 §2.3 的裸 `<script>` 通道接进这套桶语义即可（或至少复用其键格式）。
注意它仍然只是 localStorage，**不落库**，所以只解决"换卡不污染"，不解决"换设备能带走"。

### 2.5 [一手] Palink 交给插件的"角色身份"是用**名字**算的，不是 UUID

`frontend/src/components/views/character/CharacterChat.tsx:1644-1651`：

```ts
// ST 插件（如 Galgame 界面插件）通过 characterId / name2 / this_chid 识别当前角色，
// 缺失时回退到 "default" 键……使用角色名 charCode 哈希作为非零数字 ID，确保不同角色有不同键。
characterId: selectedCharacter.name
  ? Array.from(selectedCharacter.name).reduce((acc, c) => acc + c.charCodeAt(0), 0) || 1
  : 1,
characterUuid: selectedCharacter.id,   // ← 真 UUID 在另一个键上
name2: selectedCharacter.name,
```

注释自称"确保不同角色有不同键"，实际是**同名必然同键**。
同一份哈希算法在 `frontend/src/components/st-plugin-ui-host/Live2DPoolPanel.tsx:45-48` 被复制了一份（`pluginCharacterId(name)`），用于 `:147` 的 `modelId`。

### 2.6 [一手] 库里存在 4 张同名卡，id 各不相同

```
name=露缇雅1.2  id=13db28eb-…  plugin_scope_mode=NULL       plugin_rows=0
name=露缇雅1.2  id=be906232-…  plugin_scope_mode=allowlist  plugin_rows=1
name=露缇雅1.2  id=8ca6bb91-…  plugin_scope_mode=allowlist  plugin_rows=1
name=露缇雅1.2  id=a36680d6-…  plugin_scope_mode=allowlist  plugin_rows=1
```

→ 用户"删光再导"其实每次都是**新 id、同名**。§2.5 的身份算法保证它们撞在一起。

### 2.7 [一手] 后端没有任何地方存这份解锁态

- `character_expressions` 表**整表为空**（`select count(*)` → 0）。列仅 `id, character_id, expression_name, file_path, created_at`。
- `character_plugin_state` 只有 `(character_id, plugin_id, enabled, source)`，**无载荷列**。
- `chat_variables` = `(session_id, key, value)`，**无 character_id**。
- `global_variables` = `(key, value, user_id)`，**无 character_id**。
- `characters` 表无解锁相关列。

→ 结论：解锁态**从来没进过后端**。"删卡没删干净"不是后端漏清理，而是后端根本不知情。

### 2.8 [一手] 后端有一处按名字找角色的隐患（当前未发作）

`backend/app/api/expressions.py:87-94`：

```python
def _get_character_by_name_or_404(db: Session, name: str, user: User) -> Character:
    character = db.query(Character).filter(
        Character.name == name,
        Character.user_id == user.id,

```

无 `ORDER BY`、同名 4 行 → 返回哪一行取决于 DB 物理顺序。调用方：`/api/expressions/get?name=`、`/api/expressions/merge`、`/api/expressions/delete`。
因 §2.7 表为空，**目前不产生用户可见故障**，但一旦用户开始上传自定义表情就会串卡。列为本 SPEC 的 P2 顺带修。

### 2.9 [二手，施工前必须自证] 气泡插件侧的同名碰撞与 IndexedDB 全局键

子 Agent 报告了以下事实，我**未逐行复核**，不要照抄结论：

## 3. 根因分解（三个独立缺陷，可分别验收）

| # | 缺陷 | 层次 | 直接后果 | 证据 |
|---|---|---|---|---|
| D1 | 卡/插件脚本的本地存储**无角色命名空间** | 前端执行通道 | 换卡、重导入、换角色全部共用一份 | §2.1–2.4 [一手] |
| D2 | Palink 提供给脚本的角色身份**由名字派生**而非 UUID | 前端上下文 | 同名卡必然同键；UUID 明明有却没人用 | §2.5–2.6 [一手] |
| D3 | 这类状态**完全不落库** | 前后端之间 | 换浏览器/换设备丢进度；同浏览器多账号互相可见 | §2.7 [一手] |

用户报的现象 = D1 为主，D2 加重，D3 是同一层的另一半问题。

**多用户产品口径**（本项目是给外部用户用的，不是自用玩具）：D3 里"同一台设备两个账号互相看到对方的解锁立绘"是隐私问题，优先级不低于 D1。

## 4. 目标 / 非目标

### 目标
- G1：卡脚本与插件写入的本地状态，**默认按 `character_id` 隔离**。删卡 A 不得影响卡 B。
- G2：同名不同 id 的卡**不得互读**（修 D2）。
- G3：解锁态等"进度类"状态**落库**，按 `(user_id, character_id)` 归属，换设备可恢复。
- G4：删卡时**连带清理**该卡的服务端状态与本地命名空间。
- G5：不破坏既有能正常工作的卡（尤其 iframe 路径 §2.4 已隔离的那套）。

### 非目标
- ❌ 不改任何卡的内容、不改 `CG_DICT`、不动卡脚本源码。
- ❌ 不实现"跨卡共享解锁进度"（那是 D1 的现状，不是需求）。
- ❌ 不碰 `st-compat` / `st-native`（已删除，见 AGENTS.md）。
- ❌ 不动 `st_groups.py`（名为 st_ 实为 Palink 自有群聊后端，勿误删）。
- ❌ 不动 `frontend/dist`、`backend/data`（AGENTS.md 红线）。

## 5. 方案设计

### P0 — 卡脚本 localStorage 命名空间拦截（治 D1）

**落点**：`frontend/src/lib/sillytavern/card-script-runner.ts` 的裸 `<script>` 注入通道。

**做法**：在把卡脚本注入活文档之前，为其提供一个按角色加前缀的 `localStorage` 视图，使脚本内的
`localStorage.getItem('tavern_cg_album_unlocked')`
实际读写
`palink:card-storage:v1:<characterId>:tavern_cg_album_unlocked`

两种实现路线，**先做路线甲**（改动小、可回退）：

- **甲｜源码改写**：注入前对脚本文本做受限改写，把 `localStorage` 引用替换为一个包装对象（如 `__palinkNsStorage`）。必须同时覆盖 `sessionStorage`、`window.localStorage`、`topWin.localStorage`、`parent.localStorage` 等取法（§2.2 已证明该卡会用 `topWin`）。改写失败/不确定的分支一律**放行原样**并打点，不得让卡脚本抛错。
- **乙｜全局劫持**：在角色扮演页挂载期间用 `Object.defineProperty(window,'localStorage',…)` 替换。风险高（影响第一方代码自身），且 `legacy-st-sim.ts` 已有类似劫持（[二手] 称 `!ctx.trustedNative` 时才装），两条劫持会打架。**除非甲被证伪，不要走乙。**

**键前缀格式**：复用 §2.4 `SMART_CARD_STORAGE_PREFIX` 的语义，新增并列常量：
```
export const CARD_SCRIPT_STORAGE_PREFIX = 'palink:card-storage:v1:';
key = `${CARD_SCRIPT_STORAGE_PREFIX}${characterId}:${rawKey}`
```
`characterId` 必须是 **UUID**（见 P1），不得用名字哈希。

**必须同时处理的通道**（先复现再定，见 §2.9）：
- IndexedDB（`BubbleDialogueAvatars` 的 `cg_groups` / `cg_images` 主键不含角色）
- `__palink_extension_settings` 全局单例
- `palink_plugin_${pluginName}`（[二手] 称只按插件名分键）
- `galgame-ui-plugin_char_enabled`（[二手] 称按 `this_chid` 分键，且现有代码靠"每次注入时整键删除"来兜底，见 `sillyTavernPluginRuntime.ts:1485-1497`）

> 若 IndexedDB 通道复现确认存在同类问题，P0 范围要扩到 IDB 命名空间劫持，工作量显著上升 —— 届时**先回报，不要闷头扩面**。

### P1 — 角色身份改用 UUID 派生（治 D2）

**落点**：
- `frontend/src/components/views/character/CharacterChat.tsx:1647`
- `frontend/src/components/st-plugin-ui-host/Live2DPoolPanel.tsx:45-48`（重复实现，一并收敛为单一函数）

**做法**：新增一个共用函数（建议放 `frontend/src/lib/sillytavern/`），由 `characterUuid` **稳定**派生非零数字 id：
```ts
// 同一 UUID 在任何会话/任何设备得到同一数字；不同 UUID 得到不同数字
export function pluginCharacterIdFromUuid(uuid: string): number
```
要求：
1. ST 插件普遍把 `characterId`/`this_chid` 当**数字**用 → 必须返回 number，且 **≠ 0**（0 在 ST 语义里常当"未选中"）。
2. 派生必须**确定性**（不能用 `Math.random`、不能用 `Date.now`），否则刷新一次进度就"丢"了。
3. 冲突处理：4 张同名卡现在会得到同一哈希，改后应各不相同；但历史 localStorage/IDB 里已有按旧哈希写的键 → 见 §6 迁移。
4. 两处重复实现收敛为一处，禁止再复制第三份。

**注意**：`characters` 表里存在 `plugin_scope_mode=NULL` 的老行（§2.6 的 `13db28eb`），别假设所有卡都有 UUID 之外的稳定整型主键。

### P2 — 服务端落库 + 删卡连带清理（治 D3、G3、G4）

**新增表**（alembic 迁移；注意 AGENTS.md 提到的 `_RUNTIME_COMPAT_COLUMNS` 红线，**禁止回填** `silly_tavern_mode` / `silly_tavern_theme`）：

```
character_plugin_storage
  id            varchar pk
  character_id  varchar  not null   -- FK characters.id，随卡删除级联
  user_id       varchar  not null   -- 冗余存归属，用于越权校验
  ns            varchar  not null   -- 'local' | 'session' | 'idb:<store>'
  key           varchar  not null
  value         text
  created_at / updated_at
  UNIQUE (character_id, ns, key)
```

**端点**（沿用现有认证依赖 `get_st_current_user`，别新造鉴权）：
- `GET  /api/characters/{id}/plugin-storage?ns=local` → `{key: value}`
- `PUT  /api/characters/{id}/plugin-storage` → 批量 upsert（**按 key 合并，不得整命名空间覆盖**）
- 越权：`character_id` 不属于当前 user → 404（不要 403，避免探测）

**前端**：P0 的命名空间层加"写穿 + 启动拉取"：本地永远先命中（离线可用、不阻塞首屏），写成功后同步服务端；进入角色页时拉一次覆盖本地。
**失败必须静默降级为纯本地**，不得让同步失败变成卡脚本崩溃。

**删卡连带清理**：`characters` 删除路径中级联删 `character_plugin_storage`（FK `ON DELETE CASCADE` 或显式删），并让前端在切换/删除卡时清掉对应命名空间的本地键。

**顺带修 §2.8**：`_get_character_by_name_or_404` 改为优先按 id 查；只有 name 可用时，加确定性排序（`ORDER BY created_at`）并在命中多行时 `logger.warning` 登记，长期目标是让前端全部改传 id。

## 6. 迁移与兼容

> ⚠️ **§6 已于 2026-10-02 整节作废并删除实现**。原因：本产品上线前**没有真实用户**，
> 迁移没有保护对象；而「谁先读到谁拿走」的旧键回读会把上一张卡的解锁**污染给新导入的卡**，
> 正好制造本 SPEC 要修的那个现象。用户口径明确：只要卡与卡之间隔离，其余一概不管。
>
> 现状：`CardScriptStorage.getItem` 只读本卡命名空间，**不回读旧全局键、不删旧键、不登记 claim**；
> `migrateLegacy` / `readClaimMap` / `writeClaimMap` / `LEGACY_CLAIM_KEY` 已全部移除，
> 产物里已无 `palink:card-storage:legacy-claim:v1` 字面量。
> 回归锁：`card-script-storage.test.ts` 的「不回读旧全局键」四条。
>
> **后人请勿恢复本节。** 若将来真有存量用户需要保进度，那是另一个带数据归属方案的新议题，
> 不是把这段代码加回来。

1. **旧键读取兜底（只读不写）**：新命名空间读不到时，允许回读一次旧的全局键/旧哈希键，命中则迁移写入新键并删除旧键。目的：让老用户在**当前这张卡**上的进度不丢。
2. **同名多卡不可无损迁移**：旧全局键本来就没有角色归属，无法判断该给哪张卡。规则：**只迁给该用户最近一次对话的那张卡**，其余卡视为未解锁。此规则必须在 PR 描述里写明，并在 §7 用例里覆盖。
3. **不做双写长期兼容**：迁移窗口只存在于"读旧键"一次，之后旧键删除，避免隔离形同虚设。
4. 迁移逻辑要有开关或可重入（幂等），失败不得阻塞渲染。

## 7. 验收标准

### 自动化
- 后端：`cd backend && python -m pytest tests/` —— 基线 **1612 passed / 42 skipped / 0 failed**（2026-10-02 实测），施工后必须仍 `failed=0`。
  - ⚠️ **必须进容器跑**（宿主机静默少 9 例）。
- 前端：`cd frontend && npx tsc --noEmit` 通过；`npx vitest run` **failed=0**（用例数会随并行会话增长，只认 failed=0，别拿固定数字当基线）。
- 新增 vitest 用例至少覆盖：
  1. 同一 rawKey 在两个不同 `character_id` 下得到不同命名空间键，且互不可见。
  2. `pluginCharacterIdFromUuid` 确定性（同 uuid 两次调用同值）、非零、不同 uuid 不等。
  3. 旧全局键 → 新键的迁移：命中后旧键被删、新键可读。
  4. 同名两张卡（不同 uuid）不共享解锁态。
  5. 服务端同步失败时降级为纯本地且不抛错（mock fetch reject）。
- 新增 pytest 用例至少覆盖：
  1. `PUT` 按 key 合并，不覆盖同 character 其他 key。
  2. 越权访问他人 `character_id` → 404。
  3. 删卡后 `character_plugin_storage` 无残留。
  4. `_get_character_by_name_or_404` 同名多行时返回确定性那一行。

实际落地方案比本节初稿更收敛，两处关键更正：

   实现上用 `installIdbShimPropagation` 同时拦 `srcdoc` 属性赋值与 `setAttribute('srcdoc')` 两条写入路径，
   把一段自举脚本插到子帧文档最前面。

**交付物**：`frontend/src/lib/sillytavern/card-idb-namespace.ts`（TS 实现 + `IDB_NS_RUNTIME_SOURCE` 纯 JS 源码串）、
