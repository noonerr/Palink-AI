## 1. 对 spec 的独立复核（全部为本次实测，非引用）

### 1.1 五处出口"都没有 `data`" —— 确认成立

逐处读源码，五处归一化**只输出 `extra`，无 `data` 键**：

| # | 位置（实测行号） | 输出 `data`？ | 文件状态 |
|---|---|---|---|
| 1 | `smart-card-runtime/frame-shim/legacy-st-sim.ts` `normalizeChatMessage`（约 837–893） | ❌ | **脏**（含未提交 P0-FIX，见 §2.3） |
| 2 | `smart-card-runtime/SillyTavernCompatRuntime.ts` `normalizeChatMessage`（约 2762–2791） | ❌ | 干净 |
| 3 | `views/character/CharacterChat.tsx` `buildSmartCardChatEntry`（约 145–176，`extra: boundaryExtra`） | ❌ | 干净 |
| 4 | `CharacterChat.tsx` `__palinkChatMessages`（约 1537–1554，`extra: m.extra \|\| {}`） | ❌ | 干净 |
| 5 | `CharacterChat.tsx` `stContext.chat`（约 1745–1756，`extra: m.extra`） | ❌ | 干净 |

⇒ **spec 层二（读侧供给缺失）成立**，且是结构性的：数据（`extra.variables`）到得了出口，只差最后那个键名。

### 1.2 `data = extra.variables` 这个写法对不对 —— 对

卡的判据是（spec §1.2 授权引文）：

```js
const gameData = messages[0].data;
const characterData = gameData.display_data || gameData.stat_data;
```

`data` 需要是一个**含 `.stat_data` 的对象**。而库里 `extra.variables` 的形状就是 `{"stat_data": {...}}`
（见 §1.3）⇒ `data = extra.variables` 时 `data.stat_data` 命中。**不能**写成 `data = extra.variables.stat_data`（那样 `data.stat_data` 反而落空）。
⇒ spec §4.2 的 `data = (extra.variables 非空) ? extra.variables : undefined` **正确**。

### 1.3 库内取证 —— 逐条复核，全部一致

DB：容器 `palink-ai-db-1`，`psql -U ai_user -d ai_hub`；消息表是 **`character_chat_messages`**（不是 `messages`；spec 附录 A 未写明表名，是本次补上的口径）。

| spec 说法 | 实测结果 | 一致？ |
|---|---|---|
| 2740 无 `variables`、2741 无 | `character_chat_messages` 2739/2740/2741 → `extra::jsonb ? 'variables'` = **f / f**（2739 为 t） | ✅ |
| 2739 有（含 `stat_data`），仅 1 个键 | 2739 `jsonb_object_keys(extra->'variables')` = **`stat_data`（1 行）** | ✅ |
| 露缇雅会话 `chat_metadata` 787 字节含 variables | 会话 `f25daab6…` → `length=787`、含 `variables`、首段即 `stat_data.环境/露缇雅` | ✅ |
| 神明会话 `chat_metadata = {}`（2 字节） | 会话 `3d631311…` → `length=2`、`{}`、无 variables | ✅ |
| 2740 属神明卡（user 49） | 2740 `session_id=3d631311…`；`character_chat_sessions.3d631311.character_id=2687f81d…`、`user_id=49` | ✅ |

**补充实测（spec 未写）**：全库 `extra.variables` 的顶层键分布 = `stat_data` **48 条** / `pruned` **21 条**。
即 `data = extra.variables` 是**原样透传**（可能同时带 `pruned`），**不要做任何归一化**，与 agent 1 的结论一致。

### 1.4 前置 P0-1（读优先级倒挂）—— 确认已修

`silly_tavern.py` 约 1339 行：

```python
merged_variables = dict(db_variables)
```

⇒ 真源（`chat_metadata.variables`）已胜出，F-A1 的前置条件满足。

### 1.5 解析白名单缺 `add` —— 确认

`mvu_engine.py:83`：`_JSONPATCH_OPS = {"replace", "delta", "insert", "remove", "move"}` —— **无 `add`**。
与 spec §2.1 层三一致。

### 1.6 F-D1 的文件归属 —— spec 写错，agent 1 对

实测 `CharacterCardRenderer.tsx` 约 1261–1265：

```js
const sandbox = effectiveMode === 'static-html'
  ? ''
  : trustedNative
    ? `allow-scripts allow-same-origin ${CAPABILITY_TOKENS}`
    : `allow-scripts ${CAPABILITY_TOKENS}`;   // ← 非信任卡：无 allow-same-origin
```

非信任卡的 iframe 是 `allow-scripts`（**不透明源**）⇒ 父窗口（`Message.tsx` 所在文档）**读不到卡内 DOM**。
spec §3.3/§6 把 F-D1 放在 `Message.tsx` 做文本替换，**结构上不可能**。
⇒ F-D1 只能落在**跑在 iframe 内部**的 shim（`legacy-st-sim.ts` / `SillyTavernCompatRuntime.ts`）。
**这一改判顺带解开了 spec 说的"F-D1 撞脏文件"死结**（shim 文件可用）。

## 4. 决策点（需老板拍板）

### Q1｜F-D1 落点改判：接受吗？
spec 写 `Message.tsx`（实测不可行，§1.6）；agent 1 主张改落 iframe shim（实测可行）。
- **A（推荐）**：采纳改判，F-D1 落 `legacy-st-sim.ts` / `SillyTavernCompatRuntime.ts` 的 shim 脚本。
- B：维持 spec 原案（不推荐 —— 结构上做不到）。

### Q2｜开场白那一刻给什么？（spec §8 Q1）
- **A（推荐）**：**只给一句人话提示**（"这张卡的状态要聊过一轮、模型交出状态更新后才会出现"）。理由：造空壳会让卡凭空出现一张假表，且掩盖"模型没交表"这类真问题。
- B：造空壳初始状态（面板立刻出现、值显示"未知"）。
- C：本件不做 F-E1，只做 F-D1。

### Q3｜后端 F-A2/F-B1/F-C1：等收工，还是授权插入？
后端正被一条独立 MVU 工作流占用（§2.4）。
- **A（推荐）**：**等收工**。这批不是线上火，插进去会夹带别人半成品。
- B：授权插入（需承担二次撞车与提交纠缠）。
