## 二、判断什么：两个信号

### 信号 1：`gap` —— 距上一条消息多久（判断"缓存还在不在"）

- `gap` 小 ⇒ 上一条刚发不久，服务端前缀缓存大概率还在 ⇒ **继续用长方案，别切换**
- `gap` 大 ⇒ 缓存已过期 ⇒ 这一轮必然冷启动，要付全价 ⇒ **先用短方案探路**

⚠️ **阈值要取乐观（偏大）**。理由：
- 猜错方向 A（以为还在、其实没了）：这轮按全价读长上下文 = 与纯 G 相同，**不比 G 更糟**；
- 猜错方向 B（以为没了、其实还在）：白白放弃命中，还多付一次短窗口的钱。
⇒ 误判代价不对称，**建议 `CACHE_TTL_GUESS = 30min`（可配），宁可乐观。**

### 信号 2：`N_avg` —— 这个会话历史上"一次来连聊几轮"

用消息时间戳切分出历史会话段（相邻消息间隔 > `SESSION_GAP` 视为换段），
统计每个段的长度，取均值 ⇒ `N_avg`。它决定**长方案该封顶多少**：

| `N_avg` | 含义 | 封顶 C |
|---|---|---|
| < 3 次样本 | 数据不足（新会话） | **24 条**（默认保险档） |
| ≤ 2 | 每次来就说一两句 | 24 条 |
| 3 ~ 4 | 中等 | 48 条 |
| ≥ 5 | 一聊就停不下来 | 96 条 或 全量 |

⇒ 封顶越大，冷启动/升级那轮重读得越多，所以只有确认用户聊得久才放大。

## 三、状态机（无状态实现，不需要持久化）

```
每轮装配前：

    gap = now - last_message.created_at
    N_avg = 该会话历史平均连聊轮数（会话级缓存，不每轮重算）

    if gap < CACHE_TTL_GUESS:
        ── 缓存大概率还在 ──
        mode = APPEND                      # 追加式
        history_from = 代际锚点(封顶 C)     # (ti // C) * C，段内单调递增 ⇒ 前缀稳定
        memory_budget = 0 或 小值           # 原文已在上下文里，不需要回忆
    else:
        ── 冷启动：先探路 ──
        mode = PROBE                       # 短窗口
        history_from = ti - 6              # 最近 6 条
        memory_budget = 6000               # 靠回忆补（块级命中 80.7%）

    下一轮若 gap 变小 ⇒ 自动回到 APPEND（升级）
```

**关键性质：无状态。** 不需要记住"上一轮用了什么模式"，
因为 `gap` 本身就编码了"是否连续"——连续 ⇒ 追加，断开 ⇒ 探路。
省掉持久化字段，也避免状态与真实缓存不一致。

### 为什么探路轮用短窗口却不丢东西

探路轮上下文虽短，但**回忆系统**（向量检索）补上了远期内容，实测块级证据命中 80.7%（预算 6000）。
一旦确认连续聊，立刻升级为追加式，原文全部回到上下文。

## 五、落地改动点（3 处，均为小改）

### 1. 新增 `resolve_context_mode(db, session_id, branch_id, now)` → `(mode, cap, mem_budget)`

放在 `backend/app/services/character_message_builder.py` 同级，或 `roleplay_prompt_assembly.py` 附近。
职责：查最后一条消息时间 → 算 `gap`；查会话历史段 → 算 `N_avg`；返回本轮模式。
**必须做会话级缓存**（`_cache` dict，见 `PromptAssemblyRequest._cache` 既有模式），不要每轮全表扫时间戳。

### 2. `build_character_chat_messages` 支持"代际锚点"而不仅是"最近 N 条"

现状（`:216-228`）是 `order_by(created_at.desc()).limit(history_limit)` —— **只能取最近 N 条，会滑动**。
追加式需要的是"从锚点到当前"，锚点 = `(已加载条数 // cap) * cap`：

```python
# 追加式：锚点按 cap 对齐，段内只增不删 ⇒ 前缀稳定
if mode == APPEND:
    anchor = (total_count // cap) * cap
    history = query.order_by(asc).offset(anchor).all()   # 不是 limit(N)
```

⚠️ 现在是 `limit()` 语义，改成 `offset()` 需要确认 `_get_full_branch_history` 分支路径同样支持。

### 3. 记忆预算跟着模式走

现状 `roleplay_prompt_assembly._resolve_memory_max_tokens` 只读用户档位。
追加式下应该把回忆预算降到 0（或很小）：
`_memory_gate_should_skip` 已有 `history_truncated` 判据，
**可复用**：历史未被截断时不检索 ⇒ 追加式天然跳过回忆，无需新开关。
⇒ **先验证这条是否已自动生效，能生效就不用改第 3 点。**

## 五·五、★ 缓存不用猜：API 响应里直接返回命中数（2026-10-11 查证）

### 官方口径

**DeepSeek 官方文档《上下文硬盘缓存》原文**：
> 缓存构建耗时为秒级。**缓存不再使用后会自动被清空，时间一般为几个小时到几天**
> 缓存系统以 **64 tokens** 为一个存储单元，不足 64 tokens 的内容不会被缓存
> 缓存系统是"尽力而为"，不保证 100% 缓存命中

⇒ **TTL 是"几小时到几天"量级，不是分钟级。**
（网上流传的"5~15 分钟"来自第三方博客，与官方文档矛盾，不采信。）
⇒ 我仿真里用的 **64 token 粒度与官方一致**，仿真方法可信。

### 能直接读到！不需要猜

两家都在**每次响应的 `usage` 里**返回命中/未命中 token 数，零额外成本：

| 供应商 | 字段 | 我们代码读到了吗 |
|---|---|---|
| **DeepSeek** | `usage.prompt_cache_hit_tokens` / `usage.prompt_cache_miss_tokens` | ❌ **没有**（专有字段名，代码只认 OpenAI 风格） |
| **MiMo**（OpenAI 风格） | `usage.prompt_tokens_details.cached_tokens` | ✅ 解析了，但**没落库** |

代码位置：`backend/app/services/stream_builder.py:127-128`（流式）、`:204-205`（非流式）
```python
prompt_details = usage.get("prompt_tokens_details") or {}
result.cache_read_input_tokens = int(usage.get("cache_read_input_tokens", 0)
                                    or prompt_details.get("cached_tokens", 0) or 0)
```
⇒ **只有 OpenAI/Anthropic 风格的回退链，没有 DeepSeek 的字段名。**
⇒ 走 DeepSeek 时 `cache_read_input_tokens` **恒为 0**（不是真的没命中，是没读到）。
⇒ 而且 `character_chat_messages` 表只有 `tokens / prompt_tokens / reasoning_tokens`，
   **连已经解析出来的 `cache_read_input_tokens` 都没落库**。

### 三方实测印证（间接验证仿真）

独立站点 chat-deep.ai 2026-07 实测（deepseek-v4-flash，非流式）：
"精确追加"请求（前缀完整复用 + 只加新内容）达到 **98.23% 命中**
（6,906 prompt tokens → 6,784 hit / 122 miss）。
⇒ 与本报告仿真的 G 方案 **95.5%** 同量级，**说明"追加式能拿到 ~95%+ 命中"这个仿真结论是可信的**，不是纸面推算。

### ⇒ 结论：把"猜 TTL"换成"看上一轮的真实命中数"

这是本 spec 判据的**最重要改进**——原来用 `gap < CACHE_TTL_GUESS` 猜缓存还在不在，
现在可以直接用上一轮响应里的真实命中数：

```
上一轮记录的 cache_hit / (cache_hit + cache_miss) ≥ 某个阈值（如 0.8）
    ⇒ 缓存机制工作正常 ⇒ 本轮继续用追加式
上一轮 = 0 或很低
    ⇒ 缓存已失效 ⇒ 本轮探路（短窗口 + 回忆）
```
⇒ **不再依赖"几个小时到几天"这个模糊区间，也不再依赖猜的 30 分钟阈值。**

**先决条件（必须先做，很小）**：
1. `stream_builder.py` 两处 usage 解析补上 DeepSeek 字段名
   （`prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`），并新增 miss 字段；
2. `__slots__`（`:10`）加 `cache_miss_input_tokens`；
3. 把 hit/miss 两个数**落库**（`character_chat_messages` 加列，或先写日志）；
4. 上线跑几天 ⇒ **拿到真实命中率，用它校准本 spec 的所有成本比**。

### ⚠️ 主动探测不可靠，别做

想法是"发个极小请求、前缀照抄，看它命不命中来判断缓存还在不在"。**不推荐**：
DeepSeek 官方说明"**前两次请求不会命中缓存**，前两次请求完成后系统才识别并落盘公共前缀，
第三次才命中" ⇒ 探测请求本身会改变缓存状态，读到的不是真实状态。
⇒ **被动读取每轮响应的 usage 才是正道**（零成本、不改变状态、每次真实调用都有）。
