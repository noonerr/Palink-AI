## 1. 问题一：历史消息正文样式丢失

### 1.1 现象复述
20 句对话，向上滚动到第 17 条 → 正文只显示纯文本、无角色卡美化；而经"故事线"跳转到第 17 条并刷新后 → 样式完整。

### 1.2 根因（一句话）
**卡片的 iframe 在"休眠"期间完成了加载，被唤醒时浏览器没有为它重新光栅化**，于是留在"只画了文字层、没画样式层"的状态；刷新等于冷启动直接渲染，所以正常。

### 1.3 机制拆解

**第一层：`content-visibility: hidden` 是问题载体本身**

`Message.tsx:653` 的 `SmartCardDormancyGate` 在卡片出视口时把子树设为：
```
overflow: hidden; visibility: hidden; content-visibility: hidden;
```
`content-visibility: hidden` 会让浏览器**跳过整棵子树的渲染工作**（这是它的设计目的，省合成层开销）。注释里 `Message.tsx:705-707` 明确写着"让浏览器跳过子树渲染（省掉合成层开销）"。

**第二层：为什么"唤醒后不自愈"**

用户描述的关键细节是"第 17 条"，而 20 条里第 17 条距视口并不远 —— 它恰好落在 `rootMargin` 一屏缓冲的**边界灰区**：
- 缓冲算法（`Message.tsx:669`）：`buffer = max(innerHeight, 480)`，上下各扩一个视口高。
- 滚动到第 17 条时，第 17 条**刚进入缓冲边缘**，其 iframe 正在加载；此时它被判为"睡着"（`content-visibility:hidden`）→ 加载在隐藏态下完成 → 唤醒时浏览器认为"反正没显示过"，未触发完整重绘。
- 而"故事线跳转 + 刷新"是**冷启动**：iframe 从可见态直接首次渲染，不存在"隐藏态加载完再揭开"这一步，所以正常。

**第三层：为什么"之前有 Agent 为优化性能做过修改，修复后问题依旧"**

该休眠机制经历了两轮修改，都没打到这个点：
1. `63a5638`（N-12）引入休眠，最初是**卸载 DOM** → 卸载后重建 iframe 触发重导航 → 引发 iOS 幽灵历史条目，于是改成不卸载。
2. 改为不卸载后，用 `content-visibility:hidden` 做视觉休眠（`PALINK_CARD_DORMANCY_UNMOUNT = false`）。

两轮改的都是**"卸载 vs 隐藏"**这个轴，**没人处理"隐藏态下加载完成后不重绘"**。前一个 issue 的修复（改为隐藏）恰好**引入了**当前这个 issue —— 卸载态不会有"隐藏加载"问题（每次都全新重建），隐藏态才有。

**第四层：另一个被误伤的机制（已排除，但要知道）**

历史上存在 `.mes-render-skip`（`content-visibility: auto` 挂在**消息行**上，跳过视口外消息绘制）。它的跳过条件依赖 `isHtmlOrCard`，而该判定（`Message.tsx:216` `isHtmlCardContent`）只认 `div/span/iframe` 等**渲染后**标签，跑在渲染之前、输入是模型原文 ⇒ 带卡片的 AI 消息会被误判成"纯文本"而被跳过。
该机制已由 `index.css:2459` 的删除注释与 `Message.tsx:1349-1358` 的删除注释标记为 **2026-10-05 已删除**，当前源码与构建产物均已不含（实测 `mes-render-skip` 命中 0）。**本条是"另一个曾造成同类现象的原因"，现已不存在，不要与当前根因混淆。**

### 1.4 现工作区修复及其局限

工作区已在 `SmartCardDormancyGate` 加入 `repaintKick`（`Message.tsx:663-679`）：唤醒时翻转一次 `transform: translateZ(0)` 强制该子树重排+重绘，并注明"不重载 iframe，不产生新导航，不违反 iOS 幽灵历史约束"。

**方向正确，但有两点需要后续确认（本文档不代为决定）：**
1. ~~`repaintKick` 未进 10-06 19:49 构建~~ → **【第二轮订正】已入包。** 首轮在 `index-Cgbqdx2G.js` 里搜字符串 `repaintKick` 得 0，
   是因为它在压缩后**函数名被变量化**（源码里是 `const repaintKick = () => {...}`，构建后成了 `const r=()=>{...}`），
   原字符串当然不剩。按**函数体特征**重搜（`requestAnimationFrame` + `translateZ(0)` 双次嵌套 + `IntersectionObserver`），
   在该分块 `pos 63147` 命中完整实现，且外层容器带 `data-palink-card-dormancy`（全分块命中 1）。
   ⇒ **P1 修复已在 19:49 构建上线**（源码 18:41 改完，早于 19:49 构建）。
2. **`transform` 翻转是否足以唤醒光栅化，未做真机验证**。`transform` 变化会被合成器加速、可能**正好被跳过**而不触发重绘 —— 这是该手法的经典失效模式。若真机复测仍复现，应换用必然触发重绘的属性（如 `opacity` 或对子树做一次 `display` 切换），或直接**取消 `content-visibility: hidden`**（保留 `visibility: hidden`；后者同样是隐藏，但不改变"是否需要渲染"的语义，退化为纯视觉隐藏）。

> **订正的方法论教训**：判断"某修复是否入包"，**不能靠搜源码里的函数名/注释文字** —— 压缩器会去掉注释、把局部函数名变量化。
> 唯一可靠的做法是**按函数体特征串**（调用关系、字面量、属性名）搜索，且**必须 glob 全部分块**。

### 1.5 判据
修好后应满足：**长会话向上滚动到任意历史卡片，不刷新即应有完整样式**。不能只测"故事线跳转+刷新"路径——那条路径绕过休眠，永远是好的。

## 2. 问题二：AI 输出时打开侧边栏极度卡顿

### 2.1 现象复述
AI 正在流式输出、打开侧边栏 → 网页严重卡顿，苹果旗舰机 + Safari 亦复现。

### 2.2 根因（三条叠加，主次分明）

**主因 A：每个 chunk 都触发一次全量状态更新**

流式回调链（`useCharacterChat.ts`）：
```
onChunk → scheduleStreamUpdate(assistantId, fullContent, fullReasoning)
        → requestAnimationFrame(flushStreamUpdate)
        → setMessages(prev => [...整数组拷贝 + 替换末条])
```
`flushStreamUpdate` 用 `messageIndexMapRef` 定位末条（避免 `findIndex`），但**仍然是整数组浅拷贝**，并且：
- `messages` 引用变化 → 依赖它的 `useEffect`（`updateMessageIndexMap`）→ `smartCardChatMessages` memo（尾条重建）→ `Message` 的 `pipelineResult` memo → **`formatMessage` 全链路（正则 + Showdown + DOMPurify）**。
- 后端 stream_builder 每秒可发几十个 chunk（OpenAI 兼容流），**每条都走一遍**。

这正是 `63a5638` 的 N-3 修复针对的场景 —— 但它只让**历史消息**（尾部 K=2 条之外）免于重算，**末条本身仍是每 chunk 全量重算**。

**主因 B：末条每帧裸跑 DOMPurify**

`Message.tsx:1028-1041`：`pipelineResult` memo 内对 `result.content || renderContent` 调 `sanitizeStCompatHtml`（DOMPurify 全量消毒）。**流式期间末条正文持续增长，等于对越来越长的字符串每帧做一次全量 HTML 消毒。**
而注释（`Message.tsx:1031-1033`）指出：流式末条渲染分支走「正在加载卡片…」占位 / `SmoothOutput`，**根本不读 `stCompatSanitizedHtml`** ⇒ 这笔开销**全程不可达、纯浪费**。

**次因 C：打开侧边栏时的额外重算**

打开侧边栏 → `handleToggleStoryline`（`CharacterChat.tsx:649-657`）→ `fetchBranchTree()` → `setBranchTree(data)`。
`branchTree` 是新对象 → `ChatSidebar` 重渲染 → `StorylineMap`（lazy chunk 已加载则同步渲染）→ dagre 布局重算 + React Flow 全图重挂。
**触发时机恰好在"流式正忙"时**，两份重活叠加。注意 `StorylineMap.tsx:1153` 有 `layoutCacheRef`（按 `branchTree` 引用缓存），但每次 `fetchBranchTree` 返回**新对象引用** ⇒ 缓存必然 miss ⇒ 每开一次侧栏都全量重算布局。

### 2.3 工作区修复
- `useCharacterChat.ts:333-347`：加 `STREAM_FLUSH_MIN_INTERVAL_MS = 100` 节流（约 10fps），`pending` 始终持全量累计串，只降刷新频率不改内容。
- `Message.tsx:1031-1041`：`needSanitizedHtml = !(streaming && isLast)`，流式末条跳过消毒。

**已实测进入 10-06 19:49 构建**（线上包中 `model_reasoning` 命中 0，即 P3 已入；P2 节流与 P3 同一批次）。

### 2.4 未处理、建议后续评估
- **次因 C 未动**：`fetchBranchTree` 每次返回新引用导致布局缓存恒 miss。可考虑：①侧栏打开时若 `branchTree` 已存在则跳过重拉；②`StorylineMap` 的布局缓存改为按内容签名（如节点数 + active_branch_id）而非对象引用。
- **节流值 100ms 是否合适**未做真机主观评估：过低（如 16ms）无收益，过高（如 250ms）会让打字机观感变顿。100ms 是保守起点，需真机确认"不卡且不顿"。

## 3. 问题三：思考内容两字两字重复

### 3.1 现象复述
思考阶段文本出现"II want Want To To"式重复（两个字符两个字符地重）。

### 3.2 根因（结论明确：**前端累加重复，不是模型问题**）

后端 `stream_builder.py:148-153`：
```python
if enable_thinking is not False:
    result.full_reasoning += reasoning
    resp["reasoning"] = reasoning
    resp["model_reasoning"] = reasoning   # ← 同值别名
```
注释写明这是 `P2 修复`，为对齐 ST 1.18.0 前端 `generation-engine.ts:254` 的检测逻辑而**额外发射同值别名字段**。

前端 `useCharacterChat.ts` 三条 SSE 路径（原 `:855` / `:1052` / `:1424`）：
```ts
const reasoning = ...json.reasoning...;
const modelReasoning = ...json.model_reasoning...;
if (reasoning) fullReasoning += reasoning;
if (modelReasoning) fullReasoning += modelReasoning;   // ← 同一条内容被加了两次
```
⇒ **每轮 chunk 的思考文本被累加两遍**。

**"两字两字"是观感而非切法**：模型流式分块通常每块 1~4 个 token（中文常 1~2 字）。内容被翻倍后，读者会感知为"两个字一组地重复"，与用户描述完全吻合。

同样的模式在 `lib/stream-engine/index.ts:229-231`（`reasoningDelta = reasoning + modelReasoning`）与 `services/generation-engine.ts:282` 也存在。

### 3.3 工作区修复
三处 SSE 路径（`useCharacterChat.ts`）+ `stream-engine/index.ts` 均已改为**只取 `reasoning`**，`model_reasoning` 保留读取但不再累加（注释标注 `[P3 2026-10-06]`）。

**已实测进入 10-06 19:49 构建**：`index-Cgbqdx2G.js` 中 `model_reasoning` 命中 0（该分块只认 `reasoning`）。

### 3.4 为什么不是模型问题
若为模型侧重复，重复应出现在**同一 chunk 内**且与后端别名无关；而这里的重复**精确等于 chunk 数 × 2**，且别名发射点在源码中可直接读到 ⇒ 归因明确。

### 3.5 ⚠️ 漏修点：`services/generation-engine.ts`（第二轮复核新发现）

**同一缺陷在另一条链路上仍然存在，且已在线上。**

`src/services/generation-engine.ts:281-294`：
```ts
const reasoning = typeof json.reasoning === 'string' ? json.reasoning : '';
```

```js

```

**可达性（已核实不是死代码）**：该方法请求的同样是 `/api/character-chat`（同后端端点，同样会发 `model_reasoning`）。

**影响面判定**：

### 4.2 工作区已实现的部分

### 4.3 ⚠️ 发现的缺陷：需求④/⑤ 的触发时机不对

**关键**：`Message.tsx:1492` 传的是 `streaming={streaming && isLast}`，而 `streaming` 来自 `isGenerating`。
- `isGenerating` 在**整轮生成**期间恒为 true —— **思考阶段结束、正文开始输出时它并不翻转**。
- 因此 `prevStreamingRef` 捕获的 `true → false` 转变，实际发生在**整轮生成结束**，而不是"思考结束"。

后果：
- 需求⑤（展开态、思考结束 → 自动折叠）：**不成立**。用户展开思考框后，思考结束、正文开始输出时它**不会**自动折叠，要等整轮生成结束才折。
- 需求④（折叠态、思考结束即输出正文 → 保持折叠）：结果**看似正确**，但原因是"从没展开过"，而非"判定到思考结束"。属**偶然正确**。

**缺什么信号**：需要一个"思考阶段结束"的独立标识。当前 `useCharacterChat.ts` 中被认为承载此语义的 `onStreamReasoningDone`（`:466` / `:899` / `:1094` / `:1488`）全部位于 **`onDone` / 生成结束**分支内，**不是思考阶段的结束点**。⇒ 现在整条链上**没有**"思考结束、正文开始"这个事件。

**可选修法（需专门批次决定，本文档不施工）**：
1. 在流式回调里检测"首次收到 `content` 而此前只有 `reasoning`"这一转变，在消息上打一个 `reasoningEnded` 标记（或由 `useCharacterChat` 维护一个 per-message 的 phase），传给 `ThinkingProcess` 作为收合触发条件；
2. 或由后端在思考→正文的转折处显式发一个事件（改动面更大，但语义最干净）。

### 4.4 `elapsedSeconds` 在历史消息上的行为
历史消息挂载即 `streaming=false` → 计时 interval 不启动 → `elapsedSeconds` 恒 0 → 标题回退 `t.thinking`（"思考"）。
⇒ **历史消息看不到"已思考 X 秒"**。需求②的文字未限定"仅流式期"，需确认是否要持久化耗时（若需要，得把秒数写进消息 extra，属数据契约变更）。
