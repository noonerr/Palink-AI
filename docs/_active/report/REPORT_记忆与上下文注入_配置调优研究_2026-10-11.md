# REPORT — 向量记忆与上下文注入的**配置调优**研究（实测）

> **日期**：2026-10-11
> **性质**：实测研究（容器内只读探针，**零付费、零本地 LLM**；只调可配置旋钮，不改业务代码）
> **探针**：`backend/scripts/_probe_mem_cfg_snapshot.py`（P81 配置快照）、
> `backend/scripts/_probe_mem_recall_diag.py`（P80 召回归因 + 配置 A/B）
> **数据环境**：生产容器 `palink-ai-backend-1`，题集 `qa2.json`（57 题，会话 `f25daab6…`）
> **上游**：`docs/_active/spec/SPEC_记忆降本增效_对比实验设计_2026-10-11.md`

---

## 一句话结论

> **不用改代码，光调配置就能省下约 7.4% 的总 prompt：关掉邻居扩展，命中率纹丝不动（n=57，93.0% vs 93.0%）。**
> 而此前被当成主因的"语义召回失败"，在标准题集上**并不成立** —— 86.7% 的目标其实早就进了候选池。

---

## 一、三个"先别调"的坑（本次实测发现）

### 坑 1：四个配置项是**死配置**，调了不生效

| 配置项 | 定义处 | 实际消费点 | 判定 |
|---|---|---|---|
| `SEMANTIC_WEIGHT` (0.7) | `memory_module/config.py:22` | **无** | ❌ 死配置 |
| `TIME_WEIGHT` (0.2) | `config.py:23` | **无** | ❌ 死配置 |
| `IMPORTANCE_WEIGHT` (0.1) | `config.py:24` | **无** | ❌ 死配置 |
| `CHUNK_TARGET_CHARS` (250) | `config.py:86` | **无** | ❌ 死配置 |

真正在用的权重是 **`retriever.py:434-438` 里硬编码的 `0.6 / 0.2 / 0.2`**，与 config 里这三项**毫无关系**。
⇒ 想调"语义 vs 上下文邻近 vs 重要性"的配比，**改配置没用，得改代码**（且这条路前序已判定优先级低）。

半死一项：`MAX_MEMORIES_PER_QUERY`(30) 只在 `storage.py:1107/1261` 的 `limit or ...` 兜底路径生效，
生产调用全部显式传 `EFFECTIVE_CANDIDATE_LIMIT` ⇒ **改它不影响线上**。

### 坑 2：改动检索配置会被**缓存掩盖** 60 秒

`MemoryService` 的缓存键（`service.py:198`）只含：
`user / session / char / branch / scope / query / exclude / memory_mode / max_tokens`。

**不含** `NEIGHBOR_EXPAND` / `MIN_SIMILARITY` / `HYBRID_WEIGHT` / `CANDIDATE_LIMIT` 等检索参数。

实测后果：本次 A/B 第一轮，`NEIGHBOR_EXPAND` on 臂与 off 臂输出**逐字节相同**
（38.4 条 / 5149 单位 / 命中 78.6%，两臂完全一致）—— 第二次调用直接命中了第一次的缓存。

⇒ **线上改这些配置后，用户最多 60 秒内看到的是旧结果**，极易被误判为"改了没生效"。
⇒ 任何配置 A/B **必须** `MemoryService(db, enable_cache=False)`（探针已内置并打印警告）。

> 注：D6（2026-10-11）刚把 `memory_mode` + `max_tokens` 补进缓存键，但检索参数仍未进键。这是一个待补项。

### 坑 3：真实库规模让"候选池太小"这个假设**不成立**

```
总行 = 764    会话数 = 71    用户数 = 4    NULL 向量 = 0    维度全部 = 1024（一致）
会话记忆行数 top5：227 / 127 / 36 / 27 / 12
```

生产检索是**会话级作用域**。候选池 `BLOCK_CANDIDATE_LIMIT = 50`：

- 小会话（12 / 27 / 36 行）：top-50 = **全库**，池子根本不是约束
- 最大会话（227 行）：top-50 = 22%

⇒ **"目标排不进前 50"（top-K 杀）在绝大多数会话里不可能发生。**
本次 P80 实测 30 题：**TOPK_KILLED = 0 题**，与这个推断一致。
⇒ 不要再花力气去扩候选池，那是调了个不存在的瓶颈。

## 二、召回到底失败没有？—— 没有（在标准题集上）

P80 逐题归因（会话 `f25daab6`，227 行，n=30）：

| 归因 | 题数 | 占比 |
|---|---|---|
| **IN_POOL**（目标在候选池前 50 内） | 26 | **86.7%** |
| THRESHOLD_KILLED（相似度 < 0.5 被挡） | 2 | 6.7% |
| ABSENT（目标消息在库里没记忆行） | 2 | 6.7% |
| TOPK_KILLED | **0** | 0% |

```
全量 57 题复跑：IN_POOL = 48/57 = 84.2%，TOPK_KILLED 仍为 0。
注入后命中率 on/off 皆为 93.0%（高于候选池口径 84.2%，
因为注入集合还含 STM 与关键词路的并集，实际候选 > 50 条）。
```

```
target 全量排名：中位 5 / 均值 11 / max 64
进池题目的 target sim：中位 0.587 / min 0.506
候选池 top-50 内唯一 message_id 数：33~44 个；最大单簇占比 4%~12%
```

⚠️ **这与"向量检索只返回 2 个唯一 message_id、最大单簇 80%"的观察直接冲突。**

候选池层面：33~44 个唯一 message_id、最大单簇仅 4~12% —— **没有塌缩，也没有单一紧簇**。

⇒ 那个"2 个唯一 msg_id / 80% 单簇"的画像，**更可能来自注入后的集合，而不是候选池**。
最可能的机制就是**邻居扩展**（见 §三）：命中块的 ±1 邻居几乎都来自**同一条消息**，
于是注入结果里同一 message_id 大量堆积。而且它恰好在**今天 D2 改动之后**才明显
（D2 把 `NEIGHBOR_MAX_ADDS` 从全局封顶改成每命中封顶，邻居补充量 **+379%**）。

⇒ **结论：先别急着做查询扩展 / HyDE / 重嵌。这条链路上，召回不是瓶颈。**

## 三、★ 最强降本项：邻居扩展是纯成本（实测）

配置 A/B（同一题集、同一 query、关缓存，`NEIGHBOR_EXPAND` on vs off）：

| 臂 | 命中率 | 注入条数 | 注入单位 | 唯一 msg | 最大单簇 |
|---|---|---|---|---|---|
| **on（现状）** | 93.0% | 36.4 | **5133** | 29.6 | 11% |
| **off** | **93.0%** | 28.8 | **3779** | 21.9 | 14% |
| **差值** | **+0.0pp** | −7.6 | **−1354（−26.4%）** | −7.7 | — |

```
n = 57（qa2.json 全量），关缓存，同一题集同一 query。
小样本复现（n=14）：on 78.6% / off 78.6%，注入 5149 → 3830（−25.6%）—— 两档结论一致。
```

**花 26.4% 的记忆注入量，买到 0 命中率提升。**

换算成真实成本：1,354 内部单位 × 1.37 ≈ **1,855 真实 tok**
= 记忆注入（6,427 tok）的 **28.9%** = 总 prompt（25,076 tok）的 **约 7.4%**。

### 但必须诚实地说清一件事

**"命中率不变" ≠ "邻居没有价值"。** 我的判据是"证据是否进入注入集合"（检索层），
而邻居扩展的原始动机是**让切开的块恢复完整**（`config.py:142-149`），
它的收益体现在"注入文本前后文连贯"，**这一点在零付费 + 零本地 LLM 下无法离线验证**。

⇒ 三种选择，按保守程度排序：

| 选项 | 配置 | 省 | 保留的完整性 |
|---|---|---|---|
| 激进 | `NEIGHBOR_EXPAND=false` | **−26.4% 注入（实测 n=57）** | 无（半截块） |
| **折中（推荐）** | `NEIGHBOR_MAX_ADDS=1`（原 4） | 约 −20%（按 4→1 线性粗估，**待实测**） | 保留 1 条相邻块 |
| 保守 | `NEIGHBOR_EXTRA_RATIO=0.3→0.1` | 渲染预算 5200→4400 | 邻居仍补，但渲染不再为它加额度 |

⚠️ 折中档的 −20% 是**外推不是实测**，必须跑一次 A/B 再定。

## 四、其余旋钮：该调什么、别调什么

### 4.1 阈值 `MIN_SIMILARITY = 0.5`（判别力实测，用户 1 全量 708 行）

| 查询 | top1 | 过 0.3 | 过 0.4 | 过 **0.5** | 过 0.6 |
|---|---|---|---|---|---|
| 相关-回指前文（"你之前跟我说过的那个小玩具是什么"） | 0.653 | 708 | 667 | **186** | 8 |
| 相关-专名（"声波公式"） | 0.657 | 572 | 109 | **19** | 19 |
| 无关-天气 | **0.522** | 708 | 270 | **62** | 0 |
| 无关-地理 | 0.404 | 125 | 1 | 0 | 0 |

三条读数：

1. **相关查询的 top1 都 > 0.65** ⇒ 阈值 0.5 **没有**杀死最相关的那一条。
   （这与"语义召回失败"的直觉相反 —— 也解释了为什么 P80 里 IN_POOL 高达 86.7%。）
2. **但阈值决定池子大小**：专名类只有 **19 条**过阈值（会话级约 6 条）⇒ 候选池装不满。
3. **无关-天气 top1 = 0.522 也过了 0.5** ⇒ 阈值区分度本来就一般；降到 0.4 会让无关类放行 **270 条**。

⇒ **不要盲降阈值。** 它是个真实的权衡：能救专名类召回，但会放进噪声。
⇒ 建议：跑一次 **0.45 / 0.5 / 0.55 三档扫描**（纯配置、可秒级切换），
用 P80 的 IN_POOL 率 + 注入噪声占比两个指标一起看，**噪声上升就停手**。

### 4.2 配置全景表

| # | 配置项 | 现值 | 建议 | 依据 / 预期 | 风险 |
|---|---|---|---|---|---|
| **1** | `NEIGHBOR_EXPAND`（或 `MAX_ADDS` / `EXTRA_RATIO`） | true / 4 / 0.3 | **关，或降到 1** | 本次实测 n=57：注入 **−26.4%**，命中 **93.0% → 93.0%（0 变化）** | 块完整性下降，离线无法验证影响；**先折中再激进** |
| **2** | `memory_budget_level` 档位（4000） | 4000（22/22 用户） | 若要降本可测 **2500** | p55 实测：4000→2500 省记忆 6,427→3,106（总 prompt **−13%**），得分 0.698→**0.575（−12.3pp）** | ⚠️ **代价明确且很大**。只在"愿意用 12pp 换 13% 成本"时做。**不要降到 750**（0.500） |
| **3** | `MIN_SIMILARITY` | 0.5 | **扫描 0.45/0.5/0.55，别盲降** | 判别力实测见 4.1；专名类池子只有 19 条 | 0.4 时无关查询放行 270 条 ⇒ 噪声 |
| **4** | `CHARACTER_CHAT_HISTORY_LIMIT` | 24 | 16 / 12（**须先建近期题集**） | P70 长度实测：24→16 省 4,432 tok（**−20.5%**），24→12 省 6,656（**−30.8%**） | p61 实测 6→24 有 **+0.125** 分；`qa2` 0/57 证据在 24 条内 ⇒ **用它测必然测不出差异** |
| 5 | `HYBRID_WEIGHT` | 0.7 | **保持** | p47 双题集（原题+改写）扫描已定 0.7，取"较差一侧"最大化 | ⚠️ 只测原题集会得出"纯关键词最好"的错误结论（原题 58% / 改写 31%） |
| 6 | `BLOCK_CANDIDATE_LIMIT` | 50 | **保持**（扩了也没用） | 库规模实测：多数会话行数 < 50，池子已是全库；P80 实测 TOPK_KILLED = 0 | 无 |
| 7 | `QUERY_MODE` / `QUERY_MIN_CHARS` / `QUERY_FALLBACK_CHARS` | current / 15 / 120 | 可测，但**优先级低于 #1** | 生产 12/101 条用户消息不足 10 字 | 2026-10-09 实测"最近 4 条拼接 600 字"更差 ⇒ **扩展只能短而挑** |
| 8 | `CHUNK_MAX_CHARS` | 450 | 可测 350 / 550 | 影响单块成本与完整性 | **改了必须重嵌全部 764 行**；收益未测 |
| 9 | `SEMANTIC/TIME/IMPORTANCE_WEIGHT`、`CHUNK_TARGET_CHARS` | — | **别调，建议删** | 死配置，无任何消费点 | 留着会持续误导后续调试 |
| 10 | `CHUNK_STRATEGY` | structural | **保持** | P64 严格配对实测：块级中位排名 3.0 vs 句级 12.5；句级有 33% 题定位不到证据 | 句级需全量重嵌且会丢证据 |

### 4.3 线上分布（决定收益面）

```
memory_mode：        vector × 22（100%）     ← 无 rule 用户，配置改动对所有人生效一致
memory_budget_level：None × 21（→默认 4000）、1 × 1（4000）
```

⇒ **没有长尾差异**：22 个用户全部走 `vector` + 4000 档。
⇒ 好处是改动收益可全额拿到；风险是**改错了影响所有人**（务必带一键回退）。

## 五、推荐执行顺序（全部纯配置，零代码）

```
① 关/减 邻居扩展（NEIGHBOR_MAX_ADDS 4→1 先试，再考虑全关）
   ⇒ 实测全关 −26.4% 记忆注入 ≈ 总 prompt **−7.4%**，命中 0 变化（n=57）
   ⇒ 验证：P80 --ab-neighbor；同时人工看一眼注入文本是否变"半截"

② 阈值扫描 0.45 / 0.5 / 0.55（只扫不改）
   ⇒ 看 IN_POOL 率与噪声占比，有收益才动

③ 若要再降：预算档位 4000 → 2500（−13% 总 prompt，−12.3pp 得分）
   ⇒ 这是明确的"用分换钱"，需要你拍板是否接受

④ 历史 24 → 16/12（−20.5%/~−30.8%）
   ⇒ 硬前置：先建近期题集，否则验收失效
```

🚫 **本次研究不建议动的**：候选池大小、切分粒度、混合权重、切分策略。
