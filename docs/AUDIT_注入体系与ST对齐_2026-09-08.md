## 1. 提示词注入（✅ 88%，健康）

### 1.1 重要修正：装配策略不是"缺失"，而是更强

审计初判认为 Palink 缺少 ST 的 `promptConstructionStrategy`，**复核后确认该判断错误**。

Palink 走的是 ST 更完整的那条路 —— **prompt_order 全量重排**：

| 能力 | Palink | ST 1.18 |
|---|---|---|
| 提示词源标识符 | `PROMPT_ID_*`（`roleplay_prompt_assembly.py:717-730`），对齐 ST `openai.js` prompt_order | 同 |
| 按 order 重排 | `_apply_full_prompt_order` | 同 |
| **角色卡字段拆分为独立可重排消息** | `_extract_char_field_messages_for_order`（`:786-800` 判定 + `:3507-3515` 插入） | ST 无此能力 |
| 动态裁剪优先级 | `_apply_dynamic_trimming` 按 priority 裁剪 | ST 无 |

ST 的 `promptConstructionStrategy` 只有 `charDescription`/`charPersonality` 两个选项，是 prompt_order 的**简化替代品**。Palink 已有完整 prompt_order，**此项判定为"已对齐且更强"，无需补**。

## 4. MVU 变量回滚（✅ 已于 2026-09-08 修复，原评估 40%）

> **修复摘要**：新增 `_load_effective_stat_data()`
> （`roleplay_prompt_assembly.py:4445`），取值优先级
> **消息级 `extra.variables` > 群组变量 > 会话变量**，装配调用点已切换
> （`:4540`）。无 schema 变更、无迁移。详见 §7 P0-2。

### 问题（原状）

`_load_session_stat_data`（`roleplay_prompt_assembly.py:4413`）**只读 session 级** `chat_metadata.variables`，从不读消息级 `extra.variables`。

### 好消息：数据已经落库了

`backend/app/api/websocket.py:776-778` 两处都写了：

```python
cur_meta["variables"] = new_vars        # session 级
msg_extra["variables"] = new_vars       # 消息级 ← 快照已存在！
```

所以**消息级快照一直都在，只是装配侧没读**。修复成本很低。

### 后果

swipe / 重生成 / 切分支后：
- 前端状态栏面板：按消息读（`window.Mvu.getMvuData({type:'message'})`）→ 显示**正确**
- 后端注入给 AI 的 stat_data：**session 最新值** → 显示**错误**

**AI 看到的状态和用户看到的分支状态不一致**，这是会直接毁掉沉浸感的 bug。

### 现状

- 模型：`backend/app/models/persona.py:11-28`（表 `personas`）
- API：`backend/app/api/personas.py:15`，含 list/create/get-active/put-active/update/delete
- 注入逻辑：`roleplay_prompt_assembly.py:2997-3081`，内容 `[Persona: {description}]`

### 🔴 枚举值域冲突（P0）

**ST 1.18 真值**（已核验 `personas.js:88-97`）：

```
IN_PROMPT: 0,  AFTER_CHAR: 1(废弃),  TOP_AN: 2,  BOTTOM_AN: 3,  AT_DEPTH: 4,  NONE: 9
```

**Palink 现状**（`roleplay_prompt_assembly.py:2999-3003` 注释）：

```
0 = 对话中 depth=4 | 1 = 追加 system_prompt 尾 | 2 = 最后 system 消息 | 3 = 不注入
```

**冲突矩阵**（这是会真实出错的地方）：

| ST 值 | ST 语义 | Palink 收到后 | 结果 |
|---|---|---|---|
| 0 IN_PROMPT | 注入 userPersona 块 | → 对话中 depth=4 | ⚠ 位置不同 |
| 2 TOP_AN | 拼 AN **顶部** | → 最后 system 消息（=BOTTOM_AN） | 🔴 **注入到错误的一端** |
| 3 BOTTOM_AN | 拼 AN 底部 | → 不注入 | 🔴 **人设静默丢失** |
| 4 AT_DEPTH | 第 depth 条前 | → unknown → 跳过 | 🔴 **人设静默丢失** |
| 9 NONE | 关闭 | → unknown → 跳过 | ✅ 碰巧正确 |

目前 Palink 自有前端只写 0/1/2/3，所以自洽。**但只要导入 ST 配置、或第三方插件写入该字段，行为就错。**

### 6.4 更新机制

**基本没有**。`update_url` 不识别、`auto_update` 不消费、无版本比对、无定时检查、无插件市场。
`st-plugins/` 是手工适配的供应商副本，不可动态安装。

### 6.5 沙箱风险判断

Palink 用"词法遮蔽 + Proxy 假 DOM"软沙箱（`sandbox.ts`，禁 `eval`/`Function`/`alert`，`document` 走 Proxy，`fetch` 白名单）。
ST 是主窗口直接 `eval`，**无任何隔离**。

**这个差异是双刃剑**：
- 安全性：Palink 更优
- 兼容性：第三方 ST 插件普遍依赖真实 ST DOM（`#send_textarea`/`#chat`/`#option_regenerate`）与同步全局函数 → **Palink 的 Proxy 假 DOM 会让大量插件直接炸**

**建议**：不要为了兼容去拆沙箱，而是在沙箱内**补齐真实 API**（让插件不需要碰 DOM）。

```python
def _load_effective_stat_data(db, session_id, group_id=None, branch_id=None):
    """[ST-ALIGN P0-2] 消息级快照优先，回落会话/群组级。"""
    if group_id:
        return _load_session_stat_data(db, session_id, group_id)  # 群聊保持原行为
    try:
        q = db.query(CharacterChatMessage).filter(
            CharacterChatMessage.session_id == session_id)
        q = q.filter(CharacterChatMessage.branch_id == branch_id) if branch_id \
            else q.filter(CharacterChatMessage.branch_id.is_(None))
        # 只回看最近 30 条：stat_data 每轮都写，命中通常在 1-2 条内
        for row in q.order_by(CharacterChatMessage.created_at.desc()).limit(30).all():
            variables = (getattr(row, "extra", None) or {}).get("variables")
            stat = (variables or {}).get("stat_data")
            if isinstance(stat, dict) and stat:
                return stat
    except Exception:
        pass
    return _load_session_stat_data(db, session_id, group_id)
```

**取值优先级**：消息级 `extra.variables.stat_data` > 群组变量 > 会话变量。

**设计取舍**：
- **群聊不做消息级回退**（直接走原 `_load_session_stat_data`）：群组变量源不同，
  贸然引入消息级回退有回归风险，留待群聊场景单独验证。
- **只看最近 30 条**：避免全表扫描；stat_data 每轮都写，30 条足够覆盖。
- **异常全吞、回落旧逻辑**：装配主流程宁缺勿错。
