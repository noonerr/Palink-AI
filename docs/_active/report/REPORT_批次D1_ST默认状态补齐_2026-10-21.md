### 2.2 版权边界（只取配置事实，未搬正文）

- ✅ 取：键名、键的类型、标量/布尔/数值/颜色默认值、`instruct` 的格式分隔符（`### Instruction:` 一类，属配置事实）。

  - `persona_description` / `custom_stopping_strings`：ST 原值本就是空串。
- 测试 `test_prompt_bodies_are_not_copied` 钉住这四个空串，防止后续有人“顺手补全”把 ST 正文搬进来。

### 2.3 端点合并语义

`_default_st_settings()` 的顺序未变，只是默认值来源变了：

1. `build_st_power_user_defaults()` 生成 83 键新字典（深拷贝，避免一次请求改脏模块常量）；
2. `setting.power_user`（DB 列）解析后 `update` 覆盖默认值；
3. `_merge_palink_defaults()` 再把 `silly_tavern_settings` blob 里的 `power_user` 覆盖上去。

⇒ 两条 DB 持久化路径都优先于默认值，默认值只补缺。两条路径各有一条测试。

### 2.4 为凑满 83 键而删除的 3 个旧键

原 8 键中的 `message_token_count_enabled` / `charListGrid` / `auto_load_chat` **不在** `settings.json` 的 83 键里
（它们属于 §7 说的运行时默认对象）。为满足“键数 = 83”的验收口径，本批从 `_power_user_defaults` 移除；
DB/blob 里已有这三个键时仍会原样返回。`_boot_settings_override()` 仍会在 boot 请求上写 `auto_load_chat: True`（未改）。

旧宿主名单有 `quickReplyV2`，但它**不在** ST `settings.json` 的 21 键里；ST 的 quick-reply 扩展在 init 时自行创建

### 3.5 嵌套默认值

对象型命名空间只给 `{}`。ST 的 `memory.prompt` / `sd.prompts` / `objective.customPrompts` 是提示词正文，
按版权边界不搬；插件自己的 `loadSettings` 会补嵌套字段。本批的目标是“命名空间存在且类型正确、读取不抛”，不是复制 ST 全部嵌套配置。

## 7. 否证主脑：83 不是 ST 1.18 运行时默认对象的全部

### 7.1 事实

`default/content/settings.json` 的 `power_user` 确实是 **83** 键，主脑的数字没错。但它只是**保存态快照**；
ST 的运行时默认对象在 `public/scripts/power-user.js`：

```js
export const power_user = { ... }   // 实测 133 个顶层键
```

加载设置时 ST 执行 `Object.assign(power_user, settings.power_user)`（`power-user.js:1566`），
所以全新安装的真实 ST 里，`power_user` 是 **133 键**（settings.json 缺失的键保留运行时默认值，不会变 `undefined`）。

实测差集：

- 运行时比 settings.json 多 **51 键**；
- settings.json 比运行时多 **1 键**（`ui_mode`）；
- 交集 82 键；`133 = 82 + 51`，`83 = 82 + 1`。

51 个运行时独有键（全部不在本批 83 键里）：


### 7.2 为什么这不是纸面差异

本仓自己带着的第三方插件源码就在读这些运行时独有键（`grep -rn "power_user\." frontend/src st-plugins`）：

- `st-plugins/third-party/JS-Slash-Runner-main/.../better_message_to_load/index.ts:5` → `power_user.chat_truncation`
- `.../dataProcessor.ts:238-240`、`generateRaw.ts:311` → `power_user.persona_description_depth` / `_role`
- `.../responseGenerator.ts:130` → `power_user.streaming_fps`
- `.../persona.ts:225-227`、LittleWhiteBox `worldbooks.js:759` → `power_user.persona_description_lorebook`
- `st-plugins/expressions/index.js:363` → `power_user.reduced_motion`

⇒ 在只补 83 键的现状下，这些键仍然是 `undefined`，上述插件的对应分支仍可能抛错或走错默认。
“插件读 `power_user.<key>` 全部拿到值”这个目标，**83 键只完成了一部分**。

### 7.3 结论与建议

- 本批按主脑明示的 **83 键验收口径**交付，不擅自改成 133（否则“键数 = 83”的判据直接红）。
- 若真实目标是插件兼容而不是复刻 settings.json，建议**另立 D1-1b**：把 `public/scripts/power-user.js` 的
  133 键并进来（或至少补上述 51 个运行时独有键），并把验收判据从 `== 83` 改为 `>= 133` / 包含 51 键。

  `default/content/settings.json` 保存态对齐（83 键）”。
