## 1. T1：零成本筛查"为什么线上模型不交单"（主件）

### 1.1 方法（已验证可行）

1. 用容器内装配导出"下一次真正会发的提示词"（不产生模型调用）：
   参照 `backend/scripts/probe_assemble_dump.py` 的依赖注入写法，把
   `assemble_roleplay_prompt` 的 `res.messages` 按 `[i] role=…` 原样落文件。
2. 把该文件交给子模型，指令只有一句："你是这个对话里的角色扮演模型，按消息里的全部要求
   产出下一条助手回复，只输出回复本身。"**不要透露我们在测什么。**
3. 用 §2.3 的规则机器判定该回复是否"合格交单"。

### 1.2 变体清单（在导出文本上做字符串级改动，不改生产代码）

| 变体 | 改动 | 想验证的假设 |
| --- | --- | --- |
| V0 | 原样 | 基线（已知强模型 2/2 合格） |
| V1 | 删掉那段 2899 字符的 `${new_value}` 原文模板（F3） | 原文模板的占位符在干扰模型 |
| V2 | 把用户消息尾部的精简【变量更新指令】移到**系统提示词最末** | 指令位置（尾部 user vs 系统末）影响依从 |
| V3 | 在用户消息**最末一行**追加一句硬指令："回复的最后一行之后必须紧跟一个完整的 <UpdateVariable> 块" | 现有指令被长正文稀释 |
| V4 | 把 15159 字符的状态块从"开场第一位"移到主提示词之后（即旧布局 [1] 位） | 开场大段数据稀释了任务指令 |

每个变体 ≥2 个子模型实例；V0 也重跑 2 次作对照（防子模型波动）。

### 1.3 机器判定规则（合格 = 全部满足）

1. 含 `<UpdateVariable>` 与配对的 `</UpdateVariable>`；
2. 内含 `<JSONPatch>`，且其内容是**可被 `json.loads` 解析的数组**；
3. 数组每条含 `op`/`path`，且**不含** `${` 占位符；
4. 正文（标签之前部分）不含 `${new_value}`。

### 1.4 产出

- 一张变体×实例的合格矩阵（原始判定输出留档）；
- 若某变体显著优于 V0：写成**候选提示词改法**（精确到字符串与插入位置），
  并标注"仍需 1 次真机确认（等授权）"；
- 若全部与 V0 无差异：结论写"提示词不是主因，嫌疑转向模型能力/采样参数"，
  并给出下一步该查什么（如 reasoning_effort、temperature、max_tokens 截断）。
