## 一、先说人话：现在这套架构是怎么个事

把整套系统想成一个**只有几个服务员的小饭馆**：

| 饭馆里的角色 | 对应到本项目 | 现在的问题 |
|---|---|---|
| 服务员 | 后端 worker 进程 | 只有 4 个（低配机器上只剩 1 个） |
| 服务员的「脑子」 | 事件循环 | 一次只能想一件事 |
| 后厨 | AnyIO 线程池 | 只有 8 个灶台，却有 467 道菜要炒 |
| 每个摊位的水箱 | 容器内存限额 | 水箱大小是拍脑袋分的，有的装不下 |
| 门口发传单的 | nginx worker 进程 | 发了 16 个人，但门口只站得下 1 个 |
| 仓库 | PostgreSQL | 货架尺寸写死，跟水箱大小对不上 |

三条最要命的：

1. **服务员会突然站着发呆。** 客人点完菜，服务员不去招呼下一桌，而是**站在出餐口干等**厨师做完（在 `async` 里直接调同步函数）。他一发呆，他负责的所有桌子全得等。机器越差、服务员越少，这事越致命 —— 4 个服务员时只有 1/4 的客人受影响，1 个服务员时是 **全部客人**。
2. **后厨只有 8 个灶台。** 但菜单上有 467 道菜是「必须占灶台」的做法。低配机器上后厨还要跟洗碗、备菜抢这 8 个灶台。
3. **水箱分得不合理。** 自动分水脚本在小机器上会把数据库的水箱压到 256MB —— 而光货架（`shared_buffers`）就固定占 128MB，等于水刚放进去就见底了。

## 三、缺陷清单

### P0 —— 低配机器上会直接趴下

#### P0-1　流式对话里服务员站着干等（阻塞事件循环）

- **现象**：一个用户发完消息，同一 worker 上**所有其他请求全部卡住**，包括别人的流式对话。
- **物证** `[实测]`：
  - `backend/app/api/chat.py:43` `async def chat_stream(` —— 是异步函数
  - 但同一个函数里，第 `403 / 406 / 410 / 411 / 422 / 428` 行**直接同步调用**：
    `persist_snapshot(force=True)`、`compute_deduct_tokens(...)`、`deduct_usage(...)`、`mem_svc.store_memory(...)`
  - 这些函数本身是同步的：`persist_snapshot` 定义在 `chat.py:226`（`def`，非 `async def`）；
    `store_memory` 定义在 `backend/app/memory_module/service.py:57`（`def`）
  - `grep -n "await.*persist_snapshot\|to_thread" chat.py` → **空**，确认无任何包裹
- **根因**：异步函数里调用同步 I/O，Python 不会帮你让开，而是**真等着**。
  `store_memory` 内部还要去做向量化（联网问 ollama），几百毫秒到几秒。这段时间事件循环是死的。
- **低配放大**：worker 数从 4 → 1，影响面从「1/4 的客人」变成「所有客人」。
- **已登记未修**：`TODOS.md:1292` 写着「async 端点内同步 DB 调用的架构性风险仍在……
  根治需全面 threadpool 化，另立批次」。**这说明前人知道，但一直没排期。本文把它提为 P0。**
- **修法**：
  ```python
  # chat.py，async generator 内
  await asyncio.to_thread(persist_snapshot, True)

  deducted = await asyncio.to_thread(compute_deduct_tokens, result, messages, req.model)
  await asyncio.to_thread(deduct_usage, save_db, user.id, deducted)

  await asyncio.to_thread(mem_svc.store_memory,
                          user.id, session_id, "user", req.message)
  await asyncio.to_thread(mem_svc.store_memory,
                          user.id, session_id, "assistant",
                          clean_memory_content(result.full_content))
  ```
  ⚠️ **施工红线**：SQLAlchemy 的 `Session` **不是线程安全的**。上面 `save_db` 若被带进 `to_thread`，
  跨线程共用会出诡异错误。两种稳妥做法二选一：
  1. `to_thread` 里**只包不含 `save_db` 的纯计算 / 网络调用**（推荐先做这个，风险最低）；
  2. 每个 `to_thread` 内部**自己开一个新 Session**，用完即关。
  同理 `websocket.py:1076`、`character_ext.py:4748` 的 `persist_snapshot` 也要一并评估。
- **验收**：改完后连续发两条消息，用第二个浏览器窗口在流式输出期间刷页面，不得卡顿。
  代码层面：`grep -n "persist_snapshot(force=True)" chat.py` 的每一处都必须有 `await` 前缀。

#### P0-2　后厨只有 8 个灶台，却有 467 道菜

- **现象**：同步接口并发稍高就排队，表现为「点一下转半天」。
- **物证** `[实测]`：
  - 容器日志原文：`AnyIO 线程池并发令牌设置为: 8`
  - 设置点：`backend/app/main.py:257` `limiter.total_tokens = max(settings.API_THREADPOOL_TOKENS, 1)`
  - 默认值：`backend/app/core/config.py:57` `API_THREADPOOL_TOKENS: int = 16` —— 但被下面的计算压成 8
  - 计算式：`backend/start-server.sh:274` `API_THREADPOOL_TOKENS=$((THREADS_PER_WORKER * 4))`
    而 `THREADS_PER_WORKER = CPU_THREADS / WORKERS = 5 / 4 = 1` → `1*4=4` → 触底兜到 `8`
  - 同步端点规模：`grep "^def \|^async def " backend/app/api/*.py` → **467 个 `def` vs 377 个 `async def`**
- **根因（设计错误）**：**线程池是给「等 I/O」用的，不是给「算东西」用的。**
  现在的公式按 CPU 核数推算，等于说「你有几个脑子就开几个灶台」—— 但灶台是用来**等**的（等数据库、等上游模型），
  跟脑子数量没关系。于是机器越强、worker 越多，每个 worker 分到的灶台反而越少（16 核 → 4 worker → 每人 1 线程 → 8 令牌）。
- **更糟的是抢**：`asyncio.to_thread` 和同步接口**共用这 8 个令牌**。
  这些后台活也在抢：`storage.py:634`（向量化）、`service.py:212`（记忆检索）、
  `character_ext.py:3422 / 6774`（重新向量化）、`websocket.py:1076`（落库）、`worldbook.py:67 / 98`。
  8 个并发的向量化请求就能把整个 worker 的同步接口**全部堵死**。
- **低配放大**：2 核 4G 时 `APP_MIN_WORKERS=1` → 全局只有 **8 个线程**。
- **修法**：改成「全局固定一个池子，按 worker 数平分」，与 CPU 脱钩。
  ```sh
  # start-server.sh：替换掉 THREADS_PER_WORKER * 4 那一行
  # 线程池服务于 I/O 等待，不按 CPU 核数算。全局 64，按 worker 平分，下限 16。
  if ! is_pos_int "${API_THREADPOOL_TOKENS:-}"; then
    API_THREADPOOL_TOKENS=$((64 / WORKERS))
    if [ "$API_THREADPOOL_TOKENS" -lt 16 ]; then
      API_THREADPOOL_TOKENS=16
    fi
  fi
  ```
  4 worker → 每人 16（全局 64）；1 worker → 16（触底）。线程本身很轻，16 个常驻线程约几 MB，不心疼。
- **验收**：重启后日志应显示 `AnyIO 线程池并发令牌设置为: 16`（或 64/worker 数）。
  压测：同时开 20 个非流式接口，观察是否还排队。

> ⚠️ **与同日另一份报告的结论如何兼容**（重要，别看成互相打架）：
> `docs/_active/report/REPORT_后端生成期CPU内存占用排查_2026-10-07.md` 实测结论是
> 「`API_THREADPOOL_TOKENS` 现 8 → **无用**，卡住的代码根本没走线程池，在主线程上」。
> **两条都对，说的是两码事**：
>
> | 卡在哪 | 走不走线程池 | 加线程池有没有用 |
> |---|---|---|
> | `async def` 里**直接同步调用**（P0-1 那批） | ❌ 不走，占主线程 | ❌ **没用**，必须靠 P0-1 的 `to_thread` 改法 |
> | **同步 `def` 端点**（467 个） | ✅ 走，受 8 令牌限制 | ✅ **有用**，就是本条 P0-2 |
>
> ⇒ **P0-1 是根治，P0-2 是给剩下的 467 个同步接口松绑**。只做 P0-2 不通，只做 P0-1 也仍会堵。

#### P0-3　低配机器上自动分水器给出互相矛盾的配置

- **现象**：2 核 4G 这类机器上，按脚本给出的配置起来后**数据库会被内存杀掉**。
- **物证** `[实测]` —— 直接跑脚本推演，不是我手算：
  ```
  $ python scripts/autotune.py --dry-run --cpu 2 --memory 4096
  PALINK_BACKEND_CPUS=2.0      PALINK_BACKEND_MEMORY=930M
  PALINK_OLLAMA_CPUS=2.0       PALINK_OLLAMA_MEMORY=1396M
  PALINK_DB_CPUS=1.0           PALINK_DB_MEMORY=256M
  APP_MIN_WORKERS=1  APP_MAX_WORKERS=1
  ⚠ 物理内存偏小（4096 MB）：三个服务最低也要 5632 MB，现已整体压缩。
  ```
  三个硬伤：
  1. **db 256M 装不下 PostgreSQL。** 实测 db 空载就吃 111 MiB，而 `shared_buffers` **固定 128MB**（镜像默认，全仓无任何参数覆盖），
     水箱一半没了，剩下 128MB 要养 100 个连接位 → OOM。
  2. **压缩后仍超预算。** `MEM_HARD_FLOOR_MB=256` 把 db 顶在 256 不能再降，
     于是 930+1396+256 = **2583 MB > 预算 2560 MB**，脚本自己算出来的账就是超的。
  3. **ollama 1396M 装不下模型。** bge-m3 一个模型就要约 1.2 GB，实测 ollama 常驻 1.236 GiB。
- **根因**：`scripts/autotune.py` 的 `MEM_HARD_FLOOR_MB` 是一个**对所有服务一视同仁的 256MB 下限**，
  但 PostgreSQL 和 ollama 的「能活着的最小水量」远高于 nginx。
- **修法**（改 `scripts/autotune.py`）：
  ```python
  # 1) 硬下限按服务区分，别用一个数
  MEM_HARD_FLOOR_MB = {"backend": 512, "ollama": 1536, "db": 512}

  # 2) 增加「关掉本地 ollama」档：小机器改用云端 embedding
  #    --no-ollama 时 ollama 不进预算，把内存全给 backend/db
  ```
  并新增一个「低于 6 GB 就明确劝退本地模型」的判定：
  ```python
  if total_mb < 6144:
      warnings.append("内存 < 6GB：本地 ollama 撑不住。"
                      "建议 MEMORY_EMBEDDING_PROVIDER 改走云端，或用 --no-ollama。")
  ```
  **给用户的即时建议**（不用改代码，改 `.env` 就能活）：4G 机器上把向量化改走云端，
  然后把 ollama 从 compose 里停掉（`docker compose stop ollama`），省下的 1.4G 给 db 和 backend。
- **验收**：`--dry-run --cpu 2 --memory 4096` 的输出里，db 不得低于 512M，
  且 `backend+ollama+db+512(frontend)+1024(headroom)` 必须 ≤ 4096。

#### P0-4　门口发传单的站了 16 个人，但门口只容得下 1 个

- **现象**：前端容器 CPU 被打满在上下文切换上，静态资源反而发得慢。
- **物证** `[实测]`：
  - `docker exec palink-ai-frontend-1 cat /etc/nginx/nginx.conf` → `worker_processes  auto;`
  - `docker exec palink-ai-frontend-1 ps -eo pid,comm | grep -c nginx` → **18**（16 个 worker + master 等）
  - 容器 cgroup：`cat /sys/fs/cgroup/cpu.max` → `100000 100000` = **1 核**
- **根因**：nginx 的 `auto` 看的是**宿主机**核数（16），看不到容器被限成 1 核。
  后端早就处理了这个事（`start-server.sh` 专门读 cgroup），**nginx 这一侧漏了**。
- **低配放大**：低配机核数少，但 nginx 仍会按宿主机核数开进程；且每个 worker 都要维护 1024 个连接的槽位，白占内存。
- **修法**：`frontend/nginx.conf` 顶部加一行，固定小值（静态资源服务不需要多进程）：
  ```nginx
  worker_processes 2;
  worker_connections 1024;
  ```
  若坚持要自适应，可在 `frontend/Dockerfile` 里加一个启动时按 cgroup 改写的 entrypoint，
  但**固定 2 更省心也更稳**（这是纯静态文件转发，2 个进程足够喂满 1 核）。
- **验收**：`docker exec palink-ai-frontend-1 ps -eo comm | grep -c nginx` 应降到 **3**（master + 2 worker）。

### P1 —— 会明显拖慢，或迟早出事

#### P1-1　数据库货架尺寸写死，跟水箱大小对不上

- **物证** `[实测]`：
  ```
  shared_buffers       = 128MB     ← 固定，不随容器限额变
  max_connections      = 100       ← 实测只用了 27，其中 26 个 idle
  work_mem             = 4MB
  effective_cache_size = 4GB       ← 但容器限额只有 2.5GB
  random_page_cost     = 4         ← SSD 上应为 1.1
  maintenance_work_mem = 64MB
  ```
  `docker-compose.yml` 里 `db` 服务**没有任何参数覆盖**，全吃镜像默认。
- **问题**：`effective_cache_size=4GB` 是在**骗**查询规划器 —— 告诉它「你有 4GB 缓存可用」，
  实际容器只有 2.5GB，于是它会选一个依赖大缓存的执行计划，真跑起来反而慢。
  `random_page_cost=4` 是机械盘的假设，现在都是 SSD。
- **附带**：无 pgbouncer，每个 worker 各开各的连接池，连接不能共享（实测 26 个 idle 连接空占着）。
- **修法**：`docker-compose.yml` 的 `db` 服务加参数（值随 autotune 走）：
  ```yaml
  db:
    command: >
      postgres
      -c shared_buffers=256MB
      -c effective_cache_size=1GB
      -c max_connections=50
      -c work_mem=4MB
      -c random_page_cost=1.1
      -c maintenance_work_mem=128MB
  ```
  原则：`shared_buffers` 取容器限额的 25%，`effective_cache_size` 取 50%，`max_connections` 按
  `worker数 × (pool+overflow) + 20` 留余量即可，不要 100。
- **验收**：`docker exec palink-ai-db-1 psql -U ai_user -d ai_hub -c "SHOW effective_cache_size;"`
  应返回 1GB 而不是 4GB。

#### P1-2　重启时把正在进行的对话硬掐断

- **物证** `[实测]`：
  - `backend/start-server.sh:352` `--timeout-graceful-shutdown "$UVICORN_TIMEOUT"`（600 秒）
  - `docker-compose.yml` 全文 grep `stop_grace_period` → **空**，即用 Docker 默认 **10 秒**
- **后果**：每次 `docker compose up -d backend`，Docker 等 10 秒就 `SIGKILL`。
  uvicorn 本来想用 600 秒把流式对话收尾，**根本没机会**。
- **低配放大**：低配机器上更常重启（调参、OOM 后自愈），用户更常撞上「话说到一半断了」。
- **修法**：`docker-compose.yml` 的 `backend` 服务加：
  ```yaml
  stop_grace_period: 60s
  ```
  （60 秒是折中：够收尾普通对话，又不会让 `docker compose down` 卡太久。）
- **验收**：`docker compose stop backend` 计时，观察是否真等满 60 秒；日志应出现优雅关闭字样而非被杀。

#### P1-3　前端产物只进不出，堆了 20 份废弃入口

- **物证** `[实测]`：
  - `ls frontend/dist/assets/index-*.js | wc -l` → **20**，每份 1.78 MB
  - dist 总 37 MB（非 gz 28.2 MB + gz 7.3 MB），658 个文件
  - `index.html` 只引用 `assets/index-aWXo-K7r.js` —— **其余 19 份是死重量（约 33 MB）**
- **根因**：为了绕开批量删除守卫，构建流程规定「`VITE_OUT_DIR=dist_new_xxx` 构建 →
  `cp -r dist_new_xxx/. dist/` 增量合并 → 从不删除」（见 `AGENTS.md` 与运维 skill）。
  这个策略**规避了事故，但没人做回收**，于是每构建一次就多一份。
- **影响**：磁盘与备份体积线性膨胀；`gzip-dist.cjs` 每次对**全量**文件重跑，构建越来越慢；
  备份 `dist` 时白白多拷 33 MB。
- **修法**（⚠️ `frontend/dist` 是红线目录，禁止直删，必须三步走）：
  1. **先整份备份** `frontend/dist` 到 `_BACKUPS/2026-10-07_dist清理前/`（含 `BACKUP_INFO.md`）
  2. **隔离**：写个小脚本，从 `index.html` 解析出实际引用的文件名清单（白名单），
     把**不在白名单里**的 `assets/*` 移到 `_BACKUPS/_QUARANTINE_2026-10-07/`（保留相对路径），**不是删除**
  3. **验证**：重启 nginx 容器，访问站点确认正常，再考虑清理隔离区
  - 长期：在 `scripts/build-vite.mjs` 之后加一步「保留最近 2 次构建的产物，更早的移入隔离区」
- **验收**：站点 200 正常；`ls frontend/dist/assets/index-*.js | wc -l` 降到 ≤ 2；dist 体积掉到 ~5 MB。

#### P1-4　预压缩只覆盖 79%，剩下的实时压，白烧 CPU

- **物证** `[实测]`：应压缩的 js/css/json/svg 有 316 个，实际 `.gz` 只有 249 个 → **缺 67 个（21%）**
  （举例：`channel-BonUabbp.js`、`CharacterView-31PAjjCR-9c425f3e.css`、`chunk-2J33WTMH-*` 系列）
- **根因**：`frontend/nginx.conf:27` 是 `gzip_static on` —— 这个开关**只对「旁边存在同名 `.gz`」的文件生效**，
  没有 `.gz` 就退回实时压缩。新增的产物没跟着生成 `.gz`。
- **低配放大**：实时 gzip 是纯 CPU 开销，1 核机器上压一个 1.7MB 的文件能明显感到卡。
- **修法**：重跑一次全量预压缩即可（该脚本只新增、从不删，可放心跑）：
  ```bash
  cd frontend && node scripts/gzip-dist.cjs
  ```
  然后确认：`find frontend/dist -name "*.js" -not -name "*.gz"` 逐个检查是否都有同名 `.gz`。
  若脚本有类型过滤，需先补全过滤规则再跑。
- **验收**：缺 `.gz` 的数量应为 0。

#### P1-5　模型常驻内存 24 小时，闲着也占着

- **物证** `[实测]`：`docker-compose.yml:56` `OLLAMA_KEEP_ALIVE=24h`；
  `docker stats` 显示 ollama 占 **1.236 GiB**，CPU **0%**（完全闲着）
- **问题**：向量化（bge-m3）是**间歇性**调用的 —— 只在存记忆、检索记忆时用一下。
  让它 24 小时常驻，等于 1.2 GB 内存被一个 0% CPU 的进程占死。
- **低配放大**：4G 机器上这 1.2 GB 就是压垮骆驼的那部分（见 P0-3）。
- **修法**：低配机器把 `.env` / compose 里改成短驻留：
  ```yaml
  - OLLAMA_KEEP_ALIVE=5m
  ```
  代价：冷启动时要重新加载模型（约 1~3 秒），只在**本次对话的第一次记忆操作**上感受到一次。
  若完全不用本地模型，直接 `docker compose stop ollama` 并把 `MEMORY_EMBEDDING_PROVIDER` 改走云端。
- **验收**：空闲 5 分钟后 `docker stats palink-ollama` 内存应明显下降。

### P2 —— 技术债，排期处理

| # | 问题 | 物证 | 建议 |
|---|---|---|---|
| P2-1 | **前端镜像构建白做**。`frontend/Dockerfile` 里 `RUN npm run build`，但 compose 又 bind mount `./frontend/dist` 盖掉 `/usr/share/nginx/html` —— 镜像里那份 dist 是死重量，且每次 build 在低配机上要全量 `npm ci` + 构建 | `frontend/Dockerfile:9`；`docker-compose.yml:34` | 镜像里只装 nginx，不构建（构建在宿主做，靠 mount 进容器）。可省下镜像 129MB 里的 dist 部分与几分钟 CPU |
| P2-2 | 生产容器挂载测试目录且可写 | `docker-compose.yml:148` `- ./backend/tests:/app/tests`（无 `:ro`） | 加 `:ro`；或仅在 dev compose 里挂 |
| P2-3 | **autotune 的每 worker 内存模型算错了边际成本**。注释「实测单进程稳态 RSS ≈ 461 MB」**不是错的**（那是 1 worker 时的实测，见同日排查报告），错在拿它当**每 worker 成本**：实测 4 worker 总量 1014 MiB，即**每多一个 worker 只增约 184 MB**（(1014−461)/3），而非 700 MB。`PER_WORKER_MB=700` 把成本**高估约 3.8 倍** | `scripts/autotune.py:77` 注释；`docker stats` 实测 1014MiB/4 | 改成「基准 461 + 边际 184/worker」的两段式模型；`PER_WORKER_MB` 降到 250 左右。注意：高估**不会导致 OOM**，只会让 worker 数算少、性能上不去 |
| P2-4 | **`APP_MIN_WORKERS` 会绕过容器内的自适应**。实测启动日志 `min_workers=4` 强行把 CPU 算出的 2 抬成 4 | `start-server.sh:233-234`；日志 `workers_cpu_cap=2 workers=4` | autotune 不要同时写 min 和 max 为同一个值（等于关掉自适应）；只写 max，min 留 1 |
| P2-5 | **没有 Service Worker**。`nginx.conf` 配了 `location = /sw.js`，但 dist 里**根本没有这个文件** | `ls frontend/dist/sw.js` → No such file；`nginx.conf:59` | 要么补一个（冷启动能省 532 KB），要么把 nginx 里那条 location 删掉（配了个不存在的东西会误导后人） |
| P2-6 | **失败重试没有熔断**。额度不足时仍重试 3 次，每次都是一次完整网络往返 | 容器日志：`attempt 1/3`、`2/3`、`3/3` 连续 403 insufficient_user_quota | 对「余额不足 / 鉴权失败」这类**确定性失败**直接放弃，不重试 |

## 六、还没验证、别当结论的事

以下几条我**只做了代码推断，没上机验证**，写出来是为了提醒下一个人别踩：

1. **`to_thread` 包裹 `save_db` 的线程安全性** —— SQLAlchemy Session 跨线程用是已知雷区，
   本项目 `backend/app/api/websocket.py:536` 的注释也提到「`persist_snapshot` 可能在 `to_thread` 线程运行」，
   说明这里**已有过相关处理**，改之前务必先读那段，别重复踩或改坏。
2. **db 256MB 是否真的 OOM** —— 我是在**好机器**上推出的结论，没真去压一个 256MB 的 PG。
   真要确认，得在测试栈（`D:\项目\palink-new`）上把 db 限额设成 256M 跑一次写入。
3. **线程池改成 16/64 之后的真实吞吐提升** —— 需要压测，不能直接宣称「快了 8 倍」。
4. **bge-m3 的真实常驻内存** —— 1.2 GB 是按 ollama 容器 1.236 GiB 反推的，未单独测量模型本身。
