## 1. 这个项目到底在干什么（大白话版）

### 1.1 起因：三次"打补丁"留下的三套房

Palink 要接待两种"客人"：**角色卡自带的脚本**（网上下载的卡，代码不可信）和 **ST 生态插件**。核心问题是"让客人在哪干活"——这既是兼容问题，也是安全问题。

历史上为了省事/救火，搞出了**三套并行的执行环境**（报告里叫"三轨"）：

| 轨 | 大白话 | 问题 |
|---|---|---|
| **大堂轨** | 客人直接进大堂（聊天主页面）干活，脚本/插件直接插进主页面 | 最省事、兼容最好，**但极其危险**——来路不明的卡能以你的登录身份读 cookie、操作一切 |
| **帘子轨** | 拉道帘子造个假环境（自有插件用 `new Function` 在同环境伪造窗口） | 安全模型与第三方卡不同，Palink 自有插件走这条 |
| **单间轨** | 把客人关进独立"单间"（iframe），加枷锁后跑 | 最安全（浏览器视它来历不明，摸不到登录态），**但兼容最差** |

代价是**同一套能力要维护三份**，三轨核心代码合计约 1.5 万行；而且大堂轨长期漏配接口，用户表现为"看起来能用、实际静默失效"。

### 1.2 目标：三轨并成两轨

方案（2026-10-12 定）：**所有不可信代码只准在单间里跑**，主页面只当"服务员"，只执行真正危险的动作。自有插件的帘子轨保留（服务自己人，不并）。

### 1.3 六步走（S0–S5）

| 步 | 干了什么 | 状态 |
|---|---|---|
| S0 | 备料：做出《三轨行为对照表》（18 条契约测试的输入源）+ 基线留档 | ✅ |
| S1 | 补单间轨的功能缺口（世界书、变量、形状修复等） | ✅ |
| S2 | 抄帘子轨成熟的挂载点策略 + 存储迁移（旧键只读迁入新桶，只加不删） | ✅ |
| S3 | **切换默认**：卡脚本默认进单间，ST 插件默认不再注入大堂，总闸默认关 | ✅ |
| S4 | 拆单间大文件（`SillyTavernCompatRuntime.ts` 7149 行 → 8 个 part，每个 ≤913 行） | ✅ |
| S5 | **删大堂**：整文件删除 `utils/sillyTavernPluginRuntime.ts`（2447 行） | ✅ |

本次评审的对象报告（s5-arch-e2e）是 **S5 删完之后的真机评估与全量测试**（A–H 八组）。

## 3. ⚠️ 独立发现的报告问题（本节是本次评审最有价值的部分）

### 3.1 【重大措辞订正】`triggerSlash` 到底有没有？—— 报告说对了，但提示词/审计容易误读

这是本次唯一需要订正报告措辞的地方，也是**用户最该知道的一条**。

**实测（卡 iframe 内）**：
```
window.triggerSlash        = undefined
getContext().triggerSlash  = undefined
```
⇒ **报告 §9 H 组"iframe 内不暴露 triggerSlash"完全成立，我实测复证。**

**但代码事实是分轨的**（我逐行复核确认）：

| 轨 | `triggerSlash` | 证据 |
|---|---|---|
| 沙箱轨（自有插件） | ✅ **有** | `sandbox.ts:3605` |
| getContext 轨 | ✅ **有**，且**前置了 Palink 9 命令** | `getContext.ts:2517-2521`（`:2518` 先 `runPalinkSlashCommands`，未命中才落引擎 `:2520`） |
| **iframe 轨（卡内）** | ❌ **没有** | `smart-card-runtime/runtime-body/part-08.ts:191-199` 的 getContext 兼容对象**没有 triggerSlash 字段**；`runPalinkSlashCommands` 在卡内零引用 |

**订正说明**：自查提示词原文写「iframe 的 `SillyTavern.getContext()` 不暴露 `triggerSlash`」——**这句是准确的**。但如果只读了"两轨都有 triggerSlash"（沙箱、getContext）就以为"9 条命令在卡内可用"，会**得出完全相反的结论**。
⇒ **准确口径：9 条 Palink 专有命令在"自有插件"里能用（沙箱轨/getContext 轨），在"卡内脚本/插件"里用不了（iframe 轨）。** 报告 B 组的 9 条实测全部是在**沙箱轨**跑通的，这一点报告 §3.4 其实写明了，但总表里"9 条命令逐条实跑 = 通过"容易被读成"卡内也能用"。

### 3.2 【新发现】iframe 内 `localStorage` 是被换掉的，存储键读不到属正常

我第一轮探针在 iframe 内读存储键，得到 `legacy=0 / new=0`，一度以为"存储双兼容坏了"。
实测复核：iframe 内写 `localStorage` **能成功但落在内存**（`iframeStorageIsolated = true`），因为未信任帧是 **opaque origin**，被 `memoryStorage` 顶替（`frame-shim/legacy-st-sim-parts/part-a.ts:393/480-481`）。
⇒ **不是缺陷，是"陌生人模式"的设计**。存储双兼容必须回**主页面**读（我第二轮在主页面读到旧键 2 + 新键 3，正常）。
⇒ 报告 F 组结论成立，但**测量位置很关键**，后来者别在 iframe 内测存储。

### 3.3 【口径提醒】`__palinkCompatStats` 是"惰性 + 模块级"，整页重载即清零

报告 §5 已提到"惰性创建"，我实测确认：`window.__palinkCompatStats` 在我这轮是 **null**（因为我没有在**同一个 SPA 会话内**触发降级桩）。
⇒ 这不是链路坏，是**测量方法问题**。要看到它必须：在同一 SPA 会话内先触发降级桩（如 `/profile-list`）再读，**不能 `page.goto` 整页重载**。
⇒ 报告 D 组的结论（触发后能看到 + 插件管理页可见）我**未本轮复验**，沿用报告结论并如实标注。

### 3.4 【未复验项声明】

以下内容我**没有**独立复跑，直接采信报告（避免虚报工作量）：
- C 组（故意抛错卡脚本）—— 需造带坏脚本的卡，测试会话已删，只能靠 `c_seed.sql` 复现；
- D 组（降级统计可见性）—— 需同会话触发，见 §3.3；

### 4.2 安全收益：**9.5 / 10**（本项目最大价值）

- 堵住了"任何一张来路不明的卡都能以你的登录身份为所欲为"这个**真实敞口**；
- 单间轨有**手势闸门**（8 个危险 API 需真实用户点击）+ **陌生人模式**（opaque-origin iframe）；

**唯一扣分**：`setChatMessage` / `deleteMessage` **不在手势闸门集合内**（`SmartCardCompatController.ts:57-80`）—— 卡内脚本可以绕过用户手势改消息。这是**已知且未修**的。

### 4.3 ST 兼容性：**6.0 / 10**（短板，重点讲）

**为什么给 6 分（及格线上下）**：

✅ **做到的**：
- 5 个真实 ST 插件 **4 个能 init**，7 条斜杠命令注册可用；
- 我探测的 121 个 ST API，iframe 的 window 上能拿到 **93 个**（76.9%）；
- `getContext()` 契约面 **184 个顶层键**，含 Phase5 补的 39 个 ST 1.18 缺失 API；
- 存储迁移"只加不删"，用户**解锁态/CG 进度不回退**（这是最怕出事的地方，守住了）。

❌ **没做到的（这才是关键）**：

1. **"API 名字在" ≠ "API 能用"**。我实测命中的 93 个里，混着相当比例的**假实现**：
   - `part-06.ts:595-600` 世界书 `entries: []`、`data: {}` —— **恒空**（这正是 MVU 世界书读不到内容的根因，报告 H 组"66 次失败"）；
   - `part-08.ts:297` preset 名**硬编码 `'Palink'`**；`:303` `writePresetExtensionField` **假成功**（返回 true 但什么都没写）；
   - `part-06.ts:574` `getRequestHeaders` 恒 `{}`；
   - `part-03.ts:98-111` 11 个 ST 挂载容器是**离屏空 div**（`top:-9999px`）—— 插件"挂得上"但**用户看不见**。
   ⇒ **这是"静默失效"的温床**：不报错、返回看起来合理的值，但功能是假的。对用户来说这比直接报错更糟。

2. **卡内命令链路是断的**：iframe 内 `triggerSlash` 实测 undefined ⇒ **9 条 Palink 专有命令在卡内完全用不了**（见 §3.1）。

3. **quick-reply 仍未通**：`Failed to fetch`。根因经代码复核**订正**——不是"fetch 被禁"，而是 fetch 被**重写**成"白名单伪造 + 其余回落原生"（`part-06.ts:654-661`），而回落发生在 **opaque-origin 帧**里（`CharacterCardRenderer.tsx:1291-1295`，仅 trusted-native 给 `allow-same-origin`），所以非白名单请求必然失败。

4. **降级登记覆盖不全**：只有 **6 处** `recordStubHit`；而 `getContext.ts:3012` 起的 **Phase5 那 39 个 stub 未登记进 stats** —— 这批是**不留痕的静默桩**，插件管理页看不到。

### 4.4 诚实度 / 文档质量：**9.5 / 10**（本项目最值得夸的地方）

- **§11.5 主动写了"8 项没做完"**，并明说"不是遗漏，是有意取舍或能力边界" —— 这在工程报告里极其罕见。
  包括：`/model` 等 3 条命令**只跑 get 形态没跑 set**、切分支 **UI 刷新未直接证**、session 型旧键迁移**无合成证据**、cap=3 **未真机**、门禁**收尾未复跑**、交接提示词缺陷**未回写文档**等。
- 每项给"验了什么 / 怎么验的 / 结果 / **证据**"，未验成的明确写"未通过"或"无法验证"。
- 副作用**全部清理并校验**（删前备份 3 份 CSV，删后校验分支 2 条、91 条消息未动）。
- **本报告只在 §3.1 发现 1 处措辞需订正**，且是"容易被误读"而非"写错"。

### 4.5 遗留风险：**5.5 / 10**

8 项取舍 + 3 项瑕疵里，**2 项是用户看得见的**，不是纯工程洁癖：
- **ST 扩展 UI 在卡内不可见**（11 个离屏桩 + 4 个已挂载不可见）—— 用户 2026-10-15 拍板"接受"（口径 c），但**用户能感知到"装了插件没界面"**；

其余（cap=3 未真机、session 迁移无合成证据、C 组证据靠种子复现）属于**工程可追溯性**问题，不直接伤用户。
