## 3. 手工审查结论（容器链路与网络）

### 3.1 ✅ 验证为健全的部分

- **容器端口收敛正确**：sillytavern 仅 `expose: 8000`（无宿主映射）；DB 单独在 `backend-db` 网络（与 ST 容器不同网）✓；openai_compat 端点在 `ST_NATIVE_SERVICE_KEY` 为空（默认）时**穿透到标准 JWT 认证**（openai_compat.py:141-142 实读核实）——admin 回退仅在运维显式设置 service_key 且请求持有正确密钥时可达，不是公开缺口。
- **nginx 8081（宿主 9061）封存链完整**：`@st_native_unauthorized` + 所有 location（loader/asset/正则 API/兜底 `/`）一律挂 `auth_request /__palink_st_native_auth`（后端 `/api/st/native/auth` 校验会话 Cookie）；N-6 签名头（X-Palink-User-Id + X-Palink-User-Sig）在 auth_request_set 后注入 ✓。无凭据实测 401（2026-09-02 渗透验证已录）。
- **API 双轨清晰**：8081 的正则 API location 代理到 **backend:8000**（Palink st-router 接管），仅兜底 `location /` 代理到 sillytavern:8000（UI 静态资源）——ST 服务端 API 在 9061 面上并不直接暴露。

### 3.2 🔴 实测证实：docker 网内 ST 容器完全无鉴权

从 backend 容器（同 `frontend-backend` 网络）**无任何凭据**实测：

```
GET  http://sillytavern:8000/version            → 200 {"agent":"SillyTavern:1.18.0..."}
POST http://sillytavern:8000/api/characters/all → 200 返回真实角色数据（只读 300 字节即止）
```

**同网络成员**：backend、frontend、sillytavern、**ollama、new-api**（第三方容器）共 5 个。含义：
- 任何一个同网容器被攻破（如 new-api 或 ollama 的 0day），即可**无凭据读写 ST 容器全部数据**（角色/聊天/世界书），并通过 ST 的扩展安装机制（git clone 任意仓库）尝试从容器内发起进一步动作；
- 这是**纵深弱点而非直接暴露**：宿主面无映射（9061 有 auth_request 门），攻击者必须先攻破同网容器；
- 定级：**中**（单用户自部署 + 容器全部 healthy 的现状下可接受；登记为"若未来引入不可信容器/第三方镜像需先修"）。
- 若未来要收口（需拍板，本轮不动）：compose 加 `SILLYTAVERN_WHITELISTMODE=true` + 白名单只放 frontend/backend 容器 IP，或给 ST 容器单独网络 + 仅 frontend 可达。

### 3.3 🟡 登记观察（不构成现状漏洞）

- **`SILLYTAVERN_EXTENSIONS_AUTOUPDATE=true`** + third-party extensions 卷：容器运行时自动拉取第三方扩展代码——供应链面。st-native 封存状态下扩展体系不活跃，但机制在。若解封建议改 false。
- **`ST_NATIVE_SERVICE_KEY` 启用后的权限语义**：一旦设置，持钥者经 openai_compat 获得 **admin 级推理权限**（且 ST 轨未接 token 配额——配额预检只挂在 5 个主聊天入口）。当前空值=禁用=安全；解封 st-native 时应评估接配额 + 强制随机强钥。
- **`client_max_body_size 100m`**（8081 server）：与主站 8080 server 的上传上限口径不同，属封存链既有值，登记。
