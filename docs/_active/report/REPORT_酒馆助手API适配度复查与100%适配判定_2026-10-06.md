## 2. 【P0】核心结构缺陷：`SillyTavern` 全局没投影 `getContext()`

### 2.1 实测数字

| 项 | 值 |
|---|---|
| `window.SillyTavern` 实际字段数 | **14**（`getExtensionPrompts, getContext, eventSource, getRequestHeaders, getCurrentChatId, openCharacterChat, saveChat, saveChatConditional, extensionSettings, chatCompletionSettings, saveSettingsDebounced, chatMetadata, saveMetadata, Generate`） |
| ST 权威 40 项里缺失 | **33** |
| `SillyTavern.getContext()` 返回字段数 | **28**（含 `chat / characters / characterId / name2 / chatId / onlineStatus / stat_data / event_types(112 个事件) / groups`） |

**缺的包括**：`chat` `characters` `name1` `name2` `characterId` `groupId` `chatId`
`onlineStatus` `maxContext` `streamingProcessor` `eventTypes` `addOneMessage`
`generate` `stopGeneration` `extensionPrompts` `setExtensionPrompt` `callGenericPopup`
`messageFormatting` `substituteParams` …

### 2.2 这不是"缺数据"，是"缺投影"

`getContext().chat` 实测：`Array(5)`，元素结构与 ST `ChatMessage` **完全一致**
（`name / mes / is_user / send_date / extra / swipes / swipe_id / swipe_info`）。

⇒ **数据已经在手，只是没挂到全局对象上。**

### 2.3 它造成了一个真实崩溃（已定位到源码行）

当前线上**唯一的页面级报错**：

```
TypeError: Cannot read properties of undefined (reading 'length')
    at .../MagVarUpdate@beta/artifact/bundle.js:2:416630   (qo)
    at async HTMLDocument.<anonymous> (bundle.js:2:536346)
```

把 bundle 拉下来看该偏移，崩在这一行：

```js
if (!e.settings.自动清理变量.启用
    || SillyTavern.chat.length <= e.settings.自动清理变量.要保留变量的最近楼层数 + 5
    || ...) return;
```

**MVU 变量引擎读 `SillyTavern.chat.length`，而该字段不存在。**
它在 `async` 初始化流程里抛错 ⇒ 后续初始化中断。

### 2.4 修复验证（A/B 对照，已实测）

用 `addInitScript` 注入一个**纯只读 getter 投影**（12 个字段转发到 `getContext()`）：

| 指标 | 补前 | 补后 |
|---|---|---|
| `SillyTavern.chat` | `undefined` | `Array(5)` ✅ |
| `SillyTavern.name2` | `undefined` | `"露缇雅1.2"` ✅ |
| `SillyTavern.characterId` | `undefined` | `1450532749` ✅ |
| 页面级报错 | **1 个** | **0 个** ✅ |

> 补丁本身约 20 行，**零写库、零权限变化、零新依赖**。
> 这是本次发现的**投入产出比最高**的一项。

## 3. 酒馆助手真实缺口清单（按可修性分级）

### 3.1 它到底用了多少 API

> ⚠️ **本节数字已作废，正确值见 SPEC §10.1：47 项 / 208 调用点。**
> 错因：只扫了插件轨，漏了卡脚本轨（MVU 变量框架）；且词表只用了 134 项命名空间清单。

扫两条脚本正文（`TavernHelper.x` + 裸调用两种形态）：

| 脚本 | 不同 API 数 | 调用点 |
|---|---|---|
| 对话渲染系统 v7.1 | 1 | 1 |
| 数据库界面插件(@bubble改造版) | 23 | 88 |
| **合计（去重）** | **24** | **89** |

高频项：`getChatMessages`(16) `triggerSlash`(11) `setChatMessages`(9) `getVariables`(7)
`rebindGlobalWorldbooks`(7) `getGlobalWorldbookNames`(6) `substitudeMacros`(6)
`replaceVariables`(4) …

> **134 项里它只用 24 项。** 追求 134/134 对它零收益。

### 3.2 🟢 A 类：直接补，零风险（7 项，可到 100%）

| # | API | 现状 | 修法 |
|---|---|---|---|
| 1–4 | `getCharacter` `getCharData` `getCharacterNames` `getCurrentCharacterName` | 主页面 ❌ 全缺 | **沙箱轨已有真实现**（`sandbox.ts:3703-3736`，读 `getContext()`），搬过来即可 ⚠️ 但 `getCharacterNames` 必须重写，见 §3.3 |
| 5–6 | `TavernHelper.getVariables` `TavernHelper.replaceVariables` | `window` 上有 ✅，但 **`TavernHelper` Proxy 不认** ❌ | 纯名单问题：`SUPPLIED` 白名单（`sillyTavernPluginRuntime.ts:2077-2097`）漏列这两个名字。加两个字符串即可，零逻辑改动 |
| 7 | `updateCharacterWith` | 三轨全无 | 需新写，且是**写操作**，见 §3.4 |

补充：`SillyTavern` 全局投影（§2）单独算一项，能同时覆盖上面多项的数据来源。

### 3.3 🔴 卡死风险：`characters` 是 14.5 亿长度的稀疏数组

实测：

```
Array.isArray(getContext().characters) = true
getContext().characters.length        = 1450532750     ← 不是笔误
实际可枚举 key                         = ['1450532749']  ← 只有 1 个
```

它是**按 `characterId` 当索引填的稀疏数组**。后果：

- `characters.map(c => c.name)` → 遍历 **14.5 亿**次 → 浏览器长时间卡死
- `characters.filter / forEach / spread` 同理

⚠️ **沙箱轨现成的 `getCharacterNames` 实现正是这么写的**（`sandbox.ts:3723-3728`）：

```ts
getCharacterNames: () => ctx?.characters?.map((c: any) => c.name) || []
```

**直接搬到主页面 = 引入一次页面冻结。** 必须改成只遍历真实存在的索引。

### 3.4 🟡 B 类：需产品拍板（3 类）

| 项 | 实测证据 | 说明 |
|---|---|---|
| 变量**写**通道 | `__palinkCompatStats` 实测命中：`updateVariablesWith` ×1、`insertOrAssignVariables` ×1，detail =「卡内脚本回写未开放（Palink 的变量更新与正文写入走后端链路，避免双写）」 | ⛔ **Palink 刻意关闭的边界**。开了才能让 MVU 写变量，但要动变量策略，需用户授权 |
| `getGlobalWorldbookNames` | 实测命中 ×1，返回 `[]` | 世界书「全局绑定」是 ST 概念。Palink 世界书分全局/角色/聊天三层，语义可映射但需确认 |
| `rebindGlobalWorldbooks` | no-op（返回 resolved Promise） | 同上 |

### 3.5 ⛔ C 类：明确不做

完整 134 项里剩下的 ~100 项，绝大多数是 **ST 私有管理器概念**，Palink 有自有实现：

- `preset` 族 14 项（ST 的预设系统，Palink 无此概念）
- `persona` 族 12 项（人设）
- `extension` 族 8 项（扩展安装/卸载/更新 —— **任意代码执行**）
- `importRaw*` 5 项（原始数据导入）
- `audio` 族 8 项
- `lorebook` CRUD 多半为写操作

四条真风险（沿用 10-04 报告 §9.12，本次复核仍成立）：
① 数据源分裂（双写）② 权限模型被绕过（卡脚本是普通用户内容却拿管理员能力）
③ 任意代码执行 ④ 不可逆操作无确认。

> **请勿顺手补。** 补了就是"以为能用、实际静默失败"，比不补更糟。

## 5. 「能否 100% 适配」——分层判定

| 层 | 项数 | 结论 |
|---|---|---|
| **酒馆助手实际调用面** | ~~24~~ → **47** | ✅ **可到 100%**。补 8 项缺失 + 处理 5 项假可用 + 投影，全为只读或搬现存实现 |
| **`SillyTavern` 全局对象** | 40 | ✅ **可到 ~85%**。投影能覆盖数据字段；`generate` / `stopGeneration` / `callGenericPopup` 等交互类需逐个桥接 |
| **`TavernHelper` 完整命名空间** | 134 | ⚠️ **可到 ~40%（约 55 项），不该到 100%**。剩下的是 ST 私有概念，硬对齐有害（§3.5） |
| **整个 ST 生态任意脚本** | ∞ | ❌ **不可能**。任何非原生实现都不可能覆盖第三方脚本的任意调用 |

**一句话**：追求"134/134"是错误目标 —— 对这张卡零收益，还会引入 §3.5 的四条风险。
正确目标是**「把实测用到的 24 项做到 24/24」**，这个既可达又有意义。
