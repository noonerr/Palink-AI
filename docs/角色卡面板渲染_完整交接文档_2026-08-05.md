## 二、SillyTavern 原版怎么做「状态栏 / 好感度面板」

> 本节描述 ST 原版的通用机制，用于理解 Palink 应该对齐什么。注意：**不同角色卡用的机制可能不同**（有的是 Tavern Helper 动态 schema，有的是 regex_scripts 静态注入）。本案例是后者。

### 2.1 ST 的 regex_scripts 机制【已确认】
- 角色卡 `data.extensions.regex_scripts` 是一组正则替换脚本，每条有：
  - `findRegex`：匹配消息正文里的某个标记（如 `<StatusPlaceHolderImpl/>`）。
  - `replaceString`：替换内容（HTML / 文本）。
  - `markdownOnly`：是否只在 Markdown 渲染路径生效。
  - `promptOnly`：是否只影响发给模型的 prompt（不影响显示）。
- ST 在渲染消息时，会依次对这些脚本跑正则替换，把标记替换为 `replaceString`。
- 当 `replaceString` 是一段完整 HTML 文档时，ST 的显示管线会识别为「可渲染的 HTML / smart-card」，放进 iframe 或内联渲染。

### 2.2 ST 的 smart-card / 扩展 HTML 渲染
- ST 用 `looksLikeSmartCardHtml` 之类判断消息是否是「智能卡」HTML。
- 面板脚本（`<script>`）在渲染时与 HTML 一起进入 iframe，由 iframe 内的全局环境执行（读取 `getAllVariables()` / `stat_data` 等）。

### 2.3 Tavern Helper 动态 schema 机制（上一任 agent 的主线，本案例未走这条）
- 部分角色卡用 Tavern Helper 插件：卡片 `extensions.tavern_helper` 提供 zod schema（`registerMvuSchema(z.object(...))`）+ MVU 更新脚本，运行时读 schema + `stat_data` 动态生成面板 HTML。
- 这是**另一条路**。上一任 agent 按这条路做了大量后端工作（`mvu_engine.py`）+ 前端自绘（`TavernHelperPanel.tsx`），但本案例的面板并不走这条路。

## 三、真实机制（本次实测，纠正上一任 agent 前提）

### 3.1 角色卡「我被猫娘包围了！」（id=c380f835-3941-4d8e-9c62-25dbcc6cbdae）的面板来源【已确认】
- 面板 HTML 来自 `regex_scripts[4]` 的 `replaceString`（48958 字符），用纯 ```` ``` ```` 围栏包裹的完整 `<!DOCTYPE html>` 文档。
- 文档内：
  - `:root` 浅色 / 深色主题变量（CSS 变量）。
  - 完整 CSS（结构、栏位、进度条、按钮样式）。
  - 一个 `<script>`（约 325 行，纯 JS），其核心逻辑调 `getAllVariables().stat_data`（样本 `tmp_statusbar.html` 第 961 行附近）把动态值（好感度、关系等）填入面板 DOM。
- 该 `<script>` 标记是 `<script type="module">`，但实测**无 `import`/`export`**（即经典脚本语义）。

### 3.2 渲染链路（理想态）【已确认管线设计】
1. 后端把角色卡 `regex_scripts` 随角色数据下发前端。
2. `Message.tsx` 的 `pipelineResult` useMemo 用 `findStatusPlaceholderRegexScript(_characterExtensions)` 检测：若正文尚无占位符 / 非已渲染 HTML，则追加 `\n<StatusPlaceHolderImpl/>`。
3. 显示管线 `formatMessage(runRegex:true)` 跑正则替换，把占位符替换为卡片自带 HTML 文档。
4. 文档含 `<!DOCTYPE` → `looksLikeSmartCardHtml` 判为 smart-card → `CharacterCardRenderer` 用 iframe-js 渲染。
5. iframe 内 shim 注入全局环境（`getAllVariables`、`_`、各种 ST API 桩），状态栏 `<script>` 执行，读取 `stat_data` 填值。

### 3.3 用户强约束
> 「你千万不要自己再去造一个面板了」——必须渲染卡片自带的 HTML，不得自建面板组件。

**第 3 轮（状态栏被内联分支拦截，根本没进 iframe）**：
- `Message.tsx`（909 行）：原内联分支条件 `isCharacterChat && !isUser && !useNativeStRendering && isHtmlOrCard` 会抢在 914 行的 `smart-card → CharacterCardRenderer` 分支之前，用 `sanitizeStCompatHtml` 内联渲染并剥掉 `<script>`。
- 修复：追加 `&& pipelineResult?.kind !== 'smart-card'`，让 smart-card 内容不被内联分支拦截，正确路由到 iframe。

**第 4 轮（shim 模板字符串混入 TypeScript，整段 shim 解析失败——决定性根因）**：
- 加 `STATUSBAR-SRCDOC-LINES` 诊断后定位：错误在 `about:srcdoc:707`（legacy shim）与 `:4937`（compatV2 shim），而状态栏文档仅 1202 行 → 错误不在状态栏脚本，在 shim。
- 根因：shim 是 `return \`<script>...JS...</script>\`` 的**模板字符串**，浏览器当 JS 执行，但里面写了 TS（`as any`、参数 `: any`）。esbuild 只剥离 `.ts 代码` 的类型，**剥离不了字符串里的类型** → `as`/`:` 原样进生产 bundle → 浏览器 `<script>` 解析 `Unexpected identifier 'as'` → 整段 shim 失败（`getAllVariables` 等全没注册）→ 状态栏脚本即使被保留也跑不起来。
- 修复（去掉 TS，运行时无意义）：
  - `CharacterCardRenderer.tsx`（2921-2924）：`stat_data: (ctx as any)?.stat_data || (window as any).__palinkStRuntime?.context?.stat_data || {}` → `stat_data: ctx?.stat_data || window.__palinkStRuntime?.context?.stat_data || {}`（**逻辑保留，仅去 `as any`**）。
  - `CharacterCardRenderer.tsx`（getExtensionPrompts 字符串块，~3236 起）：`const result: any[]` → `const result`；循环内 `(v as any)` → `(v)`；`(window as any)` → `(window)`。
  - `SillyTavernCompatRuntime.ts`（2989）：`(event: any)` → `(event)`。
- 全量校验：`dist/assets/*.js` 扫描 ` as any|as const|as unknown|as void|as never|: any|: Any` 全空；入口 `index-C3rtbiVF.js` 无 `as any`。

## 五、我改错了什么 / 走过的弯路（诚实记录）

> 用户批评「幻觉太大」。以下弯路务必作为反面教材，避免重蹈。

1. **【错】自绘面板（`TavernHelperPanel.tsx` 等）**：第一天误信上一任 agent 的「Tavern Helper 动态 schema」前提，自己画了面板。用户明确否决。→ 浪费一轮，且留了废弃文件。
2. **【错】把 `as`/`:` 语法错误误判为「SillyTavern 社区插件（TypeScript）注入」**：曾推断错误来自 `execute_scripts` 开启的插件。实测后用诊断日志钉死——错误在 **shim 模板字符串自身**（707/4937 行都在 shim，且状态栏仅 1202 行）。**教训：在复杂 iframe srcdoc 里定位语法错误，必须加「打印各 `<script>` 块起始行 + 出错行附近内容」的诊断**，凭 grep 模板字符串「无 TS」就下结论是错的（grep 不到字符串里的 TS，因为 TS 在字符串内）。
3. **【推断偏差】多次以为「修好脚本执行」就完了，但状态栏根本没进 iframe**：前后加了 module 降级、getAllVariables 注入等，却没先确认「状态栏是否真的走到了 CharacterCardRenderer」。直到加 `STATUSBAR-IFRAME-BOOT` 日志发现用户控制台**完全没有 BOOT**，才意识到被 `Message.tsx` 内联分支拦截。**教训：先确认渲染路径是否到达目标组件，再修组件内部逻辑。**
4. **【过度自信未验证】** 每轮修复我都「预判硬刷后应该好了」，但用户多次回贴「还是不行」。最终根因（shim TS）连用户都需回贴日志才暴露。**教训：没有用户最终确认前，不要声称「修好了」。**

## 七、经验与教训（可复用的「如果再来一次」）

1. **注入 iframe srcdoc 的 shim 必须是纯 JS**：禁止在模板字符串里写 `as` / 类型注解 / 泛型。改动后 grep 构建产物确认无残留 TS（`grep -oE '.{15} as any.{15}' dist/assets/index-*.js`）。
2. **定位 iframe 内语法错误靠「诊断日志」而非 grep**：在 srcDoc 组装处打印总行数、每个 `<script>` 起始行号、出错行附近内容，直接钉死来源。
3. **先确认渲染路径到达目标组件，再修组件内部**：加 `XXX-BOOT` 日志确认组件是否被调用，避免「修了内部逻辑却根本没进组件」的空转。
4. **DOMPurify 保留 script 必须同时处理白名单 + 黑名单**：仅从 `FORBID_TAGS` 移除 `script` 不够，DOMPurify 默认 `ALLOWED_TAGS` 不含 script，不在白名单的标签会被整体丢弃（含内容）。必须显式加进 `ADD_TAGS`（用新数组避免污染共享配置）。
5. **Showdown 会把无保护围栏里的 HTML 文档转义成代码块**：显示管线里含完整 HTML 文档的消息，要在 `extractHtmlBlocks` 阶段保护（仅当内部是 HTML 文档时）。
6. **沙箱 iframe 仅 `allow-scripts` 时禁止 `<script type="module">`**：无 `import`/`export` 的 module 脚本要降级为经典 `<script>`。
7. **不假设已修好**：没有用户最终确认，不声称完成。
8. **用户强约束优先**：「不要自己造面板」= 渲染卡片自带 HTML。违背约束会浪费整轮。
