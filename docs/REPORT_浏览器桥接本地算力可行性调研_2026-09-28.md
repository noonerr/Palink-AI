# REPORT：浏览器桥接本地算力可行性调研

> 日期：2026-09-28 ｜ 性质：只读调研，零生产代码改动
> 课题（用户口径）：**服务端部署在远端服务器，通过用户浏览器这个"桥"，探测并调用用户本机运行的 Ollama / ComfyUI 等本地 AI 服务**，用于回答（LLM）或图片生成。
> 结论速览：**能做，浏览器三道闸门都能过，但"探测到"容易、"零配置用起来"不可能**——用户本机服务必须做一次性 CORS 放行配置，且 Chrome/Firefox 新版会弹一次本机网络授权。主回答链路接本地 LLM 是大手术，副任务和 ComfyUI 出图是小手术且有现成扩展点。

---

## 0. 场景界定

远端服务端（Palink 后端在公网）+ 用户浏览器。后端**永远够不到**用户本机的 `127.0.0.1`，所以本课题唯一可行的执行面是**浏览器页面 JS 直接 fetch/WebSocket 用户本机端口**。这排除了"后端代理到本地服务"的路线（那条路线只在自托管同机部署时成立，本文第 7 节顺带提及）。

这正是 LobeChat 已经验证过的模式（浏览器 Web 应用直连用户本机 Ollama），不是无人区。

## 1. 结论分档

| 档位 | 结论 | 前提条件 |
|---|---|---|
| 探测到"本机跑着 ComfyUI/Ollama" | ✅ **能** | 浏览器弹一次"本地网络访问"授权（Chrome 142+/Firefox 149+），用户点允许后持久生效 |
| 调用本地 LLM 做副任务（标题/总结/翻译/轻量对话） | ✅ **能** | 上述授权 + 用户本机服务做一次性 CORS 放行（一行环境变量或一个开关） |
| 调用本机 ComfyUI 出图 | ✅ **能** | 上述授权 + ComfyUI 启动参数加 `--enable-cors-header`；项目侧工作流模板/执行协议已有现成逻辑可搬 |
| 用本地 LLM 走角色扮演**主回答**链路 | ⚠️ **能但是大手术** | 需把"模型调用点"从服务端搬到浏览器并回传后端跑后处理（MVU/正则/入库），建议单独立项 |
| 用户**零配置**全自动探测+调用 | ❌ **不能，且永远不该做** | CORS 闸门是浏览器强制的，绕过手段只剩恶意软件式的 hack；Safari 基本没戏 |

## 2. 浏览器三道闸门（网页 → 用户本机端口要过的关）

网页从 `https://palink域名` 发起 `http://127.0.0.1:8188` 请求，依次面对三道闸门：

1. **混合内容（Mixed Content）**：HTTPS 页面加载 HTTP 资源默认被拦。但 `127.0.0.1`/`localhost` 被主流浏览器（Chrome/Firefox/Edge）视为"潜在可信来源"，**不算混合内容**，可以放行。**Safari 是例外**：WebKit 至今把回环地址按混合内容处理（WebKit bug 171934 仍开放），Safari 上这条路预期直接堵死。
2. **本地网络访问授权（LNA，2025-2026 新增，最关键的新变量）**：过去网页可以随意扫描用户本机端口（恶意网站借此探测本地服务），Chrome/Firefox 已全面补上这道锁：
   - **Chrome/Edge 142（2025-10-28 stable）**：公网页面请求本机/局域网地址一律先弹权限授权，拒绝则请求根本发不出去。企业策略 `LocalNetworkAccessRestrictionsEnabled` 可临时豁免，但官方明确会逐步收回。
   - **Firefox 144**（2025 末）上线 LNA 授权（默认关），**约 149 起（2026 初）默认开启**，**154 起把 WebSocket 也纳入管控**。
   - **Safari/WebKit**：LNA 标准还在 position 阶段，现状是混合内容直接拦回环地址（最严）。
   - 对产品的影响：**授权弹窗本身就是产品的"连接向导"入口**——首次检测时浏览器会问用户"允许此网站访问本地网络设备？"，允许后按站点持久记住。这是合规通路，不是绕过。
3. **CORS**：就算请求发出去了（授权+非混合内容），要**读到响应**还得本机服务返回 CORS 头。这是唯一一道需要用户在**本机服务侧**做一次性配置的关，也是"零配置全自动"不可能的原因。

## 3. "探测到"的技术手法与局限

探测 = 判断"用户本机某端口上有没有跑某个服务"，不需要读响应内容：

- **主手法：`fetch(url, {mode:'no-cors'})`**——端口有服务应答则 promise 成功（响应不透明读不了），连接被拒则失败。Ollama `http://127.0.0.1:11434/`、ComfyUI `http://127.0.0.1:8188/` 均可探测。
- **辅手法：WebSocket**——`new WebSocket('ws://127.0.0.1:8188/ws')` 能连上即 ComfyUI 存活（注意 Firefox 154 起同样要过 LNA 授权）。
- **局限（必须写进设计）**：no-cors 模式读不了响应，**无法从响应内容确认端口上跑的就是 Ollama**（可能是别的服务占了 11434）。正确姿势：no-cors 探测到"有东西"之后，再发一次**带 CORS 的真请求**（如 Ollama `/api/tags`）——成功了就确认身份并拿到模型列表；失败了就精确报"检测到 11434 有服务在跑，但它还没放行 Palink（需要配置 OLLAMA_ORIGINS）"，这恰好就是连接向导要引导的步骤。
- **红线**：探测必须是**用户显式点击"检测本地算力"才触发**，只探测固定已知端口清单（11434/8188/1234/7860…），绝不后台静默扫端口——既是安全姿态，也避免触发浏览器/杀软的恶意行为判定。

## 4. 本地服务逐个评估

## 5. "用起来"的两条产品路径

### 5.1 文本回答：副任务是小手术，主链路是大手术

- **副任务（推荐先做）**：标题生成、摘要、翻译、变量更新草稿、轻量闲聊面板等，本来就是前端/独立小请求，改成"浏览器直连本地 Ollama（流式 fetch）"即可，完全不碰角色扮演主链路。架构上是纯前端模块 + 一个设置页。
- **主回答链路（大手术，单独立项）**：palink-native 装配在后端，模型调用也在后端（new-api 网关）。要让本地 LLM 出主回答，只有一种干净架构——**"浏览器执行器"模式**：后端装配好 prompt → 按现有 SSE/WS 通道下发"待生成任务" → 浏览器调本地 Ollama 流式生成 → 把结果回传后端 → 后端走既有的 MVU 解析/正则/入库/事件管线。可行，但要动聊天主链路的状态机、超时、失败降级（本地模型掉线时回落网关），且本地小模型的角色扮演质量会明显低于网关模型，产品上要做预期管理。**不建议和探测/出图塞同一批施工。**
- 另有一条零服务器的补充路线（WebGPU 浏览器内推理，如 WebLLM 跑 1-3B 小模型）：不需要用户装任何东西，但模型太弱、只配玩具级场景，本文只登记不推荐。

### 5.2 ComfyUI 出图：扩展点现成

后端 `image_generation_service.py` 已实现 comfyui provider 全流程（组 workflow → `POST /prompt` → 轮询 `/history` → `/view` 取图，见 `backend/app/services/image_generation_service.py:1040` 一带），P4 的 `palink__generate_image` 工具链也已上线。托管场景下把**执行端**从后端 httpx 换成浏览器：

1. 后端生成/patch 好 workflow JSON（模板由后端下发，用户也可导入自己的）；
2. 经 SSE/WS 事件把任务下发浏览器（复用现有出图事件通道）；
3. 浏览器 `POST http://127.0.0.1:8188/prompt`（需用户已加 CORS 启动参数）；
4. WebSocket 收进度、`/view` 拉图（CORS 放行后可读成 blob）；
5. 结果回传后端入库 `extra.media`（或仅前端直显，用户可选"结果是否上传服务器"——隐私卖点）。

A1111 的 txt2img 是单次 REST 调用，比 ComfyUI 的 workflow JSON 简单，可作为第二支持。

## 7. 本项目已有底子（调研期间核实）

- **"浏览器直连本地服务"已有人验证过一半**：TODOS.md:193 登记过审计结论——"浏览器直连本地服务技术可行，唯一硬门槛是 CORS，Ollama 11434 默认可直连"（该次是从 localhost 页面测的，托管场景按第 4 节加配置）；TODOS.md:180 同时登记"浏览器直连本地服务未立项、前端图片生成设置页未做（`updateConfig` 零调用方）"。**本次调研 = 把已验证的技术事实产品化，主要工程量在前端探测 UX 和设置页，不是从零攻关。**
- **后端文生图三 provider 现成**：`openai_compatible / sd_webui / comfyui` + 自定义 base_url + 鉴权头 + 内网门控（`ALLOW_INTERNAL_SERVICE_URLS`，`backend/app/utils.py:92`），配置落 `image_generation_config.json`。托管场景它们只能打公网 URL（SSRF 守卫正确地拦内网），所以浏览器桥接是唯一补位方案，两者是互补关系而非重复建设。
- **前端 fetch 治理是现成双通道**：页面级 `guardedFetch`（`frontend/src/utils/sillyTavernPluginRuntime.ts:120`）默认放行跨源（含 127.0.0.1，仅告警）——探测/直连逻辑放这层天然可行；但 **ESM 沙箱级 `createSandboxedFetch`（`frontend/src/lib/plugin-system/sandbox.ts:1385`）会硬拦跨源非白名单**，且白名单是纯 hostname 匹配、无 localhost 概念——要打通 ST 插件生态用本地算力，需给回环地址加白名单特判。
- **Ollama 在本项目只用于 embedding**（记忆/世界书，容器网络 `ollama:11434`，`memory_module/embedder.py`），与"用户本机浏览器可达的 Ollama"是**两个不同拓扑**，不能复用其降级/维度逻辑（1024 维入库不变式），需独立设计。
- **前端没有任何本地服务探测代码**（全局 grep 确认），`useImageGenerationAvailability.ts` 只读配置不探测。
- 自托管同机部署顺带说明：那类部署可以走后端代理（零浏览器限制，`ALLOW_INTERNAL_SERVICE_URLS` 开关已备好），与托管场景的浏览器桥接并存，按部署形态二选一。

## 8. 安全红线与坑

1. **放行配置永远建议精确 origin，不建议 `*`**：`OLLAMA_ORIGINS=*` / `--enable-cors-header *` 等于任何网站都能打用户本机服务（本机服务普遍无鉴权）。已有现实案例（SiYuan CVE-2026-34449：本机服务 `ACAO:*` 被公网页面利用成 RCE 跳板）。连接向导里给出**复制即用的精确 origin 命令**。
2. **不做静默扫描**：探测仅限用户点击触发、固定端口清单、失败快速返回（连接拒绝是毫秒级）。
3. **语义分层别破坏**：`image_proxy_service.py` 刻意"无条件拒内网"（后端出站面）；浏览器桥接是**新的执行面**，不经过后端出站，两者在文档与代码注释里要写清分层，防止未来有人"顺手统一"把 SSRF 守卫拆了。
4. **iframe 坑**：Firefox LNA 对 iframe 内发起的本机请求会**逐次弹窗**（policy-templates issue #1259）。探测/直连逻辑必须放顶层页面 runtime，不放插件沙箱 iframe。
5. **Safari 降级文案**：检测到 Safari 时明确告知"本机算力功能在 Safari 上不可用（浏览器限制）"，别让用户对着没反应的按钮猜。
6. **LNA 弹窗 UX**：Chrome 的弹窗在请求发出时触发，若探测在用户没预期时弹窗会显得像恶意行为——把"点击检测 → 解释为什么需要本地网络权限 → 触发弹窗"做成显式向导步骤。
