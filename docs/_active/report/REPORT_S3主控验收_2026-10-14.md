## 2. 🔴 性能数字错误 —— 报告写"未宣称通过"，实测**达标**

报告 §6 写：**119.1 ms/1000px**，并据此说"不能宣称为劣化 ≤15%"。
对照 S0 基线 28.1 ms/1000px，119.1 意味着 **4.2 倍劣化** —— 这个数一旦被当真，结论会完全跑偏。

**主控独立重测**（同一会话 `c28061bb-…`、同一滚动容器 `.rp-chat-area`、同一 CDP `TaskDuration` 指标、30 步 × 500px、按实际滚动像素归一）：

| 轮次 | traversedPx | taskMs | ms / 1000px |
|---|---|---|---|
| 1 | 15000 | 408.5 | 27.2 |
| 2 | 15000 | 433.4 | 28.9 |
| 3 | 15000 | 384.0 | 25.6 |
| **中位** | | | **27.2** |

S0 基线 = **28.1** ⇒ 劣化 **−3.2%**（略优），**在 ≤15% 标准内，验收标准 3 实际通过**。

**为什么报告会测出 119.1**：我复现了同样的坑 —— 刚 `goto` 后内容高度仍在变（懒加载/资源加载），
`maxScroll` 在 9472 / 14035 / 42267 之间跳，**归一化分母不稳**，单次采样会算出 31.2 甚至 81.6 这种离谱值。
⇒ **性能必须在同一页面内连测 ≥3 轮、待内容高度稳定后取中位**，单点采样一律不可信。

⇒ 建议：把这条写进 S0 档案 §6.1 的"数据可信度声明"（原声明只说了"绝对值受容器影响"，没说"内容高度未稳定时归一化分母会飘"）。

```
修复前：7fa94f3 refs/heads/three-tracks-merge-20261012   ← 只有主分支，S3 不在里面
```

`fcac95b` 在 `s3-switch-default` 上，而 bundle 只打了主分支 ⇒ **磁盘事故会丢掉整个 S3**。

主控已修复（重打，含两个分支）：

```

```

⇒ **教训：`git bundle verify` 通过 ≠ 内容完整，要 grep `refs/heads` 确认目标分支在里面。**
