## 1. 长会话虚拟化（收益最大，风险也最大）

**现状（实测）**：全仓无 `react-window` / `@tanstack/react-virtual`（`frontend/package.json` 零命中）；`CharacterChat.tsx:1932` 对 `displayedMessages` 全量 `.map`；智能卡 iframe 由 `Message.tsx:644-696` 的 `SmartCardDormancyGate` 管理 —— IntersectionObserver + 上下各一屏 `rootMargin`，休眠时用 `content-visibility:hidden` + `visibility:hidden` + 固定高度占位，**iframe 文档保留不卸载**（`Message.tsx:642` `PALINK_CARD_DORMANCY_UNMOUNT = false`，注释已写明置 true 会重新引入 iframe 导航与 iOS 幽灵历史条目）。

**改动面**：引入虚拟列表 = 重写列表容器 + 滚动锚定，与三处既有机制耦合：① `CharacterChat.tsx:1412-1468` 的 N-3 稳定切片（按 `displayedMessages.length` 与元素引用做缓存）；② 上述 iframe 休眠；③ 滚动到底/回顶与「加载更早消息」。

**影响哪条兼容链**：**智能卡与 ST 插件时序**。挂载/卸载时机一变，`$('.mes')` 这类 jQuery 全表遍历（酒馆助手注入 Galgame 按钮、`renderExtensionTemplateAsync`）会因离屏消息不在 DOM 而漏项。这与 09-21 被撤回的动态拆包属同一类风险（改加载/挂载时机），也与项目「不为兼容拆沙箱」的既定立场冲突。

**需要的回归**：ST 插件注入与 `$()` 遍历、状态栏注入与 MVU 成员读取、`more_messages_loaded` 事件、iOS 幽灵历史计数（`[GHOST-HISTORY]`）、加载更早消息、故事线跳转截断、iframe 休眠/唤醒。

**结论**：先**测量**再决定 —— 用 IAB 在 200+ 条会话上量 DOM 节点数 / 内存 / 滚动帧率，拿到数字再谈实施。P0/P1 已把「重渲染成本」压到低位（历史消息 0~2 次），当前瓶颈在**首次挂载成本与常驻内存**，而这两项恰好最依赖 iframe 生命周期，收益与风险同源。

## 2. Service Worker

**现状（实测）**：`vite-plugin-pwa@^1.2.0`（`package.json:105`）与 `workbox-window@^7.4.0`（`:107`）在 devDependencies，但 `vite.config.ts` 无 `VitePWA` 插件（零命中）→ **从未启用**；`frontend/nginx.conf:59-63` 有 `location = /sw.js { alias /usr/share/nginx/html/sw.js; … }`，磁盘无此文件 → **恒 404**（有意留的占位，未清理）。09-21 批次（N1）刚把 hash 资源改为 `immutable` 1 年。

**改动面**：启用 = 新增 SW 注册 + workbox precache manifest + 更新提示 UI，并要圈定 precache 范围（当前主 chunk 1.86MB / CSS 210KB，全量 precache 首访代价大）。

**影响哪条兼容链**：**鉴权面** —— `/uploads/` 带 token、`?token=` 逻辑若被 SW 拦截，token 会写进 Cache Storage（任务书硬约束 3 明令不许动鉴权面）；**缓存语义** —— `immutable` 1 年 + SW 版本更新若处理不当，会出现「旧 HTML 引用已删 hash」；叠加 nginx 的 `proxy_cache`（`/api/st/characters/`）与多标签页并发更新。

**需要的回归**：登录态切换与 token 过期、上传/下载（`/uploads/`）、智能卡资源、离线刷新、发版后强刷一致性、iOS PWA 双 manifest 口径。

**结论**：**当前不划算**。09-21 的 nginx 长缓存 + 预压缩已覆盖「重复访问」收益，SW 的增量主要是「离线可用」，与本项目「服务器常连」的使用场景不匹配，而误缓存 token 的风险很实。建议保持依赖但**不启用**；若要动手，先把那个恒 404 的 `location = /sw.js` 当清理项删掉（无功能影响）。

## 3. 首屏 CSS

**现状（实测）**：`dist/assets/index-BnnXggvG.css` = **210,056 B**（未压缩），由 `dist/index.html` 的 `<link rel="stylesheet">` 引入，位于 `<head>`、阻塞首屏渲染。

**改动面**：三条路 —— ①按路由拆 CSS（Vite 已按 chunk 分 CSS，但 `index.css` 是全局单文件，需要先做样式归属梳理）；②关键 CSS 内联进 `index.html`、其余异步加载；③只做「清理未用规则」。

**影响哪条兼容链**：**状态栏与消息区样式**。`index.css` 含 `.palink-mes-*`、`--rp-color-*`、`.mes_text` 等 ST 兼容选择器；智能卡 iframe 走 `legacy-st-sim` 自带样式不受影响，但主文档的内联 HTML 渲染分支（`Message.tsx` 的 `isHtmlCardContent` 路径）依赖它们。若拆 CSS 时把 `.mes_text` 相关规则挪进异步块，首条消息会出现短暂无样式（FOUC）。

**需要的回归**：消息区三种 `chatStyle`（flat / bubbles / document）、状态栏渲染、插件 `$()` 操作 `.mes_text`、亮暗主题切换、移动端键盘链路（K 系列）、登录页与设置页首屏。

**结论**：**优先级最低**。210KB 未压缩经 `gzip_static`（N5 已投预压产物）后约 30~35KB，与 1.86MB 的 JS 主 chunk 相比不是首屏瓶颈 —— 先解决 JS 才有效果。若要做，只建议走 ③（清理未用规则），风险最低且可静态验证。

## 4. 角色卡状态 2 秒轮询

**现状（实测）**：`CharacterView.tsx:1104` 起 `setInterval(…, 2000)` 轮询 `GET /api/characters/{characterId}/status`，**未带 `cacheTtlMs`**（同文件其它请求普遍带：`:270` / `:463` / `:480` / `:698` / `:720`）。触发条件 = 角色卡导入或翻译处理中；退出条件 = `!status.is_processing`（`:1108`）→ **不是常驻轮询**，处理结束即 `clearInterval` 自停。

**改动面**：①改递增退避（2s → 4s → 8s，封顶 15s）；②加轮询总时长上限（防后端永不把 `is_processing` 置 false 时永久 2s 打点）；③`is_processing` 异常时的兜底重试上限。

**影响哪条兼容链**：**不进 ST 兼容面**（不碰消息链路、不碰插件、不碰 `formatMessage`），只影响角色卡处理流程的提示时序。风险点是节奏变化会让「处理中」提示的出现/结束时机改变，且自动翻译触发（`:1110`，依赖轮询的首次响应）对延后敏感。

**需要的回归**：导入角色卡（含大卡）、自动翻译触发、翻译失败提示、处理完成/失败提示、页面切走再回来（`pollingIntervalRef` 清理）、同时导入多张卡。

**结论**：**性价比最高的待议项** —— 改动面小、不碰兼容面、收益明确（长任务期间请求量可降 4~8 倍）。**注意不要加 `cacheTtlMs`**：轮询语义就是要最新值，加缓存会让它拿到旧状态、反而延长轮询。建议只做 ① + ②。

## 5. 汇总

| # | 项 | 改动面 | 触及的兼容链 | 收益 | 建议 |
|---|---|---|---|---|---|
| 1 | 长会话虚拟化 | 大（列表容器重写） | 智能卡 iframe 生命周期 + ST 插件 `$()` 遍历 | 最大 | **先测量，后决定** |

建议顺序：**4 → 1（先测量）→ 3（只做清理）→ 2（保持不启用）**。
