## 〇、先纠正三个会误导决策的既有结论

这三条不纠正，后面所有决策都会建在错的地面上。

### 纠正 1：「向量召回 93% 命中」是**消息级**口径，模型实际能看到的只有 75.4%

2026-10-11 那份报告的 93.0%，说的是"检索结果里含不含证据所在的**那条消息**"。
但模型看到的是**文本**，不是消息 ID。按"证据原文是否真出现在注入文本里"（**块级**）重测：

| 口径 | 命中率 |
|---|---|
| 消息级（捞到了那条消息） | **94.7%** |
| 块级（证据原文真的进了注入文本） | **75.4%** |

**差的 19.3pp 是"捞对了消息、但证据所在的那一块没进预算"。**
⇒ 任何用消息级口径做的 A/B，都会把这个缺口判成"0 变化"。见纠正 3。

### 纠正 2：邻居扩展**不是**纯成本（与 2026-10-11 报告结论相反）

那份报告实测"关掉邻居扩展，命中 93.0% → 93.0%，0 变化"⇒ 建议关掉省 26.4%。
在消息级口径下这个观察是对的；但换成块级口径（P93b，生产真实路径）：

| 主预算 | 现状（有邻居） | 关邻居 | Δ命中 | Δ体积 |
|---|---|---|---|---|
| 4000 | **75.4%** | 73.7% | **−1.8pp** | −25.9% |
| 6000 | **80.7%** | 77.2% | **−3.5pp** | −27.0% |
| 8000 | **82.5%** | 77.2% | **−5.3pp** | −29.5% |

⇒ 邻居扩展**确实买到 1.8~5.3pp**（因为证据常常就在命中块的邻居里）。
"花 26% 体积买 0 命中"这个结论**作废**；真实权衡是"26% 体积换 2~5pp"。要不要，你拍板。

### 纠正 3：「扩候选池没用（TOPK_KILLED=0）」也是消息级口径的错觉

P93 逐个关旋钮（预算 5200，块级口径，n=57）：

| 配置 | 块级命中 |
|---|---|
| 基线 | 77.2% |
| 关邻居扩展 | 75.4%（−1.8pp） |
| 关 STM | 78.9%（+1.8pp） |
| **候选池 50 → 200** | **80.7%（+3.5pp）** |
| 纯向量（HYBRID_WEIGHT=0） | 75.4% |

⇒ `BLOCK_CANDIDATE_LIMIT` 50→200 白捡 **+3.5pp**，成本是毫秒级内存扫描。
**这是本次发现的性价比最高的一项（纯配置、零体积代价）。**

## 一、经济学地基：命中 : 未命中 = **1 : 50**

两家你在用的上游，当前口径一致（2026-10-11 核）：

| 供应商 / 模型 | 输入（命中缓存） | 输入（未命中） | 输出 |
|---|---|---|---|
| DeepSeek-V4.1-Flash（闲时） | **¥0.02** / 1M | **¥1.00** / 1M | ¥4.00 / 1M |
| Xiaomi MiMo-V2.6-Flash（实时） | **¥0.02** / 1M | **¥1.00** / 1M | ¥2.00 / 1M |

> 高峰期（工作日 9-12 / 14-18 点）两项翻倍，比值不变。

**⇒ 结论：在这两家上，"缩短 prompt"是次要矛盾，"让 prompt 的前缀稳定不变"才是主要矛盾。**
一个 100k token 的**全命中**前缀 = ¥0.002，比 5k token 的**未命中**（¥0.005）还便宜。

而前缀缓存是**严格按位置**的：从第 1 个 token 开始，一旦某处变了，后面全部按未命中计费。

## 二、致命结构问题：滑动窗口每轮都在自杀式刷新缓存

真实装配量出来的 prompt 结构（`_probe_ctx_debug.py`，会话最后一轮）：

```
[system 角色卡        ]  2,172 tok   ← 恒定
[history 最近 24 条   ] 12,772 tok   ← 每轮整体平移一格
[常量：世界书/剧情线等]  9,595 tok   ← 恒定，但排在历史之后
[实体卡 MVU 状态      ]     48 tok   ← 每轮变
[向量记忆             ]  7,158 tok   ← 每轮变
[本轮 user 消息       ]
                        合计 ≈ 42,492 tok（装配自报 total_estimate）
```

**每一轮，history 窗口都从 `[m₁…m₂₄]` 变成 `[m₂…m₂₅]`** ⇒ 从第 1 条历史消息起就与上一轮不同
⇒ **system 之后的全部内容（含恒定的世界书 9,595 tok）永远按未命中计费**。

实测结果：**现状缓存命中率只有 11.8%**（40 轮仿真）。你付了 88% 的全价。

这就是为什么"缩短历史到 4-6 条"能省钱——但它省的是**错误的那个量**。

### 三条读数

1. **B（常量块前移）= 白捡 31%**：命中率 11.8% → 45.5%，**支撑度一模一样（30.1%）**。
   因为世界书 9,595 tok 是恒定的，只是被排在滑动历史之后才永远无法命中缓存。
   把它挪到历史**之前**，它就永久命中。**零质量代价，纯重排。**

2. **C/E（你提的 4-6 条 + 向量）确实省钱（×0.42），但支撑度掉 6.8~8.4pp**
   （30.1% → 22.9% / 21.7%）。这是真实代价：**模型对"刚刚发生了什么"的把握变弱了**。
   想补回来就得加记忆预算（D2：×0.51，支撑度回到 24.9%，仍差 5.2pp）。

3. **G（全量追加）全面胜出**：成本 ×0.24（比 C/E 还便宜一半），
   支撑度 **31.7%（全场最高）**，因为**全部历史原文都在上下文里**。

## 四、为什么"更大的上下文"反而更便宜

G 的输入是 37,788 tok/轮，比现状的 27,782 还**大 36%**，却只花 24% 的钱——
因为它的 **95.5% 都是缓存命中**（¥0.02/1M），只有 1,705 tok 按未命中计费。

反直觉但很硬：**在这两家的定价下，"全量历史 + 高命中" 比 "短历史 + 全未命中" 便宜一个数量级。**

### 记忆线长度：24 条 → 几百条

用"老片段自检索"实测（回溯 N 条之前，用该消息首 25 字回指）：

| 回溯距离 | 24 窗 | 6 窗 | 记忆4000 | 记忆8000 | 记忆12000 |
|---|---|---|---|---|---|
| 25–40 条 | 0% | 0% | 10% | 14% | 19% |
| 40–60 条 | 0% | 0% | 56% | 69% | 69% |
| 60–80 条 | 0% | 0% | 40% | 40% | 40% |

**全量追加 / 代际追加：窗口内距离恒为 100%**（原文就在上下文里，不需要检索）。

本会话 91 条消息 ≈ 49k tok。按实测 ~540 tok/条推算，在 1M 上下文下可容纳约 **1,800 条**。
经济最优上限见下表。

### ⚠️ 追加式的软肋：缓存有保质期，用「会话段」建模才对

### 三条读数（这是本报告最重要的一节）

1. **如果每次来只聊 1 轮就走，G 反而贵 45%（1.45×）。** 整段历史被白重读一遍。
   ⇒ **G 不是普适最优，它有明确的适用门槛。**
2. **门槛是一次连聊 ≥2 轮**：burst=2 时 G = 0.83 开始省钱，burst=3 → 0.66，
   burst=10 → 0.34。聊得越连续越赚。
3. **C/E（你原本提的 4-6 条 + 向量）在短会话下反而更合适**：burst=1 时 0.80，
   明显优于 G 的 1.45。**你的直觉在你的使用场景里是对的。**

### 追加式该封顶多少：现在有第二个理由

之前说封顶是为了防撞上下文墙；**会话段模型下，封顶的意义变成了「锁死冷启动的最坏代价」**——
因为冷启动要重读的正是"当前段"，段越长代价越大。

实测标定（burst=1 即最坏情况，全部冷启动）：

| 封顶（代际大小） | 上下文 tok/轮 | 冷启动最坏代价/次 | burst=1 成本比 |
|---|---|---|---|
| 24 条（K） | 22,715 | ¥0.0275 | **0.94** ✅ |
| 48 条（I） | 29,333 | ¥0.0341 | 1.16 ❌ |
| 96 条（L） | 41,201 | ¥0.0459 | 1.57 ❌ |
| 不封顶（G） | 37,788 | ¥0.0425 | 1.45 ❌ |

⇒ **抗冷启动的封顶大约在 24~32 条**。超过这个数，遇到"每次只聊一句"的用户就会亏。

### ★ 自适应：冷启动轮先探路，确认在聊了再升级

思路（用户提出）：**"一句就走"就不上追加式，"一直在聊"就上。** 实测有效：

| 策略 | 聊1轮 | 聊2轮 | 聊3轮 | 聊5轮 | 聊10轮 | 连续 | **最坏** | 支撑度 |
|---|---|---|---|---|---|---|---|---|
| G 全量追加（不判断） | **1.45** ❌ | 0.83 | 0.66 | 0.46 | 0.34 | 0.24 | **1.45** ❌ | 31.7% |
| M 自适应（第 2 轮升级） | 0.84 | 0.95 | 0.71 | 0.51 | 0.36 | 0.24 | 0.95 | 31.7% |
| N 自适应（第 3 轮升级） | 0.84 | 0.64 | 0.79 | 0.56 | 0.38 | 0.24 | 0.84 | 31.7% |
| **M24 自适应 + 封顶 24** | 0.84 | **0.68** | 0.57 | **0.47** | 0.39 | 0.35 | **0.84** ✅ | 26.2% |
| M48 自适应 + 封顶 48 | 0.84 | 0.80 | 0.64 | 0.52 | 0.42 | 0.35 | 0.84 | 29.5% |
| M96 自适应 + 封顶 96 | 0.84 | **1.02** ❌ | 0.78 | 0.60 | 0.46 | 0.36 | 1.02 ❌ | 31.7% |

**⇒ 自适应的价值是"把最坏情况从 1.45 压到 0.84"**，代价是长会话时比纯 G 多花 0.02~0.12。
**M24（自适应 + 封顶 24）在任何使用习惯下都 ≤ 0.84，推荐作为默认档。**

判断逻辑（**无状态，不需要记住上一轮用了什么**）：
```
gap = 现在 - 最后一条消息的时间
gap 小（< 30 分钟，可调） ⇒ 缓存大概率还在 ⇒ 追加式（封顶 C）
gap 大                   ⇒ 缓存已过期     ⇒ 探路：6 条 + 回忆预算 6000
```
封顶 `C` 由"这个会话历史上平均一次聊几轮"决定：默认 24，确认聊得久再放大到 48 / 96。
详细设计、改动点、验收方式见 spec。

### 想两头都要：摘要日志（append-only，推荐后续做）

封顶会砍掉记忆线。有个办法能兼顾：

```
[系统提示][世界书][往昔摘要日志 —— 只追加，永不改写][当前段原文 —— 只追加，封顶 C][实体卡][记忆][本轮]
```

- 每次封存时，把当前段最老的一部分压成摘要，**追加**到摘要日志末尾（不是替换）；
- 摘要日志因此也是"只增不改" ⇒ **冷启动时它照样命中缓存**，代价极短（几 k tok）；
- 只有"当前段"会在封存时失效一次，代价被 C 锁死。

⇒ 记忆线 = 摘要日志（无限）+ 当前段（C 条），而冷启动代价 ≈ 摘要长度 + C，可控。
⚠️ 需要调 LLM 做压缩，**本次未实测**（禁止真实 API）。

## 五、推荐落地方案（按风险从低到高）

> ⚠️ **先看 §四的决策表再动手。** 如果你一次通常只聊 1-2 轮，直接把窗口调大是**亏钱**的。

### 第 1 刀：纯配置，5 分钟，随时可回退

```bash
# docker-compose.yml → backend.environment
- CHARACTER_CHAT_HISTORY_LIMIT=400     # 原 24；仅在「一次连聊 ≥5 轮」时才这么改
```

窗口不再滑动 ⇒ 前缀稳定 ⇒ 命中率 11.8% → 95%+。**预期 ×0.24（连续聊时）。**

⚠️ 三个前提：
- **必须确认你的使用习惯**（§四决策表）。短会话请改小或直接不改。
- `token_budget` 实测为 **1,046,016**（1M 上下文），本会话 49k tok 远在里面。
- 但**没有任何代码层面的历史上限保护**——`build_character_chat_messages` 只按条数 limit，
  超长会话会一路涨到撞上下文墙。**必须配第 3 刀。**

**不管选哪条路，下面这一项都稳赚：**
```bash
- MEMORY_BLOCK_CANDIDATE_LIMIT=200     # 原 50 → 块级证据命中 +3.5pp，毫秒级成本
```

顺手可做的两个纯配置白捡项（见 §〇 纠正 3 / §六）：
```bash
- MEMORY_BLOCK_CANDIDATE_LIMIT=200     # 原 50 → 块级命中 +3.5pp
```

### 第 2 刀：常量块前移（小代码改动，**白捡 31%**）

把 `dynamic_context_parts` 里的**恒定**部分（世界书 `[World Lore]`、剧情线、长度提示、
角色校准、PHI）移到 history **之前**；**每轮变**的部分（MVU 实体卡、向量记忆）留在历史之后。

- 收益：命中率 45.5%（在 24 滑动下测），支撑度不变。
- ⚠️ **语义风险**：世界书条目在 ST 语义里有 `position/depth`（before/after char、in-chat @depth）。
  动之前必须逐个条目确认它是否依赖"在历史之后"的位置语义。**这是本方案唯一需要人工审的一项。**

### 第 3 刀：给历史上限 + 世代封存（必须做，否则长会话会撞墙）

追加到 200k tok 后，把最老的一段封存：
- 封存块放在 prompt **最前**（`[往昔摘要]`），之后的内容按原样继续追加；
- 每次封存会让后续前缀失效一次 ⇒ 那**一轮**全量未命中（200k × ¥1/M = ¥0.2）；
- 但每 200k tok（≈370 条消息）才发生一次 ⇒ **摊薄到每轮 ≈ ¥0.0005，可忽略**。
- 封存要压缩就得调 LLM（一次调用：200k 输入 + ~2k 输出 ≈ ¥0.21，同样摊薄可忽略）。

### 第 4 刀（可选）：向量记忆退居"超窗兜底"

追加式下，**会话内回看根本不需要检索**（原文在上下文里）。
`roleplay_prompt_assembly._memory_gate_should_skip` 已有这个逻辑：
`history_truncated` 为真才检索 ⇒ 历史没被截断时自动跳过记忆。

⇒ 记忆只服务两种场景：**① 超出 cap 的老内容 ② 跨会话/跨角色**。
**这直接把嵌入的 CPU 开销砍掉一个量级（见 §七）。**

## 六、记忆预算：现状 4000 已经接近饱和点

生产真实路径扫描（`get_context(B)` → 邻居扩展 `B×1.3` → `build_memory_context(B×1.3)`，n=57）：

| 预算（内部单位） | 块级证据命中 | 消息级 | 平均注入（内部单位） | ≈ 真实 tok |
|---|---|---|---|---|
| 750（档 0） | 7.0% | 8.8% | 827 | 1,133 |
| 1500 | 61.4% | 82.5% | 1,990 | 2,726 |
| 2500 | 70.2% | 87.7% | 3,361 | 4,605 |
| **4000（档 1，现状）** | **75.4%** | 93.0% | 5,389 | **7,383** |
| 6000（档 2） | 80.7% | 94.7% | 7,922 | 10,853 |
| 8000（档 3） | 82.5% | 94.7% | 10,286 | 14,091 |

**⇒ 如果坚持走"短历史 + 向量"路线：预算设 6000**（+5.3pp，成本仍在 ×0.5 左右）。

## 七、向量引擎选型：**保留 bge-m3，不要换**

同一份真实语料（227 条记忆行 / 66,419 字）+ 同一份题集（57 题），容器内 Ollama 纯 CPU：

| 模型 | 维度 | 吞吐 | 单条查询 | top1 | top3 | 注入命中@4000 |
|---|---|---|---|---|---|---|
| **bge-m3（现状）** | 1024 | **0.9 千字/秒** | **45 ms** | 8.8% | **35.1%** | **71.9%** |
| qwen3-embedding:0.6b | 1024 | 0.4 千字/秒 | 72 ms | 10.5% | 24.6% | 66.7% |

⇒ **"换小模型更快"是错的**：qwen3-0.6b 是 decoder-only（自回归架构、32K 上下文），
bge-m3 是 encoder（XLM-R，全 token 并行）。**小模型反而慢 2 倍、命中低 5.2pp。**

✔ **结论：向量引擎不动。**

## 八、「AI 输出的记忆怎么算」：现状别改装配口径，要改的是别算那么多

### 8.1 一个被否证的想法：按消息装配（别做）

假设：既然"捞对了消息（94.7%）但块没进预算（75.4%）"，那就**命中消息后回填该消息的全部块**。

实测（P92，用库里已存的 227 条向量，零嵌入成本）：

| 预算 | 块级（现状） | 消息级（建议） | Δ |
|---|---|---|---|
| 2000 | 64.9% | 57.9% | **−7.0pp** |
| 4000 | 71.9% | 68.4% | **−3.5pp** |
| 6000 | 73.7% | 75.4% | +1.8pp |
| 8000 | 77.2% | 77.2% | 0.0pp |
| 12000 | 82.5% | 78.9% | **−3.5pp** |

⇒ **否证。** 消息级装配把预算集中在少数几条消息上，**覆盖的消息数变少**，反而更容易漏。
现状的块级 + 邻居扩展（也是"多捞几条"的一种形式）已经是更好的形状。
**不要改装配口径。**

### 8.2 真正该动的是「算多少」

现状：assistant 回复 → structural 切块 → **平均每消息 2.52 块，每块独立嵌入入库**
（本会话 227 行 / 90 条消息）。这些嵌入**绝大部分在被检索到之前就已经在 prompt 里了**
（因为历史窗口本来就有原文）——**是纯粹的重复劳动**。

| 方案 | 每轮嵌入调用 | 说明 |
|---|---|---|
| 现状（24 滑动 + 全量切块入库） | ≈ 6 次/轮（5 块 + 1 查询） | 90% 的召回结果本就已在 prompt 内 |
| **追加式 + 记忆退居兜底** | **0 次/轮**（未超 cap 时） | 会话内回看走原文，不检索 |
| 追加式 + 超 cap 后 | 仅封存时批量算一次，之后靠摘要/兜底检索 | 摊薄到每轮 ≈ 0 |

**⇒ 这是能拿到的最大 CPU 降幅：不是让嵌入更快，而是让嵌入根本不发生。**

### 8.3 核显加速：容器里做不到，宿主上才有一线

实测（本会话机器，AMD Ryzen 7 8845H w/ Radeon 780M）：

```
容器内：/dev/dri 不存在，/dev/kfd 不存在
Ollama 日志：discovering available GPUs... → 只发现 id=cpu library=cpu
             n_threads = 8 / 16 | CPU: AMD Ryzen 7 8845H w/ Radeon 780M Graphics
             （OLLAMA_VULKAN 已为 true，但无设备可用）
WSL2：      ls /dev/dri → No such file or directory
```

⇒ **Docker/WSL2 里没有任何 GPU 计算通路，核显加速在现有部署拓扑下不可行。**

两条可选路径（都需你拍板，本次未实施）：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 宿主侧 ONNX-DirectML** | 在 Windows 宿主上跑一个 `/api/embed` 兼容的小服务（fastembed + onnxruntime-directml），`OLLAMA_HOST` 指过去 | 多一个宿主常驻进程要维护；Windows 更新/休眠会打断 |
| **B. 少算（推荐）** | 见 8.2，把每轮嵌入调用降到 0 | 无硬件依赖，收益更大 |

⇒ **建议先做 B。B 做完后嵌入负载已接近零，A 的边际价值所剩无几。**

## 九、诚实的局限

| 项 | 说明 |
|---|---|
| **未做端到端生成质量评测** | 零付费约束下无法验证"模型真的答得更好"。支撑度是**词汇级代理指标**，不等于生成质量 |
| 样本 | 单会话（91 条 / 45 轮）、单角色、单题集（57 题）。小会话与群聊未测 |
| 缓存命中率 | G 的 95.5% 是**仿真值**（假定服务端前缀缓存按 64 token 粒度长期有效）。**真实缓存 TTL/淘汰策略是黑盒**，上线后必须用实际账单核对 |
| token 估算 | 用本项目实测系数 0.66 tok/字（中文）。真实 tokenizer 下载失败（网络超时），未用精确计数。**绝对值可能有 ±15% 偏差，相对比较不受影响** |
| 常量块前移 | 世界书 `position/depth` 语义未逐条审计，存在行为变化风险 |
| 长上下文副作用 | "lost in the middle"、TTFT 变长等**无法离线验证**，需上线观察 |
| 封存压缩 | 需调 LLM，**本次未实测**（禁止真实 API） |
| 探针自身的坑（已修） | 早期版本自写 `render_at_budget` 会在文本中间留空洞，把块级命中从 75.4% 低估到 47.4%。**已全部改用生产同一渲染器 `utils.build_memory_context` 重测** |
