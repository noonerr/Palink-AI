## 2. 三条「不能做」的证据

### 2.1 B1 · tokenizer 合并会破坏 ST 兼容（否决）

报告说「以 `tokenizer_service`(5 引用) 为主合并」。实测三套**语义不同**，不是重复实现：

| 模块 | 行数 | 唯一消费者 | 语义 |
|---|---|---|---|
| `tokenizer_service.py` | 42 | `generation_service.py:19`（`encode_tokens`/`tokenizer_available`） | tiktoken 可用性判定 |
| `token_counter_service.py` | 237 | `quota_service.py:178`（`count_messages_tokens`/`count_text_tokens`） | **按模型精确计费**计数 |
| `st_tokenizer_service.py` | 845 | `api/silly_tavern.py:1826`、`roleplay_prompt_assembly.py:547/556/591/3323`、`worldbook_service.py:117`、`api/tokenizer.py:142` | **ST 兼容的 zh-aware 估算**（`zh_aware_guesstimate`/`smart_guesstimate`） |

- 合并进 `tokenizer_service` 等于让**计费路径**改走**估算路径**，或让 **ST 插件面**改走 **tiktoken** —— 两条都是静默行为变更。
- `st_tokenizer_service.py` 当前有 **+90 行未提交改动**（在途工作），此时合并必然冲突。
- 报告自己写的「1.5 人日」换 1,124 行，收益/风险比不成立。

**替代动作**：若嫌名字乱，只做**改名 + 顶部 docstring 标注职责边界**，不动任何实现。

### 2.2 B2 · `inference_queue` 不是僵尸（否决该项）

报告称其为「僵尸模块（8 引用）」。实测这 8 处引用分布在 **5 个活跃生产模块**，与「本地模型」无关：

```
api/chat.py:475,486,496            → 队列状态 / 取消
api/websocket.py:2389              → 连接断开时取消请求
memory_module/ai_summary_service.py:109  → submit_and_wait
services/compact_title_service.py:177    → submit_and_wait
services/inference_dispatcher.py:660     → submit_request
```

它是**全局推理排队设施**（并发控制 + 取消），删掉 = 聊天取消/并发限制整体失效。**不是本地 LLM 专属**。

### 2.3 B2 · `local_model_registry` / `llama_runtime` 处于阻塞态

`TODOS.md` §[未开工·待拍板] 明确写着：

> **⛔ 阻塞项**：**边界未确认** —— 只删 B 套，还是 A+B 全删？**确认前不动刀。**
