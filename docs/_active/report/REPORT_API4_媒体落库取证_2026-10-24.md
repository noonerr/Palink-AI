## 0. 结论（先答关键问题）

**"父侧 success 是真落库后的成功还是无脑成功？"——三条轨三种答案，且各轨 answer 不同：**

| 轨 | 落库通道 | success 语义 | 判词 |
|---|---|---|---|
| **A 帧内轨**（smart-card-runtime 卡内 `getContext().appendMediaToMessage`） | **存在且真实**（六跳全通，PUT→后端 commit，§1 表） | **失真**：三种情形静默假成功（§0.1） | best-effort 落库 + 恒真回报；`success=true` 不能作为落库证据 |
| **B ST 插件轨**（`lib/sillytavern/getContext.ts:2993`） | **无**（只写内存态） | 更糟：返回 `void`，连成功都无从回报，也从不报错 | **伪成功（静默无效）**，刷新即丢 |
| **C 插件沙箱轨**（`lib/plugin-system/sandbox.ts:4867` → 宿主桥） | 存在且真实（与 A 同一 PUT 端点） | 诚实：全失败路径 `success:false` | **三轨中唯一诚实通道** |

**数据面判词**：`character_chat_messages` 现有 248 行，含非空 `media` 数组 7 行 / 媒体项 11 条，
**11/11 全部携带 `prompt` 键**（图像生成服务 `build_media_item` 的恒写签名，`message_media_service.py:108-135`），
**0 条**具备 appendMediaToMessage 写入特征（无 `prompt` 键的条目）。历史库**零 append 落库痕迹**。

⇒ 路线图 §0 的"端到端落库未证实"本次升级为三个已证事实：
① **B 轨无落库通道**（代码级证实，`services/message-manager.ts:85-90` 无任何 API 调用）；
② **A 轨通道在场但回报语义失真**（三个静默假成功点，§0.1）；
③ **历史数据零 append 痕迹**（SQL 全量解析，§3）。

### 0.1 A 轨（帧内轨）的三个静默假成功点（代码级，未运行时复现）

A 轨端到端链路本身是通的：`extra.media` 会随 PUT 进库（后端 `_sync_message_content_to_active_swipe`
合并 extra 后 commit，`character_ext.py:3488→3508`）。但以下三种情形**不落库、照样回 true**：

1. **消息不在父侧 messages**：`CharacterChat.tsx:971` `if (!hasExplicitContent && !fallbackMessage) return;`
   —— 静默 return；而父侧分发器 `SmartCardCompatController.ts:2226` 在 if 块外**无条件**
   `result = { success: true, content }` ⇒ 帧内拿到 true。帧内 compatChat 索引与父侧
   messages 数组可能漂移（帧内 chat 是 `compactSmartCardChatMessages` 压缩版，
   `CharacterCardRenderer.tsx:437`），索引越界即触发本条。
2. **消息 id 非正整数**（未持久化尾部消息的临时串 id）：`useCharacterChat.ts:1720-1721`
   `Number.isInteger(persistedMessageId) && persistedMessageId > 0` 不满足 ⇒ **只改本地 state 不 PUT**，
   帧内仍回 true。卡对刚生成、尚未落库的最后一条消息 append 媒体正是这个场景。
   ⚠️ 更糟的分支：id 为 null 时帧内 `normalizeChatMessage` 把 id 兜底成**数组下标**
   （`part-03.ts:979` `message?.id ?? message?.message_id ?? index`）⇒ 小整数被当 DB id 送进 PUT → 404。
3. **PUT 抛错被吞**：`useCharacterChat.ts:1805-1808` catch 里只 `console.error` + `toast.error('编辑消息失败')`
   —— 异常不上抛 ⇒ 控制器 `:2226` 恒 true。is_locked 403（`character_ext.py:3440-3441`）、网络错、500 全部归于本条。

（修正记录：取证中途曾怀疑"空正文 + 无 display 层"也会被 `SmartCardCompatController.ts:2214`
门禁拦下，**该怀疑不成立**——`hasSmartCardDisplayLayerOptions` 的键表含 `'extra'`
（`SmartCardCompatController.ts:106-141`），帧内 payload options 恒带 extra ⇒ 门禁必过。)

### 0.2 A 轨附加发现：正文污染副作用（代码级，未运行时复现）

帧内 `setChatMessageCompat(undefined, id, {extra})` 时，`normalizeMessageUpdatePayload`
把 content 回落成 `targetMessage.mes`（`part-05.ts:511-521`）——那是**卡面归一快照**
（`buildSmartCardChatEntry` 经 `normalizeCardFacingMessage`：剥【声音】标记、归一引号，
并 `extractReasoningTags` 剥 reasoning，`CharacterChat.tsx:115-130`）。
父侧分发器 `SmartCardCompatController.ts:2222` 用 `payloadHasExplicitMessageContent` 把这个
string content 判为**显式内容**（覆盖帧内标记的 false）⇒ `applySmartCardMessageUpdate`
以该快照为正文走 PUT（`CharacterChat.tsx:970-975, 1005-1024`）⇒ 后端覆写 `msg.content` 与活动 swipe
（`character_ext.py:476-488`）。

⇒ **A 轨每次真落库媒体，同时把 DB 正文改写成卡面归一版**。这与沙箱轨桥注释里自述的教训同类：
`CharacterChat.tsx:1534-1538` 明言 `__palinkChatMessages` 的 mes 被洗过、"直接回写会抹掉样式块"，
沙箱桥为此专门用权威原文回写（`:1569-1571`）——A 轨没有这层防护。
仅当消息含 reasoning 标记 / 【声音】行 / 待归一引号时产生实际差异；纯文本消息无差异。

## 4. 若需修复：最小落点建议（本轮不实施）

按危害排序：

1. **A 轨假成功根修**（`SmartCardCompatController.ts:2210-2226`）：`result` 不再无条件
   `{success:true}`。最小改法：让 `applySmartCardMessageUpdate`（`CharacterChat.tsx:943`）返回
   `{success: boolean}`（消息找到且 PUT 2xx ⇒ true；`:971` 静默 return 与 `:1721` 只改本地 ⇒ false），
   控制器透传该值。帧内 `part-08.ts:377` 的 `success !== false` 判定自动变诚实，无需动帧内。
   连带要求 `handleEditMessage`（`useCharacterChat.ts:1805-1808`）把 PUT 失败向调用方上抛或回传，
   否则 toast 吞错照旧假成功。
2. **A 轨正文污染**：extra-only 更新不应携带卡面快照当正文回写。参照沙箱桥做法
   （`CharacterChat.tsx:1569-1571` 用权威原文）；或在 `applySmartCardMessageUpdate` 里对
   "content 实为回落快照"的 extra-only 更新走专用分支（PUT 前以父侧权威 content 覆盖 payload.content）。
3. **B 轨补通道**（`getContext.ts:2993`）：改走沙箱轨同一宿主桥 `window.__palinkAppendMessageMedia`
   （已在场，`CharacterChat.tsx:1546`），并返回 boolean；`:2995` 的"后端暂无媒体附件端点"注释需订正。
   ⚠️ `getContext.ts` 当前属并行会话禁区，动工需另排。
4. **A 轨 id 兜底**（`part-03.ts:979`）：id 为 null 时回落**数组下标**会把小整数当 DB id 送 PUT
   （404）。帧内应在 append 前校验 id 形态（持久化消息才放行），不符返 false。
5. **复测口径**（修后验收）：三反例——空正文消息 / 未持久化尾部消息（临时串 id）/ is_locked 消息，
   三者都必须回 false；数据面以"无 `prompt` 键的 media 项计数 >0"作为 append 落库痕迹出现的判据。
