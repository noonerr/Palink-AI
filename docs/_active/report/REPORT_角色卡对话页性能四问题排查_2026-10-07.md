## 0. 结论速览

| # | 问题 | 根因（一句话） | 瓶颈在哪 |
|---|---|---|---|
| 1 | 点击进入无 loading | 会话切换**没有 loading state**，唯一的 `loadingSessionRef` 是 `useRef`（不触发渲染）；且 5 个请求**串行 await** | 前端状态缺失 + 串行往返 |
| 2 | 历史消息补渲染滚动跳动 | `loadOlderMessages` 把消息 **prepend** 到头部，**完全没有 scrollTop 补偿**；容器高度还被异步上报的 iframe 高度二次改变 | 前端锚定缺失 |
| 3 | 每次进入都重请求全量渲染 | messages 缓存 TTL 仅 **10 秒**且是内存缓存；**同接口重复打 2 次**（memoryStats）；另有 `?limit=1` 的额外往返；后端还有 **全量回退**分支 | 缓存策略 + 重复请求 |
| 4 | 分支切换卡死 3-5s / 正文空白 | **每个卡片 iframe 要拉取并执行 4.03MB 插件脚本**（实测），一次切换 4 张卡片 = 4 次 4MB 解析执行；正文由卡脚本渲染，必须等脚本到位 → 空白 | **iframe 内脚本加载执行** |

> 远远不够 3-5 秒。真正的瓶颈是 iframe 侧的 4MB 脚本。这条写在这里，避免下一个人重复踩。

## 1. 问题一：点击对话入口后毫无反应

### 1.1 根因

**a) 没有 loading state，只有 ref**

`CharacterView.tsx:265`：
```ts
const loadingSessionRef = useRef<string | null>(null);   // ← ref 变化不触发渲染
```
`handleSelectSession`（`:1481-1497`）全程**不 set 任何 state** 表示"正在切换"，
唯一相关的 `loadingSessionRef` 是 ref ⇒ **按钮永远拿不到 loading 态**，点了就是没反应。

**b) 5 个请求串行 await，且其中一个重复**

```ts
const handleSelectSession = async (session) => {
  setSelectedSession(session);
  setMemoryStats(null);
  setForkPoint(null);
  await loadMessages(session.id);        // 内部还 Promise.all([loadMemoryStats, loadBranches, branch-tree])
  await loadMemoryStats(session.id);     // ← 与 loadMessages 内部那次完全重复
  await wb.loadSessionStatus(session.id);   // 串行
  await pl.loadSessionStatus(session.id);   // 串行
};
```
弱网下总耗时 = 各请求耗时之和。而且 `setSelectedSession` 立即生效、`messages` 要等第一个 await
才更新 ⇒ 这段空白期界面显示的是**上一个会话的内容**，视觉上就是"点了没反应"。

**c) 会话切换动画又额外加了 200-300ms 延迟**

`useSessionSwitchAnimation.ts:86-97`：切换前先 `setTimeout` 200（侧栏收起时）或 300ms（侧栏展开时）才真正发起。
这段时间是**纯等待**，且期间同样没有 loading 反馈。

### 1.2 修改方案

1. 新增 **`switchingSessionId: string | null` state**（不能用 ref），点击瞬间 `setSwitchingSessionId(session.id)`，链路结束（含 catch/finally）置 null。
2. 把它下发给会话列表组件，在被点击的那一项上渲染 spinner，并加 `aria-busy="true"` + 防重复点击。
3. **拆分首屏关键路径**：只 `await loadMessages`；`memoryStats` / `wb.loadSessionStatus` / `pl.loadSessionStatus` 改为**并发且不阻塞**（`Promise.all` 后台填充，不 await）。
4. **删掉** `:1486` 那次重复的 `loadMemoryStats`（`loadMessages` 内 `:735` 已调）。
5. 动画延迟期间就让 loading 生效（loading 在 `setSwitchingSessionId` 时立即出现，不必等动画）。

## 2. 问题二：历史消息补渲染导致滚动跳动

### 2.1 根因

**a) prepend 后零补偿 —— 主因**

`CharacterView.tsx:754-785`：
```ts
setMessages(prev => [...newMsgs, ...prev]);   // ← 往头部插入 10 条
```
插入后 `scrollHeight` 增大、`scrollTop` **不变** ⇒ 视口里的内容被整体推下去 ⇒ 用户看到"跳到别处/停在正文中间"。
**全仓无一处做 prepend 的 scrollTop 补偿。**

**b) 三个"滚到底"effect 在加载更早时全部失效**

`:1630` / `:1640` / `:1675` 的滚到底逻辑都以 `isAtBottomRef.current` 为前提。
用户点"↑ 加载更早消息"时人在顶部 ⇒ `isAtBottom=false`（`:824-825` 判定 `distanceFromBottom < 50`）⇒ 全部不生效 ⇒ 完全失去锚定。

**c) 原生 scroll anchoring 在这里不可靠**

容器 `#chat`（`CharacterChat.tsx:2030-2033`，`overflow-y-auto`）内的卡片高度是 **iframe 通过 postMessage 异步上报**的，
加载完还在持续变化；React 又是整段重渲染替换 DOM ⇒ 浏览器锚点元素可能被替换，原生锚定失效或抖动。

**d) 初始底锁有 1.5 秒时限，慢网直接失效**

`:270` `INITIAL_BOTTOM_LOCK_MS = 1500`；`:1650`：
```ts
if (performance.now() >= initialBottomLockUntilRef.current) {
  pendingInitialBottomLockRef.current = false;   // ← 直接放弃
  return;
}
```
弱网下消息请求超过 1.5s 返回 ⇒ 进来就不在底部。

### 2.2 修改方案

1. **prepend 补偿**：`loadOlderMessages` 发起前记录 `prevScrollHeight = scroller.scrollHeight`、`prevScrollTop = scroller.scrollTop`；
   成功后在 **`useLayoutEffect`**（不是 useEffect，避免闪一帧）里
   `scroller.scrollTop = prevScrollTop + (scroller.scrollHeight - prevScrollHeight)`。
2. **容器显式关闭原生锚定**：给 `#chat` 加 `overflow-anchor: none`，让代码完全接管，避免两套机制打架。
3. **初始底锁改判据**：去掉 1.5s 硬时限，改为"消息到达 → 连续两帧 scrollHeight 稳定 → 滚到底并清锁"；或至少把时限提到 8s 并在每次 `messages` 变化时重置。
4. **卡片占位高度**：iframe 高度上报前用固定占位高度（已有 `dormantHeight` 机制可复用），减少高度回填引起的二次漂移。

## 3. 问题三：请求与缓存（弱网慢）

### 3.1 根因

| 问题 | 位置 | 说明 |
|---|---|---|
| TTL 形同虚设 | `CharacterView.tsx:726` | messages `cacheTtlMs: 10_000`（10 秒）；`branch-tree` 15 秒（`:704`/`:739`）⇒ 基本等于每次重拉 |
| 缓存不持久 | `services/api.ts:319-339` | 纯**内存**缓存，刷新页面/重进全丢 |
| **同接口打两遍** | `CharacterView.tsx:1486` vs `:735` | `loadMessages` 内已 `loadMemoryStats(sessionId)`，外层 `handleSelectSession` 又调一次 |
| **额外往返** | `CharacterChat.tsx:787-795` | 为拿 `variables` 单独发 `?limit=1`，**无 cacheTtlMs**，与 `?limit=10` 无法复用 |
| 分支数据双拉 | `CharacterView.tsx:693` + `:703` | `loadBranches` 与 `fetchBranchTree` 各拉一次 |
| **后端全量回退** | `backend/app/api/character_ext.py:2951-2956` | 过滤智能卡触发消息后不足 `limit` 条 ⇒ `query.order_by(id.desc()).all()` **全表加载**。分支切换 `limit=20` 更容易触发 |
| 渲染零缓存 | `Message.tsx:964-1041` | 每次进入对每条消息重跑 `applySillyTavernDisplayPipeline`（正则+Showdown+DOMPurify）。实测 20 条 **58.4ms**，非主因但可省 |

### 3.2 修改方案

1. **删请求**：`CharacterChat.tsx:787` 的 `?limit=1` 整个删掉 —— 后端 `character_ext.py:2931`/`:2969` **已经在 messages 响应里返回了 `variables`**，直接复用。
2. **去重**：删 `handleSelectSession:1486` 的 `loadMemoryStats`；`handleStorylineNavigate` 内 `loadBranches` 与 `fetchBranchTree` 合并为一次。
3. **调 TTL**：messages 提到 60s，branch-tree 60s；并对"会话首屏数据"加一层 `sessionStorage` 快照（刷新后立即可渲染，同时后台校验）。
4. **渲染缓存**：以 `messageId + contentHash + regexScriptsVersion + 深度窗是否命中` 为 key 缓存管线结果（LRU ~50 条）。
   ⚠️ key 不能只放 depth 数值 —— depth 会随新消息变化，否则每次新消息都 miss。
5. **后端改全量回退**：`:2951` 改为"窗口加大再取一次"（如 `limit + 300`），避免 `query.all()`。
6. **预取**：会话列表渲染时预取最近使用会话的前 10 条。

## 4. 问题四：分支切换卡死 3-5 秒 + 正文空白

### 4.1 先证伪一个假设（避免重复踩坑）

假设"20 条消息同步跑显示管线 = 主线程阻塞"。**实测不成立**：

```
=== 同步渲染耗时（真实「正文美化」脚本，单线程，不含 iframe）===
1 条  : 2.1 ms    卡片=1  产物=30429 字符
20 条 : 58.4 ms   卡片=4  产物≈60KB
```

58ms 撑不起 3-5 秒。瓶颈不在前端渲染管线。

### 4.2 真根因：每个卡片 iframe 要吃下 4.03MB 插件脚本

生产库 `plugin_scripts` 实测：

| 脚本 | 体积 |
|---|---|
| 数据库界面插件(@bubble改造版) | **4,034,225 字节（4.03 MB）** |
| 对话渲染系统 v7.1 | 242,270 字节（0.24 MB） |

`CharacterCardRenderer.tsx:519` 的注释自己写着"避免 **4.4MB** 随每次 context-update 反复结构化克隆"——开发时已知这个量级。

链路：分支切换 → `setMessages`（`limit=20`）→ 20 个 Message 重建 → 窗口内 **4 条**（`maxDepth=3`，见本报告姊妹篇）是 smart-card → **4 个 iframe** → 每个 iframe：

1. `SillyTavernCompatRuntime.ts:891` `await requestParent('getPluginScriptContents', ..., { timeout: 30000 })` —— 从父页 postMessage 拉源码；
2. 父侧 `CharacterCardRenderer.tsx:1036-1056` 应答，结构化克隆 ~4.3MB 字符串；
3. iframe 内**解析并执行**这 4.3MB JS。

⇒ 4 个 iframe × ~4.3MB 解析执行，**全部在同一主线程** ⇒ 3~5 秒阻塞、掉帧、发热。
从 1 条切到 20 条特别明显，正是因为 iframe 数从 1 涨到 4。

### 4.3 正文空白的根因（同一条链的时序后果）

- **正文**由 iframe 内**卡脚本**渲染，必须等 `getPluginScriptContents` 返回并执行完才有内容；
- **变量栏 / 角色栏**的数据来源是 `sessionVariables` / `stat_data`，走 `context-update` 通道，**不需要等脚本** ⇒ 先出来；
- ⇒ 现象就是"变量栏和角色栏渲染出来，正文整块空白"。
- **"再切一次才显示"**：第二次切换时父侧 bundle 已在内存、iframe 内脚本已被浏览器编译过，路径大幅变快，赶在你观察前完成。
- **叠加项**：`SmartCardDormancyGate`（`Message.tsx:653`）在切换瞬间因布局剧变把部分卡片判为 dormant（`content-visibility:hidden`），
  iframe 在隐藏态加载完成后唤醒**可能不重绘** —— 上一轮的 `repaintKick` 用 `transform` 翻转，存在被合成器跳过的经典失效模式，**且从未真机验证**。

### 4.4 修改方案

| 优先级 | 措施 | 预期效果 |
|---|---|---|
| P0 | **首屏只挂载视口内卡片**：其余先渲染固定高度占位，IntersectionObserver 懒挂载 iframe | 同时活着的 iframe 从 4 降到 1-2，卡死时间减半以上 |
| P0 | **先出正文再跑插件**：把卡正则产物（正文）与插件脚本执行解耦，正文先挂载，脚本异步到位后 hydrate | 直接消灭"空白"现象 |
| P1 | **脚本包瘦身**：4.03MB 单脚本先做体检（是否重复拼接 / 是否内嵌 base64 资源），能拆则拆、能延后则延后 | 从源头降一个数量级 |
| P1 | **跨 iframe 复用**：脚本内容改为 `blob: URL` 或 SharedWorker 共享，避免每个 iframe 重新解析执行 4MB | 第 2~N 个 iframe 近乎零成本 |
| P2 | **分支切换首屏 `limit` 由 20 降到 10**，剩余按需补 | 首屏工作量减半 |
| P2 | **修复 repaintKick**：把 `transform` 翻转换成必然触发重绘的方式（`opacity` 切换 / 子树 `display` 切换），或直接去掉 `content-visibility:hidden`（保留 `visibility:hidden`） | 消除休眠唤醒后的空白 |
| P2 | **切换期间反馈**：`setIsNavigating(true)` 已有，但应配合骨架屏，避免"假死"观感 | 体验 |

## 5. 改动后如何验证

### 5.1 门禁（每次改动必跑）

```bash
cd frontend && npx tsc --noEmit            # 必须 exit 0
cd frontend && npx vitest run              # 只认 failed = 0（基线会随用例增长浮动）
cd backend  && docker exec palink-ai-backend-1 sh -c "cd /app && python -m pytest tests/ -q"
```
> ⚠️ 改了前端 `src` 必须 `npm run build` 并确认容器在服务新指纹（14000 端口）；改了后端必须重建镜像。

### 5.2 问题一（loading 反馈）

- **静态**：grep 确认 `switchingSessionId` 是 `useState`（不是 ref）且已传入会话列表组件并用于渲染 spinner。
- **观测**：DevTools Network 面板限速到 "Slow 4G"，点击会话 → **被点击项上必须立刻出现 spinner**（≤100ms），且点击后不可重复触发。
- **量化**：Performance 录制，从 click 到"消息列表首条出现"的时间 = T1；改造后 `memoryStats`/世界书/剧情线三项不应再计入 T1（应在其后完成）。

### 5.3 问题二（滚动跳动）

- **量化探针（推荐，可脚本化）**：切到"Slow 4G"，点"↑ 加载更早消息"前后各记录一次
  `const el = document.querySelector('#chat'); ({top: el.scrollTop, h: el.scrollHeight})`，
  断言 **`ΔscrollTop ≈ ΔscrollHeight`**（误差 < 8px）。改前必然是不等的（scrollTop 几乎不变）。
- **肉眼**：加载期间视口内的那条消息**必须始终停在同一位置**，不得被推走。
- **回归点**：加载后仍在底部时应继续吸底；向上滚动时不得被强行拉回底部。

### 5.4 问题三（缓存）

- **Network 面板**：进入同一会话两次（间隔 < 60s），第二次 `messages` / `branch-tree` 请求数应为 **0**。
- **请求计数**：改造前一次进入会话 = `messages(limit=10)` + `messages(limit=1)` + `memoryStats`×2 + `branches` + `branch-tree`；
  改造后应降为 `messages` + `branches` + `branch-tree`(缓存命中) + 后台 `memoryStats`×1。
- **后端**：对 `character_ext.py:2951` 的全量回退加一条日志/计数，确认长会话不再触发 `query.all()`。

### 5.5 问题四（卡死 + 空白）

- **卡死量化**：Performance 录制分支切换（1 条 → 20 条），看 **Main 线程最长单个 Task 时长**。
  改前应能看到 ≥3s 的长任务；目标 < 500ms。同时看 `Scripting` 占比（4MB 脚本执行应在里面显形）。
- **iframe 计数**：`document.querySelectorAll('iframe[srcdoc], .character-card-renderer iframe').length`
  —— 改造后首屏应 ≤2（而非 4）。
- **空白判据（最关键）**：切成大正文分支后，**不等任何交互**，2 秒内正文区必须有内容。
  可脚本化：切换后轮询该条消息的 `innerText.length`，记录"首次 > 0 的时刻"。改造后应 < 1.5s（理想 < 500ms）。
- **二次切换不复现**：连续切换 3 次，每次都要出正文，不能靠"再切一次"。
- **休眠回归**：切完后向上滚动到视口外的卡片，确认不空白（这条同时验证 repaintKick 修复是否真的有效 —— **必须真机验，上一轮就是栽在没验**）。

### 7.1.1 问题 1 的呈现方式调整（2026-10-07 02:5x，按用户要求，commit `c9c3739`）

**用户裁定**：不要在被点击的角色卡上打局部转圈；要「跳进对话页 + 全屏覆盖层 + 进度条」，
并让用户知道还要等多久。

**改动**：
- `CharacterList.tsx`：**完全回退** 7.1 那版的 `enteringCharacterId`（卡片 overlay + 禁用按钮）。
- `CharacterView.tsx`：
  - 新增 `CHAT_ENTER_STAGES`：`character` 35% → `messages` 70% → `done` 100%，
    进度按**实际已完成的关键路径节点**推进，不假造匀速动画；
  - `chatEnterStage` 驱动一个 `fixed inset-0 z-[9999]` 的全屏覆盖层：
    spinner + 阶段文案 + 进度条 + 「已等待 N 秒」（每秒递增，进入新阶段归零）；
  - 覆盖层是**全局 fixed 层**而非挂在卡片上：点击后先遮住列表页，页面切到聊天后继续遮住，
    消息到位才消失 ⇒ 视觉上就是「跳进对话 + 全屏加载」；
  - 进度满格后保留 300ms 再撤，避免遮罩生硬消失闪出空白。

**为什么不在点击瞬间就 `setViewState('chat')`**：聊天页需要完整角色数据
（`extensions` / 世界书绑定等）才能渲染，而列表项是精简对象，
用它先行渲染聊天页有崩溃风险。覆盖层是全局层，遮罩期间的页面切换用户看不到 ⇒
体验等价，风险更低。

**为什么显示「已等待 N 秒」而不是「还需 N 秒」**：剩余时间取决于网络与后端，无法真实预测；
给出「还需 N 秒」只能是猜测，会形成错误承诺。已等待秒数是唯一能诚实展示的量。

#### 7.1.2 再调整：改为真实进度百分比 + 放行前等首屏渲染完成（commit `928672f`）

**用户澄清**：要的是**进度百分比**（判断已经走到百分之多少），不是「已等待多少秒」；
并且**允许多等一会儿**，让前端加载得更完全再放行，进去之后的体感会更好。

**改动**：
- 阶段（含进度硬上限）：`character` 45% → `messages` 75% → `render` 92% → `done` 100%。
- **进度只平滑爬升到当前阶段的上限、绝不越过** ⇒ 百分比始终是「至少完成了这么多」的
  **下界**，不虚报。阶段停留超过 `2.2s` 后允许极慢爬行（逼近但不越过下一阶段安全线，即 `下一阶段 cap − 5`），
  既给「还在动」的感知，又不会爬到 100% 后干等。
- **新增 `render` 阶段（放行延后）**：`loadMessages` 完成后**不立刻放行**，先
  `waitForFirstPaint(700ms)` —— 双 rAF 等 React 提交与浏览器布局，再留 700ms 给
  卡片 iframe 挂载 / 字体 / 首屏图片，然后才 `done`。
  理由：**数据到位 ≠ 画面就绪**；用户进去时界面应当已经是完整的，而不是逐条补渲染。
- UI：去掉「已等待 N 秒」，改为右侧**百分比数字**（`tabular-nums`，等宽不跳字）。
