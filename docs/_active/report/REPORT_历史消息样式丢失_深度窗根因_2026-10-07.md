# REPORT：历史消息样式丢失 —— 真根因是角色卡正则的 `maxDepth` 深度窗（非 iframe 休眠）

> **状态：已定位并实证（离线受控实验 + 生产库取证），未做代码改动。**
> 建立日期：2026-10-07。
> 本文**订正** `docs/_active/report/REPORT_四问题排查_历史样式丢失与侧栏卡顿_2026-10-06.md` §1 的根因结论。
> 排查方式：生产库字段取证 + 用真实脚本跑前端显示管线的受控对照实验（vitest 探针，已跑完即删）。

---

## 0. 结论速览

| 项 | 内容 |
|---|---|
| **真根因** | 角色卡「露缇雅1.2」的显示正则脚本 **「正文美化」自带 `maxDepth = 3`**，只作用于**倒数第 1~4 条**助手消息。更靠上的历史消息一律不匹配 → 正文保持纯文本 |
| **为什么"故事线跳转+刷新"能好** | 跳转走 `switch?up_to_message_id=X`，**把消息列表截断到目标点**，目标消息变成最后一条（depth=0）→ 必然落在窗口内 → 美化完整 |
| **为什么上一轮修复无效** | 上一轮定性为「`SmartCardDormancyGate` 休眠态 iframe 加载完成后不重绘」，加了 `repaintKick`。但窗口外的消息**根本没有生成 iframe**（实测产物是 24 字符纯文本，无 HTML）→ 没有 iframe 可休眠、可重绘 → 该修复在结构上不可能修掉本现象 |
| **这是 bug 还是设定** | **是卡作者的设定，不是 Palink 的 bug**。ST 官方 `shouldSkipRegexScript` 同样按 `minDepth/maxDepth` 过滤，这张卡在 ST 里表现一致 |

## 1. 证据一：生产库里的脚本字段（决定性）

`characters.extensions.regex_scripts`（注意：`regex_scripts` **表是空的**，真数据在角色卡 `extensions` 里）：

```
角色：露缇雅1.2（8b851ded-e850-4472-b57c-833e770b453b）
脚本名：正文美化
  disabled      : False
  placement     : [2]            ← 仅 AI 输出
  minDepth      : 无
  maxDepth      : 3              ← ★ 窗口上限
  markdownOnly  : True
  findRegex     : /<(story|Lnterleaving|now_plot|content|正文)>([\s\S]*?)<\/\1>/gi
  replaceString : 30181 字符（完整卡片 HTML，含 dcRoot iframe）
```

同卡其余脚本（状态栏 / 变量更新美化 / 隐藏变量更新等）`maxDepth` 均为空 —— **全卡只有「正文美化」这一条带深度窗**。

## 2. 证据二：受控对照实验（前端真实管线）

用生产库导出的**真实脚本**跑 `applySillyTavernDisplayPipeline`，唯一变量是 `messageIndex`（即 depth）：

| 场景 | depth | 是否美化 | 产物长度 |
|---|---|---|---|
| 20 条 · 第 17 条 | 3 | ✅ 是 | 30180 |
| 20 条 · 第 16 条 | **4** | ❌ 否 | **24**（纯文本） |
| 17 条（故事线截断）· 第 17 条 | 0 | ✅ 是 | 30180 |
| **对照**：删掉 `maxDepth` 后，20 条 · 第 16 条 | 4 | ✅ 是 | 30180 |

> 最后一行为对照实验：同一条消息、同一内容、同一脚本，**只把 `maxDepth` 置空就从 24 字符变成 30180 字符**。
> 因果链闭合：元凶就是 `maxDepth`，不是渲染、不是休眠、不是缓存。

## 3. 证据三：故事线跳转确实会截断列表

`CharacterView.tsx:675-682`：

```ts
const params = messageId !== null ? `?up_to_message_id=${messageId}&limit=${limit}` : `?limit=${limit}`;
const data = await api.post(`/api/character-sessions/${id}/branches/${branchId}/switch${params}`);
setMessages(data.messages || []);   // ← 截断后的列表，目标消息成为最后一条
```

`CharacterChat.tsx:1520-1522` 的注释亦写明该语义。⇒ 跳转后目标消息 depth=0，必然命中窗口；刷新后仍在该截断分支上，故依旧完整。

## 4. 为什么上一轮的 `repaintKick` 修不好（误判复盘）

上一轮报告 §1.2 定性：「卡片的 iframe 在休眠期间完成加载，唤醒时未重新光栅化」。

**该机制在本现象中不成立**，理由是顺序反了：

```
显示管线 → 正则是否命中？
   ├─ depth ≤ 3 → 产出 30180 字符卡片 HTML → 才有 iframe → 才谈得上休眠/重绘
   └─ depth ≥ 4 → 产出 24 字符纯文本       → 压根没有 iframe → 休眠门控无事可做
```

用户看到的是**纯文本**，对应的是右分支（"没生成卡片"），而不是左分支（"生成了但没画出来"）。
⇒ 修 `content-visibility` 唤醒重绘，只可能影响**窗口内**的 4 条消息，对窗口外的历史消息**结构性无效**。

> 方法论教训（与 10-06 报告 §1 首轮教训同类）：**"看起来像渲染故障"不等于"渲染层有故障"**。
> 判定"某条消息该不该有样式"时，先问**它的输入有没有走到产出卡片的那一步**，再看渲染层。
> 上一轮是先假定"卡片一定生成了"，再去找"为什么没画出来"，跳过了一步前置校验。

## 5. 附带查清的性能改动（用户提到的"之前有 Agent 为优化性能做过修改"）

两处，都与本现象无关但是背景：

| 改动 | 位置 | 说明 |
|---|---|---|
| 消息分页 `limit=10` | `CharacterView.tsx:726`（首屏）、`:760`（`loadOlderMessages` 每次补 10 条） | 初始只加载最近 10 条，靠"↑ 加载更早消息"按钮补 |
| 卡片休眠门控 | `Message.tsx:653` `SmartCardDormancyGate`（`content-visibility:hidden`，不卸载） | 为规避 iOS 幽灵历史条目，由"卸载"改为"隐藏" |

分页**不改变 depth**（depth 是相对末尾计算的，加载更早消息不影响末尾 4 条的相对位置），故也不是本现象成因。

## 6. 修复选项（未施工，供决策）

| 方案 | 做法 | 代价 / 风险 |
|---|---|---|
| **A · 改卡（最省、最符合 ST 语义）** | 把「正文美化」的 `maxDepth` 由 3 改为空（或调大到会话长度） | 长会话里每条历史消息都生成 30KB 卡片 HTML + 一个 iframe → **正是当初做性能优化要避免的开销**，侧栏卡顿问题二会加剧 |
| **B · 渲染结果缓存（推荐折中）** | 首次在窗口内渲染成功后，把格式化产物持久化（消息 `extra` 或 IndexedDB），历史消息直接读缓存 | 需处理"卡脚本/正则变更后的缓存失效"与存储上限；改动面中等 |
| **C · 前端放宽深度窗** | 前端管线对历史消息忽略 `maxDepth`（可加全局开关） | 与 A 同开销，且偏离 ST 语义，后续对齐债增加 |

**若只想让"最近 N 条都有样式"**，最小动作是方案 A 把 3 调成期望值（如 9），并接受 iframe 数量增长。

## 7. 给用户的一秒自查判据

在会话里数目标消息**距末尾几条**（含它自己）：

- 落在**最后 4 条内** → 应有样式；没有则是休眠/重绘问题（此时才轮到 `repaintKick` 那条链路）。
- **第 5 条及更早** → 必定没有样式，`maxDepth=3` 挡下来的，**刷新、重进、换设备都一样**。

对应到 DB 实测会话（露缇雅1.2，活跃会话 `f25daab6` 共 48 条，无 system 消息）：
全局第 17 条的 depth = 48 − 17 = **31**，远超窗口 ⇒ 纯文本属预期；故事线跳到它则 depth=0 ⇒ 完整美化。与用户描述完全吻合。

**做了**：

- 未验证 `repaintKick` 对**窗口内**消息是否有实际收益（它可能是有效修复，只是与本现象无关）。
