# 一次性并轨施工方案与回退备选计划

> 日期：2026-10-12
> 上游依据：《REPORT_三轨并一轨整合方案_2026-10-12.md》（三期版的论证与证据全部适用，本文只改节奏：三期压缩为一次交付内的有序施工，回退设计相应调整）
> 阅读约定：白话为主；门牌号 = 文件:行号，供定位。

---

## 0. 前提声明（本方案成立的条件，开工前逐条确认）

1. **零改革负担**：该部署实例上没有其他真实用户（系统本身支持多用户注册，若有第二个账号在跑，本方案不成立，需回到三期版加灰度）。
2. **数据可丢或可备份**：数据库与上传文件已备份（或接受回退时丢失回退点之后的数据）。
3. **工期接受“集中”而非“更快”**：一次性不会缩短总工作量（物理摆在那），只是把三次小考换成一次大考；省掉的只是双轨对照期和开关维护，约 1~2 周。
4. **接受“回退主要靠版本控制”**：一次交付内连续施工，运行期开关窗口很短，真正兜底的是 git 标签 + 数据库快照。

**若第 1 条不成立**：停，改用三期版，不要讨价还价。

## 1. 目标与非目标

**目标（一次做完）**：
- 大堂轨（卡脚本/ST 插件注入主页面执行）整体退役：功能全部由单间轨（iframe 隔离轨）承接，大堂代码删除；
- 单间轨补齐大堂轨的全部接口缺口（MVU 变量、世界书、挂载点、存储桥、事件），并把 6,961 行大头文件拆成 4~6 个模块；
- 存储键做双兼容迁移（旧键读一次自动搬新键），用户已解锁状态不重置。

**非目标（明确不做）**：
- 帘子轨（`lib/plugin-system/sandbox.ts`，Palink 自有插件的假环境沙箱）**保留不并**。理由：它服务自有插件，需要多文件加载与深度存储集成，强并进单间成本极高（+3~4 人周）且安全模型不同。它以后可以改用统一传话协议，但轨道留着。（如你坚持连帘子一起并，见附录 A 的代价清单，拍板后我再修订本文。）
- 用户显式信任的大卡后门（授权后读真实数据库）保留——这是产品授权，不是技术轨。
- 后端链路（变量写入、装配链）不动。
- 正则/格式化管线不动。

## 2. 施工顺序（关键路径，六步，一次交付内连续做完）

> 顺序是物理硬的：先让新房能住人 → 再搬客人 → 最后拆旧房。可以并行的是步骤内部的细项，不能调换的是步骤本身。

| 步 | 内容 | 主要文件（门牌号） | 完成判据 |
|---|---|---|---|
| S0 备料 | 三轨行为对照表（同一动作在三轨下的结果）；测试基线复跑留档；性能基线（首屏/内存/50 消息会话）；18 条契约测试**先写出来**（先红或先绿均可，但必须存在）；数据库 dump；git 打基线 tag | 全仓 | 对照表评审过 + 基线数字入档 + tag 落地 |
| S1 补功能 | 单间轨补齐大堂轨接口缺口：MVU 变量读写与事件、世界书接口、存储桥对齐；按 KNOWN_TAVERN_GLOBALS 表做两侧注册对齐，消灭“大堂有、单间无” | `smart-card-runtime/SillyTavernCompatRuntime.ts`、`legacy-st-sim.ts`、`inline-st-globals.ts` | 对照表每一行在单间有对应实现；新增单间侧测试绿 |
| S2 造挂载点 + 存储迁移 | 单间内惰性创建 ST 插件挂载容器（抄帘子轨成熟策略 `sandbox.ts:754-765`）；存储键双兼容迁移（读新键→无则读旧键→写新键） | `smart-card-runtime/storage.ts:54`、`SillyTavernCompatRuntime.ts` 挂载节 | 5 个真实插件的挂载点在单间可见；解锁状态读回成功 |
| S3 切换默认 | 卡脚本与 ST 插件执行默认改道单间；大堂注入入口加“紧急停机开关”（此步起开关生效，一步之内不删） | `lib/sillytavern/card-script-runner.ts`、`utils/sillyTavernPluginRuntime.ts:2214-2225`、`components/views/character/CharacterChat.tsx` 接入点 | 18 条契约测试全绿；3 张代表卡 + 5 插件真机逐项过 |
| S4 拆单间 | 6,961 行大头文件拆 4~6 模块（传话核心/全局登记/垫片/诊断），立“单文件 ≤1,200 行”门禁；顺手清大堂死代码（空 Observer、`__dbgContent` 等已勘查项） | `smart-card-runtime/*` | 拆后测试全绿 + 行数门禁过 |
| S5 删大堂 + 收尾 | 删除大堂轨代码与注入逻辑；kill switch 保留一个版本（作为最后的后悔药，下个版本再删）；更新文档与目录 | `card-script-runner.ts`、`sillyTavernPluginRuntime.ts` 注入段、`inline-script-replay.ts` | 全量测试绿；`tsc` 无悬空引用；打包产物体积不升 |

## 3. 工期重估

| 项 | 工期 |
|---|---|
| S0 备料 | 1 人周 |
| S1 补功能 | 3~4 人周 |
| S2 挂载点 + 存储迁移 | 2~3 人周 |
| S3 切换默认 + 契约测试打磨 | 2 人周 |
| S4 拆单间 | 1~2 人周 |
| S5 删码收尾 | 0.5~1 人周 |
| **合计（含 20% 兼容性缓冲）** | **10~14 人周** |

比三期版（11~16）只少 1~2 周——**这就是一次性到底的真实价格：省的是对照期，不是工作量。** 单人全职约 2.5~3.5 个月；两人约 6~7 周。

## 4. 回退备选计划

一次性方案没有分期的事故隔离，回退设计按“**版本控制为主、开关为辅、数据双兼容兜底**”组织：

### 4.1 保险丝（开工第一天全部就位）

| 编号 | 措施 | 时机 |
|---|---|---|
| R0-1 | 全程在单独分支施工，S0 结束打 tag `merge-base` | S0 |
| R0-2 | 每个施工步结束打 tag（`s1-done`/`s2-done`/`s3-done`/`s4-done`） | 逐步 |
| R0-3 | 数据库全量 dump + 上传文件目录快照，存到仓库外 | S0 |
| R0-4 | `_BACKUPS/` 全工作区备份（已有机制） | S0 |

### 4.2 回退档位与触发条件

| 档位 | 回退动作 | 适用窗口 | 触发条件 |
|---|---|---|---|
| R1 运行期开关 | kill switch 一键切回大堂执行，不重新打包 | S3 完成起、到 S5 删码前一天（窗口较短，是“后悔药”不是主方案） | 冒烟发现代表卡/插件功能异常但不确定根因 |
| R2 存储数据回退 | 存储迁移代码本身就是“读新→回退旧”双兼容，切回开关后旧键完好，解锁状态天然恢复 | 全窗口 | 发现解锁状态/变量数据异常 |
| R3 代码级回退 | `git revert` 到目标 tag；数据库用 S0 快照恢复 | 任何时刻 | 契约测试大面积红且短期修不齐；合并后出现阻断性故障 |
| R4 全量回退 | 工作区恢复到 `merge-base` 前状态（_BACKUPS + tag） | 任何时刻 | 决定放弃本次合并 |

### 4.3 回退决策树（出事时按此走，不现场拍脑袋）

1. 测试红了但代码没上线 → **不回退**，停下查因（红测试就是来干这个的）；
2. 冒烟挂了、能开关 → R1，留现场日志；
3. 开关救不回 / 数据乱了 / 故障阻断 → R3（+ 数据库快照恢复）；
4. 连续两次 R3 后仍阻断 → R4，复盘后再决定要不要重来。

### 4.4 回退的已知代价（提前认账）

- R3 会丢掉回退点之后的**数据库写入**（新消息、新解锁）——零负担前提下可接受，这也是第 0 节要先确认没有其他用户的原因；
- 存储双兼容只保“旧键不被动过”，若 S2 之后旧键被清理逻辑删过，R2 不完整——所以 S2 的迁移代码**只准加新键、不准删旧键**（写进验收口径）。

## 5. 一次性特有风险与缓解

| 风险 | 为什么一次性更严重 | 缓解 |
|---|---|---|
| 三个坑同爆无法定位 | 分期有隔离带，一次没有 | S0 的 18 条契约测试先行（把“单间能做 X/不能做 Y”钉死）；S1 与 S3 之间插入一次全量测试，补功能的错不等切换来暴露 |
| 无对照数据，合完不知道对不对 | 分期有两周双轨对照 | S0 行为对照表 + 性能基线前置；验收用数字不用感觉 |
| 开关窗口太短，回退主要靠 git | 连续施工 | R0 的 tag 体系 + R3 演练一次（S0 之后故意 revert 一个空提交验证流程通） |
| 删码后发现问题 | S5 是单行道 | kill switch 比大堂代码多留一个版本；删码 commit 单独一个，revert 成本最低 |

## 6. 验收口径（直接沿用整合方案，不重新谈判）

1. 3 张代表卡（图鉴卡 + 变量卡 + 纯 HTML 卡）合并前后逐项一致，**旧解锁状态保留**；
2. 5 个真实插件（quick-reply / translate / token-counter / memory / regex）功能可用率 ≥95%；
3. 50 条智能卡消息会话：首屏时间、滚动帧率、内存峰值劣化 ≤15%（对照 S0 基线）；
4. 故意抛错的卡脚本不影响其他消息与页面；
5. 所有静默失效落降级统计且插件管理页可见；
6. kill switch 有效；R3 回退流程已演练通过；
7. 全量测试绿：后端 pytest 100% 通过、前端 vitest ≥95%、`tsc` 零错误；
8. 单文件 ≤1,200 行门禁通过。

## 附录 B：本方案与三期版的差异备忘（防止将来复盘时混淆）
