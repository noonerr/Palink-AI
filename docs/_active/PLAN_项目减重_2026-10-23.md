# 项目减重计划（2026-10-23）

> 配套：`REPORT_重复造轮子审计_2026-10-23.md` 的发现清单。
> 目标：**在不影响现有功能正常使用**的前提下，逐点回收重复/死代码。
> 约束（用户拍板）：①本地模型能力**保留**，不删；②一点一点往回改，每步可独立验证、可回滚。

## 0. 总原则

### 0.1 不动清单（哪怕看着像重复）

下列经核实是「按设计如此」，**不在本次减重范围**。改它们属于功能变更，不是减重：

| 项 | 为什么留着 |
|---|---|
| 本地模型栈（`local_model_registry` / `llama_runtime` / `inference_queue` / dispatcher 本地分支） | 用户明确要求保留，以后可能用 |
| 前端 `lib/worldbook/*` 世界书引擎 | `getWorldInfoPrompt` 注释（`getContext.ts:2355`）**明确声明**仅供 ST 插件显示兼容，实际注入走后端。是设计双轨，不是 bug |
| ST 面自带 `_token_from_request` 取 token | 它要从 `X-Palink-Token`/`X-Palink-Auth-Token` 头取，主依赖 `get_current_user` 只认 `Authorization`/Cookie。**取 token 这一层不可合并**；可合并的只是解码内核 |
| `variables-compat.ts` 的 TS 函数 + `VARIABLES_COMPAT_SOURCE` 字符串副本 | 模板字符串硬约束（iframe 内联必须自包含），注释要求两份同步。删任一份都会让测试或运行时断 |
| smart-card-runtime 两轨 shim（legacy + v2） | 已是逐字节搬运 + identity 守卫；合并属于大重构，不在「一点一点改」的范围 |

### 0.2 分级

按「改了会不会让用户看到不一样的东西」分三档，**严格按档推进**：

- **L1 纯减重（零行为变更）**：删重复实现、改成调用唯一实现。改前改后任意输入输出一致。可成批做。
- **L2 收口（行为收窄，但新行为更对）**：消除"两份结果不一致"，让两边走同一条路。会改变某些边界的结果，但方向是「让它们一致」。每步必须配回归测试。
- **L3 待评估**：动它需要先改功能或大重构，本次**只记录不动手**。

### 0.3 验证纪律（沿用 MEMORY）

- 每步落地后跑相关单测 + 真机探针；只认 `failed=0 errors=0`。
- L2 步骤必须「改坏会红 + 还原会绿」双证；策略内核单测全绿 ≠ 接线生效。
- 后端容器是 CRLF：改完与 `git show HEAD:` 比 sha256 必然不等，用 `diff --strip-trailing-cr` 比内容。
- 改 `docs/` 后重跑 `py scripts/docs/gen_docs_catalog.py` 再 `--check`。
- 只用 `git commit -o -- <pathspec>` 提交自己的文件，禁 `add -A`/`commit -a`。

### 0.4 工作流（每个 L1/L2 步骤固定四件套）

1. **快照**：动前记下「改这段做什么、为什么安全」+ 现有测试名。
2. **动刀**：最小改动，能删就不加层。
3. **验证**：相关单测 + 真机探针（见每步的「验证口径」）。
4. **回滚点**：每步独立成一个 commit，commit message 写清减重项编号。

### 6.7 环境教训（本次实测）

- **仓库内 LF / CRLF 混存**，且**同一文件内也可能混**。用 Python 批量改代码时，
  不能把正则里的 `\n` 直接 `replace("\n", "\r\n")` —— 那会把量词 `\n*` 破坏成 `\r\n*`，
  导致"函数没删掉但 import 加上了"的假成功。正确写法：正则统一用 `(?:\r?\n)`。
- 干跑（打印 diff 行数）**必须先做**：本次干跑第一版就暴露了 8 个文件未匹配。
