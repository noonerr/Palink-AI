## 二、每一项为什么这么定（都带实测）

### 1. 查询改用本轮消息 —— 零成本、快 4.8 倍

窗口查询 600 字里本轮问题中位只占 **3.4%**（n=50），其余是上一条 assistant 回复的尾巴，还夹着 `<UpdateVariable>` 与 `【声音：…】`。

同一批题（p46/p49，生产代码路径实测）：

| 查询 | 注入命中（目标记忆是否进注入集） | 单次耗时 |
|---|---|---|
| 窗口查询（旧） | 31.2% | 3009 ms |
| 本轮消息（新） | **66.0%** | 619 ms |

生产路径复核（p49，直接调改完的 `MemoryRetriever`）：`w_kw=0` 时注入命中 66.0%、中位排名 3、206 ms。

顺手修掉一个**回退分支的真实缺陷**（是旧测试报出来的，不是我猜的）：本轮消息常常已经落库、成为「最近一条」，旧回退逻辑会把它拼两遍，白白占掉一半查询预算。已加去重（`prev_tail` 以本轮消息结尾时剥掉）。

> 顺带回答「要不要把记忆正文再纯化一遍」：**不用**。入库侧 `clean_memory_content` 已经剥干净（227 行里 `<UpdateVariable>` / 残余 HTML 均为 0），只剩 `【声音】`（41/227，占 2% 字符）。实测把库重纯化 + 重嵌 227 条，检索指标**一行没变**。脏的是**查询**不是库，所以纯化做在查询侧（`_clean_query_text`），不动存量。

### 2. 关键词路 + RRF —— 本轮最大的一块收益

为什么需要第二条路：向量对「专名 / 数字 / 改口」这类**字面锚点**不敏感。实测两条路是**相乘**关系：只修查询 top1 22.9%，加关键词路后 41.7%。

实现两级（不做全库 Python 扫描，那在生产行数上不可接受）：

1. **SQL 粗筛**：`ORDER BY similarity(content, :q) DESC LIMIT 50`（pg_trgm）。实测 **8.9 ms/次**（227 行），gold 落在粗筛集内 **43/50（86%）**——粗筛只负责「别太贵」，漏掉的由向量路兜底。
2. **Python 精排**：字符二元组**覆盖率** = |查询二元组 ∩ 记忆二元组| / |查询二元组|，低于 0.12 视为无字面关联。分母是**查询**的长度，所以长记忆不会因为「字多」而虚高——这是这条路能用的关键。

验证「粗筛 ≠ 漏检」（p46，n=48）：

| 检索路 | top1 | top5 |
|---|---|---|
| 纯向量 | 22.9% | 58.3% |
| 关键词（全库 Python 扫描，理论上限） | 58.0% | 86.0% |
| **关键词（pg_trgm 粗筛 + 精排，落地形态）** | **58.0%** | 78.0% |

粗筛在 top1 上**零损失**（top5 掉 8pp，可接受）。

**权重定标（p47）—— 这一步差点定错**：
原题集是从原文句子生成的，**天然字面重合度高**，在上面纯关键词能到 58%。只拿它定权重会得出「纯关键词最好」的错误结论。所以额外造了 **48 道同义改写题**（与原问 bigram 重合中位 0.13，确认是真改写不是复述）反向校验：

| w_kw | 0（纯向量） | 0.2 | 0.35 | 0.5 | **0.7** | 1.0 |
|---|---|---|---|---|---|---|
| 原题 top1 | 22.9% | 41.7% | 41.7% | 41.7% | 41.7% | 43.8% |
| **改写题 top1** | 20.8% | 27.1% | 29.2% | 31.2% | **33.3%** | 31.2% |
| 较差的那一侧 | 20.8% | 27.1% | 29.2% | 31.2% | **33.3%** | 31.2% |

**取「两套题里较差的那一侧」最大化 ⇒ 0.7**（替代复核报告里定的 0.35）。

融合用 RRF（倒数排名融合，k=60）而不是加权求和：向量相似度与覆盖率不同量纲，直接相加等于让覆盖率这种天然偏低的信号永远输给余弦。

### 3. 邻居扩展单开预算 —— 一个**从未真正生效**的功能

旧实现把 `request.max_tokens` 直接传给 `_expand_chunk_neighbors`，而检索已经把窗口填到接近满额（实测 1480/1500），于是 `total + t > max_tokens` **恒真** ⇒ 实测 24 次检索**全部 +0 条**。

后果比「没做扩展」更糟：注入的是被切开的半截段落，前半句在、后半句不在，模型只能脑补。

修完（p49，w=0.7 固定）：

| | 记忆条数 | 记忆 tokens | 注入命中 |
|---|---|---|---|
| 关扩展 | 10.1 | 1380 | 74.0% |
| 开扩展（+30% 预算，封顶 4 条） | 13.1（**+3.0**） | 1880（**+499**） | 74.0% |

⚠️ **注意最后一列没变**：邻居扩展**不提升召回命中**，它补的是「被切开的另一半」。代价是记忆区 tokens +36%（1380 → 1880）。而预算审计报告已实测「记忆区放大到 6000 会掉 0.080 分」。所以它到底值不值，**只能靠端到端判分**（见 §3）。

配套改了一处**必须同步改**的地方：`build_memory_context(mem_ctx, max_tokens=...)` 的渲染预算也要跟着放大，否则多捞回来的相邻块会在渲染时被「整条跳过」重新砍掉——而且砍的是排序最后的（= 最新的 = STM），等于白捞。

#### 3.1 顺手挖出的第二个缺陷：邻居扩展**不可复现**

生产实测（p51）时发现同一问题两次检索注入长度不同（3167 / 4028 字符）。追下去是两个叠加问题：

1. `result.memories` 的顺序是**时间序**（retriever 末尾 `sort by created_at`），不是相关度序；
2. `_expand_chunk_neighbors` 用 `{m.id for m in ...}` 的 set 做去重，而封顶 4 条一旦生效，「轮到谁先被扩展」就由迭代顺序决定。

结果：**同一问题两次跑，补进的是不同的邻居块**（差一条 462 tok 的块）。邻居扩展的语义是「把最相关的那条记忆补完整」，按时间序显然不对。

修法：retriever 把**相关度序**（LTM 强→弱，再拼 STM）通过新增的 `ContextResponse.relevance_order` 传给 service，`_expand_chunk_neighbors` 按它迭代；不传时退回时间序（兼容旧调用方）。

修复后连跑 3 次：`n=20 / 1943 tok / 4148 字符 / id 尾 4 位一致`，完全稳定。

> 附带澄清一个此前的误读：p51 第一轮曾看到装配报告里记忆 **2455~2709 tok**，一度以为预算失控。实为**假象**——那份 `[Relevant Memories]` 段落是上一轮脚本 60 秒缓存命中后的残留内容，不是本轮代码产出。关掉缓存后实测：**档位 1500 + 邻居 30% = 1950 预算 ⇒ 实际用掉 1943 tok**，与设计完全一致。

#### 3.2 记忆档位预算的夹持

顺带发现一个真实的结构性风险：档位表上限是 **6000**，而 prompt 总预算 = `context_window − max_tokens − reserve`，在小窗口模型 / 长 `max_tokens` 下可能只剩两三千。此时记忆区按档位吃满会把对话历史挤没。

已加 `_MEMORY_BUDGET_MAX_SHARE = 0.4` 夹持（记忆区最多占 prompt 总预算 40%，另 40% 留给历史），并在装配报告里新增 `memory_budget` 项（`resolved=` / `prompt_budget=`）可观测。**正常窗口下逐字不触发**（本项目 `deepseek-flash` 查到窗口 1,048,576，夹持永远不会生效）。

### 4. 切分软边界 —— 诚实的结论：影响 ≈ 0

用户担心「句子中间被截断」。审计了 137 处相邻块边界，**非句边界 14 处（10.2%）**，但逐条看过：绝大多数是 `*斜体动作*` 或对话引号结尾（`*` / `”` 不在我的终止符集合里，属误判），**真正切在词中间的只有 1~3 处**，典型是：

```
块1572 尾「…贴着他的皮肤，一下一下地蹭着。\n舔穴」⇄ 块1573 头「客厅里静得能听见彼此的呼吸…」
```

修法是给 `_find_cut_index` 加第三级弱边界（逗号/顿号/引号/空格）。**但实测（p50）这个修法在默认策略下几乎不会触发**：

> 46 条 assistant 长回复、切出 238 块，`_find_cut_index` 全程**只被调用 2 次**，硬切 0 次。

原因：默认策略是 `structural`（2026-10-07 起），切点来自**空行分段 / 对话引号起句**这些结构边界，根本不走 `_find_cut_index`；它只在「结构单元仍然超长」时兜底。

**结论**：第 4 项是**纯保险**，对现存那 1~3 处没有帮助（它们不是这个函数切的）。保留它因为零风险，但**不宣称它解决了截断问题**。真正缓解截断的是第 3 项（把相邻的另一半补回来）。

### 3.2 从这组数里能读出的结论（以及不能读出的）

1. **邻居扩展（第 3 项）是正向的，但要诚实标注证据强度。**
   B 相对 A **+0.075**，`z=1.59`、`p=0.112` —— **未达 0.05 显著**，且比早先实测的跑间噪声
   **±0.09** 略小。**不能宣称"已证明有效"。** 但三条旁证同向：①1.0 的题从 19 → 23，
   0.0 从 18 → 14；②空答从 3 → **0**（补回被切开的上下文后，模型不再因信息缺失而弃答）；
   ③早先无 LLM 的实测里邻居扩展注入命中不变（74%），说明它修的是"补全残缺块"而非提召回，
   与"大幅提分"预期一致地**不剧烈**。**代价明确**：记忆区 1372 → 1902 tok（**+39%**）。

2. **权重从 0.7 提到 1.0 在统计上与 0.7 无差别。**
   C 与 B 均分完全相同（0.585），C 的 z 还更低。**没有证据支持把 `HYBRID_WEIGHT` 提到 1.0**，
   维持 `0.7` 即可（也符合早先双题集实测：纯关键词路在近义改写题上只到 31%）。

3. **A 档 0.509 不能直接和早先 p41/p45 的 0.37~0.42 比。** 那批是另写的算法、题集也不同；
   本表三档**只在本跑次内部可比**。

### 3.3 处置建议（依据以上，而非直觉）

- **`MEMORY_NEIGHBOR_EXTRA_RATIO`：保留 0.3，不降到 0.15。**
  早先"降到 0.15"的建议基于"它没收益、只占预算"的假设；本跑次否证了该假设——
  它带来 +0.075 且消除了空答。**改回 0.3 维持现状**（当前代码默认即 0.3，无需改动）。
  若要进一步验证，应**加题量**（53 → 150+）把它推到显著，而不是靠调小比例。
- **`HYBRID_WEIGHT`：维持 0.7**（0.7 与 1.0 无差，无理由冒险）。
- 四项修复**全部保留**，均可经环境变量单独回退（见第四节）。

> **遗留**：本跑次题目全部来自单一会话 `f25daab6`（29 条源消息），存在角色/语料特异性；
> 要下"已证明有效"的结论需换 2~3 个不同会话复跑。**这是本报告最大的一条限制。**


## 四、怎么回退

每一项都能单独关，互不影响：

| 想回退 | 环境变量 | 效果 |
|---|---|---|
| 查询构造 | `MEMORY_QUERY_MODE=window` | 恢复 2026-10-07 的「最近 4 条拼接 + 尾截 600」 |
| 关键词路 | `MEMORY_HYBRID_WEIGHT=0` | 检索完全走旧的 `_score_candidates`，逐条等价 |
| 邻居扩展 | `MEMORY_NEIGHBOR_EXTRA_RATIO=0` | 回到「共用预算 ⇒ 恒 +0 条」的旧行为 |
| 全部 | 上面三个一起设 | 等同 2026-10-09 之前 |
| 记忆预算夹持 | `_MEMORY_BUDGET_MAX_SHARE`（代码常量，设 ≥1 即失效） | 不再夹持档位预算 |

其它旋钮：`MEMORY_QUERY_MIN_CHARS`（回退阈值，默认 15）、`MEMORY_QUERY_FALLBACK_CHARS`（回退取多少字，默认 120）、`MEMORY_HYBRID_KW_CANDIDATES`（粗筛条数，默认 50）、`MEMORY_HYBRID_KW_MIN_COV`（覆盖率下限，默认 0.12）、`MEMORY_HYBRID_RRF_K`（RRF 平滑常数，默认 60）、`MEMORY_NEIGHBOR_MAX_ADDS`（邻居封顶，默认 4）。

**降级路径**（不是开关，是自动）：无 pg_trgm 扩展（如 SQLite）⇒ 关键词路返回空 + 告警，检索退化为纯向量；作用域内 > 20000 行 ⇒ 跳过粗筛（避免全表算 trigram）；关键词路抛异常 ⇒ 只警告不回滚，向量路照常返回。
