**"语义检索"其实从来没在做语义检索，它做的是"最近 200 条里挑像的"；而查询喂进去的

| 改了什么 | 实测收益 | 代价 |
|---|---|---|

## 2. 缺陷一：所谓语义检索 = 最近 200 条里挑像的 [实测]

### 2.1 旧实现与它的天花板

`storage.semantic_search` 三个分支都是同一条 SQL 形状：
`WHERE … AND embedding IS NOT NULL ORDER BY created_at DESC LIMIT 200`，
然后把 200 行的 **JSON 文本**（实测每行 **22747 字节**）搬进 Python 逐行 `json.loads` 再算余弦。

探针 `probe4.py`（只读，用户级作用域，真实 bge-m3 查询向量）：

```
全库带向量行数=670 维度=1024
[Q1] 用户级候选总数=614 行，SQL 窗口=200
     相似度>=0.5 的行：全量 151 条 / 窗口内 79 条 → 被窗口吞掉 72 条本该召回的
     top50 里有 22 条是窗口取不到的（44%）
     全量 numpy 扫 614 行: （实测 2 ms）
```

⇒ **不是"效果略差"，是 48% 该召回的记忆对检索不可见。**

会话侧天花板更近：主力会话 `f25daab6` 当时已 **192 行带向量**，窗口只剩 **8 行余量**；
而 10-07 把 `CHUNK_DISTANCE_EPSILON` 从 0.12 降到 0.05，那份报告自己写了行数 **+79% 增速** ——
那笔账当时没算到 200 窗口头上。**[实测]** `probe2.py: [K] 该会话现有 192 行 / 距天花板 8 行`

### 2.2 贵在哪里：不是"算"，是"搬"

`probe2.py`（同一批真实向量，容器内）：

```
[A] 查询嵌入(1 句) = 166.3 ms
[B] SQL 取 192 行 = 29.9 ms，payload=4.17 MB
[C] Python json.loads+余弦 192 行 = 42.0 ms
[G] pgvector 建表+灌 192 行 = 78.2 ms
[H] pgvector brute-force top50 = 2.6 ms，top1=0.6974
[I] HNSW 建索引（192 行）= 28.7 ms     [J] HNSW 查询 = 1.9 ms
[L] 12288 行 brute-force = 1.1 ms
```

⇒ 每轮读侧 ≈ 240ms，其中 **72ms 纯粹花在"把文本搬出来再解析"**；库内精确算只要 2~3ms。
"扫全部"这件事在本项目量级上根本不贵。

### 2.3 库里 pgvector 一直就装好了，只有记忆表没用上 **[代码面→实测]**

- `docker exec palink-ai-db-1 psql -c "\dx"` → `vector 0.8.2` 在册（db 镜像本就是 `pgvector/pgvector:pg15`）
- `world_book_entry_vectors.embedding` 已是 `vector` 类型并用 `<=>` 检索；
  `conversation_memories.embedding` 是 `text`
- 历史成因：`alembic/versions/add_memory_tables.py:32` 当年建的是 `ARRAY(FLOAT)`，
  `init_memory_tables.py:38` 又建过 `vector(384)`，最终生产落在 TEXT。
  ⚠️ `memory_module/models.py:32` 那句 `embedding = Column(ARRAY(FLOAT))` 是**死代码**
  （`ConversationMemoryORM` 全仓零引用，且不是 declarative Base 子类），别信它的注释。

### 2.4 ⭐ 为什么故意不建向量索引（容易被人"顺手补上"）

pgvector 的 HNSW/IVFFlat 扫描是**先按向量取近邻、再套 WHERE**。本项目每条检索都带
`user_id` + `session_id`（甚至分叉点截断）这种高选择性过滤 —— 索引扫出来的近邻大量被
过滤掉，于是**少返甚至返 0 条**，而它会伪装成"这用户没历史"。这正是本项目最怕的
"后端算出来了、下游拿不到"那一类静默失效（同族先例：§1 的元组解包、`[P1-2]` 变量清理）。

千行量级暴力算是精确的 2~3ms（`[H]/[L]`），比走索引还快且不漏。
**真要涨到需要索引，得连带把过滤条件下推（partial index / iterative scan）一起设计，
不是无脑 `CREATE INDEX`。** 这条判断写进 `storage._semantic_search_pgvector` 的 docstring 了。

### 2.5 落地方式：运行时通道，不是 alembic **[实测]**

生产 `docker-compose.yml:169` 是 `RUN_MIGRATIONS_ON_STARTUP=false` ⇒ **启动时 alembic 不执行**。
所以列转换的主通道是 `MemoryStorage._migrate_embedding_column()`（与 0067 靠
`_RUNTIME_COMPAT_COLUMNS` 落库同理）；`alembic/versions/0069_memory_embedding_vector.py`
只负责把变更记进 schema 历史。

**检索走哪条路由"列的真实类型"决定，不看方言猜**：`_detect_vector_column()` 读
`pg_attribute` 的 `format_type`。列还是 TEXT / SQLite ⇒ 自动退回 Python 余弦（上限从 200
提到 5000，**触顶打告警**，不再静默少召回）。
⚠️ 我第一版用 `atttypid::regtype::text` 判，它输出 `vector` 不带维度 ⇒ 探测恒 False，
已经默默把每次启动都变成一次重复 ALTER。改成 `format_type(atttypid, atttypmod)` 后
`probe5 [6] 二次初始化 8.8ms，探测=True` 才证明幂等。

存量清理判据：转换前把"元素个数 ≠ dim"的行先置 NULL（逗号计数），
一条降级期的 512 维向量不该阻塞全库 ALTER。本库实测 670 行**全部 1024 维 ⇒ 零行被清**。

## 3. 缺陷二：查询太薄 [实测]

`roleplay_prompt_assembly.py` 每轮喂给检索的 query 是 `req.message` —— 本轮用户一句话。
`character_chat_messages` 实测：用户消息**平均 29 字**，101 条里 12 条不足 10 字。

`probe4.py` 同一轮两种查询对照（真实语料）：

```
仅本轮用户消息（33 字）: 首条相似度=1.0000，top8 区间 1.0000~0.6208
最近 4 条拼接（444 字）: 首条相似度=0.8869，top8 区间 0.8869~0.7668
两种查询的 top8 重合=2/8
```

`1.0000` = 命中本轮消息自己的记忆镜像，纯烧预算（`exclude_message_ids` 只排最近 5 条消息，
镜像本身在装配前已入库）。⇒ 新增 `_build_memory_query()`：取最近 4 条消息拼接、≤600 字、
**从尾部截断保最新**、分支口径与召回作用域一致、查不到就原样退回本轮单句（宁用单句不清空查询）。

先例不是现造的：世界书向量那边早就用"最近 4 条消息拼接"当查询
（`SPEC_世界书向量召回接通与防护_2026-09-29.md` §27）。

成本：**零额外嵌入调用** —— 嵌 444 字与嵌 33 字都是一次调用。

## 4. 缺陷三：最贵的 4 秒买的是更差的召回 [实测]

### 4.1 现网写入侧在干什么

`store_memory(assistant)` → `semantic_split` 先把**每个句子**嵌一次（30~44 句，1 批）找断点，
断点定了之后**句子向量扔掉**，再把 6~9 个块**重新嵌一次**（第 2 批）。
`probe3.py` 实测：**4.3~4.7 s/轮**（另一份今日报告在负载下量到 13 s，同一件事）。

### 4.2 四种切法对照（跨 3 会话、18 条真实长回复；`probe9_expanded.py`）

两种查询口径，ground truth 必须**唯一落在一个块里**才计入（否则丢弃，避免自欺）：

| 方案 | 每轮耗时 | Q1 片段针 top1 (n=27) | **Q2 真实回指 top1 (n=21)** | Q2 top3 |
|---|---|---|---|---|
| A1 现网（句嵌入断点 + 块再嵌，2 批） | **3822 ms** | 78% | **33%** | 57% |
| B 结构边界切 ~250（零句嵌入 + 块嵌，1 批） | **1631 ms** | 74% | **43%** ← 最好 | **81%** |
| C 同 A1 断点，块向量=句向量加权均值（P1-1，1 批） | 2125 ms | **96%** | 29% | 62% |
| D 折 ~150 字微块只嵌微块，大块由微块向量合成 | 1680 ms | 85% | 38% | 71% |

**关键读法：Q1 与 Q2 的排序是反的。** Q1 的查询是"块内某句的前 25 字"，
而 C/D 存的向量正是那些句向量的均值 —— 查询本身就是被平均进去那一句的片段，
这个口径天然偏袒均值合成。C 从 Q1 第一名掉到 Q2 最后一名（96%→29%）就是证据。
Q2 用的是**真实用户消息原文**去回指前文，贴近生产形态，以它为准。

⇒ **本件默认改为 B**（`CHUNK_STRATEGY=structural`），语义断点法保留作 `=semantic` 一键回退。
⇒ ⚠️ 这条直接**否证了** `REPORT_后端生成期CPU内存占用排查_2026-10-07.md` 的 **P1-1**
（"用句向量合成块向量"，那份报告给了 ★★★★）。它省 2s 是真的，但真实回指 top1 只有 29%，
比现网还差 4 个点 —— 不该做。**那份文档的描述现在是被本件推翻的一方**，按"只进不出"原则
不删它，本件即为它的订正依据。

### 4.3 为什么切细的收益本来就不来自"语义断点" **[实测，与昨日报告一致]**

昨天 §8.5 自己量过：块内内聚度 0.5467→0.5534（**+1.2%**，几乎没变），
而话题分离度 margin 0.0376→0.0638（**+69.9%**）。
⇒ 收益来自"块变小"，不是"切点算得准"。连续剧情本来就语义渐变，切在哪都差不多内聚。
所以用零成本的结构边界同样能拿到"块变小"这份收益 —— 本件实测证实（B 在 Q2 上反超 A1）。

### 4.4 改完的真路径耗时 **[实测，probe10]**

走生产 `MemoryService.store_memory` → `store_chunks` 真写库（独立 session_id 标记，测完即删）：

```
[cfg] strategy=structural target=250 trigger=250 provider=ollama
  源消息2786 正文1322字 → 本轮写入耗时 1925 ms（该标记下累计 5 行）
  源消息2784 正文1641字 → 本轮写入耗时 2076 ms（该标记下累计 11 行）
  源消息2782 正文1535字 → 本轮写入耗时 1956 ms（该标记下累计 17 行）
[写侧] 探针行 17 条，其中带向量 17 条
[清理] 删除 17 行，残留=0；业务带向量行数 687 → 670
```

⇒ **≈1990ms/条 vs 原 ≈4300ms/条，省 54%**；17/17 条真向量写进了 `vector(1024)` 列
（顺带证明写侧 CAST 走生产路径成立）。业务数据一行没动。
