# SPEC — 消息编辑 × 向量记忆同步（message_id 关联体系）

> 日期：2026-08-24
> 分工建议：施工归修复 agent，审计线验收（沿用 R1 惯例）。
> 动机：用户后期要开放「自行修改某段对话文字」（ST 式消息编辑）。现状下编辑消息后，
> 旧版本文字仍留在向量记忆库中持续被检索召回，与新内容一起注入 prompt——正是
> 「模型左右脑互搏」的素材源之一。本 spec 给出根治方案。

## 0. ST 1.18.0 对照研究结论（设计依据）

ST vectors 扩展（`public/scripts/extensions/vectors/index.js`）的核心是
`synchronizeChat`（L440-544）的**收敛式 diff**：

```javascript
// 每条消息 → { text, hash: getStringHash(消息全文) }
const hashesInCollection = await getSavedHashes(chatId);
const newVectorItems = hashedMessages.filter(x => !hashesInCollection.includes(x.hash));
const deletedHashes  = hashesInCollection.filter(x => !hashedMessages.some(y => y.hash === x));
await insertVectorItems(chatId, chunkedBatch);   // 新 hash 增量插入
await deleteVectorItems(chatId, deletedHashes);  // 消失的 hash 自动删除
```

事件驱动（L2086-2093）：`MESSAGE_DELETED / MESSAGE_EDITED / MESSAGE_SENT /
MESSAGE_RECEIVED / MESSAGE_SWIPED` → 防抖触发同步；`CHAT_DELETED` → 整库 purge。

**为什么 ST 用内容 hash 而我们不用**：ST 的向量库是「聊天文件的完整镜像」，消息在
jsonl 里没有稳定主键，只能拿内容 hash 当身份；且它可全量重算。我们的记忆是
「生成时的副产品」，但有真实 DB 主键——**`message_id` 外键关联严格优于内容 hash**
（精确、无碰撞、天然覆盖语义切分多块）。照抄 hash 反而是退化。

## 1. 现状问题清单（全部实证）

| # | 问题 | 位置 |
|---|------|------|
| P1 | 记忆与消息零关联：`conversation_memories` 无 message_id（session_id/branch_id 均为裸 TEXT），编辑消息后旧文本记忆永久残留并被检索召回 | storage.py:113-128 |
| P2 | turn_hash 混入时间戳（`blake2b(chunks[0][:64] + utcnow)`）非确定性，不能当 diff/定位键 | storage.py:317-320 |
| P3 | continue 续写在原 assistant_message_id 上追加正文，但记忆按「追加增量」再存一份 → 与旧全文记忆重叠双份 | websocket.py:567(复用id) + 1115-1139(再次store) |
| P4 | swipe 重roll 后记忆仍是旧 swipe 内容（记忆≠当前激活显示内容）；单条消息删除留下孤儿记忆（delete_character_message 无记忆级联——孤儿修复四路径外的第五处遗漏） | character_ext.py:2877-2913 |

## 2. 设计原则

**核心不变式**：对任意消息 M，
`conversation_memories 中 message_id = M.id 的行集合 ≈ clean_memory_content(M 当前显示内容) 的语义嵌入`
——即**记忆永远是消息当前内容的镜像**。任何使消息内容变化的操作（编辑/续写/swipe 写入/
重试）都通过统一的「upsert by message_id」收敛到该不变式。

辅助原则：
- **ID 优先于哈希**：有真实主键不用内容 hash；turn_hash 保持现状不动（仅作相邻块定位，P2 不修——改它会破坏既有 #chunk 定位协议，收益为零）
- **宁缺勿错**：重嵌失败时接受记忆暂时缺失，绝不保留过时版本（错误记忆比没有记忆危害大——它会以旧剧情污染 prompt）
- **尽力而为**：user 记忆的 message_id 在部分路径不可得时允许 NULL（NULL 行不受 upsert/编辑钩子影响，行为等同现状）

## 3. 改动详述

### 3.1 Schema：conversation_memories 加一列

```sql
ALTER TABLE conversation_memories ADD COLUMN IF NOT EXISTS message_id INTEGER;
CREATE INDEX IF NOT EXISTS idx_memory_message_id ON conversation_memories(message_id);
```

落点：`memory_module/storage.py` `_ensure_tables()`（该函数已有 ALTER TABLE 迁移
先例 L184-195 branch_id，照抄模式；Postgres 用 ADD COLUMN IF NOT EXISTS 幂等）。
ORM 侧无 ConversationMemory 模型（全 raw SQL），无需改 models。

**存量数据边界（诚实声明）**：存量记忆行 message_id 为 NULL，无法可靠反查归属
消息（content 经清洗/截断/切分），**不做回填**。NULL 行不受编辑钩子影响（编辑时
只删 `message_id = X` 的行），它们随所属会话删除时被既有的 [ORPHAN-MEM-FIX]
级联清掉。功能上存量行的残留维持现状（本期不做历史清洗）。

### 3.2 存储层透传

- `storage.store(...)` 增加 `message_id: Optional[int] = None`，INSERT 列表加该列
- `storage.store_chunks(...)` 同样增加并透传到块 INSERT（同 turn 多块共享同一
  message_id —— 编辑时一删全删）
- `service.store_memory(...)` 增加同名参数向下透传（`**metadata` 已有，但显式
  参数更符合本文件风格；两条路径 chunk/单条都要带上）

### 3.3 写入侧：四处调用点 + 统一 upsert

统一模式（所有写入点在 store_memory 前执行）：

```python
# [MEM-UPSERT] 记忆 = 消息当前内容的镜像：同 message_id 先删后写（幂等）。
# 覆盖：continue 追加重叠(P3)、swipe 重roll 旧内容残留(P4)、重试路径重复写。
if message_id is not None:
    db.execute(
        text("DELETE FROM conversation_memories WHERE session_id = :s AND message_id = :m"),
        {"s": session_id, "m": message_id},
    )
```

| 调用点 | assistant 记忆 message_id | user 记忆 message_id |
|--------|--------------------------|---------------------|
| `websocket.run_character_chat_generation` finally（L1115-1139） | `assistant_message_id` ✓ 已可用 | **需新增**：ws_character_chat 用户消息落库处（L1833-1846 `db.add` + `db.commit()`）改为 `db.flush()` 后读取 `msg.id`，作为新参数 `user_message_id` 传入生成函数 |
| `websocket.run_chat_generation` finally（L458-467，普通聊天） | `assistant_message_id` ✓（L179/221） | 同上：ws_chat L1252-1258 落库处取回 id 传参 |
| `character_ext.py` SSE 主对话流 finally（L4839-4863） | `assistant_message_id` ✓ | normal 场景用户消息落库处取 id；regenerate/swipe 场景无本轮 user 消息 → None |
| `character_ext.py` SSE 动作流（continue/regenerate/swipe，persist_fn 之后） | `assistant_message_id`（persist_fn 返回值或 target_msg_id）✓ | None（动作流不改写 user 轮） |

注意点：
- DELETE 使用该路径自己的 db 连接（save_db / Depends(db)），与 store_memory 共享
  事务，随后续 commit 一起提交
- smart_card_trigger 场景不写 user 记忆的现状保持
- `store_user_memory=(idx == 0)` 多发言者逻辑保持

### 3.4 编辑钩子（核心新功能）

`character_ext.edit_character_message`（PUT `/{session_id}/messages/{message_id}`，
L3200）在现有 `_sync_message_content_to_active_swipe` 完成后、`db.commit()` 前插入：

```python
# [MEM-SYNC-ON-EDIT] 编辑即同步：记忆 = 消息当前内容的镜像。
new_content = (msg.content or "")
old_content = (old_content_before or "")          # 进入函数时缓存
if not getattr(msg, "is_locked", False) and new_content.strip() != old_content.strip():
    from sqlalchemy import text as _sa_text
    db.execute(
        _sa_text("DELETE FROM conversation_memories WHERE session_id = :s AND message_id = :m"),
        {"s": session_id, "m": message_id},
    )
    _edited_for_reembed = (msg.role, new_content)   # 交给后台重嵌
else:
    _edited_for_reembed = None
```

`db.commit()` 之后启动后台重嵌（**先嵌成功才写库，失败宁缺勿错**；放
`asyncio.to_thread` 不阻塞响应）：

```python
if _edited_for_reembed is not None:
    role, edited_text = _edited_for_reembed
    def _reembed():
        re_db = SessionLocal()
        try:
            svc = MemoryService(re_db)
            if not svc.is_available():
                return
            text_for_mem = clean_memory_content(edited_text) if role == "assistant" else edited_text
            if text_for_mem.strip():
                svc.store_memory(
                    user_id=user.id, session_id=session_id, role=role,
                    content=text_for_mem, branch_id=msg.branch_id,
                    message_id=message_id,
                )
                re_db.commit()
        except Exception:
            re_db.rollback()
            logger.warning("re-embed after edit failed (message=%s)", message_id)
        finally:
            re_db.close()
    asyncio.create_task(asyncio.to_thread(_reembed))
```

要点：
- **role 取编辑后的 msg.role**（role 字段本身也可被编辑）
- **branch_id 取消息当前 branch_id**——回答用户的担心：编辑不触碰 branch 归属，
  重嵌写回携带原 branch_id，分支过滤天然不受影响
- assistant 文本必须经 `clean_memory_content`（与生成写入管线一致，防止
  `<UpdateVariable>`/思维链块混入记忆——MEMORY-POLLUTION-FIX 同源）
- 编辑为空正文时不重嵌（无内容可记），只删旧
- 该端点已被 is_locked 拦截锁定消息，无需重复处理

**普通聊天对齐**：`sessions.py update_message`（PUT `/api/sessions/{sid}/messages/
{mid}`，L263-279）加同样的钩子（该端点无 branch 概念，branch_id=None；user/assistant
均可能被编辑）。

**swipe 切换的免费覆盖**：前端 swipe 切换若最终经 `handleEditMessage → PUT
messages/{mid}` 提交（CharacterChat.tsx L1499），则 content 变化自动命中编辑钩子，
记忆随之更新——无需额外代码。施工时验证 swipe 切换的实际请求路径；若发现存在
不经 PUT 的切换路径，登记二期。

### 3.5 单条消息删除补级联（P4 收尾）

## 4. 场景行为矩阵（改后）

| 场景 | 记忆行为 |
|------|---------|
| 正常生成 | user+assistant 各写入，带各自 message_id |
| continue 续写 | 同 message_id 先删后写 → 记忆=合并后全文（修复 P3 重叠） |
| swipe 重roll（persist_fn 更新模式） | 同 message_id 先删后写 → 记忆=新激活内容（修复 P4） |
| EMPTY-RESP-RETRY 重试 | 幂等（先删后写） |
| 编辑 assistant/user 消息 | 删该消息全部记忆 → 后台按新文本重嵌（分支归属不变） |
| 编辑但内容未变 | 零操作 |
| 删除单条消息 | 该消息记忆级联删除 |
| 删除分支/会话/角色 | 既有 [ORPHAN-MEM-FIX] 级联不动 |
| 编辑存量无 message_id 的记忆对应消息 | 只能删掉 message_id=NULL 无法命中 → 维持现状（§3.1 边界） |

## 5. 明确不做（Non-goals）

1. **不给存量记忆做 message_id 回填**——无法可靠反查，声明边界即可
2. **不引入 content_hash 列**——有真实主键，hash 是 ST 无主键环境的妥协
3. **不改 turn_hash 生成算法**（P2 不修）——它服务于 #chunk 相邻块定位协议，改动破坏既有数据
4. **不动 get_context 检索逻辑**——message_id 是管理键，不参与召回
5. **st-vec:: 前缀的 ST vectors collection** 不在本 spec 范围（封存链路）
6. **is_hidden 隐藏消息是否参与记忆**——超范围，维持现状
