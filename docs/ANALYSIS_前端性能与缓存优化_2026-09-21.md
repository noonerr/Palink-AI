合计预期：首屏 JS 传输 541KB → ~270KB（约 -50%），二次加载静态资源请求数从 ~90 降到 ~3。

## 2. 缓存策略实测（容器内 curl -I）

| 路径 | 实测 `Cache-Control` | 判断 |
| --- | --- | --- |
| `/`（index.html 与 SPA 回退） | `no-cache, no-store, must-revalidate` | ✅ 正确 |
| `/assets/index-C1GD9FUD.js` | `no-cache, must-revalidate`（有弱 ETag） | ❌ 内容 hash 资源应 immutable |
| `/katex.min.css` | `no-cache, no-store, must-revalidate` | ❌ |
| `/fonts/KaTeX_Main-Regular.woff2` | `no-cache, no-store, must-revalidate` | ❌ 66 个字体文件每次全量重下 |
| `/st/css/*`、`/st/webfonts/*` | 同上（落到 `location /`） | ❌ |
| `/icons/*` | `max-age=2592000` + `public, immutable`（**两条重复头**） | ✅ 但需合并为一条 |
| `/uploads/*`、`/api/st/characters/{key}` | 无缓存头，`proxy_cache off`，`proxy_buffering off` | ❌ |

附带发现：
- 响应未见 `Vary: Accept-Encoding`（gzip 开启时建议补）。
- `/icons/` 同时输出两条 `Cache-Control`（`expires` 指令 + `add_header`），建议只保留一条 `add_header`、去掉 `expires`。
- nginx 的 `location = /sw.js` 指向一个**不存在**的文件（`dist/sw.js` 未生成），恒 404。

## 3. 优化方案

### O1【P0 · 缓存命中率】带内容 hash 的 JS/CSS 改 immutable 长缓存

- **现状**：`nginx.conf:52-58` 对 `-<hash>.(js|css)` 发 `no-cache, must-revalidate`，每次加载 88 个 assets 各走一次 304 往返。
- **做法**：该 location 的 `add_header` 改为 `public, max-age=31536000, immutable`，删掉 `Pragma` / `Expires`。`index.html`、`/sw.js`、`/manifest.json` 保持 `no-store` 不变。
- **预期效果**：二次加载时除 index.html 外静态资源 **0 请求**（原本每个文件一个 RTT，弱网 20–200ms/个）；服务端 304 QPS 归零；重复访问可交互时间可省数百 ms～1s+。
- **实施范围**：`frontend/nginx.conf` 1 处 4 行。bind mount → 只需 `docker restart palink-ai-frontend-1`，无需 rebuild。
- **风险**：见 §4-A。

### O2【P0 · 首屏体积】把非首屏库拆成动态 chunk

| 分组 | 内容 | 未压缩 | 压缩后估算 | 改动面 | 风险 |
| --- | --- | --- | --- | --- | --- |
| **A** | 插件沙箱 ST 兼容库：jquery + select2 + toastr + handlebars(+source-map) + marked | 787KB | ~330KB | `lib/plugin-system/sandbox.ts` 改为「加载插件时才 dynamic import」 | 中 |
| **D** | react-markdown / remark / rehype（micromark+mdast 家族） | 437KB | ~183KB | `CharacterCardRenderer.tsx` 仅在检测到智能卡 HTML 时动态加载渲染器 | 中 |
| **B** | KaTeX | 583KB | ~240KB | `lib/sillytavern/formatting.ts` 检测到公式再动态 import（已有 `ensureKatexCss` 同款先例） | 中高（同步 API 改异步） |
| **C** | chevrotain 宏引擎 | 294KB | ~125KB | `lib/macro-engine` 入口动态化 | 中高（插件可能依赖同步求值） |

- **预期效果**：entry 1813KB/541KB(gzip) → **约 800–900KB / ~270KB(gzip)**，首屏 JS 传输 **-45%~-50%**；解析与执行耗时同步下降（移动端收益更明显）。
- **建议顺序**：A → D → B → C，逐组回归。只做 A+D 也能拿到约 55% 的可拆收益。
- **配套**：拆完后加**函数式** `manualChunks`（只匹配目标包自身的 node_modules 路径，切勿把 dompurify/clsx/react/katex 拉进命名 chunk——2026-09-15 已踩过一次坑，见 `vite.config.ts:54-68` 注释），让 vendor chunk 独立于业务代码哈希，业务小改动时 vendor 仍命中缓存。
- **风险**：见 §4-B。

### O3【P0 · 零代码风险】路由预取瘦身

- **现状**：`App.tsx:551-574`，登录就绪后 `requestIdleCallback(timeout:3000)` 一次性预取全部 5 个路由（ChatViewDesktop 12KB + ChatViewMobile 25KB + CharacterView 409KB + SettingsView 469KB + WorkspaceView 28KB = 943KB，加上共享依赖实际 ≈1.2MB raw / ≈330KB gzip），与首屏 API 抢带宽。
- **做法**：只预取「当前很可能去的 1–2 个」（桌面端 → ChatViewDesktop；移动端 → ChatViewMobile + CharacterView）。SettingsView / WorkspaceView 改为导航意图触发（点击/hover 前置）或更长的 idle + `navigator.connection.saveData` / 慢网（`effectiveType` 为 2g/3g）时直接跳过。
- **预期效果**：登录后前 3 秒下行流量 ~1.2MB → ~0.3MB；首屏内容与真实 API 不再被 chunk 下载抢占。功能与视觉完全不变。
- **实施范围**：`App.tsx` 1 处。风险低。

### O4【P1】非哈希静态资源加长缓存

- **现状**：`/fonts/*`（KaTeX，66 个 woff2，单文件 ~26KB）、`/st/css/*`、`/st/webfonts/*`、`/bootstrap.js`、`/katex.min.css` 全部落到 `location /` → `no-store`。
- **做法**：新增 3 个前缀 location（`^~ /fonts/`、`^~ /st/`、`= /katex.min.css`、`= /bootstrap.js`），发 `public, max-age=2592000`。
- **预期效果**：渲染数学公式时常用 5–10 个字体文件，每次加载可省 100–260KB 下行；Font Awesome 同理。
- **实施范围**：`nginx.conf` 新增约 20 行。风险低（这类文件只在发版时变，30d 足够）。
- **注意**：`^~` 必须写，否则会被 `location ~* -[a-zA-Z0-9_-]+\.(js|css)$` 抢走。

### O5【P1】图片与头像缓存

- **现状**：`/uploads/*` 与头像 `/api/st/characters/{key}` 都走通用 `location /api/`，`proxy_cache off` + `proxy_buffering off` + 无任何缓存头 → 列表每次挂载都重新下载全部头像/附件。
- **做法 A（推荐，低风险）**：为这两条路径各加专用 location，`proxy_buffering on` + 定义 `proxy_cache_path`（如 `levels=1:2 keys_zone=media_cache:10m max_size=1g`）+ `proxy_cache_valid 200 206 7d`。
- **做法 B（收益更大，需你拍板）**：普通 `<img>`/`<a>` 去掉 `?token=`，改用同源 Cookie 鉴权（浏览器对同源 img 自动带 Cookie），仅在 opaque-origin iframe / Worker 场景保留 token。这样图片才能被浏览器缓存。
- **预期效果**：角色列表、聊天里的头像与附件二次打开近乎 0 请求。
- **风险**：做法 B 涉及鉴权面，见 §4-C。

### O6【P1】gzip 预压缩（`gzip_static`）

- **现状**：gzip 实时压缩，每次请求都消耗容器 CPU；brotli 因 `nginx-mod-http-brotli` 与 `nginx:alpine 1.28.3-r7` 版本冲突而禁用（见 `Dockerfile:26-33`）。
- **做法**：构建期产出 `.gz`（`vite-plugin-compression` 或脚本），nginx 加 `gzip_static on;`（建议同时 `gzip_comp_level 6`）。
- **预期效果**：省掉每次请求的实时压缩开销；对 541KB 的 entry 尤其明显（容器 CPU 吃紧时首屏 TTFB 更稳）。
- **实施范围**：`vite.config.ts` + `nginx.conf` + 构建脚本。**前提**：需先确认 `nginx:alpine` 镜像带 `--with-http_gzip_static_module`。
- 风险低。

### O7【P2】Service Worker 离线缓存

- **现状**：`vite-plugin-pwa` 在 devDependencies 但未启用；`nginx.conf:40-44` 的 `/sw.js` 恒 404。
- **做法**：启用 workbox，只 precache 带 hash 的 assets，navigation fallback 到 index.html。
- **预期效果**：二次访问 index.html 之外**全部走 cache-first**；弱网/离线可开壳。这是缓存命中率的上限解。
- **风险中高**：与 iOS PWA 主题快照、`no-store` 的 index.html、插件 `unsafe-eval` 脚本三处耦合，需要专门的灰度与注销通道。见 §4-D。

### O8【P2】HTTP/2 与连接数

- `listen 8080 http2` 是明文 h2c，Chrome/Safari 均不支持明文 h2c → 实际按 HTTP/1.1 走，同域 6 连接上限。
- 若前面已有 HTTPS 终结（FRP / 外层 nginx）则无需处理；若没有，加 TLS 即可启用真 HTTP/2 多路复用。低优先级。

### O9【P2】CSS 拆分

首屏 CSS 205KB raw / 35KB gzip，渲染阻塞。可拆 critical CSS 或按组件级懒加载（`StorylineMap` 已有独立 15KB CSS 先例）。收益显著小于 JS 侧，建议 O1–O4 完成后再评估。

### O10【P2】轮询优化

`CharacterView.tsx:1104` 以 **2s** 间隔轮询 `/api/characters/{id}/status`（未带 `cacheTtlMs`，每次都发真请求）。可给轮询加 `cacheTtlMs: 1500` 做 in-flight 合并，或改走 SSE/WS。低优先级。

## 4. 需要你定夺的取舍

### A. hashed 资源改 immutable 长缓存 vs iOS Safari 旧 HTML 风险

`nginx.conf:46-51` 的注释记录了当初用 `no-cache` 的理由：担心 iOS Safari 内存缓存无视 index.html 的 `no-cache`，导致旧 HTML 引用旧 JS。

**我的判断：这个担心不会因 immutable 而恶化。** immutable 只作用于文件名带内容 hash 的资源——内容变了文件名必变，旧 HTML 引用的旧文件仍然是"正确的旧版本"，不会串味；新的 index.html 会引用新文件名。真正需要防的是 index.html 本身被缓存，而它保持 `no-store` 不变。

**唯一真实风险**：发版后旧 hash 文件被 `emptyOutDir: true` 清掉 → 仍停留在旧页面的用户拿到 404。

> 需要你选：`max-age=1y`（标准做法）+ 发版时保留上一版 dist 若干天；还是保守用 `max-age=7d`？

### B. 动态拆包的改动面 vs 收益

O2 四组中，**A（插件沙箱库）和 D（markdown 渲染器）改动面小、收益大**；**B（KaTeX）和 C（chevrotain）** 需要把同步调用改成异步，会碰到 `formatMessage` 的同步签名和宏求值——ST 插件可能依赖同步行为，回归成本较高。

> 需要你选：四组全做，还是先做 A+D 收手（约拿到 55% 的可拆收益）？

### C. 图片 token vs 可缓存性

现状所有 `/uploads/` 图片 URL 都带 5 分钟 `?token=`（`uploadUrls.ts`，200s 提前刷新），浏览器缓存键每次都变 → 图片永久不可缓存。

同源 `<img>` 浏览器会自动带 Cookie，理论上不需要 token；但 opaque-origin iframe / Worker / 下载场景拿不到 Cookie，token 是必要兜底。

> 需要你选：是否允许对普通 `<img>`/`<a>` 去掉 token 以换取图片可缓存？这属于鉴权面调整，我不擅自改。若否，就只做 O5-A 的服务端代理缓存。

### D. Service Worker 是否现在上

收益最大（二次访问近乎全缓存），但耦合面最广（iOS PWA 快照、`no-store` index.html、插件 `unsafe-eval`）。

> 需要你选：现在立 O7，还是等 O1–O6 稳定后单独立项？

### E. 预取策略的价值取向

"登录后 3 秒内把 5 个路由全拉下来"本质是**拿带宽换后续导航速度**。

> 需要你选：更在意"首次登录后立刻切页零等待"，还是"登录后前几秒带宽留给真正的内容"？移动端/弱网我倾向后者（即 O3）。

## 5. 建议实施顺序

| 顺序 | 项 | 风险 | 生效方式 |
| --- | --- | --- | --- |
| 1 | **O1** hashed 资源 immutable | 低（配置） | `docker restart palink-ai-frontend-1` |
| 2 | **O4** 非哈希静态资源长缓存 | 低（配置） | 同上 |
| 3 | **O3** 路由预取瘦身 | 低（1 个文件） | 重跑 build |
| 4 | **O5-A** 图片/头像代理缓存 | 低（配置） | `docker restart` |
| 5 | **O6** gzip_static | 低 | 重跑 build + restart |
| 6 | **O2-A / O2-D** 动态拆包 | 中 | 重跑 build + 回归插件与智能卡渲染 |
| 7 | **O2-B / O2-C** | 中高 | 建议单独立项 |
| 8 | **O7 / O8 / O9 / O10** | 视收益 | 视收益 |
