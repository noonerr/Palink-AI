## 2. 必须修正的问题（逐条给出证据与改法）

### B1（P0，施工阻塞）T3 的落点会打断 TTS 声线提取 —— 文档自己的红线被自己的方案违反

**文档怎么说**：T3「只影响显示，不动 `tts.ts` 从原始正文提取的路径（`playMessage` 收到的仍是原文）」，验收要求「点播放语音仍能正确提取声线（voice_description 生效）」。

**实测链路**：
1. `frontend/src/services/tts.ts:635-637`：`playMessage` 从**入参 text** 提取声线
   ```ts
   const extracted = this.extractVoiceDescription(text);   // 正则 /【(?:声音|语音)[：:]\s*([^】]+)】/
   ```
2. `frontend/src/components/ui/custom/Message.tsx:1112`：传进去的是 **displayContent**，不是 `message.content`
   ```ts
   const text = isUser ? (message.content || '') : (displayContent || message.content || '');
   void ttsService.playMessage(message.id, text, { role: 'character', characterId: ... });
   ```
3. `displayContent` 正是 T3 打算加隐藏正则的那条管线（`Message.tsx:849-900`）。

**后果**：按 SPEC 首选落点施工 ⇒ `extractVoiceDescription(displayContent)` 恒为 `null` ⇒ 声线描述丢失，正好复现 2026-09-25「[AUDIT-2026-09-25] 声线信息从未真正参与合成」的旧故障。**这不是回归风险，是确定发生。**

**改法（二选一）**：
- 首选：落点放 **formatter 侧**（`frontend/src/lib/sillytavern/formatting.ts` 的标签隐藏列表 / `sillyTavernDisplayPipeline` 的 hook），它在 `displayContent` **之后**生成渲染产物，`displayContent` 本身保持原样 → `playMessage` 仍拿到含【声音】的文本；
- 若坚持放 `Message.tsx`，必须在剥离**之前**把声线另存（例如 `voiceDescriptionRef`），并同步改 `handleSpeak` 传参 —— 改动面更大、更易漏。

另需注意 3 处 `displayContent` 回退路径（`Message.tsx:1080`、`1086`、`1582` 的 `pipelineResult?.… || displayContent`）：只改 formatter 时，pipelineResult 为空的分支仍会露出原始【声音】行，需一并核对。

### B2（P0，根因定性）R2 的证据引错消息；2382 裸显的真因是"没有渲染宿主"

**文档怎么说**：§2.6「2382 实际输出：`@bubble:露缇雅|不安|"嗯……好像是，肚子里面空空的……"`（中文引号）→ 渲染正则不匹配 → 裸显」。

**实测**（消息正文全量解码，`character_chat_messages.id=2382`）：

```
@bubble:露缇雅|慌张|[才、才不是那样……我是真的出事了！]
@bubble:露缇雅|忐忑|[*（他会觉得我很奇怪……会不会害怕我……）*]
@bubble:露缇雅|难过|[你看到了吧……我真的没有骗人。]
@bubble:露缇雅|不安|[还有这里……我醒过来的时候，它就在发光，摸上去温温的。]
@bubble:露缇雅|委屈|[哥哥，我会变成……怪物吗？]
@bubble:露缇雅|悲伤|[你不会……不要我的，对吧？]
```

**7 条全部是标准 `@bubble:角色名|情绪|[对白]` 方括号格式**，文档引用的那句话在 2382 里根本不存在。逐条复核同会话其他消息：

| 消息 | `@bubble` 格式 | 是否有 `<now_plot><content>` 包裹 |
| --- | --- | --- |
| 2382（过度思考那条） | 方括号 ✅ | **无**（正文直接以叙述开头，无 `</now_plot>`） |
| 2384 | 中文引号 “…” ✗ | **有**（`<now_plot><content>…</content></now_plot>` 完整闭合） |
| 2387 | 直引号 "…" ✗ | 无 |
| 2389 | 直引号 "…" ✗ | 无 |
| 2393 | 中文引号 “…” ✗ | 无 |

而渲染侧的真机制（实测脚本源码）：

1. `plugin_scripts`「对话渲染系统 v7.1」（237KB）的渲染宿主选择器：
   ```js
   _getBubbleRenderFrames() {
     return Array.from(this._getMainDocument().querySelectorAll('iframe'))
       .filter(f => f.srcdoc?.includes('id="dcRoot"') || f.contentDocument?.getElementById('dcRoot'));
   }
   ```
   —— 气泡**只渲染在 `dcRoot` iframe 里**（即正文美化卡产生的那个 iframe）。
2. 而产生该 iframe 的唯一入口是卡正则「正文美化」：`findRegex = /<(story|Lnterleaving|now_plot|content|正文)>([\s\S]*?)<\/\1>/gi`（**要求闭合标签**）。
3. 2382 既无 `<now_plot>` 也无 `<content>` ⇒ 正则不命中 ⇒ 没有卡 ⇒ 没有 `dcRoot` ⇒ **`@bubble` 无宿主可渲染，必然裸显**（与引号/方括号无关）。同一逻辑也解释 `<cg>` 裸显（卡内 `对ai隐藏cg标签` 是 `promptOnly=true`，只管提示词侧）。

**改法**：R2 重写为两条并列：
- R2-a（主因）**结构不合规**：模型未输出 `<now_plot><content>…</content></now_plot>`（或闭合缺失）→ 整块 tag 与 @bubble 一起裸显。修复应落在"输出结构约束/兜底包裹/渲染宿主的降级渲染"；
- R2-b（次因）**方括号→引号漂移**：2384/2387/2389/2393 确有此现象，可保留 T2 但降级为"渲染前的格式容错"（解析器同时接受 `[...]`、`"..."`、`“...”`），这比"要求模型永不漂移"更可靠。

### B3（P1）T2a 的前提不成立，且落点改不到注入文本

**前提**：文档要求"给 `@bubble` 格式规则加「内容必须方括号，禁止引号包裹」的显式约束"。

**实测**：`plugin_scripts` 表「对话渲染系统 v7.1」content 里的 `DEFAULT_FORMAT_RULE` **第 6 条原文就是**：

```
6. 台词必须用 [ ] 方括号包裹
```

**落点**：该脚本的注入文本来源实测为：

```js
// plugin_scripts「对话渲染系统 v7.1」content
async function buildInjectionPrompt(db) {
  const formatRule = await db.getConfig('format_rule', null);
  const ruleText = (formatRule && formatRule.trim()) ? formatRule.trim() : DEFAULT_FORMAT_RULE;
  ...
}
```

即：**优先读浏览器 IndexedDB 的 `config.format_rule`（用户可编辑）**，`DEFAULT_FORMAT_RULE` 只是兜底。而且整条注入是**客户端每请求组装**的：

- `frontend/src/services/prompt-injection.ts:90` `getPromptsForGeneration()`
- `frontend/src/hooks/useCharacterChat.ts:1211-1262` → `extension_prompts` 随请求发给后端
- 实库 `extension_prompts` 表 **0 行**、`user_settings.silly_tavern_settings` 中 `@bubble` 命中 **0** ⇒ 注入不落库

**结论**：改 `plugin_scripts.content`（SPEC 的首选落点）只在"用户从未自定义 format_rule"时生效，且卡一更新就丢（文档自己也注明了）。可执行的替代：
1. **服务端装配层纯增量强调**（HANDOFF 的第二选项）：对 allowlist/带 @bubble 注入的卡追加一条"结构必须 `<now_plot><content>` 包裹、台词必须 `[...]`"的短强调。风险：会与客户端 in_chat depth=0 注入叠加，需放在模型最易忽略的位置并做 token 影响评估；
2. **渲染侧容错**（推荐与 B2-b 合并）：解析器同时接受三种引号，并在缺包裹时把整条消息降级为"纯文本 + 气泡弱渲染"；
3. 若确实要改卡自带规则，只能改客户端侧来源（浏览器 IndexedDB / 卡内脚本），无法纳入服务端交付。

### B4（P1）§2.2「会话变量为空」不成立，与 §3.1 的因果链冲突

- SPEC §2.2：「会话 `chat_metadata.variables` 在 2382 生成时为空」。
- SPEC §3.1：占位值经 `<status_current_variable>{{format_message_variable::stat_data}}</status_current_variable>` 注入。
- 实测 `backend/app/services/macro_service.py:581-598`：该宏**只读会话 `chat_metadata.variables.stat_data`**，取不到就返回字符串 `"{}"`。
- 实测会话创建路径 `backend/app/api/character_ext.py:4378-4383`：`init_vars = MvuEngine.init_session_variables(...)`，**非空即写入 `chat_metadata`** —— 占位值非空，所以必然写入。
- 那模型引用的占位值从哪来？只能是会话变量本身（= 占位值）。

**影响**：若不纠正，施工者会去查"为什么变量没初始化"，而真相是"初始化发生了，只是初值错"。验收口径也要跟着改（见 B8）。另发现：**WS 主路径**（`websocket.py:1639`）与 ST 导入路径（`silly_tavern.py:1050`）创建会话时**不初始化变量**，只有 REST 路径（`character_ext.py:4350`）会 —— 建议在 SPEC 里明确验收要用哪条路径建会话，否则同一修复在不同入口表现不一致。

### B5（P1）"有配套渲染正则"的判定与真实渲染宿主不是一回事

实测（容器内实跑生产函数，user_id=1）：

```
_has_bubble_render_support(db, 1, char.extensions) = False
  ├─ 卡内 regex_scripts（6 条）命中 bubble/对话渲染/气泡：0
  ├─ _load_plugin_regex_script_dicts(db)：0 条
  │     ← 该函数只取 PluginScript.script_type == 'regex'（character_ext.py:1398-1403）
  │       而两条 BubbleDialogue 脚本 script_type 都是 'script'
  └─ extension_settings 正则：0 条
```

但注入**没有**被丢弃，因为：

```
char.plugin_scope_mode = 'allowlist'   → 装配层让位（roleplay_prompt_assembly.py:1728-1760 优先级 2）
character_plugin_state: (卡, 酒馆助手 eb1d50e9) enabled=t mode=manual
```

**含义**：本卡的 @bubble 注入是"用户显式勾选插件"的结果，与自动门控无关；而自动门控的"三源判定"结构上不可能命中 `script_type='script'` 的 BubbleDialogue 脚本，它判的其实是"是否存在配套**正则**脚本"，与真实渲染宿主（卡内 `dcRoot` iframe + 插件运行时）不是同一件事。SPEC §2.6 据此得出"插件链路本身是通的"属于**结论正确但推理链有缺环**。建议在 SPEC 里把这条写成已知分裂态，避免后续有人"顺手"改了门控把用户的 allowlist 意图打掉。

### B6（P2）T1 数据源应优先取列值，而非导入快照

实测写入口只有一处：`backend/app/services/character_import_service.py:293-294`（`extensions["palink_raw_card_data"] = raw_card_data`，仅当不存在时写）；`backend/` 与 `frontend/src/` 全库再无第二处赋值。而 Palink 卡编辑器保存 `first_mes` 只更新 `characters.first_mes` 列（`character_card.py:_overlay_field` 导出时以列值覆盖原卡值，正说明列才是权威）。⇒ **用户改过卡首条消息后，从 raw 快照取 initvar 会取到旧值**，且会与用户看到的首条开场不一致。

建议 T1 采用"**列值优先、raw 快照兜底**"：
- `build_initial_stat_data` 新增可选入参（或由调用点在 `char_ext_raw` 里预先 `setdefault("first_mes", char.first_mes)`）；
- 调用点都持有 `Character` 对象（`character_ext.py:4378/6194`、`character_message_builder.py:585` 均已 eager load），改动很小。

### B7（P2）嵌套 `character_book` 必须写成 fallback-only

文档 T1 item 2「`_extract_initvar_from_character_book` 同理补 `palink_raw_card_data.data.character_book` 层级」，配合"深合并顺序不变（后者覆盖前者）"，若实现成"额外再合并一遍"就会让**导入快照**盖掉 `world_books`（用户可编辑）来源。

实测定量：本卡 raw `data.character_book` 有 19 条，其中含 `<initvar>` 的 **0 条**（唯一 disabled 条目「格式要求」也无 initvar）⇒ 当前无实际症状，但语义上应写成"顶层 `character_book` 取不到/为空时才回退 raw 层级"，并补一条"两源都存在时以 `world_books` 为准"的回归用例。

### B8（P2）验收口径会让正确的修复被判失败

「新建会话 → 首条消息后 `chat_metadata.variables.stat_data` 等于 initvar」——但首轮 AI 回复本身会带 `<UpdateVariable>`（实测 2382 的回复就把时间推进到 小时=7/分钟=2，并改写位置），落库后 stat_data 已不是 initvar。

建议改为以下任一：
- 断言点前移到"会话创建完成、首轮生成开始之前"（例如建会话接口返回后立刻查库）；
- 或断言"stat_data 不含占位指纹"（`年 != 1`、`爱意 != 0`、`魔力值 != 100`、`当前位置 != 未知`、`穿着` 非空），这在多轮后依然稳定成立；
- 思考量验收（10605 → 回落）保留，但注明"与正文同量级"是目标、非硬门禁（SPEC §3.1 自己也说了推理模型固有行为）。
