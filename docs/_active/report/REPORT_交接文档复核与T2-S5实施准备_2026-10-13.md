### 2.1 为什么它是关的（这条决定了 T2 的三选一）

`Message.tsx:645-652` 有完整的事故记录：

> 卸载后重新入视口会重建 iframe（srcDoc 重挂载）= 一次真实导航，而 Safari 的会话历史是**联合**的（顶层 + 所有子框架），每次 iframe 导航都会往里面插一条**幽灵条目**（顶层 URL 不变，地址栏仍是当前页）。滑动返回 = 沿联合历史逐条 pop ⇒ 先快速闪过 N 个与当前页一模一样的快照，最后才回到真正的上一级。**iOS 没有 API 删除已存在的历史条目**，只能从源头避免创建。

⇒ **交接文档 P1 的选项 ①「出视野即卸载」不是新方案，是"把 `:653` 改成 true"** —— 而这么做会把一个**已经付过学费修掉的 iOS 回归**重新放出来。

### 2.2 为什么选项 ②「冻结保留」也已经被证伪

- `visibility: hidden`（当前实现）**不释放内存**：iframe 文档与 realm 全部存活。
  ⇒ S0 那组 560MB 的实测，**正是带着这个休眠门跑出来的**（48 个 iframe 中绝大多数远超一屏、处于 dormant 态）。这是「隐藏≠省内存」的直接实证。
- `content-visibility: hidden` **试过并已移除两次**（`:665-686`、`:726-732`）：它让浏览器跳过整棵子树渲染，正是「隐藏态加载完成 → 唤醒后正文整块空白」的载体。
- 另有一个已删除的 `repaintKick`：会与 IntersectionObserver 形成 `display:none → 高度归零 → 报离屏 → 休眠 → 高度恢复 → 报入屏 → 再 kick` 的自激闭环（真机表现：框内正文"有→无→有"持续闪）。
- 「停 rAF / 断 postMessage」= 改卡脚本语义，**直接撞红线**（P1 红线：不要为省内存改卡脚本语义）。

⇒ **② 能压滚动成本，压不了堆**。而 560MB 是堆问题。

### 2.3 ⇒ T2 的真实命题变了

不是"要不要卸载"，而是：

> **在已有一套「只隐藏不卸载」的休眠门之上，怎么给存活 iframe 数封顶。**

而且要把**两个问题拆开**——交接文档把它们合并在"生命周期策略"一个标题下，但它们的最优解不同：

| 问题 | 实测 | 谁能解 |
|---|---|---|
| 堆随消息数线性增长（48 iframe → 560MB，GC 后仍 ~300MB） | 边际 +9~11MB/个 | 只有 **① / ③**（必须真的移除 iframe） |
| 每千像素滚动主线程成本 1.51× | 28.1ms → 42.3ms | **② 可解**（省渲染工作） |

### 2.4 我的建议：③ LRU 封顶，叠在现有门之上

| | 评价 |
|---|---|
| **① 出视野即卸载** | ❌ 不推荐。重放 iOS 幽灵历史回归；且快速回滚时每个 iframe 重建 = 一次完整 boot（S0 实测 7 个 iframe 集体就绪 ~823ms）⇒ 肉眼可见空白/闪烁 |
| **② 冻结保留** | ❌ 不足以达成目标。当前实现即 ②-lite，560MB 就是它交的答卷；加强版（content-visibility）有两次移除记录 |
| **③ LRU 封顶** ⭐ | ✅ 推荐。堆从 O(消息数) 变 O(cap)，直接掐掉线性增长这一真实故障模式 |

③ 的具体形态：

1. **保留现有门不动**（它对普通会话是正确且已付过学费的）；
2. 新增一层 **存活配额**：注册表记录每个已挂载 iframe 的最后可见时间，超出 `cap` 时按 LRU 逐出（复用已有的 `dormantHeight` 等高占位，零跳动）；
3. **懒挂载**：从未进入过缓冲区的消息不创建 iframe —— 与配额互补；
4. `cap` 取**显著大于可见集**（可见约 2~3 个 + 一屏缓冲 ⇒ 建议 cap 12~16）⇒ **普通会话根本不会触发逐出，行为零变化**；只有超长会话才付代价；
5. **iOS 豁免**：UA 判定 iOS Safari ⇒ 只隐藏、永不卸载（配额内也不逐出）。把已知回归钉死在门外。

关于交接文档要求的「**重建后状态如何恢复**」（这句是它最有价值的一句提醒）：

- **能恢复的**：卡变量走 MVU 落库/存储，重新 boot 会从存储读回（S2 之后走双兼容键）；
- **不能恢复的**：帧内 JS 模块作用域状态（计数器、闭包里的一次性标记）；
- **架构上已有重建通路**：`srcDoc` 重建（`sourceFingerprint` / `assetModeVersion` 变化）→ `onLoad` 强制重推插件脚本包（`CharacterCardRenderer.tsx:592`、`:886` `force=true`）→ `postContextToFrame` context-update。即**重建不是外来概念，是现有设计里已跑通的路径**；
- **增量风险**：每次逐出-重建 = 1 次导航 = 1 条 iOS 幽灵历史 ⇒ 靠 cap + iOS 豁免把它**限界**，而不是消除。这一点必须白纸黑字写进方案文档。

### 2.5 守卫测试怎么落（交接文档硬性要求至少一条）

现有休眠门**零测试覆盖**（全仓 grep `dormancy` 无任何 test 文件命中）⇒ 先钉后改（交接文档 §10.1 纪律）：

1. **纯逻辑单测（主力，确定性最好）**：把 LRU 策略抽成独立纯模块（如 `iframe-lru.ts`），灌 N 次 register / evict，断言 `alive ≤ cap`、逐出顺序 = LRU 序。这就是"存活 iframe 数不随已加载消息数线性增长"的可执行形式。
2. **jsdom 集成测试**：伪造 `IntersectionObserver` 驱动 N 个门可见/不可见，断言真实挂载的 `iframe` 元素数 ≤ cap、且等高占位保留。
3. **回归钉**：默认不卸载（锁 `PALINK_CARD_DORMANCY_UNMOUNT=false` 现状）、休眠后占位高度非零、观察器 disconnect 清理。

**根因**（`card-idb-namespace.ts:118-125` 读开关 → `legacy-st-sim.ts:135-138` 拒绝暴露）：

```js
// idbNamespaceDisabled()：
var p = window.parent;
if (p && p !== window && p.localStorage) {

}
// 而 legacy parent 代理故意这么做（legacy-st-sim.ts:135）：
if (prop === 'localStorage' || prop === 'sessionStorage') {
  try { return window[prop]; } catch (e) { return undefined; }     // ← 返回卡内自己的内存存储
}
```

⇒ `window.parent` 是 legacy 段装的**安全代理**（`:39` 明写"真实父帧对象本身不暴露：

开关键写在**主框架**，卡内内存存储里永远没有 ⇒ `idbNamespaceDisabled()` **恒返回 false**
⇒ 分库 shim 永远安装 ⇒ **开关 2 是一颗哑弹**。

**为什么"单测覆盖"却没发现**：单测直接 mock `window.parent`，**没有装 legacy parent 代理** ——
和 §9.6 那条教训同宗：**桩没有照抄真机环境**。
