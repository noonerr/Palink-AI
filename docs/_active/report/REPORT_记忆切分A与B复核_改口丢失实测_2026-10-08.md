### 3.2 候选池里放了"还没发生的事"（时间泄漏）

**生产在 pos51 那一刻 pos52 还没入库**。这也正是 §3.1 低于瞎选的机制：
用户那句最匹配的是**它勾出来的下一条**回复，而它按定义算 miss。

## 4. 用户新提的顾虑：改口的那半截会不会被切没 —— 实测：会，但主因不是切块

探针 `probe_neg_recall.py`，走生产同一个 `storage.semantic_search`（pgvector 路），
向量直接取库里已存的那份，**不重新嵌入、不写库、不打印正文**。

真实库里按改口词形找到 **12 组**「被否认的事 C + 之后的改口 R」：

| 判据 | 结果 |
|---|---|
| 锚在 C 上检索，R 排第几 | 中位第 4；**12 组里 5 组排在第 7~30 名** |
| 生产一次注入几行 | **实测只能装 5~8 行**：每块平均 184 token（中位 212，`tokens_count`），预算 1500；STM 固定取 5 行就吃掉约 920，LTM 只剩约 3 行（`retriever.py:154-160` 填预算即止） |
| R 的相似度 | 12/12 过阈值，中位 0.829 ⇒ **不是像不像的问题**，是同时 ~50 行都过阈值被挤出名次 |
| **反向**：锚在 R 上找 C | 12/12 全进前 5，中位第 2 ⇒ **漏是单向的**：改口带得出原话，原话带不回改口 |
| 同一条回复内部：改口块 vs 被否认块的下标距离 | 差 1 格（邻居扩展能带上）只占 **44%**，差 2 格占 **56%**；扩展只看 ±1（`service.py:215` → `storage.py:738`） |

**分工要说清**：
- 跨条改口（用户举的例子）= 两条独立记忆，**整条不切也照样漏**，与切块无关。
  病因是"按最像排序、没有任何'后来作废前面'机制"；唯一的作废机制是**分支截断**
  `branch_scopes`（管"换故事线"，不管"同一条线里改口"）。
- 同条改口才是切块的责任，占上面那 56%。

**第二道锁**：注入格式就是 `- Assistant: 文字`（`app/utils.py:480`），**不带时间/先后**；
打分是 `similarity×0.6 + 邻近度×0.2 + (importance−0.5)×0.2`（`retriever.py:234-238`），
**没有"新胜旧"项**。⇒ 两条一起被捞回来时，模型也没有以新的为准的抓手。

**边界声明**：12 组由正则自动挑（词形见脚本 `NEG_SQL`），未逐条读正文核对是否真改口；
单向不对称这个方向是稳的，具体次数别当精确值用。
