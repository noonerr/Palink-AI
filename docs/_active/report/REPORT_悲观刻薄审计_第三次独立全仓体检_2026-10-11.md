服务端 detail 参与嗅探时（`api.ts:238` 构造 `` new Error(`${res.status} ${detail}`) ``）：

[server     ] 服务器错误   <<  iframe height 50000 exceeds cap
[validation ] 输入验证错误 <<  max_context_tokens fallback 4000 applied

[unknown    ] 发生错误     <<  HTTP 404

**误判机制**（`errorHandler.ts:80-92`）：

```ts
if (errorString.includes('timeout') || errorString.includes('504'))      errorType = 'timeout';
else if (errorString.includes('network') || ... )                        errorType = 'network';
else if (errorString.includes('500') || includes('502') || includes('503')) errorType = 'server';
else if (errorString.includes('401') || includes('403') || ...)          errorType = 'auth';
else if (errorString.includes('400') || errorString.includes('validation')) errorType = 'validation';
```

- `"15000"` 含子串 `"500"` ⇒ token 上限错误报成**服务器错误**
- `"50000"` 含 `"500"` ⇒ 卡片高度上限报成**服务器错误**（50000 正是本项目 iframe 高度上限）
- `"4000"` 含 `"400"` ⇒ 预算兜底报成**输入验证错误**（4000 正是 DEFAULT_BUDGET 兜底值）
- `"14000"` 含 `"400"` ⇒ 端口连不上报成**输入验证错误**，而不是网络错误（14000 正是本站端口）
- `includes('abort')` 在**所有分支之前**，所以 `"aborted by upstream 500"` 变成**"请求已取消"**，把服务端故障说成用户主动取消
- **没有 404 分支、没有 429 分支**

**这条确实是用户可见的**，链路已核：

```
api.ts:238   throw new ApiError(res.status, detail, analyzeError(...))
api.ts:114-123  class ApiError { errorInfo: ErrorInfo }
CharacterChat.tsx:2228   <ErrorToast errorInfo={currentError} />
ErrorToast.tsx:53/56/59/62   errorIcons[errorInfo.type] / .title / .description / .suggestion
```

**导致什么：** 最痛的一条是 **429**。本项目跑在多用户 + 网关计费模式下，额度耗尽/限流是高频事件，而用户看到的是「发生错误 / 发生了一个意外错误 / 请稍后再重试，或联系技术支持」——**指向了完全错误的行动**。而死掉的那套 `error-handler` 里，`fromApiError(429)` 会正确给出「请求过于频繁，请稍后再试」并标记 `recoverable=true`。**写对了的代码没接线，接了线的代码没写对。**

另外 `analyzeError` 的 abort 分支返回值自相矛盾：`type` 是 `'unknown'` 而 `title` 是 `'请求已取消'`（spread `errorMessages.unknown` 后覆盖 title）。任何按 `type` switch 的调用方与用户看到的文案不一致。

**改了好：** 分类不该读 message 文本，该读 `res.status` 数字。`api.ts` 的 8 个调用点手里都有 `res.status`，却把它拼成字符串再让下游用子串猜回来——**信息先被摧毁再试图重建**。改法：`analyzeError(status: number, detail?: string)`，直接 switch 数字，补齐 404/408/429。

**改了好（三档，按侵入性递增）**：

⚠️ 三档都**没有**在本次会话实施（超出用户授权的 ②范围）。本条只交付"取证 + 定位 + 选项"。

### H1 · docs job 的根因已**完全定位**，且它在 CI 上**永远不可能绿**

**机制（读生成器代码锁定）：** `scripts/docs/gen_docs_catalog.py` 会把两个"只在本机才成立"的数字写进目录：

```python
# gen_docs_catalog.py:208, 356-365
tracked = git_tracked_count([r["rel"] for r in records])
...
w(f"- 已被 git 跟踪：**{stats['tracked']}**")
w(f"- **未入库（只存在本机）：{untracked}**")          # untracked = total - tracked
w(f"> ⚠️ 这 {untracked} 份**只存在这台机器上**……")
```

已提交的那份目录里**实际写着**：

```
- 已被 git 跟踪：**258**
- **未入库（只存在本机）：2**
> ⚠️ 这 2 份只存在这台机器上。
```

而 `_strip_volatile()`（446-457 行）只抹两类易变字段：**生成时间戳** 和 **mtime 列**。
**它没有抹这两个计数。** CI 上是全新检出，检出的文件**全都算"已跟踪"** ⇒ `untracked` 恒等于 0 ⇒ 这两行必然与仓库里那份不同 ⇒ `--check` 判 STALE。

**结论：`docs` job 是一个在 CI 上结构性必红的门禁。** 与 §A2 同一种病（恒红门禁=没有门禁），只是换到了远端。

**复现（一手）：** 用 `git archive HEAD docs scripts` 造出"只有跟踪文件"的环境，跑同一条 `--check`：

```
导出后 docs/ 里的 md 数（= CI 能看到的）: 260
本地工作区 docs/ 里的 md 数（含未入库）  : 262
=== 在这个 CI 等价环境里跑 --check ===
[docs-catalog] STALE  docs\_CATALOG.md 已与 docs/ 实际内容不符
=== 同一命令在完整工作区里跑 ===
[docs-catalog] OK     261 docs, catalog up to date
```

**改了好（三选一，都很小）：**
1. **把这两个计数也加进 `_strip_volatile`**（最省，一行正则）；
2. 让生成器**根本不写**未入库统计（它属于本机卫生，不属于产物）；
3. 把 docs job 从 CI 里摘掉——`_CATALOG.md` 的校验本质是**本机**纪律（AGENTS.md §目录自动化也明说"不挂 hook、靠每个 agent 自己跑"），放 CI 上判据天然不成立。

⚠️ 我倾向 **①+③**：① 让它在任何环境都自洽，③ 让 CI 只测"能在 CI 里成立的东西"。
