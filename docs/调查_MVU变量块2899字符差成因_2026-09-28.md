## 0. 一句话结论

**2899 字符 = 世界书条目「[mvu_update]变量输出格式」里 `format: |-` 之后的那段 `<UpdateVariable>…</UpdateVariable>` 模板原文。**
删掉它的不是预算、不是裁剪、也不是宏展开，而是**角色卡自带正则脚本「[不发送]去除变量更新」**——它带
**`minDepth = 4`** 的深度窗。旧布局尾部有 2 条 system，消息总数 6、变量块距末尾 depth=4 → **命中脚本 → 整段删空**；
T2 砍掉尾部后消息总数 4、depth 变 3（T1 加下限后变 2）→ **跌出深度窗 → 模板完整进入 prompt**。

即：**这不是"宏展开依赖消息位置"，而是"消息级正则的深度窗依赖消息总数"**。

## 1. 那 2899 字符到底是什么

对同一份变量块做逐字符对齐（`block_B` = 旧布局 12260，`block_new` = 现布局 15159）：

```
lenB 12260  lenN 15159  diff 2899
common prefix chars = 11811
common suffix chars = 449
--- B-only middle ---   ''          （空！B 就是 new 抠掉这一段）
--- new-only middle ---
'<UpdateVariable>\n <Analysis>$(IN ENGLISH, no more than 80 words)\n
 - ${calculate time passed: ...}\n ... <JSONPatch>\n [\n
 { "op": "replace", "path": "/世界信息/日期时间", "value": "${new_value}" },\n
 { "op": "delta", "path": "/桃汐/好感度", "value": ${positive_or_negative_delta} },\n ...'
```

- 插入点前一句（两边完全相同）：`… - don't update field names starts with \`_\` as they are readonly, such as \`_变量\`\n format: |- `
  → 这是 **YAML 块标量 `format: |-`**，模板原文就挂在它下面。
- 该段含 `${new_value}` × 28、`positive_or_negative_delta` × 8（与复核 A.6 描述吻合）。
- 出处：世界书「猫娘神域」raw_content 第 15657–19470 字符（3813 字符）的 `## [mvu_update]变量输出格式` 条目。

标记计数对照（探针 §2）：

| | 变量块长度 | `<UpdateVariable>` | `</UpdateVariable>` | `${new_value}` | `positive_or_negative_delta` |
| --- | --- | --- | --- | --- | --- |
| 旧布局 B | 12260 | 1 | 0 | 0 | 0 |
| 现布局 | 15159 | 2 | 1 | 28 | 8 |

## 2. 凶手：卡自带正则「[不发送]去除变量更新」

`characters.extensions.regex_scripts[1]`（卡 7b064410「我被猫娘包围了！」，DB 实测）：

```json
{
  "scriptName": "[不发送]去除变量更新",
  "findRegex": "/<UpdateVariable>(.*?)<\\/UpdateVariable>/gis",
  "replaceString": "",
  "placement": [1, 2],
  "minDepth": 4,          ← 关键
  "maxDepth": null,
  "promptOnly": true,
  "markdownOnly": false,
  "disabled": false
}
```

命中链路（`backend/app/api/character_ext.py`）：

- `_apply_prompt_regex_to_messages`（:1602）由 `roleplay_prompt_assembly.py:3773-3774` 调用，
  开关是 **`req.include_prompt_regex`**（`PromptAssemblyRequest` 默认 **True**）。
- 循环里 `depth = max(0, total - 1 - index)`（:1629）——**depth 是"距末尾的距离"，由消息总数决定**。
- 非 assistant 角色（含 system）→ `prompt_placement = REGEX_PLACEMENT_USER_INPUT`（1），命中该脚本的 `placement:[1,2]`；
  `promptOnly=true` 且 `is_prompt=True` → 生效；`minDepth=4` → **仅当 `depth >= 4` 生效**。

### depth 账本（这就是 2899 出现/消失的全部原因）

| 布局 | 消息总数 total | 变量块 index | depth = total-1-index | ≥4？ | 脚本 | 变量块 |
| --- | --- | --- | --- | --- | --- | --- |
| 旧布局（T2 前，尾部 2 条 system） | 6 | 1 | **4** | ✅ | 命中删空 | **12260** |
| T2 后 / T1 加下限前 | 4 | 0 | 3 | ❌ | 不命中 | 15159 |
| T1 加下限后（当前） | 4 | 1 | 2 | ❌ | 不命中 | **15159** |

> 注意：**T1 的下限改动不参与这笔账**（depth 3→2，两侧都 <4，块长度实测皆为 15159，见 §3 探针）。
> 2899 是 **T2 砍尾部**带来的副作用，不是 T1 的。

## 3. 证据链（容器内实测，同一张卡 7b064410 / 会话 2cb171bf / 同 DB）

探针 `backend/scripts/probe_mvu_block_origin.py` 用只读 monkey-patch 抓了 3 个阶段
（`MVU_SPY_WB=1` 抓世界书 depth_entries；`MVU_SPY_STAGES=1` 抓注入后/宏展开前后）。

**① 世界书输出两侧完全一致** → 排除"世界书召回/激活差异"：

```
[SPY] depth_entry[0] depth=4 len=95    (---\n<status_current_variable>\n{{format_message_variable::stat_data}}…)
[SPY] depth_entry[1] depth=4 len=6071  (变量更新规则)
[SPY] depth_entry[2] depth=4 len=3535  (变量输出格式)  positive_or_negative_delta=8
[SPY] depth_entry[3] depth=4 len=478   (<user_information_boundary>…)
[SPY] wb_result.text len=3012
（旧布局三件套 1126b88 与当前代码逐字节相同）
```

**② 阶段探针：删除发生在「depth 注入之后、宏展开之前」**

```
B 态（旧 builder，6 条）
  S1     _insert_depth_prompt 之后        : [1] len=10117 delta=8
  S2-in  evaluate_macros_in_messages 入参  : [1] len= 7218 delta=0   ← 这里已经没了（10117-7218=2899）
  S2     宏展开之后                        : [1] len=12260 delta=0

新态（新 builder，4 条）
  S1     : [1] len=10117 delta=8
  S2-in  : [1] len=10117 delta=8   ← 没被删
  S2     : [1] len=15159 delta=8
```

**③ 反证（决定性）**：B 态下把 `include_prompt_regex` 关掉（探针 `MVU_NO_PROMPT_REGEX=1`，不动任何生产代码）：

```
B 态 + 关掉消息级正则：
  S1     : [1] len=10117 delta=8
  S2-in  : [1] len=10117 delta=8   ← 模板回来了
  S2     : [1] len=15159 delta=8   ← 与现布局一致
```

关掉这一条开关，12260 → 15159。**删它的人就是消息级正则。**

**④ 交叉复现**（逐文件二分，容器临时换文件，跑完已恢复并 sha256 校验一致）：

| 组合 | 消息数 | 变量块 |
| --- | --- | --- |
| 全旧（assembly+character_message_builder+default_prompts = 1126b88） | 6 | 12260 ← 与复核 §2.1 的 B 完全吻合（[0]492/[1]12260/[2]3047/[3]631/[4]38/[5]63） |
| 新 assembly + **旧** builder + 旧 default_prompts | 6 | 12260 |
| 新 assembly + **新** builder + 旧 default_prompts | 4 | 15159 |

→ 变量取自 **builder 输出的消息总数**，与 assembly / default_prompts 无关。

## 5. 复核为什么没查到（值得记一笔）

复核 A.6 写「角色卡 scoped 正则的深度窗 → `regex_scripts WHERE scope_id=<该卡> AND (min_depth IS NOT NULL OR max_depth IS NOT NULL)` → 0 行」。
两处偏差叠加导致漏判：

1. **查错了地方**：这条脚本不在 `regex_scripts` **表**里，而在 **`characters.extensions` 的 JSON**（`extensions.regex_scripts[]`），
   表查询天然 0 行。
2. **字段名错了**：卡内脚本是 ST 的 **camelCase**（`minDepth` / `maxDepth` / `findRegex` / `promptOnly`），
   用 snake_case `min_depth` 去匹配 JSON 键也会空手而归。
   本仓库自己的探针第一版也是这么打印的（所以第一屏全是 `minD=None`），改读 camelCase 才看见 `minDepth=4`。

## 6. 未结案 / 需要拍板的（本次未动，只登记）

1. **这是"行为变化"不是"bug"**：2899 字符的 MVU 模板原文现在**完整发给模型**。
   卡作者写「[不发送]去除变量更新」的意图是"发给模型的文本里剥掉 `<UpdateVariable>` 模板"，
   但只在中古历史（depth≥4）剥；变量块现在 depth=2 → 不剥 → 模板进 prompt。
   *要不要剥*属于产品/兼容决策（改它 = 改正则深度窗或改 system 消息的 placement 归类），**本次不擅自改**。
2. **一个可能的口径疑问**：`_apply_prompt_regex_to_messages` 把 **system 角色**消息统一按
   `REGEX_PLACEMENT_USER_INPUT`(1) 处理（:1631-1635）。世界书/变量块是 system 消息，因此会被
   `placement:[1,2]` 的"用户消息"类脚本打到。ST 里 system 有自己的 placement 位，
   这个归类是否对齐 ST 值得另立议题（本单不属授权范围）。
3. **正则深度窗的 depth 基数不稳**：`depth = total-1-index` 依赖"消息总数"，
   任何改装配尾部的动作（如本次 T2）都会让**所有**带深度窗的脚本整体漂移一格。
   这是一类"改 A 处、B 处静默变"的耦合，若要治理需另立议题。
