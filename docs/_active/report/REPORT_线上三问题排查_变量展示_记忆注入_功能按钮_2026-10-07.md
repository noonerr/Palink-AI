## 1. 问题 2：记忆/向量库注入异常 —— 确诊（P0，一行代码）

### 1.1 用户的怀疑方向是错的（这是本次最有价值的一条）

用户判断：「词条已正常录入，但**向量引擎疑似未正确将对应数据注入向量库**」「无法确认向量引擎是否正常运行」。

```

# ④ 语料：665/723 条带向量（58 条 NULL 是 09-23～10-02 的历史降级期，非当前）
$ SELECT count(*) total, count(embedding) with_vec FROM conversation_memories;

```

**而且检索这一步也是成功的**——日志明确打印「找到 50 条记忆」：

```
[INFO] MemoryModule: 语义检索完成: 找到 50 条记忆，最低相似度: 0.5983****0369, 作用域: session
[ERROR] MemoryModule: 检索记忆失败: 'tuple' object has no attribute 'message_id'
```

**检索成功 → 组装失败 → 整批丢弃。** 用户看到的现象（"记不住"）就来自这第二行。

### 1.2 根因：一行元组解包写错

`backend/app/memory_module/retriever.py` 第 131–138 行：

```python
if semantic_candidates:
    # D3: LTM 侧同样排除最近消息镜像
    if exclude_ids:
        semantic_candidates = [
            m for m in semantic_candidates          # ← m 是 (MemoryEntry, float) 元组
            if m.message_id not in exclude_ids      # ← 元组没有 .message_id ⇒ AttributeError
        ]
    scored_candidates = self._score_candidates(semantic_candidates, stm_ids)
```

`self.storage.semantic_search(...)` 的返回类型是 `List[Tuple[MemoryEntry, float]]`
（`storage.py:699` 签名 + `:885` 返回 `memories_with_similarity`），所以 `m` 是元组，`m.message_id` 必然抛异常。

**正确写法**（下方 `_score_candidates` / `_compute_context_proximity` 都是正确解包的，可对照）：

```python
semantic_candidates = [
    (mem, sim) for mem, sim in semantic_candidates
    if mem.message_id not in exclude_ids
]
```

### 1.3 为什么症状是"记忆全丢"而不是"少几条"

异常发生在 `retriever.retrieve()` 内，被同函数的 `except`（`:181-190`）兜住并**返回空结果**：

```python
except Exception as e:
    logger.exception(f"检索记忆失败: {e}")
    self.storage.db.rollback()
    return ContextResponse(memories=[], total_tokens=0, strategy_used="error", scope=scope)
```

于是 `roleplay_prompt_assembly.py:5611` 的 `if mem_ctx and mem_ctx.memories:` 判假 ⇒ **动态上下文里一个字都不注入**
——连本来已经取到的 STM（最近 5 条）也一起丢了。

### 1.4 触发条件与影响面（为什么"有时像好的"）

触发链：`exclude_ids` 非空 **且** 语义候选非空。

- `exclude_ids` 来自 `roleplay_prompt_assembly.py:5572-5586`——**正常聊天必然非空**（取最近 5 条消息 id 做去重）。
- 语义候选非空需要该会话/角色已有带向量的记忆。

⇒ 结论：**任何"有历史记忆的会话"，记忆注入恒为 0**。只有全新会话（还没有任何记忆）才是"正常"的——这正是它容易被误判成"偶发/效果差"的原因。
日志里也看得到这个分界：03:10 之前是「找到 0 条记忆」（不触发），03:20 起是「找到 50 条 + 报错」。

### 1.5 引入时间

## 3. 问题 1：变量信息展示异常（不刷新不显示）

### 3.1 先厘清"变量框"是哪一个（这决定根因不同）

Palink 上同时存在**三个**用户都可能叫"变量框"的东西，链路完全不同：

| 名称 | 位置 | 数据来源 | 组件 |
|---|---|---|---|
| **变量变化**面板 | 消息气泡内，显示「这一轮改了什么」 | **消息级**快照 `msg.extra.variables.stat_data`（本楼 + 上一楼） | `VariableChangePanel.tsx`（`Message.tsx:1755`） |
| **当前值**面板（酒馆助手兜底） | 消息气泡内，显示"现在是多少" | `msg.extra.variables.stat_data` **??** `sessionVariables.stat_data` | `TavernHelperPanel.tsx`（`Message.tsx:1739`） |
| **卡内状态栏/变量栏** | 卡片 iframe 里（卡脚本渲染） | `sessionVariables` 经 `context-update` 下发 → `Mvu.getAllVariables()` | 卡片自己的 HTML/脚本 |

用户说的"疑似角色面板也存在同类问题"提示：**共同上游是 `sessionVariables`**。
而 2026-10-05 的 `MVU-STATUSBAR-LIVE` 修复（`cardVariables.ts`）已经把"卡内状态栏"的取值改成
**会话级实时值优先**，其文件头写明整条链路：

```
sessionVariables 变化 → postContextToFrame（按签名去重）→ context-update
  → deepMergeVariablesCompat → emit mag_variable_update_ended
  → 卡片 eventOn 回调 → 重画面板
```

**这条链的成立前提是 `sessionVariables` 必须真的变。** 以下三条候选，全都断在不同位置。

### 3.2 候选 A（已确诊为契约不一致）：SSE 路径的 `final_content` 不带 `variables`

前端两条传输链路的处理**是对称的**，但后端只给了一条：

| 链路 | 后端下发 | 前端消费 |
|---|---|---|
| **WebSocket** | `websocket.py:1139-1142` — `{"type":"final_content", "content":…, "message_id":…, **({"variables": mvu_latest_variables} if … else {})}` ✅ | `useChatWebSocket.ts:205-208` → `onFinalContent({…, variables})` → `useCharacterChat.ts:491-508`：① 派发 `palink:mvuVariablesUpdated` ② `setMessages(... extra.variables = nextVariables)` |
| **SSE（回退路径）** | `character_ext.py:5972` 与 `:5147` — `{'type':'final_content','content':…,'message_id':…}` ❌ **无 `variables`** | `useCharacterChat.ts:1413-1436` 期望 `json.variables`；取不到就**跳过** `extra` 写入与事件派发 |

⇒ **只要这一轮走的是 SSE，消息级 `extra.variables` 在内存里永远不更新**，于是：

- 「变量变化」面板（需要消息级快照）**必须刷新**才出现（刷新走 `GET /messages`，从 DB 读到 `extra.variables`）；
- 卡内状态栏只能靠 `CharacterChat.tsx:1813` 那个生成结束后的 `?limit=1` 兜底重取（有延迟，且拿不到时会停住）。

**这是前后端契约不一致的确诊缺陷，与"优化"无关，属存量。**
判据：DevTools Network 里看这一轮是 `/api/ws/character-chat`（WS）还是一条流式 POST（SSE）；
若走 SSE ⇒ 候选 A 成立。日志里 `WebSocket … 403`（1 次）说明 WS 确实可能握手失败而回退。

### 3.3 候选 B（可疑，10-07 优化引入）：`sessionVariables` 主来源改成"父级 props + 60 秒缓存"

10-07 的 `d436a7e` 做了"请求去重与缓存"，把变量主来源从「CharacterChat 内部无缓存 `?limit=1`」
改成「父级 `CharacterView` 从 messages 响应承接」，同时 **messages 的 TTL 从 10s 提到 60s**：

```ts

setSessionVariables(data?.variables ?? undefined);   // ← 缓存命中时，这里是 60 秒前的旧变量

// CharacterChat.tsx:789-791（新增的同步 effect）

  setSessionVariables(sessionVariablesProp ?? undefined);   // ← 无条件覆盖本组件刚拿到的新值

```

`api.get` 在 `cacheTtlMs` 内**直接返回缓存对象**（`api.ts:318-324`），不区分是否刚生成过。

## 7. 第 4 个问题：AI 输出入库是否截断 —— 查了，**没有截断**

用户追加提问："我记得还有个问题是 ai 输出入库也会有截断，你看看有没有这个问题"。
结论：**在"消息落库"和"记忆入库"两层都没有找到截断缺陷。** 下面逐层给证据，
并给出"为什么体感上像被截断"的真实解释。

### 7.1 消息落库层 —— 无截断（DB 实测）

| 判据 | 实测 | 结论 |
|---|---|---|
| 列类型 | `character.py:114` `content = Column(Text)` | **无长度上限**，不可能被列定义截 |
| 正文 vs 候选 | `content = swipes[-1]` → 最近 12 条 **12/12 全部为 true** | 落库正文与其所在候选**逐字节一致**，不是半截 |
| 长度分布 | 42 条（id>2700）：min 906 / max 3458 / avg 1624 | 无"卡在某个上限"的聚集 |
| 重复长度 | `2385` 出现 5 次 → 分散在 **4 个不同 session** | 是**同一段开场白**的多个副本，不是撞上限（撞上限应集中在同一会话的连续消息） |
| 标签闭合 | 37 条含 `<now_plot>` 且 **37 条都有 `</now_plot>`** | 没有从标签中间被砍断 |
| 结尾字符 | `】` 74 / `>` 26 / `]` 4 / `。` 3 … 仅 1 条以"续"结尾 | 那 1 条是 2026-08-08 的 **4 字**历史消息，与截断无关 |
| 生成上限 | 日志 `[STREAM-CALL] model=deepseek-flash max_tokens=16384` | 上限很大，模型输出**不会撞 token 天花板** |
| 落库实现 | `websocket.py:694` `final_raw = result.full_content`（**累积全量**，`persist_snapshot` 从不存片段） | 最终 `force=True` 保存的一定是完整内容 |

补充：日志里 `finish_reason` **零命中**（后端根本没记录），所以"是否因 `finish_reason=length` 被上游砍断"
**无法从现有日志证实**——但 `max_tokens=16384` 与实测最大 3458 字符（≈2~3k token）相距甚远，不构成嫌疑。

### 7.2 记忆入库层 —— 是"语义切分"，不是截断

| 判据 | 实测 |
|---|---|
| 记忆条目长度 | 723 条：min 1 / **max 803** / avg 298；`>=2000` 的 **0 条**，`<=200` 的 226 条 |
| 源消息 vs 记忆块 | 源 3130 字 → 切成 **440 / 439 / 441** 三块（共 1320） |
| 单块上限 | `memory_config.CHUNK_MAX_CHARS = 450`，实测块长 416–441 |

⇒ 块长全部贴合 450 上限且源消息被**完整覆盖**（3130 剥离变量块后 1320 = 三块之和），
这是**设计内的语义切分**（`MEMORY_SEMANTIC_CHUNKING`），不是丢数据。

### 7.3 记忆注入层 —— 历史上的 200 字硬截断**已废除**

`utils.py:225` 的注释还写着"注入 prompt 时又被 `content[:200]` 硬截断"，但那是**旧描述**。
现在的 `build_memory_context`（`utils.py:449`）文件头明写：

> 变更：**废除每条 200 字砍头** —— 语义块命中即完整注入；
> 预算不足时按"**整条跳过**"处理而非截断文本。

全仓 grep `[:200]` 的剩余命中只在：摘要生成（`ai_summary_service.py:74/82/136/137`，喂摘要模型的输入，合理）、
日志/错误信息截断（无害）。**注入链路无截断。**

### 7.4 那"体感像截断"从哪来 —— 是**落库前的剥离**，不是截断

落库前后端会主动剥离四样东西（`websocket.py:694-800`）：

1. `<UpdateVariable>…</UpdateVariable>` 变量指令块（`strip_update_variable_blocks`）
2. `palink-status` 状态栏配置标记
3. `<think>…</think>` 思维链块
4. 回复末尾的 `[标题: xxx]` 标记

#### 剥离是按什么做的？—— **纯模板/正则匹配，不是语义理解**

这点要讲清楚，因为它决定了"什么情况下会漏"。以最复杂的
`strip_update_variable_blocks`（`mvu_engine.py:231`）为例，它内部是**四道机械工序**：

| 道 | 手段 | 是否涉及语义 |
|---|---|---|
| ① 块独占整行 | 正则 `^[ \t]*<UpdateVariable>[\s\S]*?</UpdateVariable>[ \t]*$\n?`（IGNORECASE） | ❌ 纯字符串模板 |
| ② 块内联在正文 | `<UpdateVariable>([\s\S]*?)</UpdateVariable>`（IGNORECASE） | ❌ 纯字符串模板 |
| ③ 围栏残留清理 | 正则 + 围栏配对状态机（`_strip_markdown_fence_leftovers`） | ❌ 结构计数，不读内容 |
| ④ 裸 JSON Patch | 平衡括号扫描 + JSON 解析 + `_looks_like_stat_data_patch` 结构校验 | ⭕ **唯一带"结构校验"的一道** |

**整个过程没有任何一步理解"这段话在说什么"**，它只是找形如
`<UpdateVariable>…</UpdateVariable>` 的**字符模板**然后删掉。

⇒ 直接推论：**模型只要换写法就会漏**。例如写成 `<update variable>`（带空格）、
`<Update_Variable>`、用了 HTML 实体转义 `&lt;UpdateVariable&gt;`、
标签未闭合、或把块塞进别的结构里 —— 正则一律匹配不到，块就原样留进正文。
（本轮实测的 8 条里，标签**都是**标准写法且配对，所以不是这个原因，见 §7.4.1。）

只有第 ④ 道（裸 JSON Patch）算"半结构"：它会先按平衡括号切出数组、解析成 JSON，
再用 `_looks_like_stat_data_patch` 判断"这像不像一条 stat_data 补丁"（要求 path 以 `/`
开头、首段非空、不以 `_` 开头等），目的是**降低误伤正文**——它是在判断"像不像补丁"，
仍然不是理解语义。

⇒ **流式过程中前端看到的是原始输出（含这些块，更长）**，
**刷新后从 DB 读到的是剥离后的干净正文（更短）**。
两者一比就"像被截断"，实际是设计如此。

**⚠️ 但这个"剥离"确实有真问题（与本轮 §3.2 的候选 A 同源）**：

- 流式结束时后端会推送一条 `final_content`（取自剥离后的 `msg.content`），用它**替换**前端显示。
  这条推送**只在 WebSocket 路径可靠**；SSE 路径的 `final_content` 不带 `variables`（§3.2），
  且若推送未达（WS 断开/中途停止），前端会**保留流式累积的原始内容** ⇒ 刷新后"突然变短"。
- 另外实测发现：DB 里**仍有 8 条**保留着完整的 `<UpdateVariable>` 块。

### 7.4.1 这 8 条其实是**两种完全不同的成因**（2026-10-07 追加取证）

按落库路径特征一分，8 条天然裂成两组：

| 组 | 条数 | 长度 | 会话内位置 | extra 形状 | 结论 |

| **B** | 3 | 3130 / 3171 / 3458 | 第 82 / 74 / 64 条 | `variables`+`mvu_patch`+`gen_id`+`model` **齐全** | ⚠️ **未定性**：MVU 解析成功了，正文却没剥 |

**A 组已确证**：开场白（含卡自带的 `<UpdateVariable>` 初始化块）走的是
`character_ext.py:3065 POST /messages` 这条"只写 `swipe_info`"的路径，
**既不跑 MVU 解析，也不调 `strip_update_variable_blocks`**。
这与 `SPEC_卡状态面板取不到数据_三层根因修复_2026-10-06.md` §2.1「层三｜写入口不对称」
的描述**逐字吻合**——那份 SPEC 当时就点名了 **2740/2741**，而 2741 正在本组里。
⇒ 这不是新 bug，是**已登记、未修**的 F-A2（写入口收敛）。

**B 组未定性**。已排除的几种可能（都是实测，不是推测）：

- 标签未闭合？→ 8 条**全部** `open=1 / close=1` 配对，排除。
- 被 markdown 围栏包住导致整行正则失配？→ 块前 60 字符**全部**无 ``` ，排除。

  `<UpdateVariable>([\s\S]*?)</UpdateVariable>`（IGNORECASE，可跨行），本组形态必然命中。
- 块在文中而非文末？→ 位置 1401/1752/2252，闭合后**几乎贴着文末**，是最容易剥的形态。

⇒ 剩下的可能只有"**这条消息不是由剥离后的内容写入的**"：
要么是另一条写入路径覆盖了 `content`，要么是生成中断后落的是中间态。
**下一步取证**（未做）：查这 3 条的 `gen_id` 与相邻消息的关系，确认是否对应一次
被中断/被 PATCH 覆盖的生成；或在 `character_ext.py` 的 4 处剥离点各加一条
「剥离前后长度」日志，跑一轮即可定位。

⚠️ **B 组不要凭推测改代码**——它只有 3 条样本，且已排除 4 种最直觉的假设。

### 7.5 结论

- ✅ **"AI 输出入库被截断"这个缺陷，证据上不成立**，不需要按截断去修。
- ⚠️ 但它指向的**观感来源是真的**：落库前剥离导致"刷新后变短"+ 剥离偶尔不生效。
  建议按 §6 第 3 项（补 SSE 的 `final_content`）一起处理，而不是去加长度。
- ⚠️ 唯一确证存在的内容缩短：`ai_summary_service` 生成剧情线摘要时把消息截到 200/300 字
  喂摘要模型 —— **影响摘要质量，不影响入库**。若剧情线摘要质量差，可从这里查。

## 8. 追加议题：记忆切分**根本没按语义切**（实测，2026-10-07）

用户提问：「如果是按每句话截断之后分配语义，是不是不太好？能不能既保持向量机性能、
又按一大段话的语义来分？效果会不会更好？」

⇒ **你的直觉是对的，而且实际情况比"按句子切"更糟：语义切分 100% 失效，现在是纯按 450 字上限硬切。**

### 8.1 实测证据（探针，只输出数字不输出正文）

容器里跑 `semantic_chunker` 的中间步骤，取 5 条真实 assistant 回复（1322~1700 字）：

```
[cfg] epsilon=0.12 min=120 max=450 trigger=250 buffer=1

msg=2786 正文1322字 句数=30 断点=0 块数=1 块长=[1322]
msg=2784 正文1641字 句数=44 断点=0 块数=1 块长=[1641]
msg=2782 正文1535字 句数=42 断点=0 块数=1 块长=[1535]
msg=2780 正文1651字 句数=37 断点=0 块数=1 块长=[1651]
msg=2778 正文1700字 句数=43 断点=0 块数=1 块长=[1700]

=== 全体相邻句余弦距离（n=191）===
  p50 = 0.0708   p90 = 0.0868   p95 = 0.0897   p99 = 0.0976
  mean=0.0703  std=0.0130  max=0.1010
  >= 当前 epsilon(0.12) 的比例: 0.0%      ← ★ 一个断点都找不到
```

**根因**：`_detect_breakpoints` 的判定下限是 `floor = max(epsilon, mean(dists))`。
bge-m3 在本项目语料上，相邻句的余弦距离**最大也只有 0.101**，而 `epsilon` 被设成 **0.12**——
比实测最大值还高，于是 `floor` 永远取 0.12，**没有任何一个间隙能达标**。

那么 DB 里那一堆 402~448 的块是怎么来的？是 `semantic_split` 末尾的
「超 `CHUNK_MAX_CHARS` 强制再分」救场——在 450 字内找最近的句边界切一刀。
所以现在的真实行为是：**按 450 字上限，在句边界硬切**。语义断点一个都没用上。

### 8.2 降阈值后能切成什么样（同一批样本实测）

| 阈值 | 平均块数 | 平均块长 | 块长范围 | <200 字的碎块 |
|---|---|---|---|---|
| **0.12（当前）** | 4.0 | 392 | 36 ~ 446 | 1/20 |
| 0.10 | 4.2 | 373 | 36 ~ 446 | 3/21 |
| 0.09 | 4.8 | 327 | 46 ~ 449 | 6/24 |
| 0.085 | 5.2 | 302 | 46 ~ 449 | 8/26 |
| 0.08 | 6.6 | 238 | 32 ~ 447 | 15/33 |
| **0.075** | 6.6 | 237 | 63 ~ 441 | 17/33 |
| **0.070 ~ 0.050** | **6.8** | **230** | **134 ~ 441** | 15/34 |

逐样本对比（同一条消息）：

```
msg=2786 正文1322字
  0.120 → 3 块 [441, 439, 440]                    ← 三块几乎等长 = 按长度切
  0.075 → 6 块 [441, 144, 189, 185, 134, 225]     ← 长短不一 = 按内容断点切
msg=2778 正文1700字
  0.120 → 5 块 [400, 409, 427, 428, 36]           ← 末尾掉一个 36 字碎块
  0.075 → 7 块 [400, 74, 187, 265, 406, 141, 223]
```

两个额外收益：
- 块长**不再整齐等长**（441/439/440 → 441/144/189/185/134/225），说明切点真的落在内容转折处；
- 0.12 时出现的 **36 字碎块消失**（最小升到 134），因为 `_shape_sizes` 能把过碎组合并到邻居。

### 8.3 ⭐ 为什么推荐"设到均值以下"而不是"挑一个最优值"

`floor = max(epsilon, mean(dists))` 这条公式意味着：
**一旦 `epsilon` 低于该文本的 `mean`，阈值就改由 `mean` 主导 → 自动随文本自适应**。

实测印证：阈值从 0.075 一路降到 0.050，**结果完全不动**（都是 6.8 块、平均 230、134~441）——
因为此时 floor 已经在吃 mean，epsilon 怎么调都不影响。

⇒ 结论：**`epsilon` 只应该是"兜底下限"，不该是"主阈值"。** 把它设成 0.05
（低于实测 mean 的 0.065~0.075 区间），就进入自适应模式，**换嵌入模型也不用重调**。
当前 0.12 把它当主阈值用了，等于把自适应机制**废掉**。

### 8.4 性能影响（这是你最关心的）

**改阈值的性能成本 = 0。**

`semantic_split` 的流程是"分句 → 对每个句子做一次批量嵌入 → 算相邻距离 → 找断点"。
**每句的嵌入本来就已经做了**（Ollama `/api/embed` 单次批量调用），
调阈值只改变后面"哪些间隙算断点"这一步的判定，**不新增任何嵌入调用**。

真正的代价在别处：

| 项 | 变化 | 说明 |
|---|---|---|
| 每轮嵌入调用 | **不变** | 已经是每句一次批量 |
| 记忆行数 | **约 +70%**（4.0 → 6.8 块/条） | 存储增长；`conversation_memories` 表会涨得快些 |
| 检索候选 | 变多 | 但 `semantic_search` 有 `LIMIT 200` + `MIN_SIMILARITY=0.5` 兜底 |
| 注入预算 | 块更短 → 同预算能放更多块 | 反而更灵活 |

### 8.5 实测验证（已做）—— 结论比预期更微妙，**别用"块内更聚焦"来解释收益**

改配置前先跑了**离线正反对照**（同一批真实消息，只换阈值，其余不变）。

**判据一：块内内聚度**（同一块内句子两两余弦相似度均值）

| | 总块数 | 平均块长 | 块内内聚度 |
|---|---|---|---|
| 改前 0.12 | 20 | 392 | 0.5473 |
| 改后 0.05 | 34 | 230 | 0.5533 |

⇒ **只提升 +1.1%，几乎没变。** 这**推翻了**我在上一版里写的预期
（"切到内容转折处 → 块内更聚焦 → 向量不再被稀释"）。
真实原因是：一段连续剧情本来就是**语义渐变**的，相邻句天生相似，
无论切在哪里，块内一致性都差不多。

**判据二：话题分离度 margin**（更贴近检索——衡量"块与块能不能分开"）

定义：对块 i 里每个句子 s，`own = sim(s, 块i)`、`rival = max_{j≠i} sim(s, 块j)`，
取 `margin = own − rival`。margin 越大，说明这句话越"认自己那块"，
检索时越不容易撞到别的块。

| | 总块数 | 内聚度 | **话题分离度 margin** |
|---|---|---|---|
| 改前 0.12 | 24 | 0.5467 | 0.0376 |
| 改后 0.05 | 43 | 0.5534 | **0.0638（+69.9%）** |

⇒ **真正的收益在这里：块的区分度提升约 70%。**

**所以正确的说法是**：收益不是"块内更纯"，而是"**块与块之间更分得开**"。
对检索而言后者才是关键——440 字的大块同时装着两件事时，
它的向量跟两件事都"有点像"，导致查 A 时命中它、查 B 时也命中它，**区分不开**；
切细后 A 归 A、B 归 B，命中更准。

**代价**：块数 24 → 43（**+79%**），即记忆行数与存储同比例增长。

⚠️ **判据的局限（必须一起看）**：
1. 样本只有 **6 条消息**，量偏小，+69.9% 这个幅度不要当精确值；
2. margin 是**代理指标**，不等于真实检索准确率——它测的是"向量空间里的可区分性"；
3. 因此**仍需线上跑一轮后按真实召回质量复核**（见 §8.6）。
