## 2. 完整对照表

图例：✅ 一一对应 · ⚠️ 语义相近但不同 · ❌ 我们没有 · 🚫 故意不给 · ➖ 无关

### 2.1 变量更新方式（核心）

| # | 插件设置 | 插件的行为 | 我们的对应物 | 判定 |
|---|---|---|---|---|
| 1 | **变量更新方式**：`随 AI 输出` | 让主模型在回复里输出变量更新指令，插件在浏览器里解析 | `backend/app/services/mvu_engine.py`（服务端解析 `<UpdateVariable>`） | ⚠️ |
| 2 | **变量更新方式**：`额外模型解析` | 主模型不输出变量，改由**副模型**读剧情产出变量 | `backend/app/services/mvu_secondary.py` + `POST /{session_id}/mvu-secondary` | ⚠️ |

**⚠️ 关键语义差异（我们的设计其实更宽）**：

- 插件是**二选一**（要么主模型输出，要么副模型解析）。
- 我们是**主 + 兜底**：默认走主模型输出；**主模型没输出时**才让副模型补
  （`mvu_secondary.py` 文件头原文：「主模型未输出 `<UpdateVariable>` 块时，用副模型解析剧情」）。
- 所以第 1、2 项在我们这儿**不是两个互斥选项，而是同一条链路的两个环节**。覆盖面比插件广。

### 2.2 自动清理变量（我们完全没有）

| # | 插件设置 | 插件的行为 | 我们的对应物 | 判定 |
|---|---|---|---|---|
| 3 | 启用自动清理变量 | 开关 | **无** | ❌ |
| 4 | 清理策略 | 怎么清 | **无** | ❌ |
| 5 | 快照保留间隔 | 每隔多少楼留一份快照 | **无** | ❌ |
| 6 | 要保留变量的最近楼层数 | 只留最近 N 楼的变量 | **无** | ❌ |
| 7 | 触发恢复变量的最近楼层数 | 往前回看多少楼以恢复变量 | **无**（我们读最近 30 楼找快照，但**只读不删**） | ❌ |

## 3. 三类判定汇总

### ✅ 真·一一对应（2 项）
- 变量更新到聊天变量（我们是"永远开"）
- 自动请求（我们是 `mvu_secondary_enabled`）

### ⚠️ 语义相近但不同（6 项，按重要度）
1. **变量更新方式** —— 插件二选一，我们「主 + 兜底」（**我们更宽**）
2. **模型来源** —— 插件可填任意 API，我们只能选平台已有模型
3. **应答格式** —— 插件 4 选 1，我们固定 1 种
4. **关闭 thinking / 副模型参数** —— 我们固定 `temperature=0.2`、`max_tokens=2048`，不可调
5. **变量更新到聊天变量** —— 插件开关（默认关），我们无条件开（**可能是倒挂问题入口**）
6. **角色卡覆盖** —— 机制已有，内容未接

### ❌ 我们完全没有（12 项）
- 自动清理变量 ×5（**长会话下 DB 只涨不降**）
- 通知 ×3（**所有失败用户无感**）
- 破限方案族 ×3（内置破限 / 目标预设 / 随机头部）
- 世界书白名单 / 黑名单正则 ×2
- 请求方式 / 请求次数 ×2（其中"并行多次"**不该补**）
- API 方案管理 ×1

### 🚫 故意不对应（2 项）
- **API 地址**、**API 密钥** —— 安全边界，不该补

### ➖ 与我们无关（4 项）
- MVU 框架加载通知、显示老旧功能、sendas 不视为 user 消息、兼容假流式

## 4. 「能否完全代替？」—— 不能。分工是清楚的

| 层面 | 谁更强 | 说明 |
|---|---|---|
| **解析** | **我们** | 服务端解析 + 剥离（4 处），标签不外显；插件在浏览器解析，标签会裸显 |
| **存储** | **我们** | 会话级 + **消息级快照**，swipe/重生成/分支回退时变量跟着退；插件是单一聊天级 |
| **进提示词** | **我们** | 我们从 DB 读、压平成中文键值行注入；插件的数据在浏览器，**到不了服务端** |
| **分支回退语义** | **我们** | `_load_effective_stat_data` 消息级优先；插件没有 |
| **副模型精细控制** | **插件** | 破限 / 重试 / 多请求 / 世界书过滤 / 参数调节 —— 我们只有"选个模型 + 开关" |
| **运维面（清理/通知）** | **插件** | 我们两项都没有 |
| **凭据与额度** | **我们** | 插件可填任意 API 地址+密钥（绕过额度与审计）；我们不给 |

**结论**：不是"谁代替谁"，而是**主干归我们、副模型支线的精细控制与运维面归插件（待补）**。
插件那 31 项里有 12 项是我们该学的，有 2 项是绝对不能给的。

## 5. 「能否适配？」—— 能。按这三类处置

### ✅ 该补（4 组，建议排期）

| 优先级 | 补什么 | 为什么 |
|---|---|---|
| **P1** | **变量自动清理**（启用 + 保留最近 N 楼 + 快照间隔） | 我们**只涨不降**；长会话 DB 与下发体积都会失控。这是真隐患，不是体验问题 |
| **P1** | **变量链路通知**（初始化成功 / 出错 / 副模型解析中） | 现在所有失败**只进日志**，用户无感 —— 与「stat_data 不更新但没人知道」的现场直接相关 |
| **P2** | **世界书条目白/黑名单正则** | 我们现在是全量参与，用户无法排除；长卡会拖慢 schema 提取 |
| **P2** | **副模型参数放开**（温度 / max_tokens / 重试次数），但**全部装限速器** | 现在写死 `0.2 / 2048 / 无重试`；放开要有上限（同「开小门 + 装限速器」口径） |

### 🚫 不该补（3 项）

| 项 | 为什么 |
|---|---|
| API 地址 + API 密钥 | 会把对话发去任意地址 + 绕过额度审计 |
| 破限方案（内置破限 / 任意预设） | 语义就是「往上游请求塞任意内容」，与 `custom_include_body` 同一类红线 |
| 请求方式「同时请求多次」 | 成倍消耗额度，服务端无法计费归类 |

### ➖ 不用补（4 项）
框架加载通知、显示老旧功能、sendas 不视为 user 消息、兼容假流式 —— 我们没有对应概念。

### ⚠️ 顺带要回头查的一项
**「变量更新到聊天变量」我们是无条件开**，而插件默认关（还专门给了"老卡打不开时才开"的说明）。
这一项正是 `REPORT_MVU变量框架与Palink自有变量体系重叠专题_2026-10-04.md` §5.2「读优先级倒挂」的入口 ——
建议在补清理功能时**一起评估**是否要改成可控。

## 7. 局限与未验证

1. **31 项是我从 i18n 字典归纳的**。i18n 里有 145 条文案，我用「是否为可交互控件」来筛选；
   少数项（如「清理策略」的可选值）**未逐项展开**，只按语义归类。
2. **未真机打开设置面板核对**。清单来自 bundle 源码，不是截图；理论上与面板一致（同一份代码驱动），
   但**控件的默认值**未逐个确认（文中标注的默认值来自 i18n 帮助文案与 `update_method_model` 等代码片段）。
3. **插件设置的实际存储键名未穷举**。文中用的是面板文案（中文），代码里的键名形如
   `额外模型解析配置.启用自动请求` / `兼容性.更新到聊天变量`（见 bundle 内 `make_boolean_model` 调用），
   两者**不完全一一对应**（部分项走 `get_character_settings_override`）。
4. **我们侧"该补"的优先级是我的判断**，不是用户裁定。
