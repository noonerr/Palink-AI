## 1. 结论（一句话）

`__tests__/compat-v2-runtime-source.ts` 用 `readFileSync` 拼出来的**未求值源码文本**被 11 个测试
文件喂进 `new Function` 执行并断言行为 —— 而生产走的是模板字符串**求值后**的产物，
**两者的反斜杠转义语义在两个方向上都不对应**，所以「本地 463 例全绿」从来不是证据。

本包做了四件事：① 新增与生产逐字节同源的求值后载体；② 把 9 份执行型测试迁到该载体；
③ 出假绿清单与生产转义缺陷清单；④ 修掉 part-07 的那处转义（并把守卫做成可复跑的用例）。

## 2. 三口径（同一份源码在两个载体里的三处系统性差异）

| 口径 | 载体一 `COMPAT_V2_RUNTIME_SOURCE`（readFileSync 文本） | 载体二 `COMPAT_V2_RUNTIME_ARTIFACT`（生产 iframe 同源） |
|---|---|---|
| ① 反斜杠转义 | 源码写几个就是几个 | 模板求值：`\\d`→`\d`（对）、单反斜杠 `d`→`d`（**反斜杠被吞**） |
| ② 插值占位 | 保留 `${bootHeader}` / `${IDB_NS_RUNTIME_SOURCE}` / `${VARIABLES_COMPAT_SOURCE}` 原文 | 占位已展开成真源码；宿主 TS 头（`buildSmartCardCompatRuntimeBootPayload` 白名单）**不在产物里** |
| ③ 行尾 | 源文件 CRLF | 模板求值按 ECMAScript 把 CR/CRLF 归一成 LF（产物里 0 个 CR） |

口径 ① 是缺陷本体，口径 ② 决定「哪些断言只能用载体一」，口径 ③ 会在跨载体逐字节比对时
造出「只差一个回车」的假阴性（本包施工时实踩过一次）。

## 3. 实测证据

### 3.1 缺陷的两个方向（最小复现，2026-10-18 实测）

同一行 part-07 源码，分别用两个载体执行，输入是宿主 v2 `requestParent` 真实回给的
展开数组 `{ok:true, 0:{…}, 1:{…}}`，看 `normalizeCompatEntries` 能还原出几条：

| 仓库源码写法 | 产物里的正则 | 载体一执行（旧测试） | 载体二执行（生产） |
|---|---|---|---|
| 单反斜杠 `/^\d+$/`（**修复前**） | `/^d+$/` | 2 条（看起来是对的） | **0 条**（线上真的坏） |
| 成对反斜杠 `/^\\d+$/`（**修复后**） | `/^\d+$/` | **0 条**（此刻载体一反而骗人） | 2 条（对） |

⇒ 载体一执行出来的行为跟生产**没有对应关系**：源码写错时它替错误辩护，源码写对时它把正确判成错。
这就是「测试载体必须与生产同语义」的硬依据，不是风格问题。

### 3.2 全套 463 例全绿 ≠ 生产没坏

施工前基线（改前的工作区，`npx vitest run .../__tests__/`）：
`Test Files 33 passed (33) / Tests 463 passed | 1 skipped` —— 全绿，
而同一时刻产物里 `/^d+$/` 确实存在（探针实测 `has /^d+$/ = true`、`has /^\d+$/ = false`）。

### 3.3 反向实验：哪些测试是「载体敏感」的

改完并修复 part-07 后，把 8 份迁移过的执行型测试**单独换回**载体一（其余一律不动）再全量跑：

```
Test Files  2 failed | 32 passed (34)
Tests       3 failed | 475 passed | 1 skipped (479)
  × lorebook-family-contract.test.ts > E getLorebookEntries >
    v2 requestParent 把数组展开进 {ok:true,...} 时也能还原（真机实测形状）
  × runtime-source-carrier-fidelity.test.ts > D1 / D2      ← 本包守卫如实抓到降级
```

⇒ **已确证的假绿：1 例**（就是包H 报的那条生产缺陷的载体侧）。
另外 7 份执行型文件在当前源码下两载体行为一致 —— 但那是「暂时没踩到位点」，不是安全；

**风险敞口有多大（实测计数）**：段文件模板体里有 **130 行**用了成对反斜杠写法
（part-01:10 / 02:30 / 03:19 / 04:51 / 05:12 / 06:2 / 07:3 / 08:3）。
这 130 行就是「载体一 ≠ 载体二」的文本位点全集 —— 任何执行型测试切到的区域一旦含这些行，
它跑的就不是生产语义，只是**这批断言恰好没摸到差异行为**。
守卫 C1/B1/B2 就是把这条路封死的（详见 §6）。

### 3.4 生产产物自身的健康度（顺手实测，结论：能跑）

- `new Function(产物)` 不抛 SyntaxError ⇒ 帧内脚本可解析，卡片不是整帧白屏级故障；
- 产物里除 LF 之外**零控制字符** ⇒ 没有 `\n`/`\b`/`\t` 之类被求值塞进字符串字面量；
- 产物长度 418,562 字符 / 8,697 行（外部脚本路径，即默认生产路径）。

⇒ 所以 §5 那类缺陷是**静默语义降级**：不报错、不白屏，只是那条分支永远不命中。
